0. The one rule: real induction only

Do not POST synthetic webhooks
Never fake a /webhook/grafana POST to "test" the platform. A synthetic alert carries no real telemetry, so the MCP bridges gather nothing and the LLM verdict is meaningless — you learn nothing about whether the platform works. Always induce a real breach so Prometheus/Loki/Jaeger/drain3 see real data. (The old hourly-demo-test.sh synthetic fire is being retired for exactly this reason.)

1. Prerequisites

  • Tailscale membership on the CIRES tailnet — every service is addressed by MagicDNS name, never raw IP (names survive AWS stop/start). Nodes: claude-controller, adolin, adolin-wsl (AI rollback fallback), observability-rca-newacct-monitoring (the monitoring VM), observability-rca-newacct-k3s (the app cluster), observability-gpu-uswest2-newacct (the GPU/triage host).
  • kubectl access to the k3s cluster (for the workload-down scenario).
  • The GPU host running. It auto-stops when idle to save cost; the first alert after idle pays a cold-start while it boots and loads qwen2.5:14b. If you want an instant demo, wake it first.
  • Read these two first: the end-to-end architecture (so you know what each scenario exercises) and the dashboard guide (so the columns make sense). Full deploy-from-scratch: Reproducibility Guide.

3. Real-induction scenarios

A. CPU stress (threshold rule)

Drive CPU on a target so a threshold rule fires with real metrics behind it. Run a stress load on the workload host (e.g. stress-ng --cpu N or the project's chaos runner), wait for the saturation rule to fire, and watch a row appear. The LLM should pull the CPU series via the Prometheus MCP and name saturation as the cause.

B. KubeWorkloadDown — the genuine-unavailability trick (with revert)

Do not kubectl scale --replicas=0 — that sets desired=0, so unavailable = desired − available = 0 and the alert will not fire. You must keep desired ≥ 1 while preventing the pod from becoming ready. Use strategy Recreate (tear the old ready pod down first) plus a nodeSelector no node satisfies:

# Make it genuinely unavailable: desired=1, available=0 -> unavailable=1
kubectl -n app patch deploy/spring-boot --type merge -p '{
  "spec": {
    "strategy": {"type": "Recreate"},
    "template": {"spec": {"nodeSelector": {"cires/induce-down": "nowhere"}}}
  }
}'
# wait > 3m, observe KubeWorkloadDown fire and a triage row appear
# (labels should name service=spring-boot, namespace=app)

# REVERT (remove the impossible nodeSelector):
kubectl -n app patch deploy/spring-boot --type json \
  -p '[{"op":"remove","path":"/spec/template/spec/nodeSelector/cires~1induce-down"}]'

An alternative real induction: point the deployment at a non-existent image tag (ImagePullBackOff also yields available=0 with desired≥1). This is the exact path verified end-to-end in commit da8b9d6. Full label-surgery explanation: K8s Observability.

Always revert
Leave the bed healthy. Remove the impossible nodeSelector (or fix the image tag) and confirm the deployment goes available and the alert clears before you walk away.

C. Drain3 log-template anomaly

Generate a genuinely novel log pattern from the app (a new error template the miner hasn't seen), so drain3 detects a novel/anomalous cluster and self-fires to /webhook/drain3. This exercises the monitor-watching-its-own-logs path. Note the audit found drain3 self-fires can currently produce duplicate rows (the fingerprint hashes volatile per-batch content) — if you see repeats, that's the known backend #1 issue, not your test going wrong.

4. Reading the dashboard

The dashboard guide is the column-by-column reference; the essentials for a tester:

  • Verdicts: ESCALATE (real, emailed), DISMISS (benign), suppressed_duplicate / triage_suppressed (a cheap-path gate absorbed it — no GPU spent), timeout_passthrough (safety fallback). Most rows being cheap is the system working, not failing.
  • The detail view: click a row to expand. Read human_cause first — that is the named diagnosis. The evidence below it is the supporting metrics/logs/traces, each with a "View in Grafana/Loki/Jaeger" link to the real source.
  • The judgment to make: did it name a cause, or just restate the alert / dump metrics? A good verdict says what broke; the validators are meant to enforce this, and a thin one should fall back to diagnostic_steps.
  • rca_quality is the 4-axis rubric score. Heads-up: the audit found it can be stale on some rows (snapshotted before the clamp/retry) — don't over-trust the number on older rows until backend #3 is fixed.

5. Giving feedback that actually trains the LLM

Every email and dashboard row links to GET /dashboard/alert/{id}/rate. Submitting it writes a feedback row, and the next time the same alert family fires the pipeline reads it back into the prompt. To make feedback that changes future RCAs:

  • Fill in actual_cause even when the verdict was right — this is the highest-value field. It teaches the LLM the named cause for the family and lifts prose quality next time, rather than letting it settle on boilerplate.
  • Set verdict_was_right=no when it's wrong — that puts the row in the high-value subset that gets proactively injected with a "trust this HEAVILY" framing.
The family-match + 14-day TTL caveat
Feedback is matched by (alert_name, service) family with a default 14-day lookback (days=14). So: (1) a correction on one family does not carry over to a different alertname or service — if you test family X then expect it to help family Y, it won't; (2) it ages out after 14 days. If a correction seems to "not stick", check you're re-firing the same family within the window. Full mechanism: feedback-loop.html.

6. If nothing fires

  • Used --replicas=0? That can't fire KubeWorkloadDown (desired=0 → unavailable=0). Use the Recreate + nodeSelector trick in scenario B.
  • Waited long enough? The rule has a "for" duration (>3m) before it fires.
  • GPU host asleep? Cold start delays the verdict, not the alert — the row should still appear; the LLM result lands once the box is up and the model is loaded.
  • Is the metrics pipeline actually scraping? Sanity check: curl -s 'observability-rca-newacct-monitoring:9090/api/v1/query?query=kube_deployment_status_replicas_unavailable' | jq '.data.result | length' should be > 0. If KSM/SD ever regresses (the no-alert-outage class), this returns empty.
  • Cross-check the pipeline stages in the architecture "why" map to see which gate may have absorbed your alert.
