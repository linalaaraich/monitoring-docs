1. The production target is the CIRES private cloud

Be explicit about the destination, because it changes every recommendation. The PoC runs on AWS because AWS was a fast, cheap dev bed. Production is the CIRES private cloud — an on-prem / self-hosted estate, not AWS. That means: prefer portable, self-hostable open-source over managed AWS services; do not assume an internet-reachable API Gateway; and integrate with what the CIRES NOC already runs rather than replacing it.

The architecture survives the move because of its seams. The MCP-only boundary (every data source reaches the LLM through a bridge) means the metrics/logs/traces backends are swappable without touching the prompt or the model. The triage service and MCP bridges are already containers shipped via GHCR. What changes is the substrate, not the pipeline. For the pipeline itself see the end-to-end architecture.

The MCP bridges are the portability win
Because the LLM only sees data through MCP /tools/*, swapping Prometheus→Zabbix or Loki→Elasticsearch is "write one bridge" — the triage prompt is untouched. This is the single most important property for a private-cloud migration.

3. The forward model: OTel single-agent + Zabbix integration

The CIRES NOC uses Zabbix for metrics and is wary of exporters. The PoC's per-target Prometheus exporters are a non-starter as a sell to that team. The production pitch is therefore:

  • One OpenTelemetry host-agent per node — a single collector that handles logs and traces (and, where useful, host metrics), instead of a zoo of exporters. One agent to deploy, secure, and reason about.
  • Metrics stay in Zabbix. The platform does not try to replace the NOC's metrics system. Instead an MCP bridge to Zabbix lets the LLM query Zabbix metrics exactly as it queries Prometheus today — same /tools/* contract, new backend. The platform owns logs + traces + the AI triage layer; Zabbix keeps metrics.
  • Prometheus becomes PoC-only. It stays in the dev bed for fast iteration but is not part of the production proposal.
Why this framing wins the NOC
It asks them to add one agent and expose a read API, not to rip out Zabbix or trust a pile of exporters. The value (AI root-cause naming on top of the signals they already collect) lands without threatening their existing investment.
Uncertain — confirm with the NOC
The exact Zabbix read interface (Zabbix API vs a metrics export endpoint) and whether host metrics should flow through the OTel agent or stay entirely in Zabbix is a design decision the NOC should own. The bridge pattern accommodates either; the choice is theirs, not invented here.

5. HA, scaling, and data retention

High availability

The PoC is single-instance everywhere (one triage service, one of each backend). For production:

  • Triage service: the FastAPI service is stateless except for its SQLite rca_history. To run more than one replica, move that store to the shared production DB (MySQL/Postgres) — otherwise the dedup/suppression/feedback state is per-replica and the cheap-path gates leak. This is a real prerequisite for HA, not a nicety.
  • Backends: Loki and Jaeger have HA modes; size per CIRES retention needs. Grafana can run behind the corporate SSO proxy in HA.
  • GPU host: a single A10G-class host handles the PoC's load comfortably (~38 s median). Scale by adding hosts behind a queue only if alert volume demands it — measure first.

Data retention

  • Logs/traces: set Loki/Jaeger retention to CIRES policy (PoC defaults are not compliance-grade).
  • rca_history + feedback: these are operationally valuable training signal — retain longer than raw telemetry. Note the feedback read-back uses a 14-day lookback by default for prompt injection, but the rows themselves should be kept for audit/analysis.

6. The AI host on-prem

The PoC migrated the AI layer to a cloud GPU specifically because it should sit on a dedicated GPU host, not on k3s with the apps. On-prem this becomes a single owned GPU box running Ollama + the triage service + the six MCP bridges. Bring it under Ansible — the audit flagged (A-3) that the GPU triage host is currently hand-managed compose outside Ansible; production must have it reproducible like everything else.

Drift is the dominant PoC failure mode
The 2026-06-04 audit's headline finding: the code was correct but never applied to the new account (dead Prometheus SD, missing KSM). For production, "in the repo" is not "in the cluster" — every IaC change must be applied and verified by real induction, not assumed.

7. PoC → production checklist

What must change before this is production on the CIRES private cloud. Honest, not aspirational:

Must-fix before greenlight

  • SEC Authenticate + network-scope Prom/Loki/Jaeger/Grafana (P2 I-4) — no unauthenticated UIs or APIs.
  • SEC Add MCP bridge auth so only the triage service can call /tools/*.
  • DATA · DONE 2026-06-04 RDS deletion protection + final snapshot enabled and applied to live (I-10). Carry the pattern to the prod DB; add backups per CIRES retention.
  • HA Move rca_history off per-instance SQLite to the shared DB if running >1 triage replica.
  • REPRO Bring the GPU/AI host under Ansible (A-3); kill hand-managed compose.
  • REPRO Apply-and-verify every IaC change by real induction (no "in repo = live").

Swap for portability

  • SES → Postfix / CIRES SMTP relay; S3 → MinIO; RDS → CIRES-managed MySQL.
  • API Gateway + Lambda → internal reverse proxy; drop EventBridge autoshutoff on owned GPU.
  • Add a Zabbix MCP bridge; demote Prometheus to PoC-only; deploy the OTel single host-agent for logs/traces.

Multi-tenancy / correctness gaps — resolved 2026-06-04

This batch of correctness gaps was closed this session; carry the behaviour forward into production rather than re-litigating it:

  • env-resolution (fa50c6c) — env is now resolved from alert labels in the pipeline (the hardcoded "prod" default is gone); the dashboard renders the stored env, falling back to "unknown" rather than silently claiming prod. Still validate the precedence chain (triage §5.3) per environment before relying on per-env routing.
  • has_named_cause (DA-2, 17debbf) — now requires a concrete subject, so unsafe actions can no longer pass the clamp on a bare "because/due to" connective.
  • MCP error semantics (82f719c) — query rejection (4xx) is now distinguished from source unavailability (5xx/conn-error), so a bad query is no longer mislabelled "source down".
  • SF-5 spike-shelved — deprecated (default flag off): the path was structurally unreachable (its 120 s window sits inside the 300 s dedup window) and never fired. Code + tests retained for a possible future redesign.
  • rca_quality (d56ce88) — now recomputed from the final decision after clamp/retry, before persistence (was stale on ~24% of PoC rows).
Sequencing
Mirror the audit's order: prove the platform sees its own apps (already done for k3s on 2026-06-04), then security-scope, then portability swaps, then HA. Each step verified by real induction — see the audit & fix methodology and the test guide.
