🧪 Overarching Validation Batch — 103 real-induction tests

2026-06-22 · PLAN (results filled on run)

What this is

A single overarching validation campaign of 103 real-induction tests spanning every stage of the platform — from a developer pushing a bad buildspec, through a service going down, infrastructure faults, client bottlenecks, data-tier failures, and the noise-control / anti-hallucination machinery itself. It is built to be executed live and then shown at the soutenance: each row carries what I do (the injected ground truth), what the platform should process (which alert rule and/or Drain3 tier, which pipeline gate), and what the LLM should find (verdict + named root cause). The two right-hand columns are blank — they get filled in on the run, and the populated matrix is the artifact.

Real induction only. Every test breaks something real — a pod, a deploy, a node, a flag, a query — so the MCP bridges serve real data to the model. There are no synthetic /webhook/grafana POSTs anywhere in this batch (platform invariant feedback_real_induction_tests_only: “la chaîne de preuves est le produit”).
Environment. Triage + 6 MCP bridges + Ollama (qwen2.5:14b) on the us-west-2 GPU host; monitored systems = the k3s Astronomy-Shop bed (otel-demo, ~22 services, loadgen live) + the two Spring Boot apps (app/rental) + Kong + RDS MySQL app_db + the monitoring host. Faults land only on the test-bed (otel-demo, the app namespaces, the k3s node, RDS) — never the GPU crown jewel or the observability backends, except the deliberate, time-boxed Ollama-stop (B9/H6) and backend-down tests (B11/B12/B13) which are reverted immediately. Every scenario reverts; the bed is restored to ad 1/1, all flags off, no lingering stress at the end.

Why 103 tests across these stages

The jury wants to see breadth and depth of validation, and that the platform was exercised the way a real incident arrives — at many layers, by many mechanisms. The batch is organised so each family targets a distinct stage of the system:

  • A. Deployment / config faults (16) — the “dev pushed a bad change” class (wrong DB name, bad image, bad probe, bad limits).
  • B. Service availability (14) — pods, deployments, nodes, gateway, dependencies, backends going down.
  • C. Infrastructure (14) — host CPU / memory / disk / IO / node pressure (the 10-rule infra group).
  • D. Client / traffic bottlenecks (12) — traffic spikes, GC pauses, slow downstreams, pool/thread exhaustion.
  • E. Data / database (8) — RDS failover, storage, deadlocks, slow queries, connection limits, schema drift.
  • F. Application logic (flagd) (10) — behavioural microservice faults via the OTel-Demo feature flags.
  • G. Drain3 novelty (8) — the novel-log path and its by-design negatives.
  • H. Noise control & resilience (10) — dedup, suppression, recurrence gate, co-fire, critical-flap, circuit breaker, timeout, bounded agency, incident entity, severity floor.
  • I. Multi-pillar correlation (5) — metrics + logs + traces at once, root-vs-symptom on cascades.
  • J. Anti-hallucination firewall (6) — thin evidence, dangerous actions, ungrounded claims, PII, hedging.

How to read each row

Verdicts in the “Expected” column: ESCALATE real incident, email sent, named cause · DISMISS transient/benign, correctly not paged · INCONCLUSIVE honest uncertainty, no fabricated cause · CONSOLIDATED folded into a co-fire primary · SUPPRESSED held by a noise gate by design · RAW circuit-breaker/timeout fail-open · NO-FIRE negative test, correctly quiet. On the day, fill Result (live) with the actual verdict, whether the cause was named correctly, the alert→email latency, and tick PASS / MISS / NUANCE.

Execution runbook (so this can be driven live)

All commands run from the controller against the live tailnet (MagicDNS, never raw IPs). Targets: deploy@observability-rca-newacct-k3s (k3s node), ubuntu@observability-gpu-uswest2-newacct (GPU host, passwordless sudo).

  • Deploy/config (A): patch the live spec — kubectl -n app set env / set resources / patch deploy, or roll the Helm release with the bad value; revert by re-applying the known-good manifest.
  • flagd (D,F): toggle the OTel-Demo feature flags by editing the flagd config (kubectl -n otel-demo edit configmap <flagd-config> → set the failure variant) or via the demo's feature-flag UI; revert sets every flag back to off. Confirm the exact flag keys against the live flagd config — names drift across demo versions.
  • Availability (B): kubectl delete/scale/cordon/drain; systemctl stop a target over SSH; SG edits via Terraform/console — each reverted immediately.
  • Infra (C): stress-ng --cpu/--vm/--io, fallocate/dd for disk, tc qdisc add … netem via nsenter into the pod netns; every one auto-removed on revert.
  • Data (E): mysql client to RDS — SELECT SLEEP, LOCK TABLES, connection floods, index drops on a throwaway copy; revert restores schema/locks.
  • Drain3 (G): the safe HTTP flood-anomalous-logs harness + targeted novel/known log injection.
  • Resilience (H): compose the above (e.g. Ollama-stop for the breaker, repeated blips for the flap gate); these are the only ones that touch the AI tier — time-box them.
Pacing. Most rules have a for: of 2–5 min before they fire, and each investigation is ~38–180s, so 103 sequential inductions is a multi-hour campaign — run it in batches by family (the prior reports ran ~8 at a time), reverting between batches, and let the GPU idle-checker sleep the host between sittings. Negative tests (B3, C11, D12, G5, G8) and the resilience gates (H*) are the cheapest to demo live; the cascade (I) and firewall (J) families are the most jury-impressive.
