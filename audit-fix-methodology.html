🔁 Audit & Fix Methodology

Methodology Runbooks

How we find and fix what's wrong — reproducibly

This page captures the working method behind the platform's quality work so the next operator (future Lina, a teammate, a reviewer) can repeat it. It is the process companion to the per-area audit docs and the Kubernetes Observability page. Use it before any non-trivial change.

Default workflow: for all non-trivial work, audit first — never fix-first. Skip the cycle only for typo-level changes.

The audit → RCA → brainstorm → fix → re-audit loop

1. Audit→ 2. RCA→ 3. Brainstorm→ 4. Fix→ 5. Re-audit↺
  1. Audit — enumerate issues per area (frontend / backend / observability / ansible / terraform / misc). Each issue gets a severity (P0/P1/P2) and a finding ID. Synthesize into a master plan with an execution order. The dominant lesson from 2026-06-04: most damage came from drift, not bad code.
  2. RCA — for each finding, isolate the single root cause, not just the symptom. Confirm against live state (e.g. ls /etc/prometheus/, kubectl get sa,secret), not just the repo.
  3. Brainstorm — list 2–3 candidate fixes with pros/cons before committing. Prefer the designed path, idempotent tasks, and production-portable open-source over AWS-coupled or one-off scripts.
  4. Fix — implement the chosen option and apply it to live where the issue was drift. Add a loud guard where a silent dependency caused the failure.
  5. Re-audit — verify by real induction, then loop. Re-run the audit check that found the issue and confirm it now passes.
Cadence: test each epic story individually as it ships (incremental). Run a full audit only at a milestone end, not continuously during the build phase.

The two IaC dimensions: code-safe AND applied-to-live

Every infrastructure finding must be graded on two independent axes. A clean --syntax-check / terraform plan proves only the first. The platform's worst outages came from IaC that was correct in the repo but never applied to the new account — invisible to any code-only audit.

DimensionWhat it checksHow to verify
Code-safeSyntax, schema, plan validity — the declared desired state is correctansible-playbook --syntax-check; terraform validate && terraform plan
Applied-to-live / driftWhether the declared state is actually realized on the live account/clusterInspect live: ls on the host, kubectl get, aws ... describe, query /api/v1/targets. Compare to repo.
Drift is silent. Examples found 2026-06-04: prometheus k8s SD jobs declared but token/CA never shipped; kube-state-metrics declared nowhere; an EventBridge rule ENABLED in Terraform state but DISABLED in live AWS (and plan blind to it); two applied-but-uncommitted .tf files. Always ask: is it in the repo? is it on the box?

Verification: render the frontend, don't curl it

A curl audit fetches server-rendered HTML/JSON — it cannot see client-side bugs in a React SPA. Several real user-facing failures (row-expand crash on null reason, light-mode stuck dark, dead "View in" anchors, hardcoded TopBar stats overriding live numbers) were invisible to curl and only surfaced by actually rendering the page in a browser and exercising it.

  • Open the page in a browser (or headless render), interact with it: expand rows, click copy buttons, toggle theme, follow evidence links.
  • Watch the console for unguarded dereferences (a.reason.split, a.tags, a.reasoning) — one producer regression = white screen.
  • Confirm displayed numbers are live, not hardcoded (e.g. test-count tile, uptime/open-alerts in the TopBar).
For backend / alerting, verify by real induction, never a synthetic /webhook/grafana POST: induce a genuine breach so the MCP bridges see real data (the hallucination-firewall / MCP-only invariant).

Concrete runbooks (2026-06-04 high-value fixes)

RUNBOOK 1

Restore k8s metrics scraping

Symptom: Grafana shows no-data for in-cluster services; no up series for employees-backend / Kong; Prometheus logs unable to read CA cert or unable to read authorization credentials.

Drift check (is it on the box?):

ls /etc/prometheus/            # expect k3s-token + k3s-ca.crt, NOT just prometheus.yml
kubectl get sa,secret -n observability | grep prometheus-scraper
curl -s monitoring-vm:9090/api/v1/targets | jq '[.data.activeTargets[]
  | select(.labels.job|test("kubernetes-pods|k3s-kubelet"))] | length'

Fix:

  1. Ensure the ClusterRole grants pods/proxy (the kubernetes-pods job scrapes through the API proxy; without it every scrape is 403) — in manifests/prometheus-rbac/rbac.yaml.
  2. Ensure the token is shipped to the monitoring VM as mode 0644 (Prometheus runs non-root inside its container; 0600/root is unreadable).
  3. Apply the designed path: ansible-playbook -i inventory/newacct.yml playbooks/k8s-manifests.yml --tags prometheus --check --diff (dry-run first), then without --check. This mints the prometheus-scraper SA + long-lived token Secret, decodes token+CA, ships them to /etc/prometheus/, and POSTs /-/reload.
  4. Pre-check the k8s ≥1.24 token quirk: kubectl get secret prometheus-scraper-token -n observability -o jsonpath='{.data.token}' must be non-empty (the manifest carries a legacy service-account-token-typed Secret to handle this).

Re-audit: re-run the targets query above → kubelet/cAdvisor + pod targets show health: up. Recommended hardening: add a stat-based guard in the prometheus role that fails loudly if the two TLS files are absent when k3s_sd_enabled, so this drift can never be silent again.

RUNBOOK 2

Deploy kube-state-metrics

Symptom: no deployment / replica / pod-phase / restart-count metrics; cannot alert on "deployment has 0 ready replicas" or CrashLoopBackOff. grep -rI kube-state-metrics returns nothing.

Fix:

  1. Add manifests/kube-state-metrics/kube-state-metrics.yaml: KSM v2.x Deployment + SA bound to a read-only ClusterRole over deployments/pods/replicasets/nodes + Service.
  2. Annotate the pod prometheus.io/scrape="true", prometheus.io/port="8080" so the existing kubernetes-pods SD job discovers it with no prometheus.yml change (matches the platform's annotation-driven discovery; open-source, fits the private-cloud prod target).
  3. kubectl apply -f manifests/kube-state-metrics/ and wire it into k8s-manifests.yml.

Re-audit: curl -s 'monitoring-vm:9090/api/v1/query?query=kube_deployment_status_replicas_unavailable' | jq '.data.result | length' > 0.

RUNBOOK 3

Add a generic workload-down alert

Goal: liveness coverage for ANY service with no per-service rules. Depends on Runbooks 1 & 2.

Fix: add to roles/grafana/templates/alertrules.yml.j2:

title: KubeWorkloadDown
expr:  max by (exported_namespace, deployment) (
         kube_deployment_status_replicas_unavailable{exported_namespace!="kube-system"}
       ) > 0
for:   3m
# route to the triage webhook contact point; for liveness rules prefer
# noDataState: Alerting (not OK) so a never-discovered target still fires

Re-audit (real induction): kubectl scale deploy/spring-boot --replicas=0 → after >3m expect KubeWorkloadDown to fire and a triage row to appear, with exported_namespace+deployment labels naming the workload. Restore with --replicas=1.
