🔁 Audit & Fix Methodology

Methodology Runbooks

How we find and fix what's wrong — reproducibly

This page captures the working method behind the platform's quality work so the next operator (future Lina, a teammate, a reviewer) can repeat it. It is the process companion to the per-area audit docs and the Kubernetes Observability page. Use it before any non-trivial change.

Default workflow: for all non-trivial work, audit first — never fix-first. Skip the cycle only for typo-level changes.

The audit → RCA → brainstorm → fix → re-audit loop

1. Audit→ 2. RCA→ 3. Brainstorm→ 4. Fix→ 5. Re-audit↺
  1. Audit — enumerate issues per area (frontend / backend / observability / ansible / terraform / misc). Each issue gets a severity (P0/P1/P2) and a finding ID. Synthesize into a master plan with an execution order. The dominant lesson from 2026-06-04: most damage came from drift, not bad code.
  2. RCA — for each finding, isolate the single root cause, not just the symptom. Confirm against live state (e.g. ls /etc/prometheus/, kubectl get sa,secret), not just the repo.
  3. Brainstorm — list 2–3 candidate fixes with pros/cons before committing. Prefer the designed path, idempotent tasks, and production-portable open-source over AWS-coupled or one-off scripts.
  4. Fix — implement the chosen option and apply it to live where the issue was drift. Add a loud guard where a silent dependency caused the failure.
  5. Re-audit — verify by real induction, then loop. Re-run the audit check that found the issue and confirm it now passes.
Cadence: test each epic story individually as it ships (incremental). Run a full audit only at a milestone end, not continuously during the build phase.

The two IaC dimensions: code-safe AND applied-to-live

Every infrastructure finding must be graded on two independent axes. A clean --syntax-check / terraform plan proves only the first. The platform's worst outages came from IaC that was correct in the repo but never applied to the new account — invisible to any code-only audit.

DimensionWhat it checksHow to verify
Code-safeSyntax, schema, plan validity — the declared desired state is correctansible-playbook --syntax-check; terraform validate && terraform plan
Applied-to-live / driftWhether the declared state is actually realized on the live account/clusterInspect live: ls on the host, kubectl get, aws ... describe, query /api/v1/targets. Compare to repo.
Drift is silent. Examples found 2026-06-04: prometheus k8s SD jobs declared but token/CA never shipped; kube-state-metrics declared nowhere; an EventBridge rule ENABLED in Terraform state but DISABLED in live AWS (and plan blind to it); two applied-but-uncommitted .tf files. Always ask: is it in the repo? is it on the box?

Verification: render the frontend, don't curl it

A curl audit fetches server-rendered HTML/JSON — it cannot see client-side bugs in a React SPA. Several real user-facing failures (row-expand crash on null reason, light-mode stuck dark, dead "View in" anchors, hardcoded TopBar stats overriding live numbers) were invisible to curl and only surfaced by actually rendering the page in a browser and exercising it.

  • Open the page in a browser (or headless render), interact with it: expand rows, click copy buttons, toggle theme, follow evidence links.
  • Watch the console for unguarded dereferences (a.reason.split, a.tags, a.reasoning) — one producer regression = white screen.
  • Confirm displayed numbers are live, not hardcoded (e.g. test-count tile, uptime/open-alerts in the TopBar).
For backend / alerting, verify by real induction, never a synthetic /webhook/grafana POST: induce a genuine breach so the MCP bridges see real data (the hallucination-firewall / MCP-only invariant).

Concrete runbooks (2026-06-04 high-value fixes)

RUNBOOK 1

Restore k8s metrics scraping

Symptom: Grafana shows no-data for in-cluster services; no up series for employees-backend / Kong; Prometheus logs unable to read CA cert or unable to read authorization credentials.

Drift check (is it on the box?):

ls /etc/prometheus/            # expect k3s-token + k3s-ca.crt, NOT just prometheus.yml
kubectl get sa,secret -n observability | grep prometheus-scraper
curl -s monitoring-vm:9090/api/v1/targets | jq '[.data.activeTargets[]
  | select(.labels.job|test("kubernetes-pods|k3s-kubelet"))] | length'

Fix:

  1. Ensure the ClusterRole grants pods/proxy (the kubernetes-pods job scrapes through the API proxy; without it every scrape is 403) — in manifests/prometheus-rbac/rbac.yaml.
  2. Ensure the token is shipped to the monitoring VM as mode 0644 (Prometheus runs non-root inside its container; 0600/root is unreadable).
  3. Apply the designed path: ansible-playbook -i inventory/newacct.yml playbooks/k8s-manifests.yml --tags prometheus --check --diff (dry-run first), then without --check. This mints the prometheus-scraper SA + long-lived token Secret, decodes token+CA, ships them to /etc/prometheus/, and POSTs /-/reload.
  4. Pre-check the k8s ≥1.24 token quirk: kubectl get secret prometheus-scraper-token -n observability -o jsonpath='{.data.token}' must be non-empty (the manifest carries a legacy service-account-token-typed Secret to handle this).

Re-audit: re-run the targets query above → kubelet/cAdvisor + pod targets show health: up. Recommended hardening: add a stat-based guard in the prometheus role that fails loudly if the two TLS files are absent when k3s_sd_enabled, so this drift can never be silent again.

RUNBOOK 2

Deploy kube-state-metrics

Symptom: no deployment / replica / pod-phase / restart-count metrics; cannot alert on "deployment has 0 ready replicas" or CrashLoopBackOff. grep -rI kube-state-metrics returns nothing.

Fix:

  1. Add manifests/kube-state-metrics/kube-state-metrics.yaml: KSM v2.x Deployment + SA bound to a read-only ClusterRole over deployments/pods/replicasets/nodes + Service.
  2. Annotate the pod prometheus.io/scrape="true", prometheus.io/port="8080" so the existing kubernetes-pods SD job discovers it with no prometheus.yml change (matches the platform's annotation-driven discovery; open-source, fits the private-cloud prod target).
  3. kubectl apply -f manifests/kube-state-metrics/ and wire it into k8s-manifests.yml.

Re-audit: curl -s 'monitoring-vm:9090/api/v1/query?query=kube_deployment_status_replicas_unavailable' | jq '.data.result | length' > 0.

RUNBOOK 3

Add a generic workload-down alert

Goal: liveness coverage for ANY service with no per-service rules. Depends on Runbooks 1 & 2.

Fix: add to roles/grafana/templates/alertrules.yml.j2:

title: KubeWorkloadDown
expr:  max by (exported_namespace, deployment) (
         kube_deployment_status_replicas_unavailable{exported_namespace!="kube-system"}
       ) > 0
for:   3m
# route to the triage webhook contact point; for liveness rules prefer
# noDataState: Alerting (not OK) so a never-discovered target still fires

Re-audit (real induction): kubectl scale deploy/spring-boot --replicas=0 → after >3m expect KubeWorkloadDown to fire and a triage row to appear, with exported_namespace+deployment labels naming the workload. Restore with --replicas=1.

Verification technique deep dive — the SSR render harness

"Render the frontend, don't curl it" needs a concrete method that works without a browser (the audit ran on a headless host over SSH). The technique used this session is a server-side-render (SSR) reproduction harness: render each top-level React component with react-dom/server against the real live payload, and watch for a thrown exception. It is fully reproducible and is how the row-expand crash (C4) and several latent null-deref crashes were found.

Why this catches what curl cannot

A curl of /dashboard returns server-rendered HTML/JSON; it never executes the client React, so it cannot see: render-crashes from a payload-shape mismatch, dead onClick/href handlers, controls that look real but do nothing, or fabricated values shown as live. The crash class is specifically dangerous because React throws synchronously inside render — one unguarded a.reason.split() on a null field blanks the entire page (white screen), not just one row.

The harness, step by step (reproduce for any SSR/React page)

# 1. A tiny harness dir with the real deps (no app build needed):
mkdir -p /tmp/jsxrepro && cd /tmp/jsxrepro
npm i react@18.3.1 react-dom @babel/core @babel/preset-react

# 2. harness2.js: babel-transform the .jsx, then renderToString against a
#    payload file. It mounts window.CIRES_* globals the component reads,
#    exactly as the server injects them.
#    Pseudostructure:
#      global.window = { CIRES_ALERTS:[...], CIRES_LINKS:{...}, ... }
#      const code = babel.transform(fs.readFileSync(component), {presets:['@babel/preset-react']})
#      eval(code); ReactDOMServer.renderToString(React.createElement(Component, {a: payload}))
#      -> prints "RENDER OK (NN KB)" or the thrown TypeError

# 3. Pull the REAL payload from the live server (not a mock):
curl -s http://observability-gpu-uswest2-newacct:8090/dashboard/alert/<id> \
  | extract-the-window.CIRES_ALERT-json > live-alert-detail.json

# 4. Render against live + hand-built EDGE payloads:
node /tmp/jsxrepro/harness2.js detail live-alert-detail.json     # happy path
node /tmp/jsxrepro/harness2.js detail edge-reason-null.json      # null reason
node /tmp/jsxrepro/harness2.js detail edge-no-tags.json          # missing tags
node /tmp/jsxrepro/harness2.js detail edge-no-reasoning.json     # missing array
node /tmp/jsxrepro/harness-expand.js edge-dash-reason-null.json  # ROW EXPANDED
The crucial nuance — render collapsed vs render expanded. The dashboard's row-expand crash (C4) renders fine in the default harness because rows start collapsed; the crash only fires when setExpandedId mounts ExpandedDetail. A separate harness (harness-expand.js) that forces the expanded state is what caught it. Lesson: the harness must exercise the same interaction states a user would — initial paint is not enough.

The payload-shape-mismatch bug class + the guard pattern

Every crash this session was the same root pattern: a component calls .split/.slice/.length/.map on a server field with no guard. They were "latent" only because today's server transform (_v2_transform_row) happens to always populate those fields — a single producer regression, a partial-refresh payload, or a new code path re-introduces the white screen. The contract lived only in the producer; the consumer had no defense-in-depth.

// BEFORE (crashes if a.reason is null):
const parts = a.reason.split(/.../);

// AFTER (guard at the consumer — the fix in commit 6045de3 / 919b5cb):
const reason = a.reason || "";
const parts  = reason.split(/.../);
// ...and when empty, render an explicit "No cause recorded" callout
// rather than silently blanking.
Apply anywhere: guard at the consumer for any field that crosses a process boundary (server→client), even if the producer "always" sets it. Pair with the SSR harness fed deliberately-missing edge payloads so the guard is proven, not assumed.

Two more frontend robustness fixes worth copying

  • Clipboard on insecure-origin HTTP. The dashboard is served over plain HTTP on the tailnet, where navigator.clipboard is undefined (the Clipboard API requires a secure context). The "Copy" buttons were doubly dead (no onClick AND no API). Fix: a shared ciresCopy() helper that tries navigator.clipboard and falls back to a hidden-textarea + document.execCommand('copy') for insecure origins (commit 919b5cb). Reproduce-note: any internal tool served over HTTP needs this fallback.
  • Theme unification (two theme systems → one key). Light mode was stuck dark because two independent systems coexisted: the React wrapper hardcoded data-theme="dark" while the toggle persisted to obs-rca-theme and CSS was scoped to a different selector. Fix: a single source of truth — the React routes read the persisted obs-rca-theme and a shared head script mirrors it onto <html data-theme>, plus a tokens.css rule so the body bg tracks the active theme (commit 6045de3). Reproduce-note: one persisted key, mirrored to the DOM attribute every render path reads — never two.

The MCP /tools/* route convention (a drift class to audit for)

The platform enforces an MCP-only data-access invariant: every data source the LLM sees must come through an MCP bridge — no direct DB/Prometheus/in-process reads. That is the hallucination firewall. A subtle drift bug this session: the deployed MCP image serves /tools/* routes only (e.g. /tools/query_instant, /tools/query_logs, /tools/find_traces), but two consumers were still calling the old bare routes (/query, /query_range, /traces) which 404 silently:

ConsumerWas callingCorrect route + param rename
bounded_agency.execute_tool (the LLM's on-demand retry-query path — was entirely dead)/query, /query_range, /traces/tools/query_instant (expr→promql), /tools/query_logs (query→logql, lookback_seconds→relative start like "5m"), /tools/find_traces (drop unsupported min_duration_ms)
entity_baselines._query_prom_mcp (every adaptive-baseline read was 404ing → falling back to non-authoritative)/query?expr=, read data.result/tools/query_instant?promql=, read result at top level (the tool lifts it out of data)
RCA + the audit pattern: context.py was migrated to /tools/* but two other callers weren't — classic partial migration drift across files (the same shape as IaC "rendered but not applied"). It was silent because a 404 just degrades to a fallback. Fix (commit c328f5d): route both callers through /tools/* with the right param names and add a regression test (test_bounded_agency_external_mcp_routes) asserting each tool hits the correct path — the gap existed because that branch had no coverage. Audit lesson: when you migrate a shared convention (route prefix, param name, label), grep every caller, not just the one in front of you, and pin the contract with a test so it can't drift back.

A related semantics finding, resolved 2026-06-04 (commit 82f719c): MCP tools previously raise_for_status()'d, so a bad-but-valid LLM query (malformed PromQL) surfaced as a bare 500 → the triage read it as "source down" rather than "your query was wrong". The fix returns a structured error that distinguishes a query rejection (4xx, the LLM's fumble) from source unavailability (5xx/conn-error, a real outage), so a bad query is no longer mislabelled "source down".

How environment SHOULD flow (the env-resolution gap)

The triage service resolves config via pydantic-settings (app/config.py) with a precedence order — env var > compose env > per-service map > coded default. The audit found a real gap class worth documenting so other environments work: callers didn't pass alert labels through to env resolution, and several defaults hardcoded the live (prod-ish) account. Concretely, defaults like triage_dashboard_url and the instance_hosts IP→hostname map drifted to dead old-account hosts and were corrected by editing the defaults (commit df1f13f). The core resolution gap is now resolved 2026-06-04 (commit fa50c6c): env is resolved from the alert labels in the pipeline (the hardcoded "prod" default is dropped), and the dashboard renders the stored env — falling back to "unknown" rather than silently claiming prod.

How env should flow (apply to any multi-env deploy): (1) every environment-specific value is an env var with a safe, override-required default (fail loud, not a stale host); (2) the deploy (compose/helm) sets those env vars per environment — the code default is only a last resort; (3) dynamic per-alert facts (like which namespace/instance an alert came from) are carried as alert labels and resolved at request time, not baked into a static map. The current instance_hosts static map is the anti-pattern: it must be re-edited on every infra move. The portable shape is INSTANCE_HOSTS as a JSON env the deploy owns, with the static map as a fallback only.

drain3 dedup — normalising volatile tokens to a stable template identity

Drain3 self-fire alerts ("Novel log-template anomaly") never deduplicated: 21 distinct fingerprints / 18 fires in one live day, each a fresh ~100s LLM investigation. Root cause: the fingerprint hashed the raw novel-template / anomalous-line text, and that text embeds the most volatile tokens in the payload — trace IDs, span IDs, entity IDs, timestamps, hex digests. So two batches of the same underlying anomaly hashed differently every time → never collapsed, never recurrence-gated.

Fix (commit d56ce88, app/dedup.py): normalise content to its stable template identity before hashing — mask the volatile token shapes with <*>, then hash. The same log template now masks to the same string across batches; a genuinely new template still produces a distinct digest.

# _normalize_drain3_content masks, most-specific first, then squeezes:
UUID  →  long-hex (16+)  →  0x-literals  →  ISO timestamps  →
bare clock times  →  decimals/dotted  →  any remaining digit run   ... all → <*>
# then collapse runs of "<*>:<*>" and whitespace.
# CONSERVATISM SAFEGUARD: if nothing but wildcards/punctuation survives
# (a pure-id line carries no stable identity), return "" so the caller
# falls back to the service-scoped key instead of minting a spurious digest.
# -> distinct anomalies are never merged; only volatile noise is collapsed.

Plus a noise-suppression gate (app/pipeline.py): a self-fire with no new templates AND anomaly_rate below a floor (default 5%) is short-pathed to a cheap drain3_noise_suppressed row (rca_quality=data_starved, 0 ms, no LLM) instead of a ~100s hedged investigation. Any batch introducing a new template is always investigated — the gate only suppresses confirmed benign noise. Verified by inducing a real recurring benign pattern (collapses to one row) and a real new ERROR template (still investigated).

Apply to any dedup/fingerprint: hash the stable identity, never the raw text, when the text embeds high-cardinality tokens. Order the masking most-specific → least-specific (so a UUID isn't half-eaten by the bare-number rule), sort the normalized parts (ordering carries no meaning), and add a conservatism fallback so an over-masked line degrades to a coarser key rather than a false-unique digest.
