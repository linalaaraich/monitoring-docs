Build pipeline

How the triage-service container image gets built, tagged, and published on every push to main — and why we picked GitHub Actions and the GitHub Container Registry as the zero-cost option that fits an open-source-first brief.

GitHub Actions GHCR (ghcr.io) Zero cost, public repo No secrets to manage

Why this pipeline exists

Until recently the monitoring-triage-service compose file pinned an image tag (cires/triage-service:${IMAGE_TAG}) that had to be built locally on every host that ran the stack. That was fine while the service only ran on the AWS k3s cluster, but it broke as soon as we moved the AI stack to Lina's laptop: pulling the latest source code was no longer enough, because the Python was baked into an image nobody had built with the new code yet.

We needed an automated build that produces an image any host can pull. The constraint was: cheapest possible, most open-source option. The pipeline documented here is the result.

Why GitHub Actions + GHCR

OptionCostVerdict

Jenkins + GitLab CI + ... Requires a runner host we'd have to pay to keep up 24/7 Too heavy for a single-service build
Why it's free
GitHub gives public repositories unlimited CI minutes on Linux runners (standard tier), and GHCR storage & bandwidth for public images is uncapped. The triage image is ~200 MB compressed and we build ~10×/day at most, so we sit comfortably inside the free tier with no credit card on file.

What happens on every push to main

1
Trigger
Any commit touching app/, requirements.txt, Dockerfile, drain3.ini, or the workflow itself. Docs-only commits skip CI.
2
Checkout + Buildx setup
actions/checkout@v4 + docker/setup-buildx-action@v3. Buildx enables layer caching via GHA's cache backend.
3
Log in to GHCR
docker/login-action@v3 using ${{ secrets.GITHUB_TOKEN }} — no PAT, no service account, no manual rotation.
4
Derive tags
docker/metadata-action@v5 generates three tags: main (rolling), sha-<short> (immutable, for pinning), and latest (only on default branch).
5
Build + push
docker/build-push-action@v5 with cache-from/to: type=gha,mode=max. Typical cold build ~90 s; typical warm build ~15 s when only app/** changes.
6
Run summary
The final step writes the pushed tags + a copy-paste docker pull command into the GitHub Actions run summary, so you never have to hunt for the right tag.

How the compose stack consumes it

gpu-migration-staging/compose/docker-compose.yml now references the GHCR image via an override-friendly env expression: 

triage-service:
  image: "${TRIAGE_IMAGE:-ghcr.io/linalaaraich/monitoring-triage-service:${TRIAGE_TAG:-main}}"

Two knobs, both optional:

  • TRIAGE_TAG — which GHCR tag to pull. Defaults to main (rolling-latest). Pin to sha-a1b2c3d for reproducible deploys.
  • TRIAGE_IMAGE — a full image reference that overrides everything else. Use when you want to run a local build for iteration: docker build -t cires/triage-service:local ./monitoring-triage-service && export TRIAGE_IMAGE=cires/triage-service:local.

The laptop workflow

From now on, picking up a new triage build on the laptop is:

cd ~/cires-ai
docker compose pull triage-service          # fetch the new :main from GHCR
docker compose up -d --force-recreate triage-service

No more git pull && docker build dance — the CI builds once in the cloud and every host just pulls.

Manual rebuild (when you need it)

Triggering a rebuild without a code change (e.g. to pick up a base-image security patch):

  1. Go to the Actions tab in the repo.
  2. Select the build-push workflow on the left.
  3. Click Run workflow → Run workflow (on main).

Known gaps / followups

Not yet pipelined

The five MCP servers (prometheus, loki, jaeger, drain3, rca-history) are still built locally under the cires/mcp-*:${IMAGE_TAG} convention. They'll each get their own build-push.yml once their repos stabilise — same workflow template as this one, with the repo name swapped in.

  • Multi-arch builds. Currently linux/amd64 only. If a future GPU host runs ARM (e.g. a Graviton), add linux/arm64 to the platforms list — GHA emulates via QEMU, roughly 2× slower.
  • Image signing. Not doing cosign yet. Consider signing the GHCR manifests before any production use that isn't just Lina's laptop.
  • Security scan gate. No Trivy / Grype scan in the workflow. Easy to add as a separate job before push: true.
  • Scheduled rebuilds. No weekly cron to re-pull the base Python image and pick up CVE patches. One-line add.
Reference
The workflow lives at monitoring-triage-service/.github/workflows/build-push.yml and is short (~70 lines including comments). Copy it into each MCP repo when you're ready to pipeline those too.
