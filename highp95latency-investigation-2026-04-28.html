The 2 regressions — what they actually said

Row 1 — 2026-04-28 10:12:28 (HighP95Latency on spring-boot, conf 0.85)

Based on the repeated log entries for actuator health and prometheus queries, it appears that there is a recurring issue with the system's health checks or metrics collection. The logs indicate that these requests are being made frequently without any errors, suggesting potential performance degradation or resource contention issues. Specifically, the repeated calls to /actuator/health and /actuator/prometheus endpoints could be indicative of either an application misconfiguration or a backend service issue affecting the availability or responsiveness of these endpoints.

Row 2 — 2026-04-28 10:13:59 (HighP95Latency on spring-boot, conf 0.95)

Based on the observed metric values and PromQL queries, it appears that the Spring Boot application is frequently querying actuator endpoints such as /actuator/health and /actuator/prometheus. This behavior suggests that either the application itself is performing these checks for monitoring purposes, or there might be an external system (e.g., a monitoring tool) making these requests. The repeated nature of this activity over multiple days indicates a persistent issue that requires further investigation.

Both ledes:

  • Open with "Based on the (observed | repeated) ..." — surface-level framing rather than a named cause.
  • Hedge with "it appears that", "suggesting potential", "could be indicative of either ... or ...", "requires further investigation" — every standard SRE-bullshit-bingo phrase.
  • Do not name a single cause — the LLM constructed a narrative around the most-frequent log lines (actuator endpoints), which is itself a hallucinated correlation: actuator endpoints are scraped by Prometheus, not by users. They have nothing to do with user-visible p95 latency.

Why the validator missed both

The 2026-04-28 morning shipping (D19) added two regex sets to app/response_validator.py:

  • _SURFACE_ONLY_LEDE_PATTERNS — matched ^PromQL `<expr>`, ^The PromQL expression, raw metric{}=value ledes.
  • _SURFACE_ONLY_HEDGE_PATTERNS — matched "indicates that there are X experiencing Y", "suggests (high|elevated|increased)", "appears to be experiencing".

Both regex sets were calibrated against the operator's literal example (the HighKongP95Latency RCA pasted in the morning's review). The model's actual regression shape was less specific:

  • Lede: "Based on the repeated log entries..." — does not start with PromQL or The PromQL expression; doesn't match any LEDE pattern.
  • Hedges: "appears that there is a recurring issue", "suggesting potential performance degradation", "could be indicative of either ... or ...", "indicates a persistent issue that requires further investigation" — none of these match the narrow patterns in the original set.

In short: the validator caught the exact bad output Lina cited, but not the broader hedge class the model actually produces under load. That's the classic regex-too-narrow failure mode.

Why the new prompt + exemplars didn't fully fix it

The exemplar matcher scores by: 

alertname-regex 0.10 + service 0.40 + deployment_type 0.30 + signal 0.20 + severity 0.10

For HighP95Latency on spring-boot:

So the model received upstream-latency-attribution as its calibration target. That exemplar is calibrated for the Kong-as-alert-subject pattern ("Kong itself is healthy: kong_proxy_latency_ms p95 is in single-digit ms; the observed p95 is upstream time inside a downstream service") — which is the wrong shape for the alert-on-spring-boot case. The LLM correctly recognised that the exemplar didn't match its evidence and fell back to its training-data regression: surface-level paraphrase.

The fix shipped today (revision 261537f)

Both gaps closed in monitoring-triage-service@261537f:

1. Validator regex set widened

New patterns added to app/response_validator.py:

  • ^Based on (the) (observed|repeated|reported|metric|PromQL|log entries)... LEDE
  • ^Looking at (the) (metrics|data|observations)... LEDE
  • indicates a (persistent|recurring|potential|ongoing) issue
  • appears (that there is | to be) ... issue/problem/concern
  • suggests (potential|possible|some kind of)
  • could be indicative of
  • could be (related|due|caused) by either/some/various
  • might be (a|an) X (issue|problem|concern)
  • requires further investigation/review/analysis
  • (potential|possible) (performance degradation | resource contention)
  • either ... is ... or there might be ... dual-hedge

Plus a positive test (test_named_cause_with_indicates_does_not_match_recurring_issue_pattern) guarding against false positives on legitimate causal prose like "this indicates that the JDBC pool's max=20 setting is the bottleneck".

2. New exemplar — service-self-p95-saturation

Added to app/exemplars/library.yaml (12 archetypes total now, was 11). Specifically calibrated for HighP95Latency / CriticalP95Latency on spring-boot, spring-boot-app, springboot-app, frontend with signal=metric:

The alerted service itself is the bottleneck — there is no upstream layer to redirect attribution to (unlike the Kong-says-upstream pattern). The diagnosis is "what inside this service is slow," and the trace breakdown will name it: a connection-pool-acquisition wait points at JDBC pool size; a long single-span on a downstream call points at a saturated dependency or query-plan regression; long gaps between spans point at JVM GC pauses; a uniform slowdown across spans points at thread-pool saturation.

Score for HighP95Latency on spring-boot with this new exemplar: alertname 0.10 + service 0.40 + deploy 0.30 + signal 0.20 = 1.00 — wins decisively over upstream-latency-attribution's 0.60 for the same alert.

3. Tests

6 new tests in tests/test_response_validator_surface_only.py — both production regressions reproduced verbatim, plus 4 standalone pattern checks. Existing exemplar count assertions (test_list_all_returns_all_exemplars and test_execute_list_exemplars_returns_catalogue) updated 11 → 12.
