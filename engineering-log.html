2026-06-09

Alert-quality collapse — drain3 infra-noise, honest quality tags, recurrence-not-"see-prior"

monitoring-triage-service 21677b1 · monitoring-audit-results 2026-06-09-alert-quality-collapse.md

  • Symptom (Lina): every alert over the weekend gave nothing — each was either a "see prior" duplicate or an RCA hedging "cannot determine the root cause / insufficient data." Evidence (live DB, 7d): 108 of 137 investigates (78%) were hedges; 91 were Drain3AnomalyDetected; 62 of the hedges were mis-tagged rca_quality=actionable. Audit → RCA → brainstorm → fix → re-audit cycle.
  • RC-1 (the source, ~91 hedges). The Drain3 BE-B3 source-exclusion denylist exact-matched service names, so the observability stack's OWN logs streamed into the miners and looked "novel" every batch: Jaeger's embedded BadgerDB compaction INFO (badger … LOG Compact), the OTel collector's batch-processor self-noise, even empty {"body":"\n"} records. They ship under service=monitoring-vm / jaeger — neither matched by the bare monitoring bucket. Fix: added monitoring-vm, jaeger, ollama, coredns, host-syslog, gpu-stack, drain3, dcgm-exporter to the denylist + a new is_empty_log_body() guard in DrainAnalyzer.analyze() (drops raw blanks AND JSON-wrapped empty bodies before any miner is touched).
  • RC-3 (the mislabel, 62 rows). _classify_rca_quality was called with decision.rca but not decision.human_cause — where the hedge actually lives ("Insufficient data to determine root cause…") — and its hedge patterns omitted "evidence"/"additional investigation". So a hedge slipped through as actionable, escaping the data-starved retry + Stage-E quarantine and showing on the dashboard as a good RCA. Fix: the classifier now scans human_cause and reuses the validator's authoritative _BANNED_PHRASE_PATTERNS as the single source of truth (no more classifier/validator drift).
  • RC-4 ("see prior" → recurrence). Lina asked to scrap the standalone suppressed_duplicate row that read "Duplicate fire … See prior RCA <id>". A duplicate now registers a recurrence on the existing incident (RCAStore.record_recurrence bumps fire_count+last_seen) with no stub feed row; the alert's detail page shows "fired N times" sourced from the incident entity, so the history lives ON the same alert.
  • RC-2 (honest verdict). The drain3 prompt playbook gained an explicit benign-noise exit — routine compaction/healthcheck/INFO novelty is named "Benign infrastructure log noise — <what> (routine, not an incident)" rather than hedged. The prompt now states plainly that a Drain3 alert ALWAYS carries its own evidence (the templates), so "insufficient data" is never the right answer.
  • +34 regression tests (test_alert_quality_2026_06_09.py); suite 726 green. → System Explained
2026-06-08

G2 per-container log naming → Docker service discovery (recreate-stable)

monitoring-project bb176be

  • The GPU host's OTel collector named each container's Loki service_name stream from a container-id→name map captured once at ansible apply time and templated into per-id OTTL rules. Docker IDs change on every recreate (image pull, compose up, OOM-restart-with-recreate), so a recreated container's new id matched no rule and its logs silently collapsed into the gpu-stack catch-all until the next apply — the fragile stopgap the 2026-06-04 audit flagged.
  • Fix: OTel-native Docker service discovery. The contrib collector's docker_observer extension watches the daemon event stream and, via receiver_creator, spins up a filelog receiver per running container that tails its json-log and stamps service.name from the live container name. On recreate the observer rediscovers the new id within cache_sync_interval — no stale fallback, no apply needed. Stream names are identical to before (the container name), so the drain3 per-service miners + BE-B3 infra exclusion are unaffected.
  • Required bumping the (logs-only) collector 0.120.0 → 0.145.0: the observer's include_all_containers flag — which emits a port-less endpoint per container — only landed in 0.145.0, and our ai-*/mcp-* containers publish no host ports, so older observers discover zero of them. Rule type == "container" && port == 0 selects exactly one filelog per container. Config validated with otelcol-contrib validate against 0.145.0 + 0.153.0 (fails on 0.120.0, documenting the floor).
  • ⚠ Honesty caveat: ships gated behind triage_stack_apply; the live discovery behaviour is pending real-induction acceptance on the GPU host (no local docker to runtime-test — only static config validation was possible). Rollback = revert the image tag to 0.120.0. Security note: docker_observer needs the docker socket (mounted read-only); front it with a docker-socket-proxy in production (EPIC15). → System Explained
2026-06-05

S5-DRN-01 — 3-tier hierarchical Drain3 thresholds (component → application → system)

monitoring-triage-service ba3eeae

  • Drain3 now evaluates three scopes independently each batch instead of one global anomaly rate: component (per-service, 0.25 / 30 lines) catches one service being weird even when globally diluted; application (per-namespace aggregate, 0.15 / 60) catches whole-app drift no single component crosses, at high severity; system (global, unchanged) catches broad elevation. Apps group via drain3_app_map → k8s namespace label → service-name fallback. Each (tier, scope) has its own cooldown + a per-tier cap so one incident can't storm. Webhook carries tier+scope; the RCA lede is tier-aware. 11 new deterministic unit tests (692 total).
  • ⚠ Honesty caveat: tier logic is proven by unit tests, but a live flagd induction on the warmed otel-demo bed fired 0 drain3 anomalies — correct behaviour, not a bug: drain3 has learned essentially every template (recent_rate ≈ 0.0008) and flagd faults are behavioural (error-rate/latency over gRPC), not novel-log-emitting. A real component/app fire needs a genuinely novel template (new exception/stack-trace), which real incidents produce. → System Explained
