Operator feedback loop - Epic 2 - SHIPPED 2026-06-03

Closed-loop operator feedback - the LLM now reads what operators wrote back

Operator wisdom must flow back into the LLM. Sprint 4 shipped the collection half (SF-7: rate.html + 7-column feedback schema + POST endpoint); the 2026-06-03 work ships the read-back half. Every alert evaluation now consults the operator's prior corrections on the same alert family, both proactively (injected into the initial prompt) and on-demand (a new rca_history.list_feedback tool the LLM can call during its bounded-agency window). This page describes the loop end-to-end.

1. Why - operator wisdom must flow back

Epic 2 doctrine, restated: the people who actually run the platform see things the model does not. They know that a given MediumCpuUsage on a given service is a known nightly cron, not a real fire. They know that a verdict the LLM keeps choosing for a given alert family is structurally wrong. They know the actual cause when the LLM names the wrong one. If that knowledge stays in the operator's head (or worse, in a closed Jira ticket), the LLM repeats the same mistake on the next firing of the same alert family. The fix is structural: persist operator corrections, and feed them back into the LLM the next time the same alert family fires.

The 2026-05-21 critical RCA audit (12 cases sampled across the 6 dominant alert families) named Epic 2 as the cross-cutting amplifier for P8 (rca_quality=actionable drift) and P11 (actionable tag has lost meaning) - today these are point-in-time fixes, with Epic 2 they become continuous. The collection half shipped 2026-05-23 inside Sprint 4 (SF-7, 10ebd4e); the read-back half shipped 2026-06-03 (Phase 6, this page).

Hard rule preserved

Read-back goes through the MCP-only data-access invariant. The proactive-injection path is a pre-LLM pipeline read (not the LLM reading the DB directly); the tool path goes through the rca-history MCP at port 8095 on the GPU host. There is no direct DB read from the LLM at any point. See the Hallucination Firewall page for the broader invariant.

2. Collection - what was already in place (SF-7, 2026-05-23)

The collection surface has been live since Sprint 4 day 4. Every escalation email and every dashboard row carries a "Rate this RCA" link to a per-alert form; the form persists to a 7-column extension of the existing feedback table.

At collection time the row sits in the DB as evidence. Until 2026-06-03 it did not flow back into the LLM. That is what changed.

3. Read-back - the 2026-06-03 work

Two paths, both wired into Phase 6 (commits 8b7b319 on monitoring-triage-service + 5c690f4 on monitoring-mcp-bridges). Together they make the operator's corrections visible to the LLM on every relevant alert evaluation.

3.1 Proactive injection (always-on, pre-LLM)

The pipeline now fetches operator feedback for the (alertname, service) family before the LLM is called, filtered to the high-value subset:

  • verdict_was_right = 'no' (operator explicitly corrected the verdict), OR
  • actual_cause is non-empty (operator wrote down what was actually wrong).

Implementation: RCAStore.get_high_value_feedback_for_family() in app/rca_store.py:897, called from TriagePipeline._process_alert() at pipeline.py:564. Results are formatted by llm_client._format_corrective_feedback_block() (app/llm_client.py:393) and injected into the prompt under: 

## OPERATOR CORRECTIVE FEEDBACK ON SIMILAR PAST ALERTS

[one line per feedback row: verdict/action override + actual_cause + notes]

Trust this feedback HEAVILY. If your reasoning contradicts what
operators wrote here, prefer their judgement.

The "trust this HEAVILY" framing is deliberate. The LLM's default posture is to lean on its own model of the world; this prompt language tells it the operator's recorded correction outranks that model whenever the two disagree. Empty operator history => empty block => prompt is unchanged from the pre-Phase-6 shape; this path adds zero tokens when there is nothing to say. Failures in the lookup are swallowed and logged at WARNING (non-fatal); the pipeline continues without proactive feedback rather than dropping the alert.

3.2 On-demand tool - rca_history.list_feedback

Proactive injection only catches the high-value subset for the exact (alertname, service) pair. The LLM may still want to inspect a wider feedback corpus during its bounded-agency window (one MCP call, see system-explained.html §4.8). Phase 6 registers a new bounded-agency tool:

This is the broader-corpus path - the LLM uses it when it wants to understand the operator history for an alert family in more depth than the high-value subset gives it, or to inspect a related family (different service, same alertname). It costs the LLM its single agency call for that alert evaluation.

4. End-to-end flow

The full loop, from one operator's correction to the next LLM evaluation of the same alert family:

[T0] Alert fires -> triage pipeline -> LLM -> verdict + RCA -> email + /dashboard row [T1] Operator opens /dashboard/alert/{id}/rate Submits: verdict_was_right=no, actual_cause="cron at 03:00 UTC, known" POST /feedback/rate/{id} -> feedback table [T2] Same alert family fires again (same alertname + service) TriagePipeline._process_alert(): 1. dedup + suppression checks 2. context gather (Prometheus / Loki / Jaeger MCPs) 3. metric_interpreter 4. exemplar injection > 5. get_high_value_feedback_for_family(alertname, service) > -> formats as "## OPERATOR CORRECTIVE FEEDBACK ..." block > -> appended to prompt with "Trust this HEAVILY" framing 6. LLM call (Ollama, qwen2.5:14b) -> sees the operator's prior correction -> verdict + RCA reflect it (verifies or contradicts) [T3] Optional: LLM uses its single bounded-agency call to invoke rca_history.list_feedback for a wider view -> rca-history MCP :8095 -> GET /tools/list_feedback -> returns recent feedback rows for the family -> LLM revises and emits final decision

Both T2 and T3 are pure read paths from the LLM's side; the write path (T1) is entirely operator-driven and goes through the existing feedback endpoint. The pipeline is the only component that touches the DB directly. The LLM only sees feedback rows that arrived through either the proactive-injection prompt block or the MCP tool result.

5. What this means for operators

Rate alerts - it actually matters now

Before 2026-06-03 the Rate form was data collection only. The form persisted your input but the LLM never saw it. From 2026-06-03 onwards, your corrections actively shape every subsequent LLM evaluation of the same alert family. The Rate link in every email and every dashboard row is now the highest-leverage tuning surface on the platform.

The two highest-value things you can write down:

  • verdict_was_right = no, with one line in actual_cause explaining why - this is the single strongest correction signal; it pre-empts the LLM's default reasoning on the next firing.
  • actual_cause, even when the verdict was right - this teaches the LLM the named cause for the family, raising prose quality next time and lifting rca_quality off boilerplate.

Operational caveat: the proactive-injection path only consults feedback for the exact (alertname, service) pair. A correction on HighCpuUsage / spring-boot does not surface on the next HighCpuUsage / kong. The list_feedback tool can cross that boundary on demand but it costs the LLM's single agency call. This is intentional - it keeps the proactive path bounded and predictable; broader cross-service generalisation is Sprint 5 work.
