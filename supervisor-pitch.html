1. The problem we are solving

Two failure modes cost an ops team time and trust, and both are visible in our own PoC history:

  • Alert noise. A single active incident re-fires every evaluation interval; flaky patterns page repeatedly; benign blips look identical to real ones. The team learns to skim or mute — and muting is how the real one gets missed.
  • Slow human root-cause analysis. When an alert is real, a human still has to open Grafana, Loki, and Jaeger, correlate across them, and write down what broke. That is minutes-to-tens-of-minutes of skilled attention per incident, repeated.
  • The monitor going blind. The worst case is the one we actually hit: a service was down and no alert fired at all because the metrics pipeline itself had silently failed. A monitoring system that can't monitor itself is a liability dressed as an asset.

The MCP-only boundary is both the hallucination firewall and a backend-portability seam: it lets us integrate with the NOC's existing Zabbix metrics by writing one bridge, rather than asking them to replace anything. See the firewall page and the OTel+Zabbix model.

3. Proof points (from work already done)

  • The no-alert outage — caught and closed. The 2026-06-04 audit found the platform was blind to its own apps' health: Prometheus k8s service-discovery was dead on the new account, kube-state-metrics didn't exist, and all 20 alert rules used noDataState: OK so a never-discovered target could never fire. We restored scraping, deployed KSM, and added the generic KubeWorkloadDown rule — then verified by real induction (made a workload genuinely unavailable, watched the alert fire and a triage row appear that had been silent before). Commit da8b9d6. Write-up: K8s Observability.
  • Real-induction verification, not synthetic tests. We don't POST fake webhooks to claim success; we induce real breaches (CPU stress, genuine unavailability, real anomalies) so the MCP bridges see real data. That is why the proof above is credible.
  • The GPU migration. Moving the AI runner from a laptop GTX 1060 / 7b model to an AWS A10G / qwen2.5:14b took the real-load median from ~5 minutes to ~38 seconds end-to-end — measured, not projected (Phase 2 smoke test, 2026-05-21). See D24/D25.
  • A disciplined audit habit. The platform is built audit-first: audit → RCA → brainstorm → fix → re-audit, checking both "is the code safe" and "is it actually applied to live". See the methodology.
Deliberately no invented metrics
We do not claim an MTTR reduction percentage or a noise-reduction figure — we have not run a controlled production measurement, so quoting one would be dishonest. The latency numbers above are the only hard figures, and they are measured smoke-test medians. The right next step is to measure noise/MTTR in a CIRES pilot, which is part of the ask.

4. The demo flow (which screens, in order)

1Open the dashboard.
http://observability-gpu-uswest2-newacct:8090/dashboard — show the live feed of decisions: escalated, dismissed, suppressed. Point out that most rows are cheap (deduped/suppressed) — the noise the operator never had to see.
2Induce a real failure.
Make a workload genuinely unavailable (the Recreate + impossible-nodeSelector trick) or run a CPU stress. No synthetic webhook — induce the real thing so the bridges gather real evidence. Steps: Test & Onboarding §scenarios.
3Watch it travel the pipeline.
Grafana fires KubeWorkloadDown → API Gateway → triage. A new row appears within seconds-to-a-minute. Open it.
4Read the named root cause.
The detail view shows human_cause (the diagnosis), the evidence, and "View in Grafana/Loki/Jaeger" links. Emphasise: this is a named cause, not a metric dump.
5Correct it and show the loop close.
Open the Rate form, submit a correction with an actual_cause. Re-fire the same family; show the correction re-injected into the next RCA. See feedback-loop.
6Revert.
Restore the workload; show the alert clear. Leave the bed healthy.

5. The ask

Greenlight a hardening-and-integration phase to move the platform onto the CIRES private cloud as a monitored pilot. Concretely: approve the security hardening + portability swaps in the production checklist, the OTel-single-agent + Zabbix-bridge integration with the NOC, and a scoped pilot to measure noise reduction and time-to-named-cause on real CIRES alerts. The ask is not "this is done" — it is "this has earned the next phase".

6. Honest roadmap (Sprint 5)

  • Hierarchical drain3 thresholds — 3-tier (component → app → system) anomaly detection; depends on a microservice test bed.
  • Incident table — group related alerts into incidents rather than treating each in isolation.
  • Operator config UI — let operators tune gates/thresholds/opt-ins without code changes.
  • Zabbix MCP bridge + OTel single-agent — the production integration model for the NOC.

7. Risks & open gaps (stated plainly)

  • It is a 3-person PoC. Production-grade ops (on-call, SLAs) is a staffing question, not solved by the code.
  • Security is not hardened. Prom/Loki/Jaeger are unauthenticated and open in the PoC; MCP bridges have no auth. These are must-fixes before production (P2 items).
  • Some internal paths are imperfect. SF-5 is dead and should be deprecated; rca_quality can be stale; has_named_cause needs tightening; the env-resolution chain needs confirming across all CIRES environments. All are tracked and scoped — see the checklist.
  • No production noise/MTTR measurement yet. That is exactly what the pilot is for; we will not quote a number we haven't measured.
