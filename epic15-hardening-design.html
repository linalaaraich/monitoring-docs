1. Scope & trust model

EPIC15 absorbs the P2 security backlog surfaced across the deep audits (SEC-S1…S-10). The destination changes every recommendation: production is the CIRES private cloud, an on-prem estate the supervisor deploys herself via Ansible onto her own NVIDIA L4 GPU host + existing k8s. AWS (account 321556173045) is a dev/PoC bed and is treated as throwaway — so AWS-native fixes (KMS, RDS encryption) are framed as "do it right in the private-cloud build" rather than "churn the dev bed."

The hardening splits cleanly along three trust boundaries:

  • Ingress edge — Grafana → /webhook/grafana. Today fronted in the AWS PoC by API Gateway (implicit auth boundary); on-prem there is no API Gateway, so the webhook needs app-level auth + TLS.
  • The AI stack's internal mesh — triage ⇄ 6 MCP bridges ⇄ Ollama, on the ai-stack docker network / tailnet. Network-isolated today (security groups confirmed tight), but zero application auth — defense-in-depth is missing.
  • Data & supply chain at rest — container image provenance, secrets on disk, and storage encryption.
What is already strong — do not re-do
The Terraform security groups are well-hardened (provisioning-newacct/security-groups.tf): no 0.0.0.0/0 ingress on any data port; SSH restricted to the operator IP /32; k3s SSH is tailnet-only; Grafana/Prometheus/Loki/Jaeger UIs closed to the public (public_ui_cidrs = []); RDS 3306 reachable only from the k3s SG, in private subnets, publicly_accessible = false. The network perimeter is good — the gaps are application auth and at-rest, not the firewall. The MCP-only data boundary also remains intact and is a security property, not just a correctness one.

3. Auth on the wire

The recon's headline finding: every hop in the AI stack is unauthenticated. That is tolerable only because the security groups isolate the network — but a single mis-scoped SG, a tailnet node compromise, or a future public ingress turns "open on a private net" into "open." EPIC15 adds defense-in-depth so auth does not depend solely on the firewall.

HIGH

S3 / O-9 — Webhook authentication

Current: app/main.py:250 webhook_grafana() and :262 webhook_drain3() take a payload and run — no dependency, no header check. In the AWS PoC the only thing in front is API Gateway; on-prem that boundary disappears.

Design (two complementary mechanisms, both reusing the existing controller-env-secret + preflight pattern that already works for SMTP):

  • Grafana → triage: Grafana's webhook receiver natively supports auth in the contact-point settings block — username+password (HTTP Basic) or authorization_scheme: Bearer + authorization_credentials. Add a bearer token to roles/grafana/templates/contactpoints.yml.j2 rendered from a vault/env secret. The triage service validates it with a FastAPI dependency (Depends(require_webhook_token)) — constant-time compare against settings.webhook_token.
  • drain3 self-webhook: the drain3 analyzer POSTs to /webhook/drain3 from inside the same stack. Give it an HMAC-SHA256 signature over the body with a shared secret (X-CIRES-Signature), since it is our own code on both ends — stronger than a static bearer and no Grafana-config dependency.
  • TLS: FastAPI runs plain HTTP. On-prem, terminate TLS at the existing reverse proxy (Kong/nginx/Caddy) in front of :8090 — the same place the prod deployment guide already routes internal traffic.

Rollout safety (must not dark the live alert path): ship the validator with a webhook_auth_enforced flag defaulting to warn-only (log + accept unsigned) for one deploy cycle, flip to enforce once Grafana is confirmed sending the token. Preflight asserts the secret is present before enforce mode.

Acceptance: unit tests for accept-valid / reject-missing / reject-wrong / reject-tampered-HMAC; live — a real Grafana alert still triages end-to-end with the token, and a curl without the token gets 401.

MED

S2 — Triage ⇄ MCP service auth

Current: context.py:481 calls MCP /tools/* over plain HTTP with no auth header; every MCP main.py serves /tools/* with no Depends/auth. Confirmed open across all five bridges at review time (a sixth, deploy-mcp :8096, joined 2026-06-11 under the same open contract).

Design: a single shared service token (env MCP_SERVICE_TOKEN) injected into the triage client and each MCP server. The client adds Authorization: Bearer; each MCP validates via a shared require_service_token dependency (factor it into a tiny module imported by all five, mirroring the existing shared install_error_handlers). Health endpoints stay open for container healthchecks. Per-service tokens are a later refinement — a single rotatable token closes the gap with minimal surface. Keep it on the ai-stack network; this is defense-in-depth on top of the existing isolation, not a replacement for it.

Acceptance: unit test each MCP returns 401 without the token and 200 with it; integration — triage still resolves Prometheus/Loki/Jaeger context with the token wired; healthcheck still green.

MED

S-6 — Ollama auth DESIGN

Current: Ollama is a host systemd unit bound 0.0.0.0:11434 (roles/ollama/tasks/main.yml:67) with no auth, no TLS, no proxy. The SG restricts 11434 to the VPC CIDR + tailnet, so it is not internet-open — but any tailnet node or VPC host can call it, and Ollama has no native auth.

Design decision needed: Ollama can't authenticate itself, so the options are:

  • (A, recommended) Reverse-proxy + token: bind Ollama to 127.0.0.1, put Caddy/nginx on 11434 requiring Authorization: Bearer; the triage llm_client sends it (extend the httpx client at llm_client.py:482). Adds TLS for free.
  • (B) Network-only: accept the current SG isolation as sufficient for the PoC, bind to the tailnet interface only, document the residual risk. Cheapest; no app change.

Recommend A for the private-cloud prod build (no AWS SG safety net on-prem), B acceptable as the documented PoC interim. Lina's call on whether to build the proxy now or defer to the prod cutover.

4. Secrets & rotations

The pattern to standardise on already exists and works: the SMTP password is supplied via controller-env (roles/triage_stack/defaults/main.yml:81) with a hard preflight assert (tasks/main.yml:64), and the main Grafana SMTP password is vault + env-fallback with a placeholder-rejecting preflight (roles/preflight/tasks/main.yml:64). Three secrets do not yet follow it.

HIGH

SEC-S1 — Grafana admin password LINA

Current: a live host_var at inventory/newacct.yml:40,58 set to a weak baseline; the preflight (roles/preflight/tasks/main.yml:48) rejects CHANGE_ME* placeholders but accepts weak common values. Rotation is Lina-only (she holds the vault + the live Grafana).

Plan: (LINA) generate a strong password, store as vault_grafana_admin_password in the ansible-vault, drop the host_var override. (CODE) tighten the preflight to also reject a small denylist of weak values (admin, password, < 12 chars) so a weak value can't silently ship.

HIGH

S4 — MySQL password LINA

Current: a weak value hardcoded in version-controlled inventory/group_vars/application.yml:30, no preflight guard, no vault path. (This is the React/Spring app's DB — part of the app-under-observation, not the AI stack.)

Plan: (CODE) move to vault_mysql_password + a preflight assert mirroring SMTP; (LINA) set the strong value in vault and rotate the live DB user. Note: the RDS-side master password (below) is a separate secret.

HIGH

SEC-TF — RDS master password on disk LINA

Current: plaintext at provisioning-newacct/terraform.tfvars:44. The file is gitignored (verified) so it is not in git history — the exposure is a cleartext secret sitting on the controller disk, not a repo leak. The variable is already sensitive = true (variables.tf:153).

Plan: (CODE) supply it via TF_VAR_db_password from an env/secret file exactly as the Tailscale auth key is already handled (terraform.tfvars comments show that pattern at lines 60–64); remove the plaintext line. (LINA) rotate the RDS master password and store the new value in the secret source. Tracks alongside the standing Lina-only rotations (Gmail SMTP app-password).

MED

S4b — Triage Grafana-API password CODE

Current: default "admin" at roles/triage_stack/defaults/main.yml:46, rendered into env.j2:34 + compose, no guard. Used by the startup backfill's Basic-auth to the Grafana API.

Plan: (CODE) source from vault/controller-env + preflight assert; it should track whatever grafana_admin_password becomes (same credential). Fully doable without Lina once SEC-S1's vault var exists.

5. Image supply chain — digest pinning (S5)

Current: five first-party GHCR images pull the moving :main tag (triage + the four MCP servers + rca-history), defaulted in roles/triage_stack/defaults/main.yml:33-34; the monitoring-VM compose pulls grafana/grafana:latest (roles/grafana/defaults/main.yml:2). Moving tags mean a redeploy can silently pull a different image than what was tested — non-reproducible and a supply-chain foothold. All upstream images (node-exporter, KSM, dcgm, the otel collector now at 0.145.0) are already version-pinned. ✓

Design:

  • Pin the five GHCR images to immutable @sha256: digests. CI already builds on main push — have the workflow emit the pushed digest and write it to an ansible var (triage_image_digest, mcp_image_digest) / the .env; compose references image@sha256:…. A documented "promote" step updates the digest var deliberately, so deploys are reproducible and an upstream :main can't drift in.
  • Pin grafana:latest → a concrete grafana/grafana:11.x.y.
  • Folds into the same change as the G2 collector pin (0.145.0) — keep one "pinned images" doctrine across compose + manifests.

Acceptance: --check --diff shows the digest rendered; a redeploy pulls the exact digest; docker inspect on the host confirms the running image digest matches the pinned one.

6. Encryption at rest / in transit (S-10)

Current (AWS PoC): RDS storage_encrypted unset (rds.tf); EC2 root volumes have no encrypted = true on root_block_device (ec2.tf, all three hosts); S3 has no explicit server-side-encryption config (s3-cloudfront.tf). CloudFront already enforces redirect-to-https ✓.

Why this is DESIGN, not a quick terraform apply
Toggling storage_encrypted on an existing RDS instance is not in-place — it requires a snapshot → encrypted-restore. Encrypting existing EBS roots requires instance recreate. On a throwaway AWS dev bed that churn buys little. The honest call: do not churn the PoC; instead provision encrypted from day one in the private-cloud build.

Private-cloud design (the real target):

  • Block storage: LUKS / dm-crypt on the volumes backing the DB and the RCA-history SQLite + drain3 state — host-level at-rest encryption, no cloud KMS needed.
  • Object storage: MinIO with server-side encryption enabled for backups/artifacts (replaces S3; see the prod guide swap table).
  • DB: self-managed MySQL/MariaDB (or Postgres) on an encrypted volume; TLS for client connections.
  • In transit: terminate TLS at the reverse proxy for every externally-reachable surface (Grafana, the webhook, MCP if ever exposed); internal mesh stays on the isolated network.

Optional cheap PoC win: if the AWS bed is rebuilt for any reason, add storage_encrypted = true + root_block_device { encrypted = true } + an aws_s3_bucket_server_side_encryption_configuration at that point — free with the AWS-managed key, zero ongoing cost.

7. Implementation order & acceptance

Recommended sequence — code-doable + high-value first, Lina-only rotations interleaved, design decisions last:

  1. S3/O-9 webhook auth (CODE+DESIGN) — highest exposure (the one ingress edge); warn-then-enforce rollout. This is the "Friday hardening overdue since 2026-05-01" item.
  2. S5 digest-pinning (CODE) — pure IaC, no secret, low risk; lock down the supply chain and fold in the G2 collector pin.
  3. S2 MCP service token (CODE) — shared dependency across the six bridges.
  4. Secrets to vault + preflight (CODE for the scaffolding: S4b, S4 var, SEC-TF env-var supply, preflight weak-value denylist).
  5. Lina-only rotations (LINA, can happen in parallel): Grafana admin (SEC-S1), MySQL (S4), RDS master (SEC-TF), + the standing Gmail SMTP app-password rotation.
  6. S-6 Ollama proxy (DESIGN→CODE) — pending Lina's now-vs-cutover call.
  7. S-10 encryption-at-rest (DESIGN) — built into the private-cloud provisioning, not retrofitted onto the AWS bed.
Non-negotiables carried from the platform invariants
Every new secret ships vault/env-sourced with a preflight assert (no weak defaults reach live); no change may break the live inventory/newacct.yml deploy or dark the Grafana→triage alert path (hence warn-then-enforce); the MCP-only data boundary is preserved; and each fix lands with a real-induction acceptance, not just a unit test.
