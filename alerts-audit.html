Executive summary

The triage pipeline is doing real work on real problems. Most decisions are legitimately actionable (74% of rows tagged actionable), the LLM is citing observed values, and the suggested-action templates are producing deployment-type-correct commands. Three things undermine it right now, and all three were caught + fixed in this audit:

  1. 14 % of decisions were pipeline timeouts (7/50). The post-P1 prompt is ~3× larger (few-shot + schema) and cold-start on GTX 1060 + qwen2.5:7b can push past 5 minutes. Fixed by bumping OLLAMA_REQUEST_TIMEOUT 300 s → 1800 s (30 min) and PIPELINE_TIMEOUT 900 s → 2400 s.
  2. Drain3 has NEVER fired a self-alert despite processing 123 701 log lines across 257 clusters including real OOM / JDBC / OTel-export-timeout templates. The 100-line + 10 % thresholds were essentially unreachable once the clusters warmed up. Fixed by lowering to 20 lines + 2 %.
  3. Spring-boot was in an OOM-kill loop (45 restarts in 47 h, exitCode=137). Cause: 1 GiB container memory limit with no explicit JVM heap → ~256 MB effective heap. Fixed by bumping limit to 2 GiB and setting -XX:MaxRAMPercentage=75.

The LLM itself is not the bottleneck — the surrounding plumbing is. Each of the three fixes above is a parameter change, not a rewrite.

Drain3 deep-dive — why 0 self-alerts in 123 k lines

Finding
Drain3 has learned 257 templates across 123 701 log lines of real spring-boot traffic, and every single "top new pattern" it surfaced is a genuinely interesting error the operator would want to see:

From /drain3/stats at audit time — the 5 most recent novel templates drain3 learned (sanitized excerpts):

  1. Spring-boot log envelope — noise, not error
  2. org.springframework.jdbc.CannotGetJdbcConnectionException: Failed to obtain JDBC Connection; nested exception is java.sql.SQLException: HikariPool-<N> - Interrupted during connection acquisition
  3. org.springframework.beans.factory.BeanCreationException: Error creating bean with name 'entityManagerFactory' ... Bean instantiation via factory method failed ... NoSuchBeanDefinitionException
  4. [otel.javaagent] ERROR io.opentelemetry.exporter.internal.grpc.GrpcExporter - Failed to export ... Error message: timeout
  5. Exception in thread "http-nio-8080-Acceptor" ... java.lang.OutOfMemoryError: Java heap space

These are EXACTLY the symptoms that would explain the spring-boot 45 restarts. Drain3 saw them. The triage pipeline did not — because drain3 never told it.

Root cause of the silence

The self-alert trigger logic in app/drain_analyzer.py requires BOTH conditions per 30-second batch:

  • batch_total ≥ drain3_alert_min_lines (was 100)
  • len(anomalous) / batch_total ≥ drain3_alert_rate_threshold (was 0.10)

After drain3 warms up, most log lines match existing clusters with match_count ≫ 5 (the drain3_anomaly_threshold), so they are NOT counted as anomalous. Steady-state anomaly rate is near 0 %. An OOM burst of 10 lines against a batch of 400 steady-state actuator log lines is 2.5 % — below the 10 % threshold. The rule of thumb "anomaly rate is the signal" is fundamentally wrong for post-warmup drain3.

Fix applied today

  • laptop_drain3_alert_rate_threshold: 0.10 → 0.02
  • laptop_drain3_alert_min_lines: 100 → 20
  • Cooldown stays at 600 s to avoid alert storms

This catches an OOM burst against a small 20-line batch as long as it makes up ≥ 2 % of the batch (so ≥ 1 anomalous line per 50 steady-state lines). Still conservative — the same one-command ansible-playbook playbooks/laptop.yml from the controller will re-tune if we see noise.

The structurally correct fix (deferred)

Design note for Sprint 3
A ratio-based trigger is the wrong abstraction. Drain3's unique value is template novelty detection. The right trigger is: "a new cluster has appeared AND the new cluster's template contains a severity marker like Exception/Error/FATAL/OOM". That would have fired instantly on the OOM template's first observation, not waited for a rate to build. Implementation sketch: 
if result.is_new_pattern and re.search(r'Exception|Error|FATAL|OOM|failed', result.template):
    fire_alert(template=result.template, occurrence=1)
This gets drain3 from "noise detector" to "first-occurrence anomaly detector" — closer to what the tool is actually good at.

Traces aren't in drain3 — what that would take

Today drain3 ingests logs from Loki only. Jaeger's traces don't flow through it. This matters because the single most useful latency signal we have is "this span took way longer than its normal sibling" — invisible to log templating.

Conceptual model

A trace template is a tuple (service, operation, span.kind, duration-bucket) where duration-bucket is a power-of-10 bucket of the span duration. Drain3 currently operates on textual templates, so we'd either:

  1. Feed stringified spans into drain3 — serialize each span as "spring-boot::GET /actuator/health::SERVER::12000ms" and let drain3's tokenizer treat the duration-bucket as a variable position. The 12 s span becomes a NEW template vs the usual 50 ms one. Crude but zero new code.
  2. Purpose-built trace anomaly detector — track a running distribution per (service, operation) pair, flag spans > 3σ from the mean. More accurate, ~150 lines of code in a new trace_analyzer.py.

Both approaches need a Jaeger puller (currently only logs are polled continuously). Recommend option 2 for Sprint 3 — it's the right abstraction for latency signals. Option 1 would double drain3's cluster count without much benefit.

Data today

The Jaeger probe during this audit found a GET /actuator/health span with duration 13.2 seconds. The "normal" health check is sub-10 ms. A trace analyzer would have flagged this the first time it fired — weeks before p95 crossed the HighP95Latency threshold. Same principle as drain3 novelty detection, just applied to trace duration instead of log templates.

Improvement plan — Sprint 3 priority order

Overlap with Epic 5 (UEBA)
Several Track A/C items below correspond 1:1 to stories in the new Sprint 2 Epic 5 — UEBA page. Those stories are cross-referenced inline (e.g. "→ US-5.2 incident correlator"). If Epic 5 lands before Sprint 3 starts, these items get ticked off early; the remaining Sprint 3 work becomes the harder evaluation + dashboard + widening pieces.

Based on this audit, the following ordered plan takes the pipeline from "works" to "measurably reliable."

Track A — data quality (highest leverage)

  1. Drain3 novelty trigger (~1 hour). See drain3-fix note above. Make drain3 fire on new-template + severity-marker instead of rate. Retires the need for threshold tuning. Subsumed by US-5.1 per-service Drain3 + baselines.
  2. Trace-anomaly detector (~1 day). New app/trace_analyzer.py module. Running distribution per (service, operation); flag > 3σ as an alert source. Opens the fourth pillar (metrics, logs, and now traces) for drain3-style novelty detection. Would have caught the 13 s /actuator/health latency on day 1. Related to US-5.1 (entity baselines applied to traces).
  3. Incident correlator — kill-chain grouping (~1-2 days) → US-5.2 (Epic 5 core)
  4. Closed-loop analyst feedback (~half-day) → US-5.3 (Epic 5 core)
  5. Adaptive thresholds (~2 hours) → US-5.4 (Epic 5 core)
  6. P2 golden-test set in CI (~4 hours). 20 synthetic webhooks with expected-RCA-contains assertions. Prevents regressions when we iterate on the prompt.
  7. Evaluation dashboard (~1 day). Grafana panel tracking rca_quality distribution, llm_confidence histogram, fallback rate (conf=0.00), template-fill rate, banned-phrase-hit rate. Turns quality from vibes into a number.

Track B — reliability

  1. Spring-boot resilience rounds — if OOM recurs after F3, add HikariCP tuning (maximumPoolSize, connectionTimeout), right-size the RDS instance, investigate whether we actually need JPA's hibernate.ddl-auto=update (can hot-path a lot of I/O).
  2. Webhook authentication — /webhook/grafana currently accepts any POST. Add a shared-secret header check before any external demo. ~30 min.
  3. RCA history S3 backup — nightly aws s3 cp /data/rca_history.db s3://… via cron on the laptop. ~30 min.
  4. Durable ansible key — the key currently lives only on the controller VM. Encrypt with ansible-vault + commit to monitoring-project, or store in AWS Secrets Manager. ~1 hour.

Track C — product UX

  1. Human-readability pass (P1.11) — Lina's list of what reads badly on the dashboard/email. Known offenders: Unix timestamps in LLM prose, long labels overflowing row cells, RCA prose not citing the MetricFacts.one_liner verbatim when available.
  2. Per-row fix-it links — each dashboard row shows a "Ship suggested fix" button next to each suggested action, preparing a kubectl patch or PR body the operator can one-click apply.
  3. Operator feedback loop — "Was this RCA useful?" Yes/No after reading the email. Feed the signal into the evaluation dashboard; over time, use the "No" rows as golden tests for prompt regression.

Track D — ops hygiene

  1. Weekly namespace-drift audit — already scheduled (trig_01WjYBtiUyCA11BJPwLk1u6W, runs first on 2026-04-27 08:00 UTC).
  2. Weekly RCA-quality digest — one more scheduled agent: Monday summary of the prior week's rca_quality distribution, flagging regressions.
  3. Monthly infra-diff — monthly scheduled agent that diffs Terraform plan against running state; opens issues on drift.

Coda — what this exercise proves

The triage pipeline is instrumented well enough that an audit of its own output surfaces the bugs it would have missed on its own. Drain3 saw the OOM pattern. Prometheus recorded the up==0 flips. Jaeger has the 13-second actuator trace. The missing piece was any automated mechanism that cross-referenced these signals against each other and said "these are all the same incident." That's what Track A (drain3 novelty + trace analyzer + golden tests + evaluation dashboard) builds toward. The plumbing is all there now — next sprint is about using it.
