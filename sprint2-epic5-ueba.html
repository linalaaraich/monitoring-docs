Epic 5 — Entity-behavior-driven observability (UEBA applied to AIOps)

UEBA (User and Entity Behavior Analytics) is a mature discipline in the SIEM/security world. Its core insight — reason about entities whose behavior you profile continuously, not events in isolation — maps directly onto observability. This Epic lifts seven concrete patterns from UEBA and applies each to the CIRES AI triage pipeline. Four are core Sprint 2 deliverables (US-5.1 through US-5.4); three are stretch (carry to post-presentation sprint if time allows). The philosophical shift — from "alert-driven" to "entity-behavior-driven" — is what makes the platform defensible as a production-grade AIOps system, not a demo toy.

New Epic · 2026-04-24 7 user stories 4 core · 3 stretch
2026-04-27 update — exemplar library shipped (D17). Every US-5.x story below ultimately produces RCA text via the LLM. To raise the quality floor across all of them, an exemplar library was added that pre-injects a canonical good-RCA shape (matched to this alert's archetype) into every prompt. Eleven archetypes are catalogued — the per-story acceptance criteria below assume this baseline is in place. The library is separate from rca_history.db precisely so it doesn't pollute US-5.3's closed-loop feedback or US-5.7's precision/recall metrics. Source-of-truth: monitoring-triage-service/app/exemplars/library.yaml; prose: monitoring-triage-service/docs/happy-path-scenarios.md.

Why this Epic

Everything we've shipped in Sprint 2 is event-centric: a Grafana rule crosses a threshold, the triage pipeline synthesizes an RCA for that single event, an email goes out. That's useful, but it's what a senior SRE was already doing manually — just faster and at 3 AM. UEBA systems in the security world made the jump to entity-centric reasoning 10 years ago. The same jump in observability collapses four classes of current-state problems:

  • No baselines. Our alerts use static thresholds (CpuUsage > 85%). Real traffic is not stationary — Tuesday 10 AM ≠ Sunday 03 AM. Static thresholds miss daytime regressions and over-fire on nighttime batch jobs.
  • No incident grouping. Today a cascade (disk fills → DB slow → connection pool exhausts → Kong 503s → users report errors) fires 4 separate alerts, produces 4 separate RCAs, sends 4 emails. The human sees one incident. So should the system.
  • No learning loop. Every past analyst verdict is training data we're throwing away. False positives repeat. True positives that the LLM marked DISMISS repeat too. We have the storage (rca_history); we just haven't closed the loop.
  • No entity memory. Drain3 has a global template cluster pool. kong and spring-boot logs cluster together, diluting each service's signal. A 50 % log-volume drop on the triage service would go unnoticed because the global rate barely moves.

The seven stories below address these directly, using UEBA's vocabulary and methods. Each links to code paths in this codebase and acceptance criteria a reviewer can check.

Meta-lesson

The deepest lesson isn't any single feature — it's the philosophical shift from alert-driven ops to entity-behavior-driven ops. Every service has a running behavioral profile. Alerts are samples from that profile. The RCA is always "this entity behaved differently than its own baseline / its peers / its recent history" — and the machine tracks that continuously, whether or not an alert has fired. That's the 10-year UEBA endgame; Epic 5 gets us 80% of the way there architecturally.

The 7 stories

US-5.1
Per-service Drain3 instances + per-service metric baselines
Core Medium effort · ~1 day

UEBA lesson

Don't profile events globally. Profile entities whose behavior you track continuously. A login at 3 AM matters differently if the user has done it 50 times before vs never.

Apply to observability

Keep the existing global Drain3, but add a second dimension keyed by service label: separate template state files per service so spring-boot logs don't blend with kong logs. Add per-service metric baselines for p95 latency distribution, error rate, memory curve — stored as quantile_over_time() aggregates in Prometheus and exposed to the LLM prompt as a new "behavioral context" block.

Concrete implementation

In app/drain_analyzer.py, replace the single TemplateMiner with a dict[service_name → TemplateMiner]. FilePersistence paths become {drain3_state_dir}/{service}.bin. The analyze() method routes by service label (extracted from the Loki stream labels during ingest). /drain3/stats returns per-service stats.

For metric baselines: new module app/entity_baselines.py with get_baseline(service, metric, window='7d') → {mean, stddev, p50, p95}. Called by metric_interpreter.interpret() and included in MetricFacts as baseline field. The LLM prompt then gets "p95 latency = 30000 ms — 4.2σ above spring-boot's 30-day baseline (mean=850ms, σ=250ms)" instead of just "above 1000 ms threshold."

Acceptance criteria

  • /drain3/stats?service=spring-boot returns distinct template count from service=kong
  • Any RCA for a service with ≥7 days of history cites at least one "Xσ above baseline" claim sourced from entity_baselines
  • New Prometheus metric triage_baseline_sigma{service,metric} exported for observability
US-5.2
Incident correlator — group co-firing alerts into one "kill chain" incident
Core · biggest demo impact Medium effort · ~1–2 days

UEBA lesson

Single events rarely matter. Sequences matter. Attackers do recon → exploit → persist → lateral movement. UEBA platforms score the chain, not the steps.

Apply to observability

Real incidents are cascades: disk fills → DB writes slow → connection pool exhausts → Kong 503s → user errors. Today the triage pipeline sees 4 alerts, produces 4 RCAs, emails 4 times. A human sees one incident with four symptoms. The LLM is dramatically better at RCA when it reasons over the WHOLE chain at once.

Concrete implementation

New module app/incident_correlator.py. On every alert arrival, check for other alerts within a settings.incident_correlation_window_seconds (default 900 s = 15 min). If any exist, all alerts in that window join a shared incident_id (UUID). The incident object carries alert_ids[], earliest_start, latest_start, aggregated affected_services, and a single shared RCA.

New SQLite table incidents(id, created_at, status, alert_ids_json, rca_report, verdict, ...). The pipeline's LLM call changes: for incident-scoped alerts, send ALL alerts in the incident to the LLM in one prompt under a new "Related alerts firing concurrently" section. Single email per incident with all symptoms listed.

Dashboard: incident rows become parent records, with child alerts shown indented when expanded.

Acceptance criteria

  • Given 4 Grafana webhooks within 12 min, exactly 1 escalation email is sent (not 4)
  • The incident object carries all 4 alert_ids; dashboard renders them as indented children
  • The LLM RCA references the causal chain explicitly (rule H of SYSTEM_PROMPT already enforces this for dyads; extend to N)
  • New metric triage_incidents_total{size} tracks incident-size distribution
US-5.3
Closed-loop feedback from analyst verdicts
Core · lowest effort, highest signal Low effort · ~half-day

UEBA lesson

Every analyst decision is training data: false positive, tuned threshold, confirmed true positive. UEBA platforms use this to auto-tune detection over time. Without this loop, the system degrades instead of improving.

Apply to observability

Today rca_history is read-only from the LLM's perspective. It reads past RCAs as context but doesn't LEARN from analyst overrides. Close the loop.

Concrete implementation

Two new endpoints on the triage service:

  • POST /feedback/override — body: {decision_id, new_verdict: "escalate"|"dismiss", reason}. Flags the row as analyst-overridden and updates rca_quality.
  • POST /feedback/confirm — body: {decision_id, outcome: "true_positive"|"false_positive"}. Records the ground truth.

Link in each escalation email: two one-click buttons "Was right" and "False positive" that POST to these endpoints with a signed URL token.

Extend the existing Layer-2 suppression (pipeline._check_suppression()): if the same (alert_name, service) was marked false positive by an analyst within settings.feedback_suppression_days (default 7 d), suppress the new alert without calling the LLM. If a similar alert was confirmed as incident by analyst override within the same window, bias the verdict toward ESCALATE even if the LLM says DISMISS.

New Prometheus metrics: triage_precision (true_positives / escalations) and triage_recall (true_positives / all_confirmed_incidents). These become the KPIs for Sprint 3 evaluation dashboard.

Acceptance criteria

  • Escalation emails carry the two feedback buttons; POSTs hit the endpoints and persist
  • A same-alert false-positive marker within 7 days suppresses the next fire without Ollama
  • triage_precision and triage_recall exposed at /metrics
  • Feedback is sourced-tagged: analyst-override rows are visually distinguished on the dashboard
US-5.4
Adaptive thresholds — time-of-day / day-of-week baselines instead of static
✅ Shipped 2026-04-27 · see D18 Low effort · ~2 hours actual

What shipped

3 rules rewritten in roles/grafana/templates/alertrules.yml.j2: HighP95Latency, HighKongP95Latency, MediumCpuUsage. Each is now a single PromQL expression: (current) - (avg_over_time + 3·stddev_over_time over 1h offset 7d, with `or vector(static_floor)` fallback), threshold gt 0. All three gain an adaptive_threshold: "true" label so dashboards and the triage service can distinguish adaptive vs static rules. Applied via ansible-playbook -i inventory/tailnet.yml playbooks/monitoring.yml --tags monitoring; verified live in Grafana provisioning API. Full philosophy + tradeoff analysis in D18.

UEBA lesson

A user logging in at 3 AM means nothing for an on-call sysadmin. It means everything for a 9-to-5 accountant. Static thresholds over-fire on expected-busy times and under-fire on expected-quiet degradations.

Apply to observability

Your alert rules today are static: CpuUsage > 85%. Real traffic is not stationary. Tuesday 10 AM ≠ Sunday 03 AM. An adaptive rule like "CPU is 3σ above the last-7-days-same-hour baseline" catches real regressions that a static threshold misses, and silences the nightly batch jobs that currently fire at 02:00 every day.

Concrete implementation

PromQL pattern for a same-hour-seasonal baseline:

(
  avg_over_time(node_cpu_busy_percent[5m])
  - avg_over_time(node_cpu_busy_percent[7d] offset 1h)
)
/ stddev_over_time(node_cpu_busy_percent[7d] offset 1h)
> 3

Rewrite 3–5 of the most-flappy static rules in roles/grafana/templates/alertrules.yml.j2 (start with MediumCpuUsage — it fired 8 times in the audit window, most post-P1 dismissed). Keep the static rules as fallback until adaptive proves stable.

Annotate converted rules with label: "adaptive" so the dashboard can render them with a visible tag. MetricFacts one-liner gets updated to say "CPU = 94% — 3.4σ above same-hour-Tuesday-10am baseline".

Acceptance criteria

  • At least 3 alert rules converted to adaptive thresholds; all 18 rules document their threshold strategy in a comment
  • Before/after comparison: 7-day window, count of fires for the converted rules drops ≥ 30% (baseline: MediumCpuUsage fired 8× pre-change in one 40-min window — target: fires only on genuine anomalies)
  • Grafana dashboard distinguishes adaptive vs static rules visually
US-5.5
Peer grouping — per-pod z-score within replica set
Stretch · post-Sprint 2 Medium effort · ~1 day

UEBA lesson

Compare a user to users like them. If a backend engineer runs kubectl it's fine; if an accountant does it, page someone.

Apply to observability

In Kubernetes, replicas of the same Deployment are natural peers. If spring-boot-abc has 5× the latency of spring-boot-def and spring-boot-ghi, that's a specific-pod issue — very different RCA from a service-wide degradation. Most observability tools aggregate at service level and miss this entirely.

Concrete implementation

New MCP tool in monitoring-mcp-servers/prometheus-mcp: compare_peers(service, metric, window) → {pod: z_score}. Internally runs:

PromQL: histogram_quantile(0.95,
    sum by (pod) (rate(http_server_requests_seconds_bucket{service=X}[window])))

Then: z-score each pod against the mean + stddev of its siblings.

Add to the bounded-agency whitelist (app/bounded_agency.py): the LLM can request prometheus.compare_peers on data_starved retry. RCA prose then says "Pod spring-boot-abc is 4.2σ above its 2 sibling replicas' latency — local issue, not service-wide."

Acceptance criteria

  • compare_peers MCP returns per-pod z-scores for a given service+metric
  • At least one live RCA cites peer-comparison evidence (can be verified via a synthetic imbalanced-replica load test)
  • Tool appears in TOOLS_DESCRIPTION of bounded_agency.py
US-5.6
Deployment-history enrichment — "what changed 30 min ago?"
Stretch · post-Sprint 2 Medium effort · ~1 day

UEBA lesson

Correlate internal events with external context — threat feeds, CVE databases, geo-IP.

Apply to observability

≈ 87 % of production incidents come from recent changes. Correlating alerts with deployment history converts most RCAs from "something is wrong somewhere" to "Service X started failing at 14:32. At 14:28, Helm upgraded spring-boot from v1.4.2 to v1.4.3. Probable cause: the 1.4.3 deployment. Suggested: rollback." That's senior-SRE quality.

Concrete implementation

New MCP server monitoring-mcp-servers/deployment-history-mcp (port 8096). Endpoints:

  • GET /recent?service=X&window=30m — returns recent deployment events for this service from three sources:
  • Helm release history: helm history spring-boot -n app -o json
  • Git commits on the deployment repo since timestamp: git log --since='30 minutes ago' --oneline
  • Jira ticket transitions (existing CSV export under monitoring-docs/jira/) filtered by service label

Wire into the context gatherer (app/context.py) as a FOURTH pillar. Add to SYSTEM_PROMPT rules: "If a recent deployment exists within ±30 min, state it explicitly and weight it as a probable cause."

Acceptance criteria

  • New MCP server deployed + healthy
  • Every RCA shows a "Recent deployments" section (even if empty)
  • Synthetic test: deploy a broken config, fire an alert — RCA attributes to the deployment
US-5.7
Batch reanalysis + labeled corpus → objective precision/recall tracking
Stretch · folds into Sprint 3 evaluation dashboard High effort · ~2 days

UEBA lesson

When detection logic improves, re-run it against old events. You find past incidents you missed AND quantify your improvement objectively.

Apply to observability

Sprint 3's Track A already plans precision/recall as a first-class metric. Make it a loop instead of a one-off: every prompt change, every threshold tweak, every MCP tool addition re-runs against a labeled corpus and reports F1 delta.

Concrete implementation

Curate monitoring-triage-service/tests/corpus/ — a directory of JSON webhook payloads + expected verdict + expected RCA phrases (goldens). Start with 20 from the current rca_history where the verdict is manually verified correct.

New endpoint POST /evaluate — runs the corpus through the current pipeline (temperature=0, so deterministic), compares outputs to goldens, returns {precision, recall, f1, per_alert_results[]}.

CI hook: on every push to monitoring-triage-service, run /evaluate inside the built image. Fail the build if F1 drops by more than 5 % vs the main-branch baseline.

New table evaluations(commit_sha, timestamp, f1, precision, recall, corpus_size) persisted to SQLite. Grafana panel plots F1 over time against commit markers.

Acceptance criteria

  • Corpus of ≥ 20 labeled goldens in tests/corpus/
  • POST /evaluate runs end-to-end and returns scores
  • CI fails on > 5 % F1 regression
  • Grafana panel renders F1 over time (sourced from evaluations table)
US-5.8
Recurrence gate — two-tier hysteresis for known-flappy alerts
Core · structured noise suppression Medium effort · ~4–6 hours

UEBA lesson

Single events rarely matter; sequences do. UEBA platforms score the chain, not the steps. The corollary: an event that fires once can be ignored, but the same event firing repeatedly (in a window) is itself signal — even if no individual fire is concerning enough on its own.

Apply to observability

Today the pipeline has two recurrence-aware features:

  • Fingerprint dedup (D9) — collapses identical fires inside a 10-minute window. Catches "same alert, refired immediately."
  • Drain3 7-day recurrence (D8) — escalates a Drain3 anomaly when its template fired ≥3× in 7d.

Both are great, but they leave a gap: a Grafana metric alert (e.g. MediumCpuUsage) that fires every 90 minutes — too slow for dedup, too noisy to page someone every time, but eventually meaningful if it keeps happening. Today every fire goes through the LLM and gets dismissed individually; on fire #5 the operator's mental model is "something IS going on" but the system is still treating each fire in isolation.

The recurrence gate adds a third layer: a windowed counter that gates the LLM call, then a post-LLM override that forces escalation when the LLM has dismissed the same alert too many times.

Concrete implementation

Two-tier behavior (configurable per-alert in the rule annotation):

  1. Pre-LLM gate — first N fires (default 4) of the same fingerprint within a window (default 2h) are persisted as triage_decision=recurrence_gated_pre_llm with no LLM call, no email. Cheap rows that show in the dashboard but don't burn GPU or wake the on-call.
  2. Post-LLM override — when fire N+1 reaches the LLM and the LLM dismisses it, the gate counts that as one "LLM-seen dismissal." If past LLM-seen-dismissals on the same fingerprint within the window reach a threshold (default 2), the next fire's LLM dismissal is overridden to ESCALATE. The reasoning: "the LLM said 'noise' twice and the alert kept firing — there's a real signal the model isn't picking up."

Per-rule opt-in via Grafana rule annotation:

annotations:
  recurrence_gate: "pre_llm=4,llm_dismiss=2,window=2h"

Without that annotation, the gate is bypassed entirely. Critical-severity alerts must NEVER opt in — for TargetDown, OOMKill, OTelCollectorDown, the customer is already in pain on fire #1 and waiting four fires is malpractice. The gate is for warning- and info-tier rules with a known noise problem.

Code shape:

  • monitoring-triage-service/app/recurrence_gate.py — new module with two pure functions: pre_llm_gate(alert, history) and post_llm_gate(decision, history). Both return either None (no gate triggered) or a GateResult with the new triage_decision and a reason string.
  • app/pipeline.py — wire in two new gate calls: one right after dedup (pre-LLM), one right after the LLM call (post-LLM, only if the LLM verdict was DISMISS).
  • app/main.py — add humanize entries for the two new triage_decision values: recurrence_gated_pre_llm → "Gated (count under threshold)", recurrence_gated_post_llm_force_escalate → "Escalated by gate (LLM dismissed too many)".
  • roles/grafana/templates/alertrules.yml.j2 — add the recurrence_gate annotation to 2–3 specific noisy rules (good candidates: MediumCpuUsage, MediumMemoryUsage; never to TargetDown, CriticalCpuUsage, or OOM-style rules).
  • monitoring-docs/dashboard-guide.html — add the new triage_decision values to the codes glossary; add a 7th worked scenario "Recurrence-gated row" to the scenarios section.
  • monitoring-docs/decisions-log.html — D19 entry documenting the philosophy + the "never on critical-severity" guardrail.
  • tests/test_recurrence_gate.py — test the two gate functions against synthetic history fixtures (fire counts, window expiry, threshold crossing, critical-severity bypass).

Acceptance criteria

  • The two new triage_decision values render correctly on the dashboard with humanized labels and tooltips.
  • An opted-in alert (e.g. MediumCpuUsage with the annotation) shows N pre-LLM-gated rows in the dashboard before the first LLM-evaluated row.
  • An alert without the annotation behaves unchanged (no regression to existing pipeline).
  • A critical-severity alert with the annotation logs a warning and the gate is bypassed (defense in depth — even if a misconfigured rule opts in, criticals never wait).
  • After 2 LLM dismissals of the same fingerprint within the window, the third fire's verdict is force-escalated and the email is sent with a clear "Escalated by gate" line in the body.
  • D19 in decisions-log explains the philosophy + composes the gate cleanly with existing dedup + Drain3 7d-recurrence layers.

Recommended delivery order

Based on effort × demo impact × reviewer legibility (a PFE jury recognizes UEBA vocabulary, so leading with incident correlation is strategic):

  1. ✅ US-5.4 (adaptive thresholds) — shipped 2026-04-27. See D18. 3 rules rewritten; largest immediate false-positive reduction; visible in Grafana now.
  2. US-5.8 (recurrence gate) — 4–6 hours, structured noise suppression with safety guardrails. Slot here because it's the natural follow-up to adaptive thresholds: where adaptive thresholds reduce raw fire frequency, the recurrence gate decides which fires actually deserve a human's attention. Pairs cleanly with US-5.3 (the post-LLM override IS a feedback signal).
  3. US-5.3 (closed-loop feedback) — half-day, zero new infrastructure. Get triage_precision and triage_recall exported so every future change can be measured. Couples well with US-5.8 — both rely on the same "LLM-was-wrong" signal.
  4. US-5.2 (incident correlator) — 1–2 days, biggest demo moment. "4 alerts collapse to 1 email with a proper RCA of the whole chain" is a jury-stopper.
  5. US-5.1 (per-service Drain3 + baselines) — 1 day, enables the "Xσ above baseline" framing in every RCA. Pairs naturally with US-5.4 (which already shipped).
  6. Stretch: US-5.5, US-5.6, US-5.7 — deliver in order of dependency; US-5.7 folds into Sprint 3 evaluation work already planned.

Total core Epic 5 budget: ~3–4 days of work if executed sequentially by one engineer; parallelizable to ~2 days if US-5.3 and US-5.4 are done in parallel with US-5.2.
