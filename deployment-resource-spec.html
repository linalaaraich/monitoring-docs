Deployment — Resource & Dependency Specification

Exactly what hardware, software, and external dependencies are required to deploy and run the platform — sized from live measurement of the running system, with a GPU recommendation for the L4.

Prepared for the production-deployment hand-off · 2026-06-04 · figures measured from the live running stack, not estimated.

What this platform is (one paragraph)
A self-hosted pipeline that turns monitoring alerts into written root-cause analyses with zero alert reaching a human until the AI has investigated it. An alert (from Grafana / your k8s) hits a triage service, which gathers evidence from Prometheus, Loki (logs), Jaeger (traces) and a log-anomaly engine through read-only "MCP" bridges, then a locally-hosted LLM (Ollama) writes the diagnosis and either escalates with the cause or dismisses noise. Everything runs on your own infrastructure — no data leaves your network, no external API. It watches whatever you point it at: your ML apps on GPU instances and your existing Kubernetes workloads.

1. Topology — three tiers

The platform deploys as three independent tiers. The AI tier needs a GPU; the others do not. Tiers communicate over plain TCP on your network — co-locate or separate them as your capacity dictates.

TierWhat runs thereGPU?Where it can live
A · AI / triageOllama + the LLM model, the triage service, 5 MCP bridge containers, 1 OTel collector, GPU-metrics exporterYesYour GPU instance (e.g. the L4 box)
B · Observability backendPrometheus, Loki, Jaeger, Grafana, node/cAdvisor exportersNoA CPU VM (can co-locate on the GPU box if it has spare CPU/RAM)
C · Collection (on your targets)OTel collector DaemonSet + kube-state-metrics + a read-only Prometheus scraper on your k8s; an OTel collector on your ML/GPU app hostsNoInside your Kubernetes + on your monitored hosts

Tiers A and B are what the Ansible stands up. Tier C is the thin agent layer the Ansible points at your cluster and hosts so the platform can see them.

Storage sizing (Tier B is the only tier whose disk grows)
Plan the data volume by retention × ingest, not by a fixed number:
  • Prometheus: ≈ active_series ÷ scrape_interval × 1.5 bytes × retention. Example: 100k series @ 15 s, 15-day retention ≈ ~12 GB.
  • Loki: ≈ daily_raw_log_GB × 0.15 (compression) × retention_days. Example: 5 GB/day raw, 15 days ≈ ~11 GB.
  • Jaeger (Badger): trace-volume driven; budget ≈ Loki's order of magnitude for similar app traffic.
A 100 GB SSD comfortably holds 15–30 days of moderate production telemetry. Mount it as a separate volume so the OS disk can't fill.

4. GPU recommendation — the L4 is a good fit ✓

The platform runs qwen2.5:14b-instruct (quantised, ≈ 13 GB on disk, ≈ 11 GB resident in VRAM with working context) as the primary model, with qwen2.5:7b-instruct as a lightweight fallback. The workload is bursty, single-stream, non-interactive — one alert investigation at a time, not a chat service.

NVIDIA L4 (your option)NVIDIA A10G (current)
VRAM24 GB GDDR623 GB GDDR6
Memory bandwidth300 GB/s600 GB/s
ArchitectureAda Lovelace (FP8 capable)Ampere
Power (TDP)72 W300 W
Fits the 14B model?✓ comfortably (24 GB ≫ 11 GB)✓
Verdict: yes, deploy on the L4
The L4 has ample VRAM for the 14B model (24 GB vs the ~11 GB needed — room for larger context windows or running 7B + 14B side by side) and is dramatically more power-efficient (72 W vs 300 W). The one trade-off: LLM token generation is memory-bandwidth-bound, and the L4's 300 GB/s is half the A10G's 600 GB/s, so per-investigation latency will be somewhat higher than our current ~38 s median. For a triage workload this is fine — the pipeline budgets 180 s per investigation and alerts are not real-time. If lower latency is ever required, the 7B model on the L4 is very fast, or a higher-bandwidth card (A10/L40S/A100) trades cost and power for speed.

Minimum viable GPU: any NVIDIA card with ≥ 12 GB VRAM runs the 14B model; ≥ 8 GB runs the 7B. The L4's 24 GB is generous and recommended. One L4 is sufficient — the platform uses a single GPU; it does not need multiple cards or NVLink.

Tier B — backend host

  • Docker Engine + compose plugin
  • Containers: Prometheus, Loki, Jaeger (v2), Grafana, OTel collector, cAdvisor, node-exporter
  • Grafana provisioning: Prometheus + Loki + Jaeger datasources (with trace↔log↔metric correlation), alert rules, contact points — no paid panel plugins required

5.3 Container images

Application images are published to a container registry (currently GitHub Container Registry, ghcr.io). For your deployment you can either pull from that registry or host them in your own (e.g. Harbor / your internal registry) — the image references are a single configurable variable. Sizes (measured): triage-service 338 MB · each MCP bridge 266 MB · OTel collector 397 MB · DCGM exporter 487 MB. Third-party images (Prometheus, Loki, Jaeger, Grafana, Ollama) are pulled from their public upstreams.

7. Secrets & configuration you must set

There are no usable default credentials — every weak default was removed, and a preflight check fails the run if anything required is left unset or at a CHANGE_ME placeholder. You provide two kinds of values:

(a) Non-secret environment values — in your inventory (copy inventory/example.yml → inventory/my-env.yml and fill in):

# per host
monitoring_vm_ip:          "<backend-host-ip>"      # reachable IP of the backend
gpu_host_ip:               "<gpu-host-ip>"          # reachable IP of the GPU host
k3s_host_ip:               "<your-k8s-api-endpoint>"# for Prometheus discovery
grafana_external_url:      "http://<backend-host>:3000"
triage_service_webhook_url:"http://<gpu-host-ip>:8090/webhook/grafana"
smtp_username:             "alerts@your-org"
smtp_from:                 "alerts@your-org"
alert_email_to:            "oncall@your-org"
llm_model:                 "qwen2.5:14b"             # or qwen2.5:7b for speed
image_registry:            "ghcr.io/linalaaraich"    # or your own mirror

(b) Secrets — in an Ansible-Vault file (copy inventory/group_vars/vault.example.yml → vault.yml, fill, then ansible-vault encrypt):

vault_grafana_admin_password: "<your-strong-password>"
vault_smtp_password:          "<your-smtp-app-password>"

8. How the deploy runs (operator flow)

Control machine needs: ansible, kubectl (pointed at your cluster), helm, rsync; then ansible-galaxy install -r requirements.yml.

  1. Copy inventory/example.yml → inventory/my-env.yml, fill in your host IPs + kubeconfig context. Copy inventory/group_vars/vault.example.yml → vault.yml, fill secrets, ansible-vault encrypt it.
  2. Backend (Tier B): ansible-playbook -i inventory/my-env.yml playbooks/monitoring.yml -e @inventory/group_vars/vault.yml --ask-vault-pass — Prometheus/Loki/Jaeger/Grafana. (A preflight check stops you here if anything required is unset.)
  3. GPU/AI (Tier A): ansible-playbook -i inventory/my-env.yml playbooks/gpu-host.yml -e @… --ask-vault-pass — installs NVIDIA driver, Docker, container toolkit, Ollama + pulls the model, then the triage stack. note a fresh driver install needs one reboot then re-run.
  4. Collection (Tier C): ansible-playbook -i inventory/my-env.yml playbooks/k8s-manifests.yml -e @… --ask-vault-pass — applies the OTel DaemonSet + kube-state-metrics + scraper RBAC to your cluster via your kubeconfig. Do not run k3s.yml — that bootstraps a new cluster; you bring your own.
  5. Point your Grafana alerting at triage_service_webhook_url; instrument your ML apps to send OTLP to the collector endpoint. (Optional: playbooks/otel-demo.yml stands up a 22-service demo app to validate the whole platform end-to-end — including inducing a real fault — before wiring your own.)
Verification baked in
Every tier has a health check; after deploy you confirm: GPU visible to Ollama (nvidia-smi + a model query), the triage dashboard reachable, traces/logs/metrics arriving in Grafana, and an induced test alert producing a written RCA. Section 9 below lists the exact checks.

9. Acceptance checks after deploy

  • GPU: nvidia-smi shows the card; docker run --gpus all sees it; ollama run qwen2.5:14b "ping" returns on the GPU.
  • Backend: Grafana loads; Prometheus, Loki, Jaeger datasources all green.
  • Collection: your k8s pods appear as Prometheus targets (up=1); pod logs appear in Loki; app traces appear in Jaeger.
  • End-to-end: induce a real fault (e.g. scale a deployment to an unavailable state) → an alert fires → the triage service emails a written root-cause analysis and records it on the dashboard.
