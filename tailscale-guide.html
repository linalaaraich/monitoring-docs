Tailscale guide

How CIRES Observability uses Tailscale to keep hands-off operations working across the cloud controller, monitoring VM, k3s node, and Lina's laptop — without chasing public IPs after every redeploy. This is the networking spine the ansible role, deep-links, and webhook URLs all lean on.

WireGuard-based Zero-config mesh MagicDNS hostnames Free tier sufficient

Why Tailscale

The CIRES platform has four moving pieces that need to reach each other: the cloud controller (where this documentation and the ansible control node live), the monitoring VM on EC2, the k3s node on EC2, and Lina's laptop running the AI stack. Three of those are on AWS EC2 with elastic IPs that can drift; one is on a residential WSL2 box with a dynamic home-router IP. Coordinating them via public IPs + security groups is brittle — every re-provision is a hand-editing exercise.

Tailscale fixes this by putting every node on a single WireGuard mesh (the tailnet) with stable 100.x.y.z addresses and MagicDNS hostnames. The monitoring VM reaches Lina's laptop at adolin-wsl regardless of what IP her ISP hands out that morning. Ansible runs against observability-rca-monitoring regardless of whether AWS re-assigns the EIP. And none of this crosses the public internet — traffic goes peer-to-peer when possible, encrypted, with a NAT-traversal relay fallback.

Free tier

Tailscale's free tier allows 100 devices and 3 users, unlimited bandwidth, and MagicDNS — far beyond what this project needs. No payment method required for setup. Paid tiers add audit logging, SSO, and device posture features we don't use.

Setting up a new host

Two paths depending on whether the host is cloud-provisioned from Terraform or an already-running box (VM, laptop, etc.):

Path A — fresh AWS instance (Terraform-driven)

  1. Generate an ephemeral+reusable auth key at the tailscale admin panel. Check both Reusable and Ephemeral; set TTL to 24 h or less.
  2. Set it for Terraform via env: 
    export TF_VAR_tailscale_auth_key="tskey-auth-xxxxxxxxxx"
  3. Run terraform apply. The user_data for each instance has a conditional Tailscale-install snippet that fires on first boot when the var is set — the instance joins with hostname ${var.project_name}-monitoring (or -k3s / -gpu) and --ssh enabled.
  4. Once the apply completes, run tailscale status from the controller and you should see the new node listed.
Ephemeral node benefit

An ephemeral node auto-removes from the tailnet admin panel when it goes offline, which keeps the panel clean across terraform destroy + re-apply cycles. The hostname is re-used when a new instance with the same name comes up.

Path B — already-running host (ansible-driven)

Use the tailscale role in the monitoring-project repo. Two steps from the controller: 

# 1. Generate an ephemeral+reusable auth key as above.
# 2. Run the tailscale playbook, which applies the role to every host:
TAILSCALE_AUTH_KEY="tskey-auth-xxxxxxxxxx" \
  ansible-playbook playbooks/tailscale.yml

The role installs the Tailscale repo, apt-installs the package, enables the systemd unit, and runs tailscale up with the current inventory hostname. It's idempotent — re-running after the first join is a no-op.

MagicDNS — the hostname convention

MagicDNS is enabled by default on all new tailnets (since 2023). It publishes every tailnet member's hostname as a resolvable short name on all its peers. No /etc/hosts edits, no DNS server setup.

The CIRES convention: a node's Ansible inventory name is also its MagicDNS hostname. The tailscale role uses inventory_hostname as the --hostname argument on join, so they can't drift. The complementary inventory file inventory/tailnet.yml then sets ansible_host to that same hostname, and ansible routes over the tailnet transparently: 

# Point ansible at the tailnet inventory
ansible-playbook -i inventory/tailnet.yml playbooks/site.yml

# Or make it the default in ansible.cfg:
[defaults]
inventory = inventory/tailnet.yml

ACLs — who can reach what

By default every tailnet member can reach every other member on every port. For this project that's what we want: the controller ansibles the other boxes, the monitoring VM webhooks the laptop, and the laptop pulls from the monitoring VM's Loki. If you want to tighten it later, edit the ACL at login.tailscale.com/admin/acls — the default policy looks like: 

{
  "acls": [
    { "action": "accept", "src": ["*"], "dst": ["*:*"] }
  ]
}

A tighter version keyed on tags the tailscale role applies on join would be: 

{
  "tagOwners": {
    "tag:controller":   ["linalaaraich2002@gmail.com"],
    "tag:server":       ["linalaaraich2002@gmail.com"],
    "tag:workstation":  ["linalaaraich2002@gmail.com"]
  },
  "acls": [
    // Controller can reach everything
    { "action": "accept", "src": ["tag:controller"], "dst": ["*:*"] },
    // Servers can reach each other on observability ports only
    { "action": "accept", "src": ["tag:server"], "dst": ["tag:server:3000,3100,9090,16686,4317,4318"] },
    // Laptop can reach servers for ansible + webhook targets
    { "action": "accept", "src": ["tag:workstation"], "dst": ["tag:server:*"] }
  ]
}

To apply, set tailscale_tags: ["tag:server"] (or :workstation, :controller) in the inventory group vars and rerun the tailscale role.

Troubleshooting common gotchas

tailscale up fails with "failed to connect to local tailscaled"

Almost always because the tailscaled systemd unit hasn't finished starting yet. After apt install tailscale, systemd kicks off tailscaled.service which can take 30–60 seconds on a cold install. Wait and retry. The role handles this with systemd: state=started before invoking tailscale up.

Node joins but MagicDNS short name doesn't resolve

Usually --accept-dns=false was passed on join, which tells Tailscale not to publish its DNS into /etc/resolv.conf. Fix: sudo tailscale up --accept-dns=true (re-run, adds the flag without re-auth). The role defaults to true.

Another failure mode: the tailnet admin has MagicDNS globally disabled. Check at login.tailscale.com/admin/dns.

Controller can ping tailnet IP but ansible times out

SSH isn't enabled on the target. Either install openssh-server + start sshd, or join the target with --ssh so Tailscale SSH handles it (no port 22 exposure needed). Our Terraform user_data sets --ssh; the ansible role doesn't (it assumes sshd is already there). To add Tailscale SSH to an existing node: 

ssh deploy@<host> "sudo tailscale up --ssh --accept-dns=true"

Ephemeral key expired mid-session

Ephemeral keys default to 1-hour TTL if you don't set a longer one. If a terraform apply spans more than an hour, new instances late in the apply can fail the join step. Always generate keys with 24 h TTL for non-trivial applies. The key is gone from the admin panel after you rotate; no cleanup needed.

I see the node but can't reach it

Run tailscale status and check the state of the peer:

  • - (just a dash): idle, never connected. Probably never came up on the network.
  • idle, tx 0 rx 0: reachable in principle, no traffic yet. Try tailscale ping <host>.
  • offline: the node hasn't heartbeated recently. If it's a cloud instance, check it's running (aws ec2 describe-instances). If it's your laptop, Tailscale daemon may have crashed — sudo systemctl restart tailscaled.

What happens when an EIP changes?

Short answer: nothing, from the ansible perspective. The controller reaches the monitoring VM at observability-rca-monitoring; Tailscale routes that over the tailnet regardless of what aws_eip_association.monitoring currently points at. Security groups can even drop port 22 from 0.0.0.0/0 entirely — you still reach the box via Tailscale SSH.

This is the single biggest reproducibility win from adopting Tailscale: the infra-setup runbook no longer has to say "now copy the new EIP into inventory/production.yml".
