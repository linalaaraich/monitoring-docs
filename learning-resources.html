CIRES Observability Platform

Learning resources

A focused primer on the four infrastructure tools this project uses — Kubernetes / k3s for the application workload, Terraform for the AWS estate, and Ansible for everything that runs on the VMs after Terraform creates them. Each section is one paragraph of "what it is and why it's here", a short concept list, the actual files in this project that use it, and a curated jump-off to the canonical external docs.

1. Kubernetes

☸️ Kubernetes
Orchestration Application layer

Container orchestrator. In this project Kubernetes runs the application workload (the react-springboot-mysql demo plus the secondary car-rental app) on observability-rca-k3s. We picked it over plain docker-compose so the same deploy primitives could survive a multi-node future, and because Helm charts make the per-service configuration auditable.

Core concepts to know

  • Pod — the smallest deployable unit (one or more containers sharing a network namespace).
  • Deployment — declarative spec of "I want N replicas of this pod, with these env / probes / resources".
  • Service — a stable DNS name + virtual IP that load-balances across the pods behind it.
  • Ingress — external entry point routing host/path → service. Replaced here by Kong as an in-cluster API gateway.
  • Namespace — soft tenant boundary; we use app (main stack) and rental (car-rental side-deploy).
  • Helm chart — a packaged set of templated manifests with a values.yaml override layer. Every service in monitoring-project/charts/ is a Helm chart.

Where this project uses it

  • monitoring-project/charts/ — Helm charts for spring-boot, react-frontend, mysql, kong, rental-*.
  • monitoring-project/manifests/node-exporter/daemonset.yaml — node-level Prometheus exporter as a DaemonSet.
  • monitoring-project/playbooks/k3s-bootstrap.yml — Ansible playbook that brings k3s up and deploys the workload Helm charts.

2. k3s

🚀 k3s
Lightweight Kubernetes Single-binary

A certified Kubernetes distribution packaged as a single binary, designed to run on resource-constrained or single-node environments. We use k3s instead of full k8s on observability-rca-k3s (one t3.xlarge EC2 instance) because the full control plane would dominate the workload's resource budget on a single VM. From an application perspective k3s is just Kubernetes — every concept above applies — but the install is one curl | sh instead of kubeadm.

What's different from "vanilla" Kubernetes

  • Single binary — controller + scheduler + kubelet + kube-proxy all in one process.
  • Embedded SQLite datastore by default instead of etcd (we use the default; for HA you'd swap in an embedded etcd cluster or an external one).
  • Built-in Traefik, ServiceLB, and local-path storage class — most things you'd otherwise install via Helm post-bootstrap are pre-wired. We disabled Traefik (Kong handles ingress instead) but kept local-path for stateful workloads.
  • Kubeconfig path — /etc/rancher/k3s/k3s.yaml instead of ~/.kube/config.

Where this project uses it

  • monitoring-project/playbooks/k3s-bootstrap.yml — single-node bootstrap on the observability-rca-k3s EC2 instance.
  • monitoring-project/inventory/tailnet.yml — points Ansible at the host via MagicDNS.
  • kubectl on the host is shimmed via sudo k3s kubectl; the kubeconfig is owned by root.

3. Terraform

🏗️ Terraform
Infra as Code AWS estate

Declarative tool for provisioning cloud infrastructure. You describe the desired end state in HCL files (.tf); Terraform diffs against the recorded state, computes a plan, and applies the delta. In this project every AWS resource — VPC, subnets, security groups, EC2 instances, RDS, S3 buckets, IAM, EIPs — is created via Terraform; the AWS console is read-only by convention. Why it's here: no clickops, no untracked drift, reproducible from a fresh account, and changes are diffable in git.

Core concepts to know

  • Provider — the plugin that translates HCL into API calls (e.g. hashicorp/aws).
  • Resource — one cloud object (e.g. aws_instance, aws_db_instance).
  • State — the file Terraform uses to remember what it created. Stored remotely in an S3 bucket here, so multiple operators see the same world.
  • Variable / tfvars — parameterised inputs. The only file an operator normally edits during day-to-day work is terraform.tfvars.
  • Plan vs apply — terraform plan shows the diff; terraform apply executes it. Never skip the plan on a shared environment.
  • Output — values exported from the plan for downstream tools (we use outputs to feed Ansible the EC2 IPs).

Where this project uses it

  • provisioning-monitoring-infra/ — the entire AWS estate.
  • terraform.tfvars — the operator-editable knobs (allowed_ssh_cidrs, instance types, AMI pin).
  • Managed resources (us-east-1): observability-rca-monitoring (t3.large), observability-rca-k3s (t3.xlarge), observability-rca-mysql (RDS), the Loki S3 bucket, the Terraform state bucket.
  • Managed resources (us-west-2, added 2026-05-21): observability-rca-gpu (g5.xlarge, A10G 24 GB VRAM), Lambda router + idle-checker, API Gateway HTTP API, SQS cold-start queue, DynamoDB gateway-state table, EventBridge cron, VPC endpoints. See D24.
  • Account: 735115318342, regions: us-east-1 + us-west-2.

Day-to-day commands

  • terraform init — first time in a clone; downloads providers + wires up the S3 backend.
  • terraform plan — see what would change.
  • terraform apply — execute the plan (asks for confirmation).
  • terraform output — read exported values (e.g. EC2 public IPs to feed Ansible).

4. Ansible

⚙️ Ansible
Config management Agentless

Agentless configuration management. Ansible takes a target host (over SSH), a playbook (an ordered list of tasks grouped into roles), and an inventory (the hosts to apply it to), and brings each host to the declared state. In this project Terraform creates the empty VMs; Ansible turns them into the monitoring VM, the k3s host, the laptop, etc. Why it's here: idempotent VM configuration, role-level reuse, single source of truth for what each host is supposed to look like.

Core concepts to know

  • Inventory — the list of target hosts and how to reach them (here: a Tailscale tailnet declared in inventory/tailnet.yml).
  • Playbook — a YAML file pairing a set of hosts with a list of roles or tasks.
  • Role — a reusable directory of tasks / templates / files / handlers / defaults. One role per service is the convention.
  • Task — one declarative action (install a package, render a template, restart a service).
  • Handler — a task that only runs when notified by another task (e.g. restart Prometheus when its config template changed).
  • Template — a Jinja2 file rendered into the target host's filesystem.
  • Idempotency — running the same playbook twice should be a no-op the second time.

Where this project uses it

  • monitoring-project/roles/ — one directory per service: prometheus, loki, jaeger, grafana, otel-collector, node-exporter, plus app-side roles.
  • monitoring-project/playbooks/monitoring.yml — the top-level playbook for the monitoring VM.
  • monitoring-project/inventory/tailnet.yml — Tailscale-MagicDNS-keyed inventory; means IPs don't matter and hosts are reachable from anywhere on the tailnet.
  • monitoring-project/roles/grafana/templates/alertrules.yml.j2 — the Jinja2 template that produces Grafana alert rules; this file is the source of truth for every alert the platform fires.

Day-to-day commands

  • ansible -m ping all — sanity check: every host in the inventory reachable?
  • ansible-playbook playbooks/monitoring.yml — apply the monitoring stack.
  • ansible-playbook playbooks/monitoring.yml --tags monitoring — narrow to one tag.
  • ansible-playbook playbooks/monitoring.yml --check --diff — dry-run with diffs.

How the four tools fit together

The provisioning chain that produces the entire platform from a fresh AWS account, top to bottom:

  1. Terraform creates the AWS estate — VPC, EC2 instances (monitoring VM + k3s host), RDS, S3 buckets, IAM. Outputs the EC2 IPs.
  2. Ansible takes those hosts (via Tailscale MagicDNS) and brings the monitoring VM up to spec — Prometheus, Loki, Jaeger, Grafana, OTel Collector, alert rules.
  3. Ansible (different playbook) bootstraps k3s on the k3s EC2 instance.
  4. Helm deploys the Kubernetes workload (Spring Boot, MySQL, React, Kong, rental-*) onto the k3s cluster.
  5. The AI triage layer runs separately on a Tailscale-attached us-west-2 g5.xlarge GPU host (A10G 24 GB VRAM, since 2026-05-21 — see D24) and reads from this stack via MCP servers — see Architecture.

The exact end-to-end sequence with commands is in the Reproducibility Guide. The mapping from each tool to the repo that owns it is in the Repository Map.
