1. Orientation

The dashboard shows the most-recent 100 decisions the triage pipeline has produced, newest first. Each row is one alert that was processed end-to-end — the triage service queried Prometheus, Loki, Jaeger, and Drain3, ran the LLM, validated the response, and persisted the result.

Where this lives

The dashboard is rendered by app/main.py:dashboard() from rows in rca_history (SQLite at /data/rca.db inside the container). Source for every label below is in the same file — search for _humanize_* for the label maps and _render_detail_panel for the expanded row layout.

Page layout, top to bottom:

  1. Hero — title and refresh state.
  2. Stats tiles (5) — at-a-glance summary across the loaded window.
  3. Drain3 panel — log-template state from the in-memory analyzer.
  4. Filter bar + auto-refresh toggle.
  5. Decisions table — 9 columns; click any row to expand.

3. Drain3 panel

Drain3 is an online log-template miner that runs in-process. As Loki logs flow in during context-gathering, Drain3 clusters lines into templates (e.g. "<*> ERROR connection pool exhausted"). The panel shows live state:

FieldMeans
Anomaly rateFraction of recent ingested lines that landed on a low-frequency template (recent = last ~window). Above ~5% suggests something genuinely novel is happening; near 0% means the system is in a known steady state.
Templates learnedTotal distinct clusters in the in-memory state. Grows over time as new log shapes arrive. Persisted to disk every 30s so restarts don't reset learning.
Lines processedLifetime count of log lines fed through Drain3. Restarted every container restart unless the on-disk state is restored.
Anomalies flaggedCount of lines tagged [ANOMALY] by the analyzer — those whose template falls in the rare-frequency tail.
Most recent templatesClick "Show most recent templates" to expand. Each template is a regex-with-wildcards form — useful to see what kind of log shape Drain3 is currently fitting.

4. Table columns

9 columns, left to right. The first is a chevron icon (click any row to expand it).

4.1 Time

When the decision was persisted to rca_history, rendered in Africa/Casablanca local zone (GMT+1). Source: rca_history.timestamp (stored as UTC ISO; rendered locally by _to_local_time).

4.2 Alert

The Grafana alert rule's title (e.g. HighP95Latency, TargetDown, OTelCollectorHighSpanDropRate). Maps 1:1 to the rule name in monitoring-project/roles/grafana/templates/alertrules.yml.j2. Synthetic alerts (Drain3 self-bridge, replays from the startup-backfill) get conventional names like Drain3AnomalyDetected.

4.3 Source

Where the alert came from. Two values today:

  • grafana — the alert was POSTed to /webhook/grafana by Grafana's contact-point dispatcher.
  • drain3 — the alert was synthesized by the in-process Drain3 self-bridge (POSTed to /webhook/drain3) when the anomaly threshold was crossed.

4.4 Service

The service the alert is about. Comes from alert.labels.service in the webhook payload. Known values today: spring-boot, kong, otel-collector, monitoring (= the Grafana host VM), k3s-node, loki, drain3.

4.5 Severity

Three values, color-coded:

  • critical — page now (today: TargetDown, OOMKill loops, OTel pipeline drop)
  • warning — investigate within hours (most CPU/memory/latency rules)
  • info — context only, not paging-worthy (Drain3 anomalies, threshold-tuning hints)

4.6 Verdict + quality

Two stacked elements: the LLM's verdict (left pill) and the post-hoc RCA quality (right pill, smaller).

Verdict pill (LLM decision):

  • escalate — LLM thinks this is a real issue → email sent.
  • dismiss — LLM thinks this is noise / self-resolving → no email.
  • inconclusive — LLM couldn't pick. Treated as ESCALATE downstream (safer).
  • timeout — pipeline exceeded the budget. No verdict; raw alert forwarded.

Quality pill (RCA quality, post-hoc tag):

  • fits (was actionable) — concrete RCA + at least one valid suggested action. The good case.
  • thin (was data_starved) — model hedged or evidence was empty. Worth re-firing once data is richer.
  • review (was needs_review) — confidence below the floor (0.30) or validator flagged the row. Surface to a human.

4.7 Action

What the pipeline did downstream of the verdict. Renamed in 2026-04-27 from raw pipeline codes to engineer-friendly labels (with the raw code preserved next to the label in a small monospace tag for grep purposes).

LabelRaw codeMeans
NotifiedemailedTriage emailed the on-call (LLM produced a verdict, validator passed, SMTP send succeeded).
Notified (no LLM)emailed_rawLLM was unavailable or timed out — raw alert forwarded for human review. Verdict column will show "timeout" or "—".
SuppressedsuppressedPre-LLM suppression — duplicate fingerprint inside the dedup window, or recent dismissed history. No email.
Droppeddrop_alertBelow severity threshold or matched a quiet-hours rule. No email, no LLM call.
—(empty)No action recorded — usually a row that's still in flight, or persisted before the column was added.

4.8 Duration

End-to-end pipeline duration, from webhook arrival to row persistence. Includes MCP context-gathering (~1–5s) + LLM inference (typically 3–15 s on the us-west-2 A10G running qwen2.5:14b; was 10–80 s on the laptop GTX 1060 + qwen2.5:7b) + validator + persistence. Dashboard format scales: under 1s shows ms, 1–60s shows decimal s, over 60s shows "N min M s".

5. The detail panel

Click any row to expand. Sections, top-down:

Meta-grid (top tile cluster)

9 fields giving the row's identity and core LLM facts:

  • Timestamp (local) — full timestamp with zone label.
  • Decision ID — UUID, useful for cross-referencing with logs.
  • Alert fingerprint — Grafana's stable hash over labels. Two fires of the same fingerprint are the same alert; collapsing on this is what dedup does.
  • Service / Component / signal / Instance — labels from the webhook.
  • Triage path — humanized label + raw triage_decision code. See glossary.
  • LLM confidence / quality — confidence is a 0–1 float; quality is the post-hoc tag (fits/thin/review).
  • Action + duration — the same Action column value with the duration appended.

Observed value + PromQL

The lede card: the actual metric value at fire time and the PromQL expression that produced it. Empty if the alert webhook didn't carry a value (rare but possible for synthetic alerts).

Root-cause analysis

The LLM's narrative. 2–5 sentences typically, starting with a restatement of the observed value + PromQL (mandated by SYSTEM_PROMPT rule A), then the hypothesis, then the supporting reasoning. 10-digit Unix timestamps embedded by the LLM are auto-converted to <unix> (<Casablanca>) at render time.

Reasoning

A separate field for the model's "thinking" — usually a longer-form expansion of the RCA. Not always populated.

Suggested actions

Remediations only. As of 2026-04-27, the LLM is constrained to emit state-changing commands (kubectl rollout restart, helm rollback, docker restart, systemctl restart, kubectl set resources, terraform apply, etc.) — never read-only inspections like kubectl get or Query Grafana: .... The triage service has already inspected the telemetry; that data is in evidence/RCA.

Empty list = the model didn't have a concrete remediation. The pipeline falls back to app/suggested_actions.yaml templates keyed by alertname × deployment type. For Drain3 alerts with no correlation, the fallback is a "Shelved — awaiting recurrence" marker (see scenarios).

Evidence

Specific metric values, log lines, or trace IDs the LLM cited. Each entry must be concrete (a number with units, a quoted log line, a trace ID) — vague entries like "Prometheus metrics" or "Log patterns" get rejected by the validator.

Drain3 anomaly summary

If the alert was sourced by Drain3, this section shows the anomalous templates that triggered the fire (e.g. "java.lang.OutOfMemoryError <*>" with frequency count). For Grafana-sourced alerts where Drain3 found anomalies in the gathered Loki context, those are also listed here.

Correlated alerts (±5 min)

Other alerts that fired within ±5 minutes of this one. The LLM is required (SYSTEM_PROMPT rule H) to address these in the RCA — either "X caused Y", "they share cause Z", or "coincident timing." A sortable mini-table; columns: When · Alert · Service · Verdict · Quality.

Queries to paste into Grafana Explore

Pre-built LogQL/PromQL the operator can copy. These are references for the operator's own deeper investigation, not part of the triage decision (suggested actions must be remediations; the queries here are a courtesy).

6. Codes & abbreviations

Internal codes (raw enum values stored in SQLite)

action_taken
emailed · emailed_raw · suppressed · drop_alert. See column 4.7.
triage_decision
Higher-level pipeline path. investigate = ran the full LLM pipeline. triage_suppressed = pre-LLM dedup short-path. dismiss / escalate = LLM verdict (echoed). dismiss_shelved = Drain3 anomaly with no correlation, awaiting recurrence. timeout_passthrough = pipeline exceeded budget.
rca_quality
actionable (label: fits) · data_starved (label: thin) · needs_review (label: review). Post-hoc tag, classified by _classify_rca_quality in app/pipeline.py.
alert_source
grafana (POST to /webhook/grafana) or drain3 (POST to /webhook/drain3 from the Drain3 self-bridge).
severity
critical / warning / info. Comes from alert.severity or the LLM's overridden severity in the decision.
llm_verdict
ESCALATE · DISMISS · INCONCLUSIVE. Stored uppercase. Pipeline treats INCONCLUSIVE as ESCALATE downstream.
deployment_type
k8s (k3s pod) · docker-vm (Grafana / Loki / Jaeger on the monitoring VM via docker-compose) · systemd (host daemons like node-exporter on bare metal) · external (RDS, etc.) · unknown. Drives the architecture-mismatch validator and template selection.

Acronyms used in the UI and emails

RCA
Root-cause analysis — the LLM's narrative explaining why the alert fired.
MCP
Model Context Protocol — the contract by which the triage service queries Prometheus, Loki, Jaeger, Drain3, and rca-history. Each pillar runs as its own server (5 MCPs total, all containerized on the laptop).
p95 / p99
The 95th / 99th percentile of a latency distribution over a window. histogram_quantile(0.95, ...) in PromQL.
OTel / OTLP
OpenTelemetry / OTLP = the wire protocol it uses. Spring-boot ships traces via OTLP; otel-collector receives them and exports to Jaeger.
LogQL / PromQL
Loki's log query language / Prometheus' metric query language.
refId (A / B / C)
Grafana alert rules are 3-step pipelines: A=query, B=reduce, C=threshold-as-boolean. The observed value is the B step (the actual number); C is just a 0/1 indicator. The triage service picks B explicitly via pick_primary_value() (was a bug pre-2026-04-24 where the alphabetically-last refId was picked).
fingerprint
Stable hash Grafana computes over alert labels. Two webhooks with the same fingerprint represent the same logical alert (perhaps re-fired). Used by the dedup layer.
kill chain / cascade
A sequence of related alerts firing in close succession (e.g. disk-fills → DB-slow → connection-pool-exhaust → 503s). The correlated-alerts section is meant to surface this.
shelved
Drain3-specific verdict: anomaly was detected but no correlation with metric/trace data was found. The decision is logged with triage_decision=dismiss_shelved; if the same template recurs ≥3 times in 7 days, the LLM is told to escalate on pattern alone.
data_starved / thin
Quality tag indicating the LLM hedged because evidence was empty. Triggers a one-time bounded-agency retry: the LLM can request one additional MCP query from a whitelist (Prometheus, Loki, Jaeger, rca-history) before re-deciding.

7. Email layout

Escalation emails mirror the dashboard's structure but front-load the actionable bits. Layout:

  1. Hero strip — alert name + service + severity badge.
  2. Observed value card — the lede number with PromQL.
  3. Alert details — table of name/service/component/severity/instance/environment/fired-at/status. "Fired at" shows local time with the raw ISO in a smaller mute span.
  4. RCA verdict card — Decision · Confidence · Quality (humanized: "fits" / "thin" / "review"). Reason and full RCA narrative below. Suggested actions and evidence as bullet lists.
  5. Collected context — metrics preview · top log patterns (Drain3-ranked) · top traces by duration.
  6. Correlated alerts — same ±5 min table as the dashboard.
  7. Deep links — Grafana alerting list (other deep-links were removed because Grafana 13's URL format is unstable).
  8. History — recurrence count of this alert in the last 7 days.

Empty actions lists no longer print "Review the alert manually" (misleading post-philosophy-fix); they print "(no concrete remediation proposed — see RCA above; treat as a heads-up)". Empty evidence prints "(no specific evidence cited — RCA reasoned from the observed value alone)".

8. Reading common rows

Scenario A — clean ESCALATE on a Java service

Verdict: escalate. Quality: fits. Action: Notified. Confidence ≥0.7. Suggested actions list two or three kubectl set resources / kubectl rollout restart commands. Evidence cites a specific Loki line ("java.lang.OutOfMemoryError") and a metric value (0.984). The on-call has a clear next step; pipeline did its job.

Scenario B — DISMISS on a noisy threshold

Verdict: dismiss. Quality: fits. Action: Dismissed (no email). RCA explains the metric briefly crossed the threshold and immediately fell back. Suggested actions point at the alertrules YAML — raise the threshold or add a for: 2m clause. This is the LLM telling you the rule is too tight; tune it.

Scenario C — Drain3 anomaly, shelved

Source: drain3. Verdict: dismiss. Triage path: Shelved (raw: dismiss_shelved). Suggested actions contain one entry: "Shelved — no correlation between this log-template novelty and metric/trace anomalies in the same window…". RCA explains the new template that fired, what it might describe, and that no metric/trace correlation was found. No action this round; the system will escalate automatically if the same template recurs ≥3 times in 7 days.

Scenario D — Deduped row

Triage path: Deduped. Verdict: empty. Action: Suppressed. RCA empty; reasoning empty. The detail panel's "Action" line will say see_previous_rca:<prior_id>. Click that previous decision to see the full RCA — this row is just a marker that the same fingerprint refired inside the dedup window.

Scenario E — Timed out (Notified, no LLM)

Verdict: timeout. Action: Notified (no LLM). The pipeline exceeded its budget. No RCA, no suggested actions — the raw alert was forwarded. Investigate Ollama health if you see a cluster of these. On the us-west-2 GPU host, Ollama is a systemd service (not in compose) — check with sudo journalctl -u ollama -f over Tailscale SSH (or SSM as break-glass). Most common cause: GPU memory contention, Ollama-loading-a-cold- model latency, or the autoshutoff Lambda just brought the instance back from "stopped" (~90 s cold-start where SQS buffers webhooks — a single post-idle spike of "timeout" rows is normal). On the laptop fallback the Ollama container is reachable as docker logs ai-ollama.

Scenario F — thin RCA (data_starved)

Verdict: escalate. Quality: thin. RCA hedges because Loki had 0 lines or Jaeger was empty. The pipeline already retried once with bounded-agency (the LLM gets to request one more MCP query). If the row is still thin after that, it usually means the alert is for a service that doesn't log through the app pipeline (k3s-node, monitoring-vm, etc.) — expected.

When in doubt

The Action column tells you what the system did downstream; the Verdict + Quality tells you what the LLM thought; the Triage path in the detail panel tells you which pipeline branch the alert took. If those three disagree (e.g. verdict=escalate but action=Suppressed), the row is interesting — open it and read the reasoning.
