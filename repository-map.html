Repository map

The platform is split across seven Git repositories. This page is the canonical answer to "where does that piece of code live?" — for both the engineering team and anyone catching up on the project from the outside. Visibility, ownership, and the cross-repo dependency shape are all summarised below.

The seven repositories

monitoring-docs
Public Docs · the website

The pages you're reading right now. Architecture, decisions log, sprint history, solution brief, triage-service reference, system-explained — the operator-facing and reviewer-facing documentation surface of the entire platform. Served as a static site.

Contains: ~25 HTML pages, the FYP report (PDF + LaTeX), sprint3-plan.md, the-bigger-picture.md, decisions-log.html. Maintainer: Lina Laaraich.

monitoring-triage-service
Public AI · core

The FastAPI triage service itself — webhook receivers, 10-stage pipeline, LLM client, dedup + suppression, dashboard, SMTP escalation, the 14 exemplar archetypes, the validator stack, the bounded-agency retry layer. The production AI workload runs from this image.

Key paths: app/pipeline.py, app/llm_client.py, app/response_validator.py, app/clamp_actions.py, app/bounded_agency.py, app/exemplars/library.yaml, app/hallucination_blocklist.yaml, docs/happy-path-scenarios.md. Image: ghcr.io/linalaaraich/monitoring-triage-service:latest. Test suite: 333/333 green.

monitoring-mcp-servers
Public AI · bridges

The five MCP bridge servers — every datum the LLM sees passes through here. Each server is a small Python process exposing 3–4 tools over JSON-RPC, with a Prometheus-style /metrics endpoint for self-observability.

Bridges: prometheus-mcp:8091, loki-mcp:8092, jaeger-mcp:8093, rca-history-mcp:8094, deploy-events-mcp:8095. Invariant: the MCP-only data-access rule lives here in spirit — see hallucination-firewall.html § MCP-only invariant.

provisioning-monitoring-infra
Public Terraform · AWS

The Terraform state for the entire AWS estate. VPC, subnets, security groups, EC2 instances, RDS, S3 buckets, EIPs, IAM. Pinned Ubuntu AMI to remove silent drift. SG rules parameterised so terraform.tfvars is the only file an operator edits during day-to-day work.

Managed resources (us-east-1): observability-rca-monitoring (t3.large), observability-rca-k3s (t3.xlarge), observability-rca-mysql (RDS), Loki S3 bucket, Terraform state bucket. Managed resources (us-west-2, added 2026-05-21): observability-rca-gpu (g5.xlarge, A10G 24 GB, instance i-03aec662b1a47ad8f, EIP 52.27.21.89), Lambda triage-gateway-router + triage-idle-checker, API Gateway HTTP API, SQS triage-cold-start-queue, DynamoDB triage-gateway-state, EventBridge cron, VPC interface endpoints (EC2, SQS) + DynamoDB gateway endpoint. Account: 735115318342, regions: us-east-1 + us-west-2. Sub-tree at us-west-2/ holds the GPU + serverless gateway stack.

monitoring-project
Public Ansible · k3s · chaos

The operational side: Ansible roles for every observability component, playbooks for the monitoring stack, the k3s bootstrap for the application workload, the OTel Collector configuration, the Grafana alert-rule template (roles/grafana/templates/alertrules.yml.j2), and the chaos-injection test harness.

Key paths: roles/ (per-service Ansible roles), inventory/tailnet.yml, scripts/chaos/runner.py, scripts/chaos/lib/rca_scorer.py, scripts/chaos/tests/, manifests/node-exporter/daemonset.yaml. Default inventory: Tailscale tailnet (managed via MagicDNS).

monitoring-audit-results
Private Audits · daily

Private repository holding the daily static + live audit reports. The static audit checks code/doc drift against the latest published state; the live audit fires three synthetic webhooks at the triage service and grades the produced RCAs. Both push here on completion.

Cadence: static — manual via "run full audit" trigger phrase or ~/monitoring-audit-results/scripts/audit-static.sh; live — cron 0 12 * * * on claude-controller. Why private: contains raw RCA prose and operator notes that include working evidence (alert payloads, log excerpts) not intended for public publication.

jira
Public Planning · CSV

CSV exports of the SCRUM Jira project and the import scripts that fed them. Versioned alongside the code because the Jira UI is not always reachable and because the CSV format encodes the workflow (numeric Work Item IDs, Parent/Sub-task relationships, Sprint mapping).

Key files: Sprint3-additions.csv (the Sprint 3 import), SPRINT3-README.md (per-row Story Points + Due-date table since the importer drops those fields). Story IDs: SCRUM-### in Jira ↔ human codes (E3-01, S3-HF-04 …) preserved via the Summary prefix.

Local clones

On the development controller these live under /root/:

  • /root/monitoring-docs
  • /root/monitoring-triage-service
  • /root/monitoring-mcp-servers
  • /root/provisioning-monitoring-infra
  • /root/monitoring-project
  • /root/monitoring-audit-results (private clone)
  • /root/linalaaraich/jira

A one-liner that pulls all of them up to date:

for r in monitoring-triage-service monitoring-project monitoring-docs \
         monitoring-mcp-servers monitoring-audit-results provisioning-monitoring-infra; do
  git -C /root/$r pull --ff-only 2>&1 | head -1 | sed "s|^|$r: |"
done
