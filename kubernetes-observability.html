☸️ Kubernetes Observability & Self-Monitoring

SHIPPED 2026-06-04 k3s as metrics datasource

The cluster now reports its own health — metrics, logs, and traces

The application workload (employees-backend / Spring Boot, MySQL, the Kong API gateway, the in-cluster OTel Collector) runs on a single-node k3s cluster. Logs (OTel filelog → Loki) and distributed traces (OTel → Jaeger) already flowed out of that cluster. The missing leg was metrics: Prometheus was supposed to scrape the kubelet/cAdvisor and per-pod actuator targets, but on the new AWS account the service-discovery credentials were never provisioned, so it discovered zero pod targets and there was no up series for any in-cluster service. The platform was effectively blind to its own apps' health.

This session closed that gap. Kubernetes is now a first-class metrics datasource, completing the metrics + logs + traces triad for the cluster, and a single generic alert gives liveness coverage for every service.

Metrics (newly restored)

  • kubelet + cAdvisor per-pod metrics
  • pod actuator targets via prometheus-scraper SA through the k3s API proxy
  • kube-state-metrics: deployment / replica / pod-phase / restart-count

Logs (already live)

  • OTel Collector DaemonSet, filelog receiver
  • pod + Kong logs (with trace_id) → Loki

Traces (already live)

  • OTel Java Agent → OTel Collector :4317
  • Kong OTel plugin → OTel Collector :4318
  • OTel Collector → Jaeger

What shipped (2026-06-04)

1. k3s restored as a metrics datasource commit bfa4b0b

Two IaC bugs made the k8s scrape path unable to work at all, plus one piece of state that was never applied to the new account:

  • Provisioned the prometheus-scraper ServiceAccount + long-lived token. The repo declared the service-discovery jobs, but k8s-manifests.yml --tags prometheus had never been run on the new account, so the SA, the token Secret, and the /etc/prometheus/{k3s-token,k3s-ca.crt} files on the monitoring VM did not exist. Prometheus dropped both the k3s-kubelet-cadvisor and kubernetes-pods scrape pools silently → zero targets.
  • Fixed the ClusterRole RBAC — added pods/proxy. The kubernetes-pods job scrapes pods through the k3s API-server proxy, which requires get on pods/proxy. Without it every pod scrape returned 403 Forbidden (up=0).
  • Fixed the token file permissions — 0644, not 0600/root. The playbook shipped the SA token as mode 0600 owned by root, but Prometheus runs as a non-root user inside its container → "unable to read authorization credentials" → kubelet/cAdvisor + pod scrapes failed.

Result, verified live on account 321556173045: k3s-kubelet-cadvisor is up; kubernetes-pods discovers and scrapes employees-backend (Spring Boot), Kong, and the in-cluster OTel Collector → up=1. up==0 is now a real liveness signal these targets were previously invisible to.

2. kube-state-metrics deployed previously absent

kube-state-metrics (KSM) — the standard exporter of the cluster's own object state — did not exist anywhere in the repo or the cluster before this session. A new annotation-discovered manifest (manifests/kube-state-metrics/, KSM v2.x, SA bound to a read-only ClusterRole over deployments/pods/replicasets/nodes, pod annotated prometheus.io/scrape=true prometheus.io/port=8080) is now deployed and picked up by the existing kubernetes-pods SD job with no prometheus.yml change. This unlocks deployment-readiness, pod-phase, and restart-count metrics — and the strongest k8s liveness alerts.

Production portability: KSM is shipped as a raw open-source manifest (no AWS coupling), matching the platform's annotation-driven discovery and the CIRES private-cloud production target.

3. Generic KubeWorkloadDown alert routed to triage self-monitoring

One KSM-driven rule gives liveness coverage for any service, with no per-service rules to maintain:

expr: max by (exported_namespace, deployment) (
        kube_deployment_status_replicas_unavailable{exported_namespace!="kube-system"}
      ) > 0
for:  3m

When any deployment has unavailable replica(s) for 3 minutes, the alert fires with exported_namespace + deployment labels identifying which one, and routes to the triage webhook for AI root-cause analysis. No more "the platform is blind to its own apps' health" — scale a deployment to zero and a triage alert follows. (Source: roles/grafana/templates/alertrules.yml.j2.)

What shipped (2026-06-10) — demo-app metrics + crash-loop coverage

1. otel-demo OTLP metrics wired into Prometheus commit e8fffd3

The in-cluster OTel Collector had only traces + logs pipelines, so the 22 Astronomy Shop services' OTLP metrics hit :4318 and were silently discarded — the Sprint-5 bed was 2/3-signal, Prometheus had zero demo app metrics, and a behavioral flagd fault could never fire a metric alert (2026-06-09 audit O-2, P1). The fix adds a metrics pipeline terminating in a prometheus pull exporter on :8889, plus a dedicated otel-demo-app-metrics scrape job routed through the same k3s API-server pod proxy as every other in-cluster scrape (section A below).

  • Why pull, not prometheusremotewrite: the monitoring-VM Prometheus runs without --web.enable-remote-write-receiver, and flipping that flag means recreating the container (stack restart). A pull target also stays auditable as up{job="otel-demo-app-metrics"}.
  • Label semantics: the exporter mints job=<service.name> / instance=<service.instance.id> per the OTLP→Prometheus compat spec; the scrape job sets honor_labels: true so they survive relabeling. So demo metrics are queried as {job="checkout"}, {job="frontend"}, … — only the scrape meta-metrics (up, scrape_*) carry job="otel-demo-app-metrics". Don't be fooled by the meta-job looking "empty".
  • Cardinality, measured not guessed: head series 28,147 → ~32.6k after first scrapes (~3.5k samples/scrape across all services) on the t3.large. No keep-list filter applied, deliberately — full RED + runtime metrics are worth more for RCA than the ~4.5k saved series. Revisit with a filter/keep processor if prometheus_tsdb_head_series approaches ~150k.

Verified live: 16+ demo services report series (checkout has 411 duration/request series; frontend shows the load-generator's ~0.9 req/s via rate(http_server_duration_milliseconds_count[5m])).

2. PodCrashLooping — the fast-loop blind spot closed commit c6dbf81

The accounting pod (otel-demo) OOMKilled every ~17–19 min for days (exit 137, 120Mi limit, 420+ restarts) with zero alerts: each crash self-healed in seconds, so KubeWorkloadDown's for: 3m gate never saw 3 continuous minutes of unavailability, and the pod-resource rules are hard-scoped to the app|rental namespaces. The new rule keys on the restart rate itself, which a crash loop cannot hide:

expr: max by (namespace, pod, service) (label_replace(… 3× …,
        increase(kube_pod_container_status_restarts_total{exported_namespace!="kube-system"}[1h])
      )) > 1
for:  5m        # noDataState: OK
  • Window sizing: [1h] so even a slow-burn loop (~3 restarts/h) trips it; for: 5m rides out a single legitimate restart spike. Trade-off documented in the template: after the loop is fixed, the alert takes up to the [1h] tail to clear (or clears via staleness when the pod is replaced).
  • Label surgery: same exported_* → real-name label_replace trick as KubeWorkloadDown (section D below) — KSM's labels arrive prefixed because the scrape goes through the API-server proxy with honor_labels off for KSM; the rule re-mints namespace/pod/service so triage gets a real affected service.
  • Proven on a live breach, not a unit test: the rule was hot-reloaded while the real accounting OOM loop was running → fired → flowed Grafana → API GW → triage (decision 29a05711, affected_service=accounting). Only then was the workload fixed (limit 120Mi → 256Mi, commit 4c1cc5b — upstream flink default is known-hungry) and the pod went Running 0 restarts.

3. First fireable latency SLO + honest dormant rules same commit

HighDemoFrontendP95Latency (histogram_quantile(0.95, …http_server_duration_milliseconds_bucket{job="frontend"}…) > 1000ms, for: 2m) rides the new demo metrics + the load-generator's 24/7 traffic — the first latency rule on this bed with a real signal behind it, and the one a behavioral flagd fault (e.g. adHighCpu) can actually trip. HighP95Latency (spring-boot sees only excluded /actuator probe traffic) and HighKongP95Latency (the demo bypasses Kong via its own frontend-proxy) are kept deliberately — they're production-relevant on the CIRES private cloud where real traffic exists — but are now explicitly marked DORMANT ON THE PoC BED in the template with noDataState: OK, so they sit inactive/health=ok instead of erroring or false-alerting. Do not "fix" them by setting noDataState: Alerting.

Deep dive — the mechanism, key by key

The summary above is the what. The rest of this page is the why and the exactly how, written so you can point an external Prometheus at any k3s/k8s cluster and add self-monitoring to any workload without re-deriving it. Every claim here is grounded in the live files cited.

A. The scrape topology: an off-cluster Prometheus reaching pods through the API server

The non-obvious design choice that everything else follows from: Prometheus does not live in the cluster. It runs as a Docker container on the monitoring VM, outside k3s, with no route to the pod network (k3s pod CIDR is not reachable from the VM's VPC subnet). So Prometheus cannot connect to a pod IP directly. Instead, every pod scrape is proxied through the kube-apiserver:

Prometheus (monitoring VM, non-root container)
   │  HTTPS + bearer token, TCP :6443 only
   ▼
kube-apiserver  (k3s node)
   │  /api/v1/namespaces/<ns>/pods/<pod>:<port>/proxy/<metrics-path>
   ▼
pod  (employees-backend :8080/actuator/prometheus, kong, otel-collector, KSM)
Why this matters for reproducing it: the only network reachability you need from the Prometheus host to the cluster is TCP :6443 (the API server). No pod-network peering, no VPN into the CNI, no NodePort-per-pod. The monitoring VM's security group opens 6443 to the monitoring SG by design for exactly this. If you are putting an external Prometheus on a cluster you don't control the CNI of, this proxy pattern is the path of least resistance.

The relabel chain that makes the proxy work (the load-bearing config)

Source: roles/prometheus/templates/prometheus.yml.j2, job kubernetes-pods, gated by k3s_sd_enabled. The kubernetes_sd_configs: role: pod block discovers every pod via the API server; the relabel_configs then do four critical rewrites. Read these in order — each line is doing real work:

Relabel stepWhat it does & why
keep on __meta_kubernetes_pod_annotation_prometheus_io_scrape == "true"Opt-in discovery. A pod is scraped only if it carries prometheus.io/scrape: "true". This is why adding a new scrape target later needs no prometheus.yml change — you annotate the pod and SD finds it.
drop on __meta_kubernetes_pod_phase =~ Pending|Succeeded|Failed|UnknownDon't try to scrape pods that aren't Running — avoids noisy up=0 on transient/terminal pods.
Rewrite __metrics_path__ to /api/v1/namespaces/$1/pods/$2:$3/proxy$4 from (namespace; pod_name; io_port; io_path)This is the whole trick. Instead of scraping pod-ip:port/path, the metrics path is rewritten to the API-server proxy URL for that pod. The port and path come from the pod's own prometheus.io/port + prometheus.io/path annotations.
Rewrite __address__ to {{ k3s_host_ip }}:6443Every target's network address is forced to the API server. Combined with the path rewrite, the actual HTTP request Prometheus makes is https://<k3s>:6443/api/v1/namespaces/ns/pods/pod:8080/proxy/actuator/prometheus.
labelmap __meta_kubernetes_pod_label_(.+) + explicit namespace/pod/container targetsPromotes pod labels to metric labels so the series are queryable by workload. Gotcha: this also writes a namespace label on every series — remember this for section D, it's the cause of the exported_namespace clobber.

The two TLS files and why insecure_skip_verify: true is set

Both the proxy job and the k3s-kubelet-cadvisor job authenticate to the API server / kubelet with:

  • bearer_token_file: /etc/prometheus/k3s-token — the prometheus-scraper ServiceAccount token.
  • ca_file: /etc/prometheus/k3s-ca.crt — the cluster CA, so Prometheus trusts the API server cert.
  • insecure_skip_verify: true — set because the k3s API server cert's SANs don't include the MagicDNS / tailnet name the monitoring VM dials it by (tracked follow-up in commit bfa4b0b: "k3s API cert lacks a tailnet tls-san"). All traffic is already inside the Tailscale tunnel, so skipping hostname verification is an acceptable PoC posture; the production-correct fix is to add the tailnet name as a --tls-san on the k3s server and drop the skip.

B. The ServiceAccount + long-lived token (the k8s ≥1.24 quirk)

Source: manifests/prometheus-rbac/rbac.yaml (SA + ClusterRole + binding) and playbooks/k8s-manifests.yml (mints the token, ships it). The audit's root cause of the whole outage was that this playbook had never been run on the new account — the SD job definitions were in prometheus.yml, but the token + CA files they reference did not exist on disk, so Prometheus logged unable to read CA cert: open /etc/prometheus/k3s-ca.crt: no such file or directory and silently dropped both scrape pools (0 active, 0 dropped targets — not even a failed scrape).

The k8s ≥1.24 token gotcha (reproduce-anywhere): since Kubernetes 1.24, creating a ServiceAccount no longer auto-creates a Secret with a token. kubectl create token gives a short-lived token (expires, useless for a long-running scraper). To get a stable, long-lived token you must create a Secret of type kubernetes.io/service-account-token annotated kubernetes.io/service-account.name: prometheus-scraper; the token controller then populates its .data.token + .data["ca.crt"]. The playbook waits/retries for that field to be non-empty before decoding it. Pre-check before trusting it: kubectl get secret prometheus-scraper-token -n observability -o jsonpath='{.data.token}' must be non-empty.

Why the ClusterRole needs pods/proxy specifically

The ClusterRole grants get,list,watch on nodes, nodes/proxy, nodes/metrics, pods, services, endpoints — and (the fix in bfa4b0b) pods/proxy. The distinction is exact and easy to miss:

  • pods (get/list/watch) lets the SA discover pods — that's what makes SD find targets at all.
  • pods/proxy (get) lets the SA route an HTTP request through the API server to a pod — which is precisely what the __metrics_path__/__address__ rewrite in section A does. Without it, discovery succeeds (targets appear) but every scrape returns 403 Forbidden → up=0. A confusing failure mode: the target shows up but is permanently "down".
Apply to another cluster: any time you scrape pods through the API-server proxy (rather than reaching pod IPs directly), the scraping identity needs pods/proxy. If you scrape pod IPs directly (Prometheus inside the cluster), you do not need it — pods alone suffices. The grant follows the network path.

Why the token file must be 0644 (not 0600)

The playbook ships /etc/prometheus/k3s-token + k3s-ca.crt as root:root. Originally mode 0600. But Prometheus runs as a non-root user inside its container and bind-mounts /etc/prometheus read-only. A 0600 file owned by host-root is unreadable by the in-container non-root UID → Prometheus logs unable to read authorization credentials → kubelet/cAdvisor + pod scrapes fail. Changing the mode to 0644 makes the file world-readable so the container UID can read the bearer token.

The security reasoning (so you can judge it for your own deploy): 0644 means any local user on the monitoring VM can read the bearer token. That is acceptable here because (a) the directory is host-root, (b) the VM is single-tenant, and (c) all API-server traffic is inside the Tailscale tunnel. On a multi-tenant host, the correct fix is to run the Prometheus container with a user: matching the file owner (or a shared group + 0640), not to widen the file. The general lesson: file perms for bind-mounted secrets must match the in-container UID, not the host's intuition.

C. kube-state-metrics — what it is and why it's a separate exporter

Source: manifests/kube-state-metrics/kube-state-metrics.yaml (KSM v2.13.0). Two different metric sources are easy to conflate:

SourceAnswersExamples
kubelet / cAdvisor"how much is each running container using?"container_cpu_usage_seconds_total, container_memory_working_set_bytes
kube-state-metrics"what is the cluster's object state — what should exist vs what does?"kube_deployment_status_replicas_unavailable, kube_pod_status_phase, kube_pod_container_status_restarts_total

KSM watches the API server and turns the state of Deployments/Pods/ReplicaSets/Nodes/etc. into gauges. It is the only source that can answer "is a workload supposed to have replicas it doesn't have" — i.e. the liveness signal. It was entirely absent on the new account (no role, chart, or manifest anywhere), which is why there was no "is anything down" signal at all.

Design choices in the manifest worth copying:

  • Annotation-discovered, not a new scrape job. The Deployment's pod template carries prometheus.io/scrape: "true", prometheus.io/port: "8080", prometheus.io/path: "/metrics" — so the existing kubernetes-pods SD job picks it up with zero prometheus.yml changes. This is the same opt-in pattern from section A working for you.
  • Read-only ClusterRole (list/watch only, no write verbs) over the full object catalogue KSM v2 needs (configmaps, secrets metadata, nodes, pods, deployments, replicasets, jobs, HPAs, PDBs, ingresses, leases, …).
  • Locked-down securityContext: runAsNonRoot, UID 65534 (nobody), readOnlyRootFilesystem, drop: [ALL] capabilities — KSM only reads the API, so it needs no privileges.
  • Raw open-source manifest, no AWS coupling — image registry.k8s.io/kube-state-metrics:v2.13.0 — matching the platform's private-cloud production target.
Apply to another cluster: deploy KSM once and annotate its pod for whatever discovery your Prometheus uses (annotation-based here; a ServiceMonitor if you run the Prometheus Operator). Every kube_* metric then exists fleet-wide. KSM is cluster-scoped, so one deployment covers all namespaces.

D. The generic KubeWorkloadDown alert — the label surgery explained

Source: roles/grafana/templates/alertrules.yml.j2. The full query in the rule is:

max by (namespace, service) (
  label_replace(
    label_replace(
      kube_deployment_status_replicas_unavailable{exported_namespace!="kube-system"},
      "namespace", "$1", "exported_namespace", "(.+)"
    ),
    "service", "$1", "deployment", "(.+)"
  )
) > 0
for: 3m

Why ONE generic rule beats per-service rules

The expression is over all deployments. Any deployment in any namespace (except kube-system) with an unavailable replica for 3 minutes fires. That means liveness coverage is automatic for every workload, present and future — deploy a new service tomorrow and it is covered the moment KSM sees its Deployment, with no rule to write. The alternative — an EmployeesBackendDown, a KongDown, etc. — is N rules to author, label-select correctly, and keep in sync as services come and go. One generic rule is strictly less to maintain and has no coverage gaps.

Why exported_namespace, not namespace (the label clobber)

This is the subtlest part. Recall from section A that the kubernetes-pods SD job writes a namespace label on every series it scrapes — set to the namespace of the pod being scraped, which for KSM is observability (where KSM runs). But KSM's own metrics already carry a namespace label naming the namespace of the object they describe (e.g. app for employees-backend). Prometheus cannot have two labels of the same name, so on collision it keeps the scrape-applied one and renames the metric's original to exported_namespace (Prometheus's standard honor_labels: false behaviour). Net result:

  • namespace = observability (where KSM's pod runs) — useless for naming the down workload.
  • exported_namespace = app (the real namespace of the broken deployment) — what you actually want.

So the filter and the label minting both key off exported_namespace. If you wrote namespace!="kube-system" you'd be filtering the wrong label and every KSM series would look like it lives in observability.

Reproduce-anywhere rule of thumb: whenever you scrape an exporter through pod-annotation discovery and that exporter emits its own namespace/pod/job labels, expect the scrape to clobber them into exported_*. Either query the exported_* labels (as here) or set honor_labels: true on that scrape job to keep the exporter's labels authoritative. For KSM specifically, honoring labels is the common alternative; this platform chose the exported_* path to avoid touching the shared SD job.

Why label_replace and not Grafana label templating

The alert needs the down workload's real service + namespace as alert labels, because the triage pipeline reads affected_service off the alert labels (without it, triage sees service=unknown). The instinct is to set them in the rule's labels: block with templating like service: "{{ $labels.deployment }}". That does not work in Grafana. Grafana evaluates Go templating in a rule's annotations: block but not in its labels: block — labels must be literal or come from the query result. So the two real labels have to be minted inside the PromQL:

  • The first label_replace(..., "namespace", "$1", "exported_namespace", "(.+)") copies exported_namespace into a clean namespace label.
  • The second label_replace(..., "service", "$1", "deployment", "(.+)") copies KSM's deployment label into a service label (the name the rest of the platform routes on).
  • max by (namespace, service) then reduces to one series per workload carrying exactly those two labels. Grafana carries query-result labels onto the firing alert, so they land as real alert labels.
Gotcha to internalise: "set it as an alert label via templating" is a reflex that silently fails in Grafana-managed alerting. If a label must be dynamic, it must be a label on the query result — i.e. label_replace/label_join in the expression, not templating in the labels: block. Annotations (the human-readable summary/description) can template, and this rule does: the summary uses {{ $labels.namespace }}/{{ $labels.service }}.

noDataState: Alerting as a watchdog

Most threshold rules on this platform use noDataState: OK (a CPU rule shouldn't page just because a node briefly stopped reporting). KubeWorkloadDown deliberately uses noDataState: Alerting: if KSM itself disappears (crashes, gets deleted, SD breaks), the query returns no data — and for a liveness watchdog, "no data" should mean "alert", not "all clear". This closes the structural blind spot the audit found in the old up == 0 rule, which could never fire for a target that was never discovered (empty vector → NoData → OK → silence). The general principle: liveness/absence rules want noDataState: Alerting; noisy threshold rules want OK. Choose per-rule, never uniformly.

E. Real-induction verification — and the trick to make a deployment genuinely unavailable

Per the real-induction-only invariant, the alert was verified by inducing a genuine breach, not by POSTing a synthetic webhook. There is a sharp gotcha here worth its own callout:

kubectl scale deploy/X --replicas=0 will NOT fire this alert. The metric is kube_deployment_status_replicas_unavailable = desired − available. Scaling to 0 sets desired = 0, so unavailable = 0 — the deployment is intentionally empty, not "down". To make a deployment genuinely unavailable (desired ≥ 1 but available = 0) you must keep the desired count up while preventing the pod from becoming ready. Two reliable ways:
# Trick: force the pods unschedulable while desired stays = 1, using
# strategy Recreate (so the old ready pod is torn down first) + a
# nodeSelector no node satisfies. desired=1, available=0 -> unavailable=1.
kubectl -n app patch deploy/employees-backend --type merge -p '{
  "spec": {
    "strategy": {"type": "Recreate"},
    "template": {"spec": {"nodeSelector": {"cires/induce-down": "nowhere"}}}
  }
}'
# wait > 3m, observe KubeWorkloadDown fire with labels
#   service=employees-backend namespace=app, then a triage rca_history row.

# Revert (remove the impossible nodeSelector):
kubectl -n app patch deploy/employees-backend --type json \
  -p '[{"op":"remove","path":"/spec/template/spec/nodeSelector/cires~1induce-down"}]'

(An alternative real induction is to point the deployment at a non-existent image tag — ImagePullBackOff also yields available=0 with desired≥1.) The KSM commit (da8b9d6) verified exactly this end to end: the workload was made unavailable → KubeWorkloadDown fired → API Gateway → a triage rca_history row appeared (silent before the fix) with labels confirmed service=spring-boot, namespace=app → app reverted and healthy.

F. Reproduce-elsewhere checklist — point an external Prometheus at any k3s cluster

  1. Network: open TCP :6443 from the Prometheus host to the API server. That's the only reachability you need (proxy pattern).
  2. Identity: create a prometheus-scraper SA + a read-only ClusterRole with get,list,watch on pods/nodes/services/endpoints/nodes/proxy/nodes/metrics and get on pods/proxy. Bind it.
  3. Long-lived token (k8s ≥1.24): create a kubernetes.io/service-account-token Secret annotated with the SA name; wait for .data.token to populate; decode token + ca.crt.
  4. Ship the files to the Prometheus host as mode that the in-container UID can read (0644 here, or match the container user:).
  5. Configure two jobs: a kubelet/cAdvisor static job (:10250/metrics/cadvisor, https + bearer + CA) and a kubernetes_sd_configs: role: pod job with the four relabel rewrites (keep-on-annotation, drop non-Running, rewrite __metrics_path__ to the proxy URL, force __address__ to <api>:6443).
  6. Annotate workloads you want scraped with prometheus.io/scrape|port|path. Done — they appear with no config change.
  7. Deploy KSM (annotated) for object-state metrics, then add the generic KubeWorkloadDown rule (mind the exported_namespace clobber + label_replace + noDataState: Alerting).
  8. Harden: add a loud guard that fails the playbook if the token/CA files are absent when SD is enabled (so this drift can never be silent again), and add the tailnet name as a k3s --tls-san to drop insecure_skip_verify.
