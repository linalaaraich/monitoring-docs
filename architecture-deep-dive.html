1. The big picture

The platform answers one question that traditional monitoring never quite does: when an alert fires, what is the actual root cause, and is it worth waking someone for? A Prometheus rule can tell you CPU is at 94% — it cannot tell you why, and it cannot tell you that this particular spike is the third identical flap in ten minutes and not worth a page. The platform layers an AI reasoning stage on top of conventional observability to produce a named root cause with supporting evidence, while a thick stack of deterministic gates keeps the expensive AI from ever seeing noise.

1.1 Three layers on an observability socle

Conceptually the system is three layers sitting on a shared telemetry foundation (the "socle"). Each layer has a different job and a different failure mode it guards against.

LayerJobBuilt from
SocleCollect every metric, log, and trace through a single agentOpenTelemetry Collector → Prometheus / Loki / Jaeger
Layer 1 — Detection detectNotice that something is wrong, by threshold and by noveltyGrafana alert rules + Drain3 3-tier log-novelty
Layer 2 — Triage filterDeduplicate, suppress, gather correlated evidence, decide what reaches the GPUThe triage pipeline (pipeline.py) + 6 MCP bridges
Layer 3 — AI-RCA explainRead the correlated picture and narrate a grounded root causeLocal LLM (qwen2.5:14b) + response validator + exemplars
Why this design — a layered funnel
Each layer is cheaper and more numerous than the one above it. Thousands of raw samples become a handful of alerts (Layer 1); most alerts are deduplicated or suppressed by deterministic code before any AI runs (Layer 2); only the survivors — genuinely novel, un-suppressed incidents — reach the GPU (Layer 3). The expensive, fallible component (the LLM) sits at the narrow end of the funnel and only ever narrates a picture that deterministic code has already assembled and verified. This is the recurring through-line of the whole platform: deterministic-first, AI-last.

2. The observability foundation (the socle)

Before any AI can reason about a fault, the fault has to be visible in telemetry. The socle is the three-pillar collection layer — metrics, logs, traces — fed by a single agent.

2.1 Why OpenTelemetry as the single agent

Why this design — one agent, three signals
The platform standardises on a single OpenTelemetry Collector rather than one exporter per backend (Promtail for logs, a tracing agent, node-exporter sidecars, etc.). One agent means one thing to deploy, one place where service.name and Kubernetes attributes are stamped, and — critically — a vendor-neutral seam. The collector's pipelines fan out to Jaeger, Loki, and Prometheus today, but swapping any backend is a config edit, not a re-instrumentation. This directly serves the production story: CIRES's NOC runs Zabbix for metrics and is wary of per-host exporters, so a single OTel host-agent that can later feed Zabbix is the future pitch, not Prometheus-forever.

The collector runs as a DaemonSet in the observability namespace (otel/opentelemetry-collector-contrib:0.120.0) on every k3s node, plus a VM-mode collector for the monitoring host. It listens on OTLP gRPC :4317 and HTTP :4318, exposes a Prometheus pull exporter on :8889, and runs three pipelines (manifests/otel-collector/configmap.yaml:194-207):

  • traces: OTLP in → k8sattributes, resource, batch → otlp/traces to Jaeger at ${MONITORING_VM_IP}:4317.
  • logs: filelog (tails /var/log/pods) + OTLP → k8sattributes, resource, transform/service_name, loki-labels, batch → Loki push at :3100/loki/api/v1/push.
  • metrics: OTLP in → k8sattributes, resource, batch → Prometheus pull exporter on 0.0.0.0:8889 (shipped O-2, 2026-06-10).

2.2 Prometheus scrape topology

Prometheus (15s scrape, 15d retention) pulls from three distinct layers. The non-obvious one is how it reaches pods inside k3s without pod-network reachability.

  1. Static monitoring-VM targets — cAdvisor :8081, node-exporter :9100, Prometheus :9090, Grafana :3000, Loki :3100, Jaeger :14269, the collector :8888.
  2. GPU self-monitoring over the tailnet (100.114.76.43, no security-group change) — ai-triage-service :8090 (which aggregates triage_*, ollama_*, drain3_*, triage_mcp_*), GPU node-exporter :9100, DCGM exporter :9400.
  3. k3s discovery (prometheus.yml.j2:32-147) — the interesting layer, below.

cAdvisor vs. kube-state-metrics — two different questions

These are frequently confused. They answer different questions and both are needed:

  • cAdvisor (scraped from the kubelet at {k3s_host_ip}:10250/metrics/cadvisor, https + bearer token) gives per-container resource usage — container_memory_working_set_bytes, CPU, etc. This is what the PodHighMemoryUsage / PodHighCpuUsage rules read. It answers "how much is this container using?"
  • kube-state-metrics (KSM) (discovered via the prometheus.io/scrape annotation) gives object-state — kube_deployment_status_replicas_unavailable, kube_pod_container_status_restarts_total, kube_replicaset_created. This is what the KubeWorkloadDown / PodCrashLooping rules read, and what the deploy bridge mines for rollout events. It answers "what does Kubernetes think the desired vs. actual state is?"

The k3s API-server proxy trick

Note — scraping pods without pod-network access
The kubernetes-pods and otel-demo-app-metrics jobs use kubernetes_sd_configs role:pod but rewrite __metrics_path__ to /api/v1/namespaces/<ns>/pods/<pod>:<port>/proxy<path> and set __address__ to {k3s_host_ip}:6443 — i.e. every pod scrape is proxied through the k3s API server. The monitoring VM only needs TCP :6443 to the k3s node; it never needs to route into the pod network. The in-cluster collector's :8889 exporter (carrying the otel-demo metrics) is scraped this way with honor_labels: true so each demo service surfaces as its own job=<service.name>.

2.3 Loki

Loki receives logs pushed by the collector's logs pipeline. The crucial concept is the stream label. The collector's transform/service_name processor sets service_name = k8s_container_name (special-casing Kong to service_name="kong" for namespace="network",container="proxy"), and attributes/loki-labels promotes service_name / namespace / pod into Loki stream labels (configmap.yaml:112-134). That is why the triage service can query {service_name="<service>"} to pull exactly the logs for the alerting service. The loki-mcp bridge hard-caps any query at 50 lines.

2.4 Jaeger and the service-naming problem

Jaeger stores the traces the collector forwards. The subtle, real-world wrinkle here is that the same logical service can carry different names across the three pillars, because OTEL_SERVICE_NAME and the k8s container label don't always agree. The employees app appears as both employees-backend and spring-boot; Kong as kong and kong-gateway. This dual-identity (tracked as design-debt G6) is deliberately not aliased away in the collector.

Where the naming is reconciled
Rather than rewrite telemetry, the triage service maps alert-label service names to the canonical name Jaeger indexes at query time: trace_service_name (v2_mappings.py:256-259) turns spring-boot → employees-backend and kong → kong-gateway so Jaeger deep links and trace queries hit a service that actually exists. The operator-facing display name (employee-spring-backend) is a third, display-only rendering (DISPLAY_SERVICE). Three name spaces, reconciled at the edges — the underlying streams keep their original tokens.

2.5 The otel-demo microservice bed

A single service is a poor test bed for an AIOps platform — real incidents are about cascades across services. The platform deploys the OpenTelemetry Demo (the "Astronomy Shop", Helm chart 0.40.9) in the otel-demo namespace as a 22-service distributed application. Every bundled backend (its own collector, Jaeger, Prometheus, Grafana, OpenSearch) is disabled — all components point at the platform's collector FQDN (otel-collector.observability.svc.cluster.local), so the demo drives real traces, logs, and metrics through the one production pipeline. It is the bed for 3-tier Drain3, for real-induction testing (via flagd fault injection), and for the downstream-latency exemplars.

3. Layer 1 — Detection detect

Detection has two complementary engines. Grafana alert rules catch the known-bad — thresholds someone thought to encode. Drain3 catches the never-before-seen — log shapes no rule anticipated. You need both: a threshold rule cannot fire on a brand-new exception type, and a novelty detector cannot tell you CPU crossed 95%.

3.1 Grafana alert rule families

Rules are Grafana-provisioned unified alerting, generated from roles/grafana/templates/alertrules.yml.j2. They fall into five families:

Several latency rules are deliberately dormant on the PoC bed because the synthetic load only hits /actuator (stripped, so the refId is empty → NoData → OK); they are prod-relevant and kept warm. The resource rules are currently static thresholds, a temporary regression from the adaptive (or vector()) version that hit a label-loss bug on 2026-06-02. Only MediumCpuUsage carries a live recurrence-gate annotation (pre_llm=4,llm_dismiss=10,window=2h).

3.2 Drain3 — 3-tier log-novelty detection

Drain3 is an online log-template miner. It reads a stream of log lines and groups them into templates (e.g. "User <*> logged in from <*>"). The platform runs one miner per service (drain_analyzer.py:269-282), each persisted to {service}.bin, so spring-boot templates never blend with Kong or frontend ones and every service is judged against its own history.

A line is flagged anomalous when its template is brand new (cluster_created / cluster_template_changed) or rare (match_count < threshold) — drain_analyzer.py:330,339.

Why this design — novelty ≠ volume
The signal is a new or rare log shape, regardless of how many lines are flowing. A million identical "request served 200 OK" lines is not anomalous; a single never-seen NullPointerException stack frame is. This is exactly the failure mode threshold rules miss — you cannot write a Prometheus rule for an exception that hasn't been invented yet. Drain3 surfaces emergent failure modes, then self-fires a synthetic Drain3AnomalyDetected webhook into the same triage pipeline as any Grafana alert.

The three tiers: component → application → system

Each batch of logs is evaluated independently at three scopes (drain_analyzer.py:632-698), with broader scope = lower bar because a novelty visible across a whole application is more significant than one in a single component:

TierScopeThresholdCatches
componentone service0.25a single service emitting a novel template
applicationall services in a k8s namespace (so otel-demo aggregates)0.15novelty spread across an app's services — a cascade
systemeverything0.10platform-wide novelty

A double-fire guard skips an application tier whose only component already fired at the component tier (a pure duplicate); multi-component apps still fire both. Each tier is rate-capped per batch and has its own cooldown, so a noisy component never starves a system-level alert. Two boundary filters keep the miners honest: source exclusion (observability/infra services and *-exporter never enter a miner — pure string logic, no data reads, preserving the MCP-only invariant) and an empty-body guard (blank/empty-body OTel envelopes were minting a fake "novel template" every batch; now dropped from both numerator and denominator).

4. Layer 2 — The triage pipeline filter

This is the heart of the platform: app/pipeline.py, an ordered async lifecycle that takes a webhook and produces (eventually) a persisted decision. Most alerts exit early through a cheap path; a minority run the full gather-and-narrate sequence. The ordering is load-bearing — the cheap gates run before any GPU work, and the fail-safe gates (MCP-outage) run before the quiet-suppression gates so an outage is never mistaken for "nothing's wrong".

4.1 The full ordered lifecycle

Entry is process_grafana_webhook (pipeline.py:237) or process_drain3_webhook (:249, which synthesizes a tier-aware GrafanaAlert from Drain3 anomaly data and content-hashes a fingerprint). Both call _process_alert (:396) per alert. The ordered stages:

webhook │ ▼ _process_alert (pipeline.py:396) ┌─────────────────────────────────────────────────────────────────────────┐ │ STAGE 1 Dedup / fingerprint window (:405) ── dup → record │ cheap │ family_dedup_key + dedup.check recurrence, NO new row │ path │ STAGE 1b Layer-2 pre-LLM suppression (:456) ── recent DISMISS for │ exits │ same (alert,service) within 10m (alert,svc) → replay │ here │ STAGE 1c Recurrence gate (pre-LLM) (:485) ── under fire thresh │ (no │ → cheap gated row │ GPU) ├─────────────────────────────────────────────────────────────────────────┤ │ (pipeline timeout wrapper, 300s → _investigate_and_act :589) │ │ STAGE 3 Context gather ctx=context.gather(alert) (:710) │ │ 3 parallel MCP (prom/loki/jaeger) + deep-trace + deploy bridge │ │ STAGE 4 Drain3 annotate lines (:712) │ │ STAGE 5 History + correlation (±5min), quote prior data_starved (:745) │ │ STAGE 6 Metric interpreter + behavioral baseline (:797) │ │ DA-3 prior-decision (30m) + Phase-6 operator feedback (14d) │ │ STAGE 5.9 MCP-outage fail-OPEN (:892) ── all pillars errored → │ fail │ escalate raw, NOT suppress │ safe │ STAGE 6.0 Data-starved early-exit (:953) ── all signals empty → quiet │ cheap │ row (criticals bypass) │ exit ├─────────────────────────────────────────────────────────────────────────┤ │ STAGE 7 exemplar select + SCORE-GATE → LLM.investigate() (:1020) │ GPU │ STAGE 8 response_validator.validate (:1033) │ │ STAGE 9 empty-action template fallback (:1056) │ │ STAGE 10 quality classify → retry / bounded-agency (:1073) │ │ STAGE 11 override gate, post-LLM recurrence gate, F-4 clamp, DA-2 strip │ │ STAGE 12 demotions (empty-evidence, no-trace) + Stage-E quarantine │ │ STAGE 13 notify (escalate→email) + persist + dedup link + incident │ └─────────────────────────────────────────────────────────────────────────┘

The expensive part is one asyncio.gather of the three pillar fetches (context.py:558-564) — Prometheus :8091, Loki :8092, Jaeger :8093 — run in parallel, plus two conditional extra calls:

  • Deep trace (context.py:596-617): for latency/error alerts on a service whose slowest trace exceeds 200ms, one extra get_trace call. The result is PII-sanitized (masks db.statement literals, http.target IDs), then ranked and slimmed to the top-15 spans so the slowest downstream span survives the character cap. This is the "keystone evidence" for latency RCAs — it lets the LLM name which span is slow, not just that p95 is high.
  • Deploy bridge (context.py:619-633): for kube-workload and Drain3 alerts, one call to deploy-mcp :8096 over a 2h window. A rollout just before the alert is a cause candidate; an empty list explicitly rules deploy-regression out — a grounded negative, not silence.

After gathering, the deterministic metric interpreter (metric_interpreter.py) computes — never the LLM — the observed value, unit (ms/percent/bytes/sec…), threshold and direction, the signed delta and delta-percent, and the deployment family (k8s/docker-vm/systemd). It renders a one-liner like "CPU busy = 94.4% — 9.4pp above the 80% threshold" that the LLM is told to cite verbatim, not re-derive.

Why this design — code does arithmetic, the LLM only narrates
Every number an operator might act on — the observed value, the delta, the fire count, the dedup decision — is computed by deterministic Python and handed to the model as a fact to quote. The LLM is forbidden from doing arithmetic or inventing figures (the prompt and validator both enforce this). The model's only job is to read the assembled, correlated picture and write the causal narrative — "the accounting pod is OOM-looping because its 120Mi limit is below working set, evidenced by exit-137 and 420 restarts". A language model is unreliable at math and reliable at prose; the architecture plays to that, not against it.

4.2 Four different noise concepts (do not confuse them)

MechanismWhereWhat it is
Dedupdedup.pyIn-memory sliding window (~600s) keyed on fingerprint/family. Collapses identical re-fires. Writes no feed row — it bumps the incident's fire_count instead.
Recurrence gaterecurrence_gate.pyPer-rule opt-in (Grafana annotation), DB-backed, ~2h window. Pre-LLM caps the first N fires (cheap rows); post-LLM force-escalates after M LLM dismisses. Criticals bypass.
Layer-2 suppression_check_suppression :555Replays a recent DISMISS for the same (alert_name, service) within 10m to skip the GPU. Criticals never suppress.
Incident entityrca_store.py:85One persistent row per distinct fingerprint, carrying fire_count / last_seen. "The same flapping rule firing 40 times is ONE incident, not 40 feed rows." Dedup recurrences bump it.

The mental model: dedup is short and textual (same thing, right now); the recurrence gate is long and policy-driven (this rule flaps, throttle it but escalate if it persists); suppression replays a recent human-or-AI dismissal; the incident entity is the durable "this is one ongoing thing" record that the dashboard renders as "fired N times".

4.3 The cheap-path economics

Everything that short-circuits before LLM.investigate() writes a lightweight row and returns, never touching the GPU: the Drain3 noise gate → dedup → Layer-2 suppression → recurrence pre-LLM gate → MCP-outage fail-open → data-starved early-exit gate. In real-induction testing the platform paged on 7 genuine faults out of dozens of fires with zero false pages from 28 non-incidents — the bulk of that filtering is deterministic code, not the model. The GPU is the scarcest, most expensive, most fallible resource in the system; the entire Layer 2 exists to make sure it only ever runs on something worth a real root-cause analysis.

5. The hallucination firewall

This is the platform's central safety invariant and arguably its most important design idea: every piece of data the LLM ever sees must arrive through a read-only MCP bridge. No direct database reads, no in-process Prometheus client, no querying Loki's HTTP API from the pipeline. Six bridges, one per data source, each a small read-only FastAPI app:

BridgePortWrapsKey read-only tools
prometheus-mcp:8091Prometheus HTTP API (:9090)query_instant, query_range, get_alerts, get_targets
loki-mcp:8092Loki HTTP API (:3100)query_logs (50-line cap), get_label_values, get_log_volume
jaeger-mcp:8093Jaeger HTTP API (:16686)find_traces, get_trace, get_services, get_operations
drain3-mcp:8094the triage service's /drain3/stats (:8090)get_clusters, get_anomaly_rate, match_log, get_baseline_info
rca-history-mcp:8095the SQLite RCA store (shared volume)get_recent_rcas, search_rcas, get_similar_decisions, get_alert_frequency, list_feedback, list_exemplars
deploy-mcp:8096kube-state-metrics series in Prometheus (:9090)recent_deploys, last_deploy
Why this design — provenance is the point
An LLM will happily invent a plausible service name, a metric value, or a deploy that never happened. The firewall makes that structurally impossible: if a figure appears in an RCA, it came through a bridge, and the bridge call is logged — so every number is traceable to a real query. This was not theoretical. Incident 0b215ef3 saw the model fabricate a service that did not exist; the firewall plus the validator's parrot/placeholder guards are the direct response. The deploy-mcp bridge itself was born this way: until 2026-06-11 the platform had no deploy data source, so the validator rejected any deploy-as-cause claim as ungrounded. The fix was not to loosen the validator — it was to build a bridge so the claim could be grounded.

How the invariant is enforced

The CI lint scripts/check_mcp_invariant.py (run by .github/workflows/ci.yml on every push) gates builds. It is regex-based and fails the build on: any direct observability port (:9090/:3100/:16686) or /api/v1/query path in app/; import aiosqlite outside the store; the Grafana datasource-proxy bypass on :3000; and ungated loads of the blocklist/exemplar YAML. A handful of boundary files (config, the Drain3 input path, boot-time backfill) are explicitly allow-listed. The bridges' shared error layer reinforces it: an upstream 4xx maps to HTTP 422 ("your query was bad") and a 5xx/unreachable to 502 ("source outage"), so the triage client can tell a bad query from a dead source — which is what makes the MCP-outage fail-open in the pipeline correct.

Bonus — the firewall is also a portability seam
Because the pipeline only ever speaks the bridge's small read-only vocabulary, the backend behind any bridge can be swapped without touching the reasoning code. Point loki-mcp at a different log store, or deploy-mcp at a real CD system instead of kube-state-metrics, and the LLM never knows. The safety boundary doubles as the vendor-neutral boundary.

6. Layer 3 — AI-RCA explain

6.1 The local LLM

The reasoning model is qwen2.5:14b (primary) with qwen2.5:7b as a fallback, served by Ollama as a host systemd service (:11434) on the GPU host's A10G. The call is a single /api/chat POST, temperature=0, num_ctx=32768, with format=<response schema> so the model's output is structured at decode time (llm_client.py:1288,1269). A circuit breaker plus two retries with backoff guards transient failures; a 4xx is non-retriable and does not trip the breaker.

Note — the in-code default vs. production
The Python default in config.py:7 is llama3.1:8b; the qwen2.5:14b primary / 7b fallback is set via OLLAMA_MODEL in docker-compose.gpu.yml for the GPU deployment. So "14b/7b" is the production fact, not the bare code default.
Why this design — a local model, not a frontier API
Three reasons. Sovereignty: CIRES telemetry — internal service names, log contents, infrastructure shape — never leaves the org's hardware. Cost: a self-hosted model has no per-token bill, which matters when the pipeline runs on every survivor alert indefinitely. Replaceability: because the model only ever narrates a pre-assembled, validated picture (it does no arithmetic and reaches no data except through the firewall), it is a swappable component — a better local model drops in with a config change. The architecture deliberately does not depend on any one model's cleverness; it depends on the scaffolding around it.

6.2 Prompt construction

The prompt (_build_prompt, llm_client.py:860) is assembled from deterministic blocks in a fixed order. The system prompt carries the cause-first quality rules (name a mechanism in the first sentence; never let "value above threshold" be the conclusion; remediation-only actions; correlation must be explained) plus three few-shot examples and the output schema. The user message stacks:

  • Alert details + the exact metric that fired (PromQL + observed value, skipping the boolean threshold step).
  • Metric-interpreter facts — the deterministic one-liner, "cite verbatim, do not re-derive".
  • Correlated-picture framing — the "ALL THREE correlated signals … reconcile them" preamble plus the neighboring-alerts block (±5 min). This is the instruction to investigate metrics, logs, and traces together.
  • DA-3 prior-decision block and Phase-6 corrective-feedback block (operator overrides on similar past alerts).
  • Exemplar — the selected archetype rendered as a structural template (§7), with an explicit numeral guard: never copy the exemplar's numbers.
  • Deploy block (rollouts in the window, or the explicit "no deploys" negative), metrics (capped 6000 chars), anomalous-log primary block, traces, and the deep-trace span breakdown ("keystone evidence for latency").

The output's reason field is an investigation log: 3–6 numbered steps in the form "1. checked X → found Y" with concrete numbers; when a deep-trace breakdown is present, one step must cite the slowest span. This makes the model's reasoning auditable — an operator can see how it reached the cause, not just the cause.

6.3 The response validator

Between the LLM and persistence, response_validator.py scans the decision and either mutates it (stripping bad actions) or flags it for retry. The guards:

GuardRejects
Banned-phrase scanhedges: "insufficient data", "no metrics/logs/traces", "cannot determine", "needs further investigation"
human_cause formula guardPromQL or metric{…}=value in the operator-facing prose (it must be plain English)
Template-slot guardunfilled exemplar slots: "N minutes", "cluster #N", "HH:MM", "v<X.Y.Z>", "{service}" — proof of copy-paste
Ungrounded-deploy guarda deploy/rollout-as-cause claim unless the decision's own evidence contains a deploy token (the deploy bridge is the only legitimate source)
Parrot/placeholder scanliteral service=X, service={{SERVICE_NAME}} — the 0b215ef3 failure class
Numeral guardcopied exemplar numbers (prompt instruction + template-slot guard)
Vague-action / investigation-only scanread-only "kubectl get/describe" commands with no actual remediation verb
Architecture-mismatch scancommands from the wrong deployment family (docker command for a k8s service)

A severity floor (in llm_client.investigate) prevents the model from downgrading below the Grafana label's severity. Confidence demotions live in the pipeline, not the validator, and run at persist time:

  • Empty-evidence demotion (pipeline.py:1542): actionable + confidence >0.5 + zero corroborating evidence → cap at 0.5, retag needs_review.
  • No-trace demotion (:1559): a confident latency/error RCA on a traced service that returned no traces → cap at 0.6, needs_review.
  • F-4 clamp (:1381): a surface-only/hedge pattern, data-starved quality, or template-sourced actions → cap confidence ≤0.4 and replace the action list with read-only diagnostic_steps.

6.4 Bounded agency — the data-starved retry

When the first pass is thin — data-starved, a banned-phrase hit, a thin INCONCLUSIVE/ESCALATE at low confidence, or a latency alert on a traced service with no traces — the pipeline gives the model exactly one extra MCP call (bounded_agency.py). The model may request one whitelisted tool (prometheus.query, loki.query_range, jaeger.get_traces, rca_history.similar/list_exemplars/get_exemplar/list_feedback); the request is Pydantic-validated, executed at temperature 0, and re-prompted with the result. Crash-loop alerts skip the model's tool-pick entirely — the platform auto-issues a fixed three-family kube-state query and digests it into plain-English facts plus a ready verdict the model only confirms (the 14b repeatedly failed to compose the query itself).

Why this design — agency, but bounded
A full autonomous-agent loop is exactly the kind of unbounded, hard-to-audit, expensive behaviour the platform is built to avoid. But a model that hits a missing signal and simply hedges is useless. The compromise: one extra, whitelisted, validated, deterministic call — enough to resolve "I couldn't see X" into "I checked X and found Y", and no more. The governing principle is investigate all three signals, never guess past a missing pillar: if a pillar is genuinely empty, the honest output is INCONCLUSIVE, not a fabricated cause.

7. The exemplar / archetype system

An exemplar is a worked example of a good RCA's shape — not a fact, not a rule. The library (app/exemplars/library.yaml) holds 17 archetypes plus one neutral default (generic-sre-shape): OOM-loops, upstream-latency attribution, crash-loop-bad-config, workload-replica-deficit, TLS-cert pre-expiry, a synthetic-blip dismiss archetype, the closed-loop-override sentinel, and more.

How selection works

Selection (app/exemplars/__init__.py) is two-stage — a regex gate, then additive scoring:

  1. alertname regex gate — if the archetype's compiled pattern doesn't match the alert name, it scores 0 and is skipped entirely (:99-101).
  2. additive scoring (:103-119) — base 0.10 for the name match; +0.40 service match (-0.15 if a service set is named but excludes this one); +0.30 deployment-type; +0.20 signal; +0.10 severity.
  3. tie-break — highest score wins; ties broken by an explicit integer priority, then by lower id, so selection is fully deterministic and independent of YAML order.
  4. SCORE-GATE (:160-182) — if the best score is below exemplar_min_fit_score (default 0.25), the weak match is discarded and the neutral default is used instead, with score 0.
Why this design — calibration, not a taxonomy
The exemplar is framed in the prompt as a structural template: "match this RCA STRUCTURE… It is NOT a source of facts. THIS alert's facts come from the gathered context above. If your evidence diverges from the archetype, say so and reason from your own evidence." The cause always comes from evidence; the archetype only decides whether a trustworthy shape is worth showing. The score-gate is the discipline that makes this safe: a weak fit (only the alert name matched) would drag the RCA toward the wrong shape, so a weak fit is not shown at all — it falls to the neutral "name the mechanism, don't restate the alert" default. Combined with the numeral guard (a real bug: a crash-loop RCA once cited the exemplar's example "128Mi" instead of the real 4Mi) and the validator's template-slot guard, the system gets the benefit of worked examples without letting the model force-fit one. This is "earned influence" — an archetype only steers the output if it genuinely fits.

The selected exemplar_id and its exemplar_score are stamped onto the decision and persisted (pipeline.py:1643-1644) so the dashboard can later answer "which archetypes actually help". A coverage CI guard (tests/test_exemplar_coverage.py) asserts every live Grafana rule either matches a real archetype's regex or is an explicit, recorded waiver — so falling to the default becomes a conscious choice, never silent drift. Exemplars are kept in their own YAML, deliberately not mixed into the empirical RCA history, so they never contaminate the dashboard or the precision/recall metrics.

8. Quality & honesty mechanisms

The platform treats honesty as a feature: an "I don't know" that is correct is worth more than a confident guess that is wrong. Several mechanisms enforce this.

Quality tags

Every persisted decision carries a quality tag, classified deterministically by _classify_rca_quality (rca_store.py:138-206), most-severe-wins:

  • needs_review — no actions and no evidence: may sound confident but is unactionable; surface to a human.
  • data_starved — hedge phrases present (matched against the validator's same banned-phrase list, so the classifier and validator can never drift) or empty narrative.
  • actionable — everything else.

Quarantine

A row that still hedges or parrots after both LLM passes is written with excluded_from_lookup=1 (Stage E, pipeline.py:1582-1610). Quarantined rows are hidden from every LLM-context lookup (the DA-3 prior-decision, similar-decisions, high-value-feedback queries all filter COALESCE(excluded_from_lookup,0)=0) so a bad row can never be quoted back to the model and reinforce the hedge — but they remain fully visible to operators on the dashboard and in audits. The quarantine is LLM-context-only, by design.

The closed-loop feedback

Operator feedback flows back into future prompts three ways (all pipeline.py):

  • Past-hedge replay — prior data_starved RCAs for this fingerprint are quoted verbatim so the model sees its own past hedges and avoids repeating them.
  • Proactive high-value feedback — operator corrections on similar past alerts (14 days) are injected when present.
  • Override gate — if the model DISMISSes but an operator has an active override (a "this is a real incident" flag, default 14-day window), the verdict is force-flipped to ESCALATE with the override note prepended.

The feedback table also backs confirm (timeless ratification for precision/recall) and a rate-this-alert form (useful yes/no, verdict-right, action-right, actual-cause, tags, notes). The recurrence history is surfaced to operators as clickable past investigations with review badges, and the escalation email states how many times the alert fired in the last 7 days (reconciled from the incident entity's fire_count).

9. State & data model

All persistent state lives in SQLite via aiosqlite (app/rca_store.py) — a single shared DB file (mounted to the rca-history bridge as a volume; backed by RDS MySQL only for the application under test, not the platform's own store). Migrations are additive: every new column is nullable and historical rows are never back-filled, because SQLite has no ADD COLUMN IF NOT EXISTS so the code probes PRAGMA table_info first.

Why this design — SQLite
The platform's own record is low-volume (one row per surviving alert) and single-writer. SQLite is a zero-ops embedded store with no server to deploy, secure, or back up separately — it ships inside the triage container and is exposed read-only through one MCP bridge. For a PoC and a portable BYO bundle, that is exactly the right amount of database. The application-under-test uses real MySQL/RDS; the platform's metadata does not need it.

10. Infrastructure & deployment

The current topology is the three-host AWS bed described in §1.3 (monitoring t3.large + k3s t3.xlarge in us-east-1, GPU g5.xlarge A10G in us-west-2, RDS MySQL), provisioned by Terraform and configured by Ansible. Container images for the triage service and all six bridges are built and pushed to GHCR via GitHub Actions (matrix over the six bridge directories, tagged main/sha/latest).

The 3-command BYO deploy

The platform is designed to be portable — handed to the supervisor to deploy on her own L4 GPU and existing Kubernetes. The bundle ships:

  • preflight — a fail-fast Ansible role that asserts every required var/secret is defined, non-empty, and not a CHANGE_ME placeholder before anything runs.
  • vault — a committed plaintext template (vault.example.yml) that the operator copies, fills, and ansible-vault encrypts; secrets are the Grafana admin password, SMTP password, MySQL password.
  • gpu-host.yml — a from-bare-OS GPU bring-up playbook (common → docker → gpu_driver → nvidia_docker → ollama → triage_stack), with the header explicitly targeting an NVIDIA L4 (Ada Lovelace) — the supervisor's production GPU, not the AWS A10G.
  • example.yml inventory — a genericized, BYO-portable template alongside the canonical live newacct.yml.
Important — AWS is the bed, not the target
The AWS three-host topology is a dev/test bed only. The production target is the CIRES private cloud with an L4 GPU — which is why the BYO bundle, the L4-targeted gpu-host playbook, and the portability-first choices (the MCP firewall as a swappable seam, SQLite over a managed DB, OTel over vendor exporters) all exist. For prod hardening the recommendation is portable open-source — Postfix not SES, MinIO not S3 — and, longer term, a single OTel host-agent feeding the NOC's existing Zabbix for metrics rather than Prometheus-forever.

11. Design principles that recur

Step back from the components and the same handful of through-lines appear at every layer. If you internalise these five, the rest of the platform follows.

PrincipleHow it shows up
Deterministic-first, AI-lastCode does dedup, suppression, arithmetic, the metric interpreter, the quality tags. The LLM sits at the narrow end of the funnel and only narrates a picture code has already assembled and verified.
Provenance / the firewallEvery datum the model sees comes through one of six read-only MCP bridges, CI-enforced. Every number in an RCA is traceable to a real query. The same seam makes backends swappable.
Honesty as a featureBanned hedges, quality tags, confidence demotions, quarantine, "never guess past a missing pillar". A correct INCONCLUSIVE beats a confident wrong cause.
Real-induction-only testingNo synthetic webhook POSTs — faults are induced for real (flagd on otel-demo, resource stress, bad-deploy canaries) so the bridges see real data and the whole path is exercised.
Earned influenceThe exemplar score-gate, the override window, the deploy-grounding requirement: a signal only steers the output if it genuinely fits the evidence. Weak fits fall back to the neutral default.
Measured, not aspirationalDecisions are scored against ground truth in real-induction batteries (detection recall, cause accuracy, false-page rate); exemplar usefulness is persisted and rolled up. The claims on this page are the ones the tests support.
If you read one thing
The platform's whole bet is that a fallible language model becomes trustworthy enough to page a human not by being smarter, but by being wrapped in deterministic scaffolding that controls what it sees (the firewall), what reaches it (the cheap-path funnel), what shape it should produce (gated exemplars), and what it is allowed to claim (the validator and demotions). The intelligence is in the scaffolding as much as the model.
