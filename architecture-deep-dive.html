1. The big picture

The platform answers one question that traditional monitoring never quite does: when an alert fires, what is the actual root cause, and is it worth waking someone for? A Prometheus rule can tell you CPU is at 94% — it cannot tell you why, and it cannot tell you that this particular spike is the third identical flap in ten minutes and not worth a page. The platform layers an AI reasoning stage on top of conventional observability to produce a named root cause with supporting evidence, while a thick stack of deterministic gates keeps the expensive AI from ever seeing noise.

1.1 Three layers on an observability socle

Conceptually the system is three layers sitting on a shared telemetry foundation (the "socle"). Each layer has a different job and a different failure mode it guards against.

LayerJobBuilt from
SocleCollect every metric, log, and trace through a single agentOpenTelemetry Collector → Prometheus / Loki / Jaeger
Layer 1 — Detection detectNotice that something is wrong, by threshold and by noveltyGrafana alert rules + Drain3 3-tier log-novelty
Layer 2 — Triage filterDeduplicate, suppress, gather correlated evidence, decide what reaches the GPUThe triage pipeline (pipeline.py) + 6 MCP bridges
Layer 3 — AI-RCA explainRead the correlated picture and narrate a grounded root causeLocal LLM (qwen2.5:14b) + response validator + exemplars
Why this design — a layered funnel
Each layer is cheaper and more numerous than the one above it. Thousands of raw samples become a handful of alerts (Layer 1); most alerts are deduplicated or suppressed by deterministic code before any AI runs (Layer 2); only the survivors — genuinely novel, un-suppressed incidents — reach the GPU (Layer 3). The expensive, fallible component (the LLM) sits at the narrow end of the funnel and only ever narrates a picture that deterministic code has already assembled and verified. This is the recurring through-line of the whole platform: deterministic-first, AI-last.

Two things are worth internalising from this picture. First, everything the LLM ever sees passes through one of the six MCP bridges — there is no arrow from the LLM directly to Prometheus or Loki. Second, most alerts never reach the LLM at all: stages 1–3 (and several more, §4.3) write a cheap database row and return before any GPU work happens.

1.3 The real hosts and ports

The current proof-of-concept runs on three AWS EC2 hosts joined by a Tailscale tailnet (addressed by MagicDNS, never raw IPs). This topology is a dev/test bed; the production target is the CIRES private cloud (see §10).

Note — webhook path
Grafana does not POST directly to the GPU host. The firing webhook goes through an AWS API Gateway (…execute-api.us-west-2.amazonaws.com/webhook/grafana) fronting a Lambda autoshutoff, which forwards to triage :8090. The individual MCP containers (:8091–:8096) bind only inside the GPU host's docker network; Prometheus sees them aggregated as triage_mcp_* metrics on :8090, never scraping them directly.
