Framing — useful today, still in training

The good. This audit shows the platform doing real work on real traffic: 8/16 decisions in the window were absorbed without an LLM call by the recurrence gate, dedupe, and see_previous_rca paths — half the load handled cheaply. The 14b on the GPU produced cause-first RCAs at a 22 s median (vs. 6–7 min on the 7b laptop baseline). Both dismisses in the window were correct — the system did let benign signals go. The kong-SIGCHLD attribution at 18:34 (see §7c.2) is the kind of selectivity an AI layer can add on top of conventional observability — the model picked the operationally-meaningful side effect over the louder volumetric signal.

The bad — what this page documents in detail. 2/6 operator emails in the window were false positives. 1 alert fingerprint flipped verdict in 5 minutes. 2 duplicate-class patterns let unrelated events share buckets. 2 unsafe-or-misleading actions reached the operator inbox. Only 1 of 8 LLM-pathed RCAs named the actual operational cause. These are real failure modes; they are also not architecture failures — they are gate-tuning gaps and training-data gaps that show up because the system is being asked to make judgment calls without yet having an operator feedback signal to learn from.

How Sprint 4 + the operator feedback loop close the gap. Two structural changes in Sprint 4 attack most of these findings directly:

  • Feedback loop (Sprint 4 — operator override schema + rate.html UI + 4 MCP tools). Every operator "this was noise" override feeds the suppression cache; every "wrong remediation" flag adds to the hallucination blocklist; every operator-confirmed root cause becomes an exemplar; every cross-row verdict conflict resolved by an operator becomes a tuning example. Q1, Q2 and the unsafe-actions class of findings all gain a learnable signal.
  • Mechanical Sprint 4 candidates (~13 SP, named in §5 below). The shelved-in-disguise email gate (already shipped — see status banner above), drain3 fingerprint hashing, alertname-family dedupe equivalence, cross-row coherence check, and unsafe-action stripping independent of the clamp. Each maps to a specific row in §3 below.

The framing for the supervisor. The platform is useful today as a triage assistant — it routes 50% of alerts cheaply, names operational causes when it can, and keeps the dashboard row even when it shouldn't have paged. It will become measurably better as Sprint 4 lands and operator overrides start flowing into the cache. The honest claim is not "this is finished"; it is "this is the right architecture and the right hardware; the refinement work is named, scoped, and underway."

Deep dive 1 — the bingbot 404 escalation (Lina's question 1)

Failure mode · 2026-05-21 16:32:53 UTC · Drain3AnomalyDetected · drain3 · RCA id c4561c89

What landed in the operator's inbox. An email titled Drain3 anomaly detected on service drain3, action_taken emailed, llm_verdict escalate, llm_confidence 0.00, rca_quality needs_review.

What the prose actually said (rca_report, verbatim):

"The alert triggered due to a low anomaly rate (3.19%) with three lines flagged as anomalous in the logs. The anomalies are related to HTTP GET requests returning status code 404 and involve bingbot activity, but there isn't enough context or metric data to determine if this is an actual issue or normal behavior."

What was actually happening. Bingbot was crawling /view on spring-boot and getting 404s. That's the cause — a search-engine crawler hitting a path that doesn't exist. It is not a production problem. It does not require an email. The 14b model already knew this — the cause-prose self-describes the input as "low anomaly rate", "three lines", "bingbot activity", and explicitly hedges that "there isn't enough context … to determine if this is an actual issue or normal behavior."

So why did the operator get emailed. The verdict path defaults Drain3AnomalyDetected to escalate unless the model produces an affirmative dismiss. The model produced uncertainty ("not enough context"), which is treated as escalate-with-low-confidence. The confidence value (0.00) did not gate the email. The single suggested action is a deadpan "Shelved — no correlation found, no remediation issued. Awaiting recurrence." — the model itself describes its own work as shelved, yet the email went out anyway.

This is the answer to Lina's question 1: the operator gets notified when there isn't a problem because the verdict policy treats uncertain-drain3-anomaly as escalate. The fix is mechanical, not LLM-quality-bound: when llm_confidence < 0.30 AND rca_quality = needs_review AND no correlated alerts within ±5 min, the verdict should be downgraded to dismiss or queued without an email. Sprint 4 P5-bis candidate.

Deep dive 2 — the HighCpuUsage verdict flip (Lina's question 2)

Failure mode · 2026-05-21 18:42:12 → 18:47:14 UTC · HighCpuUsage / k3s-node · fingerprint c4e3f62ba279e5c0

Two RCAs, same fingerprint, opposite verdicts, 5 min apart.

18:42:12 — verdict escalate, confidence 0.85, rca_report:

"The k3s-node service on instance 10.0.1.194:6443 has been experiencing elevated CPU usage, reaching 92.3%. The observed value is above the threshold of 85% for over 5 minutes. … This suggests that there may be unexpected load on the node."

18:47:14 — verdict dismiss, confidence 0.85, rca_report:

"The CPU usage on the k3s-node (10.0.1.194:6443) has spiked to 41.1%, which is above the static threshold but well within expected seasonal variations. The metric values show a transient spike that quickly returned to normal levels … This pattern suggests a known traffic fluctuation rather than an actual degradation."

Is this actually a conflict. Both RCAs are looking at the same alert fingerprint, but at different moments along the cpu-stress decay curve. At 18:42 CPU was at 92% with hey-load still running. By 18:47 cpu-stress had ended (~18:39:40) and hey-load had ended (~18:42:40); the node was at 41% recovering. Both verdicts are individually defensible. But the operator sees two adjacent rows with the same alert name, same service, same fingerprint, and opposite calls.

The real problem. Neither RCA names the operational cause (cpu-stress pod from default namespace, hey-load synthetic traffic). The first says "unexpected load" — generic. The second says "seasonal variation" — wrong, this was synthetic stress, not seasonality. Without a named cause in the first RCA, the second RCA can't tell that the cause has cleared — it has to re-derive intent from the metric value alone, which is why it lands on "seasonal".

This is the answer to Lina's question 2: RCAs conflict because the model is reasoning from instantaneous metric values rather than from named-cause continuity across the alert lifecycle. The fix is the §7.5 P1 axis (cause-prose must name a culprit), extended with a cross-row coherence check: when a re-fire of the same fingerprint flips verdict, the new RCA must explicitly reference and reconcile the prior one. Sprint 4 candidate, new axis.

Deep dive 3 — wrong-metric evidence and unsafe actions (the two worst LLM outputs)

Failure mode A · 2026-05-21 18:45:22 UTC · PodHighMemoryUsage / spring-boot · RCA id 4aa43e6f

Real PodHighMemoryUsage at 97.49% (spring-boot heap under hey-load HTTP fan-out). Verdict escalate at confidence 0.00. Email sent. The cited evidence (verbatim):

"sum(rate(spring_boot_http_requests_seconds_count{...}[1m])) / sum(rate(spring_boot_http_server_requests_seconds_count{...}[1m])) = 1.25"

The alert's actual rule is (container_memory_working_set_bytes / container_spec_memory_limit_bytes) * 100 — a memory query. The cited evidence is a ratio of two HTTP request-rate counters, value 1.25, which is neither the memory value (97.5%) nor evidence for the memory hypothesis. The model produced PromQL that looks plausible for spring-boot but is the wrong metric family for the firing alert. The suggested action: "kubectl rollout restart deploy/spring-boot — universal first-line remedy for k8s services" — the §7b P1 anti-pattern verbatim. The clamp didn't fire because severity is info and the clamp currently runs warning+. The verdict was correct (real problem); the email body was misshapen.

Failure mode B · 2026-05-21 18:40:22 UTC · CriticalCpuUsage / k3s-node · RCA id aaea032e

Real 98.6% sustained CPU; verdict escalate at confidence 0.95 — correct call on a real problem. But the suggested action (verbatim):

"ssh root@10.0.1.194 'systemctl restart k3s-node.service' — restart the k3s service to clear transient issues"

Restarting k3s on the only k3s node would bring down every pod — spring-boot, kong-kong, prometheus, loki, drain3, the triage service itself. The actual cause was a polinux/stress pod in default ns, which the prose does not name. The safe remediation is kubectl delete pod cpu-stress -n default. The §5.3 clamp keys on "rollout restart" / "universal first-line remedy" — it does not currently key on systemctl restart. Sprint 4: extend blocklist to include systemctl restart k3s, kubectl delete node, shutdown, reboot; run clamp at all severities.

Sprint 4 candidates surfaced by this audit (in priority order)
  1. Verdict-policy gate on low-confidence drain3. When llm_confidence < 0.30 AND no correlated alert within ±5 min AND rca_quality ∈ {needs_review, data_starved}, downgrade verdict from escalate to queue-without-email. Closes the bingbot-style false-positive (Lina's Q1). Mechanical fix, ~1 SP.
  2. Prose-vs-verdict consistency check. If the cause-prose contains phrases like "does not significantly deviate", "not enough context", "normal behavior" — verdict must not be escalate. Static text classifier, ~2 SP.
  3. Cross-row verdict-flip reconciliation. When a re-fire of the same fingerprint produces a flipped verdict, the new RCA must reference the prior RCA id and explicitly reconcile. Closes Lina's Q2. ~3 SP.
  4. Logical dedupe across alert-family. Within N min on the same service, treat (HighCpu, CriticalCpu) as a single incident regardless of fingerprint. Closes the "paid 2× for one incident" duplicate (Lina's Q3). ~3 SP.
  5. Unsafe-action blocklist extension. Add systemctl restart k3s, kubectl delete node, shutdown, reboot to §5.3 clamp keyword set. Run clamp at all severities, not just warning+. ~1 SP.
  6. Evidence PromQL family-match check. If alert is in family memory/cpu/latency, the evidence PromQL must contain a metric from the matching family. Reject HTTP-rate evidence on a memory alert. ~2 SP.
  7. Drain3 fingerprint disaggregation. Drain3-self-fires currently share fingerprint drain3-{service}. Add a content-hash suffix so bingbot 404s and Kong SIGCHLDs land on different fingerprints. ~1 SP.
The honest read for the production greenlight conversation

What is genuinely working. The dedupe gate, the recurrence gate, the see_previous_rca path, the 14b-on-GPU latency (median ~28 s), and the Kong-SIGCHLD identification at 18:34 where the model resisted the volumetric red herring and named the operational change.

What is genuinely not. Verdict policy on low-confidence drain3 (Q1). Cross-row coherence on verdict flips (Q2). Cross-alert-family dedupe (Q3). And the §7.5 P1 axis — cause-prose that names a culprit — is showing 1-of-8 hit rate on this window. That is the dominant Sprint 4 axis, with the 7 candidates above as the concrete work items.

Production-readiness call. The gaps above are mechanical fixes (~13 SP of Sprint 4 work). None require a model swap or re-architecture. The 14b-on-GPU substrate is delivering the latency and partial prose quality needed; the deterministic guardrails around it need the Sprint 4 pass. Recommend conditional greenlight: pilot on one operator queue with the Sprint 4 fixes shipped, gate broader rollout on a re-audit of the same shape against a fresh 4 h window.

6. How to use this going forward

This page is intended as a working reference for refining the triage service. After each sprint that closes a Sprint 4 candidate above, expect to:

  1. Re-run a 4 h audit-of-the-output using the same shape as this page — pick a real 4 h window with at least 1 operationally-stressful event, pull /decisions?limit=200, filter to the window, and grade each LLM-pathed row against ground truth. Use this page's structure as the template.
  2. Track the headline metrics over time: false-positive email rate, verdict-conflict pair count, "RCAs that named the actual operational cause" rate. The last one is the dominant axis — it should climb above 1/8 across runs.
  3. Compare against the Sprint 4 candidates list above — for each candidate, name the row(s) in this page that motivated it, and once the candidate ships, verify the next audit shows a delta on that specific failure mode.
  4. The supervisor presentation moment (the §7d card in Solution Brief) should be re-derivable from this page in <5 minutes — pick the most operator-relevant question of the day, find the worst row, find the best row, build the slide. Keep this page as the source of truth.

The framing matters: the system is honest about its failure modes because they're written down here, with the actual row IDs, in the same repo as the service. A reviewer who doesn't trust the §7d card can come here and re-grade every row. That's the contract.
