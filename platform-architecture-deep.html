Platform Architecture, End to End

1. The shape of the pipeline

The platform has two halves that meet at the triage service. The observability half (Prometheus metrics, Loki logs, Jaeger traces, Drain3 log-template anomalies) watches the react / employees-backend / MySQL workload running on k3s. The AI half (the FastAPI triage service + Ollama + six MCP bridges) lives on a dedicated AWS g5.xlarge GPU host (observability-gpu-uswest2-newacct, A10G) in us-west-2, attached over Tailscale. An alert is the unit of work that travels between them.

Crucially, the work is cheap-first. The GPU is the expensive resource, so the pipeline spends as little of it as possible: three synchronous, sub-second gates try to dispose of an alert before the LLM ever runs. Only alerts that survive all three gates earn a full investigation.

2. Alert sources — what can fire

Three kinds of signal enter the pipeline, all as Grafana-shaped webhooks:

  • Grafana threshold rules — the classic alerts (CPU saturation, p95 latency, error rate, disk pressure). These mostly use noDataState: OK on purpose: a CPU rule should not page just because a node briefly stopped reporting.
  • The generic KubeWorkloadDown rule — KSM-driven (kube_deployment_status_replicas_unavailable > 0), it gives liveness coverage for any deployment with no per-service rules. It deliberately uses noDataState: Alerting so that if kube-state-metrics itself disappears, "no data" means "alert", not "all clear". This closed the structural blind spot behind the no-alert outage. Full label-surgery write-up: kubernetes-observability.html.
  • Drain3 self-fires — when the log-template miner sees a novel or anomalous template, it posts to the triage service's own /webhook/drain3 bridge. These are the monitor watching its own log stream.
Why a generic workload-down rule
Per-service down-rules rot: every new service needs a new rule, and the one nobody wrote is the one that fails silently. A single KSM-driven rule that names the workload from its own labels scales to N services with zero new config. That is the difference between "we monitor what we remembered to" and "we monitor what exists".

3. API Gateway + Lambda router

Grafana cannot reach the GPU host directly — the host's SSH is closed and the service is Tailscale-internal. Instead, webhooks hit an AWS API Gateway endpoint that invokes a small Lambda router. The router forwards the payload to the triage service over the tailnet and, importantly, wakes the GPU instance if a cost autoshutoff has stopped it.

  • Cold start (historical): the cold-start path (SQS queue + Lambda router that boots a stopped instance) still exists, but as of 2026-06-04 the GPU host runs 24/7 by decision — so steady-state operation no longer pays cold-start. The machinery is retained for an optional future return to idle-stop.
  • Autoshutoff — DISABLED (2026-06-04): the 20-minute idle timer (EventBridge → Lambda) is turned off (idle rule state=DISABLED); the box runs continuously, trading ~$724/mo for predictable latency. Cost guard is now an AWS Budgets monthly budget ($800/mo, 80%/100%-actual + 100%-forecast email). The legacy $50/mo CloudWatch EstimatedCharges alarm cannot fire until Billing → "Receive Billing Alerts" is enabled (console/root-only); Budgets needs no such flag.
Known gap (audit P0.2)
The triage-idle-check EventBridge rule was found disabled in live AWS but enabled in Terraform state — so plan was blind and the GPU ran 24/7 guarded only by the $50 alarm. The fix pins state="ENABLED" and re-applies. Flagged here so the narrative does not pretend the autoshutoff has always worked.

4. Triage ingestion

POST /webhook/grafana accepts the payload, returns 202 immediately, and enqueues the work. Stages 1–3 run synchronously and cheaply; stages 4 onward run under an asyncio.wait_for(...) budget with a raw-alert fallback so a slow or stuck LLM can never hang the request. Every alert — escalated, dismissed, suppressed, or timed-out — is persisted as a row in the local SQLite rca_history, which doubles as the dashboard feed, the Layer-2 suppression signal, the frequency context for future prompts, and the feedback storage shape.

5. The cheap-path gates

Three gates try to dispose of the alert before any GPU spend. Each exists for a specific noise class.

Gate 1 Fingerprint dedup (Layer 1)

Keyed on Grafana's stable label-hash fingerprint with a 10-minute TTL. Grafana re-fires the same alert every evaluation interval while it stays active; without this gate one incident would trigger dozens of RCAs. On a hit, the pipeline writes a short-path suppressed_duplicate row linked to the first decision and exits. Why fingerprint, not alertname+instance: the fingerprint already encodes the full label set, so it dedups precisely the alerts Grafana itself considers identical.

Gate 2 Layer-2 history suppression

A different fingerprint but the same (alertname, service) family that we recently dismissed (within TRIAGE_HISTORY_LOOKBACK_MINUTES, default 30 m). We replay that dismiss verdict without paying the GPU. This is what stops a flaky-test noise pattern from re-investigating itself every half hour.

Gate 3 Recurrence-gate + SF-5 spike

For opted-in flappy alerts (US-5.8), a per-rule hysteresis: suppress fires 1–4, then force-escalate fire 5 — a sustained pattern is real even if each instance looks benign. Critical-severity alerts are explicitly never gated. The SF-5 "spike-shelved" path was intended to shelve very short spikes here, but is deprecated (see below).

Deprecated 2026-06-04 (audit backend #4)
SF-5 spike_shelved was structurally unreachable: its 120 s window sits inside the 300 s dedup window, so the dedup gate always fired first and SF-5 never saw a fire (zero spike_shelved rows ever written). Rather than a standing bug, the path is now deprecated — the default flag is flipped off (safe deprecation: code + unit tests retained should a future redesign make a spike gate reachable). The recurrence-gate (US-5.8) plus dedup remain the canonical noise absorbers.

6. MCP context gathering

An alert that survives all three gates earns a real investigation. The first expensive step is gathering evidence — and here the platform's defining invariant applies: every data source the LLM ever sees comes through an MCP bridge. There are five bridges: Prometheus, Loki, Jaeger, drain3, and rca-history, each exposing a small /tools/* HTTP contract. The pipeline pre-gathers a context bundle (recent metrics, log slices, trace samples, matching log-template clusters, prior RCAs for this family) and renders it into the prompt under ## Pre-Gathered Context.

Why MCP-only (the hallucination firewall)
The LLM has no direct database, Prometheus, or in-process read access. If it cannot fetch a number through an MCP tool, it cannot cite that number — so it cannot invent one and dress it as evidence. The bridge boundary is the firewall. It is also a portability seam: swap Prometheus for Zabbix, or Loki for Elasticsearch, by writing one new bridge — the prompt and the LLM never change. See hallucination-firewall.html.
Resolved 2026-06-04 (audit misc)
The MCP /tools/* handlers previously raise_for_status()'d on any non-200, so a malformed LLM query (a 4xx) surfaced to the model as "source down" — conflating an LLM fumble with a real outage. Fixed (82f719c): query rejection (4xx) is now distinguished from source unavailability (5xx/conn-error), so a bad query is no longer mislabelled "source down".

7. LLM investigation

The prompt is assembled in a deliberate order: a matched exemplar (one of 14 archetypes, scored against this alert) is rendered before the gathered context, giving the model a structural target before it sees the evidence; then the context; then the frequency/recurrence framing; then any high-value operator feedback for this family. Ollama runs qwen2.5:14b-instruct (7b fallback).

The model's first answer is not trusted blindly. Several mechanisms harden it:

  • Bounded agency (one extra query): if the first pass comes back data_starved, the model is handed a 6-tool whitelist and asked to issue exactly one MCP call before re-deciding. Bounded, not open-ended — it cannot loop.
  • Validators & clamps: a surface-only validator rejects a verdict that merely restates the alert; a hypothesis-menu validator rejects a hedge that lists every possibility; a confidence clamp downgrades a thin verdict to a diagnostic_steps fallback rather than letting it masquerade as a confident root cause.
  • Anti-hedge retry: a data_starved first pass triggers one more run with an escalated anti-hedge prompt before persisting — but only if budget remains.
Resolved 2026-06-04 (audit backend #3; DA-2)
Two of these are now fixed: (#3, d56ce88) rca_quality was snapshotted before the clamp/retry on ~24% of rows — it is now recomputed from the final decision after the gates, before persistence; (DA-2, 17debbf) the has_named_cause check previously false-allowed bare "because/due to", which could let an unsafe systemctl restart action pass the clamp — it now requires a concrete subject.
Resolved (2026-06-04 PM): the rca_quality recompute was forward-only, so a one-shot idempotent backfill was run against the live DB. It corrected only 2 stale rows — the audit's "~22%" estimate was a large overcount; the forward-fix had already kept the live history near-consistent. The "actionable %" KPI now reads true.
Resolved 2026-06-04 PM (audit backend #2 + BE-B2)
The data-starved verdict that previously cost ~100–140 s of GPU before emitting "cannot determine the root cause" now short-circuits via an early-exit gate that fires after all context-gather + anchor lookups (so it sees every groundable signal) but before the LLM. Two correctness sub-fixes this session: the gate's predicate is now keyed on content emptiness (a reachable-but-empty 200 is starved) rather than source reachability, which never tripped; and a distinct MCP-outage fail-open path (all pillars erroring) now escalates (raw-alert email + an explicit mcp_outage_escalated row) instead of silently suppressing a real alert during a transient MCP outage. Critical severity still bypasses both.

8. The verdict

The output is a structured RCARecord, not prose. Its load-bearing fields:

FieldWhat it carries
human_causeA named root cause in plain language — the diagnosis. Telemetry is the evidence for it, never a substitute.
evidenceThe supporting PromQL/log/trace citations, each tied to a real MCP fetch with a "View in {source}" link.
rca_quality4-axis rubric score — measures whether the verdict actually names a cause vs hedges.
envResolved environment (prod/stg/.../unknown) via the precedence chain — drives the email subject, dashboard filter, and URL filter so all surfaces agree. See triage §5.3.
Why "name a cause" is the contract
A verdict that recites metric values but never says what broke is not RCA — it is a dashboard screenshot in sentences. The validators exist precisely to enforce that human_cause is a real diagnosis. This is the platform's core value claim.

9. Notify + dashboard

If the verdict is ESCALATE, the notifier builds an HTML email (with correlated alerts in the same incident window) and sends it via SMTP. A notifier failure is logged and swallowed so persistence still happens. Every verdict — escalate or not — lands on the /dashboard as a row, with an expandable detail view showing the evidence and the "View in {Grafana/Loki/Jaeger}" links. The dashboard reads the same persisted env and stats as the email, so the two can never disagree. Operator-facing reading guide: dashboard-guide.html.

10. Closed-loop feedback

Every email and every dashboard row links to GET /dashboard/alert/{id}/rate — a form that POSTs to /feedback/rate/{id} and writes a 7-column feedback row (rating, verdict_was_right, action_was_right, actual_cause, tags, notes, rater). The loop closes because the next time the same (alertname, service) family fires, the pipeline reads that feedback back two ways: (a) proactive injection of the high-value subset (operator said the verdict was wrong, or supplied an actual cause) into the prompt with a "trust this HEAVILY" framing; (b) an on-demand rca_history.list_feedback tool the model can call. Operator corrections actively reshape subsequent RCAs. Full write-up: feedback-loop.html.

Family-match caveat
Feedback is matched by (alert_name, service) family with a default 14-day lookback (days=14). A correction on one family does not transfer to a different alertname or service, and it ages out after the window. Operators should know this when they wonder why a correction "didn't stick" elsewhere.
