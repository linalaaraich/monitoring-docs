1The 60-second pitch

Problem. The operational gap that motivated this work, surfaced in Sprint-0 field research: production incidents were being discovered after the fact — by clients or during retrospective log review — rather than by the monitoring system itself. Per-alert investigation cost was high and uniform regardless of whether an alert was a real incident, a flake, or a known recurrent pattern.

What it does. The CIRES Observability Platform is a two-layer response. The foundation: a conventional open-source observability stack (Prometheus / Loki / Jaeger / Grafana on AWS, Ansible-deployable). The differentiator: an AI triage service on top that, for every Grafana webhook, gathers cross-pillar context through five MCP servers, picks the closest of 14 RCA archetypes, asks a local LLM (qwen2.5:7b-instruct on Ollama) for a cause-first analysis, runs three validators, and emits ESCALATE (email the on-call) or DISMISS (record the reason and move on). Operators can override either way; their feedback flows back into the suppression and exemplar layers.

Scope of this brief. This is a proof of concept, built and validated on a local test bed — a sample react-springboot-mysql application (Spring Boot + Kong + MySQL + React) plus an additional co-located test application — running on a lab AWS environment. Inference moved on 2026-05-21 from a Tailscale-attached laptop (GTX 1060 + qwen2.5:7b, which ran the platform for the first 28 days) to a dedicated AWS g5.xlarge in us-west-2 (A10G GPU + qwen2.5:14b-instruct primary), reached over Tailscale at observability-gpu-uswest2; the laptop is retained as rollback fallback. Intended deployment target: CIRES Technologies (Tanger Med) production, contingent on the greenlight this brief supports. Alert volumes, latencies, and load shapes discussed below describe the test bed, not CIRES production — see §7.6 for an honest read on how the architecture would scale.

Why it's worth your time. Three things distinguish this from a typical LLM-on-alerts integration:

  1. Hallucination firewall. Every data source the LLM ever sees flows through an MCP bridge — no direct DB reads, no in-process module imports of evidence, no ad-hoc HTTP calls. The invariant is enforced by a CI lint (scripts/check_mcp_invariant.py), not just convention. If the LLM tries to invent a metric or a service that doesn't exist, the MCP call returns empty and the validator catches the unsupported claim downstream. See §5 and hallucination-firewall.html.
  2. Five reinforcing output-quality defenses. Exemplar retrieval, alert-keyed hallucination blocklist, surface-only LEDE + hypothesis-menu validators, confidence clamp, bounded-agency single retry. Each catches a different failure mode; together they make LLM mistakes recoverable rather than load-bearing.
  3. Operational track record, not promises. The triage container ran on adolin-wsl (laptop GTX 1060) for 28 days from Sprint 3 kickoff (2026-04-23); on 2026-05-21 it was promoted to a dedicated AWS g5.xlarge in us-west-2 (A10G GPU, instance i-03aec662b1a47ad8f, Tailscale name observability-gpu-uswest2) with the laptop kept as rollback fallback. 274 / 274 triage tests pass, the MCP-invariant lint is clean, and the 2026-05-19 heavy-load test produced 95 production-shape RCAs with a documented quality grade per RCA. Five of the twelve issues that test surfaced are already shipped.

What we deliberately didn't build. The system prefers determinism and auditability over raw model capability. No agentic multi-step planning loop (one bounded retry max). No vector DB (the exemplar library is a curated YAML, deliberately frozen until operator feedback can curate retrieval well). No microservice mesh (one pipeline, one process, deterministic ordering). No native tool-calling (structured JSON output schemas instead, until we stabilise on the new larger-model runner). Every quality mechanism exists to make the LLM's mistakes recoverable. If you'd weight that trade-off differently, §8 is the conversation we want to have.

End-to-end latency. Real-load median ~38 s on the new AWS A10G runner with qwen2.5:14b-instruct (Phase 2 smoke test, 2026-05-21; per-token ~50-65 tok/s, prompt eval ~1350 tok/s, cached model load ~177 ms). Prior 7b/laptop baseline was median ~5 min, worst 23 min on the heavy-load test (2026-05-19) — the migration is the structural fix that supersedes most of the Sprint 4 P0 latency bundle. Cheap-path short-circuits (dedup, recurrence gate, suppression replay) still complete in milliseconds. See §7.5 for the residual P-list.

2What we built (and what we deliberately didn't)

What we built: a single FastAPI service (monitoring-triage-service) that ingests webhooks, talks to five MCP servers (one each for Prometheus, Loki, Jaeger, the RCA history DB, and a deployment-events stub) over JSON-RPC, calls a local LLM via Ollama, persists decisions to SQLite, exposes a self-hosted dashboard, and emits 27 Prometheus metrics for its own observability. Around 9,500 lines of Python plus ~1,800 lines of declarative config (exemplar library, hallucination blocklist, alert-template fallback, recurrence-gate annotations).

What we deliberately didn't build:

  • An agentic loop with multi-step planning. We make at most one retry call (bounded agency) before committing to a verdict. The cost ceiling is predictable and the system stays reproducible at temperature=0.
  • A vector-DB / RAG layer. The exemplar library is a curated YAML of 14 archetypes injected at prompt time; we explicitly chose a frozen seed over learned retrieval until we have enough operator feedback to curate well.
  • A microservice mesh of small AI services. One pipeline, one process, deterministic ordering. Easier to reason about; easier to validate.
  • Tool-calling. The LLM produces structured JSON via prompt-engineered output schemas, not native tool calls. We'll move to native tool-calling when we move off the laptop to a larger model.
Design bias to flag for review

The system prefers determinism + auditability over raw model capability. Every quality mechanism (validators, blocklist, clamp, exemplars) exists to make the LLM's mistakes recoverable. If you'd weight that trade-off differently, we want to know.

5How we keep it honest

Five reinforcing mechanisms catch different failure modes. Each one exists because a real RCA went wrong in a specific way; the mechanism was the fix.

5.1 Exemplar library — structural scaffolding

Frozen seed of 14 RCA archetypes in app/exemplars/library.yaml. Each archetype carries a model RCA paragraph (3–5 sentences), an evidence pattern, a suggested-actions pattern, a confidence band, and an alertname-regex matcher. The pipeline picks the best-matching archetype before the LLM call and renders it as a ## Reference exemplar section in the prompt. The LLM sees "this is what a good RCA for this kind of alert looks like, structurally" before it sees any evidence. The factual claims in the exemplar are not the answer — they're the shape.

The 14 archetypes (see §6) were curated by hand from real incident playbooks + Sprint 2's "happy-path scenarios." Three were added during the 2026-04-28 audit cycle after coverage gaps surfaced.

5.2 Hallucination blocklist — alert-keyed phrase rejection

YAML at app/hallucination_blocklist.yaml. Per-alertname banned phrase list. Examples:

  • HighP95Latency + HighKongP95Latency reject /actuator/* in the RCA — actuator endpoints are scrape-internal, citing them is always a tell that the LLM is reading the wrong evidence.
  • Drain3AnomalyDetected rejects PromQL, Prometheus query, Drain3Alert, Drain3Threshold — log-anomaly RCAs that lead with metric prose are leading with the wrong evidence pillar.

A hit triggers a retry with an alert-specific HINT in the feedback string. The LLM doesn't get to ignore the violation; it has to address it explicitly.

5.3 Surface-only LEDE + hypothesis-menu validators

The surface-only LEDE regex catches RCAs that restate the alert without attributing cause. Real example we caught and fixed in F-2: "Based on observed metrics, the HighP95Latency alert indicates that service kong is experiencing elevated p95 latency." That's surface-only — it restates the alert and signals nothing about why. Six widening rounds cover PromQL-leading prose, "based on observed/repeated/context/...", "the alert for X", "looking at the metrics", and the alertname-first form.

The hypothesis-menu validator (shipped 2026-04-29 as S3-HF-03) catches the opposite failure mode: the LLM hedging by listing multiple possible causes without committing. Seven regex patterns target "possibly X or Y", "may be due to slow query, pool exhaustion, or GC pressure", "either A or B" prose with 5+ word noun phrases on either side. Negative lookahead excludes idiomatic "either way" / "either case". Pair this with a cause-evidence rule: the named cause's tokens must overlap with the evidence tokens (tokenized as [a-z]{4,} so hikaricp_connections_active splits into [hikaricp, connections, active] for cross-matching).

5.4 Confidence clamp + diagnostic steps fallback

The clamp is the user-visible trust signal. When any validator hits, or RCA quality lands as data_starved, or suggested actions look templated, the clamp forces confidence ≤ 0.40 and replaces suggested_actions with a small list of diagnostic_steps — read-only verbs like "Check Grafana panel X", "Tail Loki for <service> in the last 10 min". The email + dashboard render diagnostic steps as a separate card with a "Withheld — confidence clamped to 0.40" notice in the actions section. The operator sees clearly that the system is not confident and not recommending any change-of-state.

5.5 Bounded-agency retry — exactly one extra call

When the first pass is flagged data_starved or INCONCLUSIVE, instead of just scolding the model in the retry prompt, we let it request one additional MCP call from a fixed 6-tool whitelist (Prom instant query, Loki range, Jaeger get-traces, RCA-history lookup, deploy-events, get-trace). The model returns a structured tool request; we execute it; we re-prompt with the new evidence. Properties: exactly-one-extra-call ceiling, Pydantic-validated args (no arbitrary command execution), still reproducible at temperature=0.

7Case study — the 0b215ef3 incident

Real RCA · 2026-04-29 · the failure that drove Epic 4

The alert: HighKongP95Latency — p95 at the Kong gateway crossed threshold. Upstream service was spring-boot.

What the LLM said: Cause-first, fluently — but it recommended kubectl rollout restart deployment/spring-boot and kubectl describe pod -l app=spring-boot | grep -i oom in the suggested actions. These are OOMKill remediations on a p95 latency alert. The actions were templated from the wrong archetype — the OOM template (app/suggested_actions.yaml:64-77) only matches ^(High|Medium|Critical)MemoryUsage$ regex; it didn't fire here. The LLM produced these directly.

Why the system shipped it anyway: The F-4 confidence clamp correctly fired (RCA was tagged data_starved because the pipeline only gathered service-boundary trace summaries — it never called get_trace(trace_id) to drill into spring-boot's spans). The clamp lowered confidence to 0.40, which is the trust signal. But it didn't strip the bad actions — the operator saw "low-confidence verdict" next to "here are some kubectl commands to run." Bad combination.

What we shipped to fix it:

  • S3-HF-01 (Tier 0): the clamp now strips suggested_actions entirely and emits a separate diagnostic_steps field with read-only verbs.
  • S3-HF-03 (Tier 2): hypothesis-menu validator + cause-evidence rule (the LLM here also hedged with "possibly upstream is slow due to GC or pool exhaustion").
  • S3-HF-02: defensive tests pinning the action-template lookup so a YAML regex widening can never key wrong-archetype actions.

Epic 4 close-out — shipped 2026-05-19 (Sprint 3, 15/15 SP):

  • S3-HF-07 (Tier 1, 3 SP): get_trace(trace_id) MCP tool plus PII sanitizer (db.statement literals → ?, http.target IDs → :id) plus a new ## Trace span breakdown prompt section. The LLM now sees per-span attributes on the failing trace and can say "hikaricp connection pool exhausted: 27/30 active, all spans queued" rather than "upstream is slow." 16 new tests.
  • S3-HF-04 / S3-HF-05 / S3-HF-06 (4 SP combined): the last three MCP-only invariant bypasses closed (entity_baselines.py → prometheus-mcp; bounded-agency rca_history.similar path → rca_history_mcp; get_similar_decisions(min_quality) + get_low_rated_examples_for_alert on RCA-history MCP). Six in-process exemptions (config, drain3 poller, boot-time) explicitly documented.
  • S3-HF-08 (2 SP): MCP-integrity CI lint at scripts/check_mcp_invariant.py + GitHub Actions workflow + 4 self-tests with synthetic-violation probes — regression guard for the firewall.
  • S3-HF-09 (3 SP): chaos-corpus regression gate as the 5th evaluation axis. The hallucination firewall now has its own behavioural test corpus.

See §7b for a live RCA from 2026-05-20 showing this work in production.

7bCase study — Epic 4 in production (2026-05-20)

Real RCA · 2026-05-20 · the deliberate inverse of 0b215ef3

The alert: PodHighMemoryUsage (critical) on spring-boot, instance 10.0.1.194:10250. Container working set sat at 99.63% of cgroup limit — the same shape of alert that drove 0b215ef3, with the same tempting "just restart the pod" remediation hanging in front of the LLM. RCA id 8891233d, fired 2026-05-20T12:47:04Z.

What the LLM produced: Verdict ESCALATE, cause-first prose pointing at frequent /actuator/health, /actuator/prometheus and /api/employee requests, and high span counts on Kong. But the prose hedged — "could be a sign of either frequent monitoring or potential performance bottlenecks", "might be a significant number of concurrent requests", "could lead to increased resource utilization". That is textbook hypothesis-menu language.

What the system actually emitted: the hypothesis-menu validator (S3-HF-03) flagged the prose; the F-4 confidence clamp then fired, forcing llm_confidence to exactly 0.40 and stripping suggested_actions to []. In their place, four read-only diagnostic_steps rendered. The fourth is the load-bearing one, verbatim:

  • "Do NOT run kubectl rollout/scale/set or restart spring-boot until a specific cause (slow query / GC pause / pool exhaustion / downstream timeout) is named with trace or metric evidence."

That sentence is the lesson from 0b215ef3 baked into the diagnostic_steps fallback template. The operator sees a clamped verdict next to read-only investigation verbs and an explicit guard-rail — not a kubectl command. That is the entire point of Epic 4.

Correlation surfaced as context, not cause: three nearby TargetDown fires on the monitoring service landed in correlated_alerts (timestamps within 3 min). The pipeline passed them to the operator as evidence of a possible cluster without letting the correlation become a causal claim in the RCA prose. Hypothesis-menu discipline working on a live fire.

Secondary success — a different mode, same epic: earlier that morning at 08:50 UTC the audit-live cron fired a synthetic MediumCpuUsage (RCA 275ddbaf). Verdict DISMISS at confidence 0.92 — not clamped, the system was genuinely confident. The prose cited "+0.4σ above the same-hour baseline from one week ago" and "matches the prior 32 firings in the last 7 days, all of which were dismissed." Suggested actions pointed at the alert rule itself (stddev_over_time + offset 7d > 3), not at the workload — the P7 "dismiss-with-recommendation" pattern. This is the adaptive-threshold-noop archetype plus closed-loop feedback: the 32 prior dismisses arrive via the suppression layer and inform the next verdict.

What worked:

  • S3-HF-01 (Tier 0), in production: clamp stripped suggested_actions on a hedged memory-pressure RCA — no kubectl in the operator-facing output.
  • Diagnostic-steps fallback template: the "do NOT run rollout/scale/set" guard-rail prose, lifted from the 0b215ef3 postmortem, rendered verbatim on a live critical fire.
  • S3-HF-03 hypothesis-menu validator: caught the "could be either X or Y" hedging that 0b215ef3 also exhibited; the clamp fired automatically.
  • Closed-loop dismiss (P7 archetype): MediumCpuUsage dismissed at 0.92 with a rule-fix recommendation, informed by 32 prior suppressed firings.

Where it's still slow / still drifting:

  • P0 latency (Sprint 4 anchor): investigation duration on the primary RCA was 1,557 s (~26 min). The verdict and the output shape are right; the speed is not — too late to be load-bearing in an active incident. See §7.5 P0.
  • P1 prose-quality drift: the RCA cited routine /actuator/* and /api/employee log volume as if causal to 99.63% memory pressure. The clamp blocked the bad remediation, but the LLM still produced surface-level evidence selection. Sprint 4's P1 (PromQL/numerical-noise scrubber + context sanitizer) tightens this.

7cReal-condition stress test — 14b on GPU under induced load

Real RCA · 2026-05-21 18:32–18:42 UTC · four real inductions, not synthetic webhooks

What this section is. §7 and §7b each describe a single live RCA. This section is different in shape: a deliberate stress run with four parallel inductions against the live qwen2.5:14b-instruct pipeline on the AWS g5.xlarge GPU host (observability-gpu-uswest2:8090 on Tailscale). The point is to test the full chain — real Prometheus up == 0 / real cgroup CPU saturation / real drain3 template novelty / real p95 spike → real Grafana evaluation against the configured for: windows → real Alertmanager webhook through API Gateway → triage service on GPU — under simultaneous load. Q3 — Why do I get duplicates?

Two distinct duplicate classes

(a) Fingerprint collisions. drain3-{service} is the fingerprint for every drain3 self-fire on that service regardless of payload. Bingbot 404s at 16:32 and Kong SIGCHLDs at 18:34 shared the same drain3-drain3 bucket — completely unrelated events, same fingerprint. The dedupe gate compares fingerprints; this looks like a duplicate to the gate even when it isn't.

(b) Cross-alert-family duplicates. HighCpuUsage at 18:42 and CriticalCpuUsage at 18:40 fired on the same incident (the cpu-stress pod). Both ran the LLM. Both shipped to the operator. The dedupe gate keys on (alertname, fingerprint) — it doesn't know the two alertnames describe the same root cause.

Fix (Sprint 4): (a) make drain3 fingerprints include a hash of the dominant novel template — different content, different fingerprint. (b) add an alertname-family equivalence table ({HighCpuUsage, CriticalCpuUsage, MediumCpuUsage} is one family) so the dedupe gate collapses cross-family duplicates on the same instance.

Architecture review — what scales, what doesn't yet

Honest structural read drafted 2026-05-20. Distinct from the output-quality findings above: those are prose-level failures on a sound foundation. One-line verdict

Sound bones, single-host fragility — but the prior laptop-GPU ceiling was lifted 2026-05-21 (GPU migration to AWS g5.xlarge / A10G in us-west-2; see D24). 7.6.3 Scalability verdict

Sound for one mid-sized application stack with bursty-but-low-concurrency alert volume, which is what the PoC test bed has demonstrated. CIRES production load shape has not been measured on this stack and is materially larger — that gap is the central question the greenlight conversation needs to address. The architecture will not survive, in order of likelihood:

  • (a) a second comparably-loaded application on the same inference host — Ollama serialises and one application's storm starves the other's triage;
  • (b) a sustained alert storm above ~3 concurrent fires — directly reproduced today, the symptom is /decisions unresponsiveness while one inference is in flight;

12.1 The operator-cognitive-load doctrine

Design principle — adopt at the top of every UX decision

The supervisor's exact framing: "the engineer who is the end user needs to be at the forefront of our UX. He is most probably tired and doesn't have the time nor the bandwidth to read a lot of useless info. We have to give him poignant info and give him the name of things so he can fix / investigate immediately instead of getting decision fatigue. It should be very simple and intuitive to read."

Operationalized as five rules — every dashboard column, every email line, every detail-page section gets evaluated against these:

  1. Names not metrics. Show the name of the thing the operator has to look at — the namespace, the service, the component. Hide PromQL, raw IPs, metric values from the primary view.
  2. Brief not verbose. Reason is just the reason, not five sentences of how. Suggested action is few words, executable. Cut everything else.
  3. One row not duplicates. Same alert on same (env, namespace, service, component) = one row that updates over time. Not N separate rows. History shown inline.
  4. Click-through not wall-of-text. Full reasoning + evidence + history lives on a detail page reachable by clicking the alert. The dashboard view is poignant + actionable.
  5. Sustained not spikes. A momentary spike isn't important. Sustained over hours / days is what's worrying. The system needs to differentiate at the verdict level.

12.5 The canonical test case — dev-deletes-a-letter

The end-to-end use case the architecture should be designed against

The supervisor walked through a concrete scenario that's now the benchmark for whether the platform actually works in CIRES production conditions. Verbatim:

"If we have 5 services in Kubernetes pods, each one has a name, each one related to a different app the company does, all of them have the classic front / back / db and let's say some have other stuff — for example one is related to cameras, one is related to smoke sensors and whatnot. So if a problem happens in one solution, an example of such a problem is the CI/CD configuration file: a dev by accident deleted a letter from the name of a DB, so he's calling something that doesn't exist. The script runs and he goes home thinking everything is all good because such problems won't show for him in the pipeline platform. First how is he gonna be notified of this? And second is our system gonna be able to know exactly where the problem is at? Like which service and starting when, and maybe why? Like it should see through logs and whatnot that a new deploy was pushed. So it should deduce that there is a problem with the name written in the file of the new deployment and it should notify the engineer."

What the platform must do to pass this test:

  1. Notice the failure. The DB-name typo means the app fails at startup or at first connection-pool init. Loki sees the error logs from the misconfigured service ("Connection refused: pool exhausted for datasource typo'd-name" or "Unknown database typo'd-name"). Drain3 sees these as a novel template cluster on that specific service → self-fires.
  2. Attribute to the right service. The Drain3 RCA must name the service (which app) and the namespace, not just "a database error happened." The existing exemplar library has upstream-latency-attribution and crashloop-bad-config archetypes; the latter is the right pattern but needs the deploy-event correlation to make it concrete.
  3. Correlate with the deploy event. SF-9 (k8s data source) + SF-11 (deploy-event correlation): when a new failure shape appears within N minutes of a Helm release / kubectl apply, the LLM gets the deploy diff as context. RCA names the deploy as the trigger: "new deploy <sha> introduced a config referencing nonexistent DB <typo'd-name>; service <svc>; deploy at <timestamp>; pre-deploy was healthy; suggested rollback: kubectl rollout undo deploy/<svc> or fix the config and re-deploy."
  4. Notify the engineer who pushed the deploy. Email body includes the deploy author (from git commit metadata via k8s data source labels) so it gets to the right person, not a generic on-call.

None of this is far away. Drain3 already catches the novel templates (proven in §7c.2). The exemplars cover the crashloop-bad-config archetype. The missing pieces are: a real multi-application test bed (SF-13 — the supervisor's "5 services in k8s each related to different apps" shape doesn't exist on the test cluster yet; current bed has only react-springboot-mysql + car-rental), the kubernetes data source (SF-9 plumbing), the deploy-event correlation (SF-11 mechanics), and the app-layer monitoring expansion (SF-10) so the new services emit the right framework-level signal. 13.5 Phase 4 — production hardening (mostly Sprint 5)

  • Server-side filter + sort + pagination on /decisions — the dashboard's column dropdowns currently filter client-side. For larger row counts this needs proper query-param filtering. Adds parameters ?env=&namespace=&service_type=&verdict=&page=&size=.
  • Real-time updates (SSE) — currently 30 s polling. New endpoint GET /api/decisions/stream using Server-Sent Events; design's auto-refresh becomes push-driven.
  • Operator identity — feedback rows currently have no rater field tied to a real user. Add session cookies + a tiny users table for the Tailscale-authenticated operators.
  • Email template overhaul — port the design's EmailDesktop / EmailMobile JSX into the server-side email-rendering path in notifier.py. Same data contract as detail page.
  • Pre-compile React (drop Babel-in-browser) — the v2 dashboard's first paint is ~3 s due to Babel parsing 6 jsx files at runtime. Esbuild pre-compile saves ~2.5 s. Sprint 5 polish.
  • k8s / Rancher MCP (SF-9) — the 6th MCP that gives the LLM deploy-event correlation, pod metadata, namespace ownership. Prerequisite for the dev-deletes-a-letter scenario (§12.5). New service in monitoring-mcp-servers.

13.6 Dependencies + ship order (recommended)

If we ship strictly in dependency order — ~6 weeks total
  1. Phase 2.1 — detail page route + short-ID lookup (~1 day) — Highest visible-progress per hour. Click any v2 row → see the full incident view.
  2. Phase 2.2 — incident entity table + backfill (~1 week) — Schema migration; enables proper same-fingerprint collapsing across views.
  3. Phase 3.A — Anomalies + Stats + KPI (~1 week parallel) — Three pure-read aggregation routes; signals already exist; no new schema.
  4. Phase 3.B — Incidents page (~3 days) — Builds on the incident table from Phase 2.2.
  5. Phase 3.C — Alerts config + Drain3 engine + Integrations (~1.5 weeks parallel) — Three managed-state surfaces; new schema + UI for each. Wire Alerts config into the email gate.
  6. Phase 4 — Filter/sort/pagination + SSE + email template + Rancher MCP (~2 weeks) — Production polish.

Tight coupling worth flagging:

  • Incidents page can't exist before the incident entity table — Phase 3.B depends on Phase 2.2.
  • Services page can't be useful before the Rancher MCP (SF-9) lands — defer Services to Phase 4 unless we accept "Services" = "alerts grouped by affected_service" without pod metadata.
  • Alerts config is the natural home for the SF-1 environment taxonomy decision (dev/int/uat/stg/preprod/prod) — that taxonomy gets locked when the subscriptions schema gets written.
  • Drain3 engine is a Sprint 4 carry (S3-DR-01..03 from §12 Sprint 4 plan); its control surface naturally lives in this sidebar item.

That order gives him three click-through surfaces inside ~2 weeks, with the incident entity backfill happening after he's verified the design shape.
