1. Overview

The CIRES AI triage pipeline is a FastAPI service that consumes Grafana alert webhooks (now via an API Gateway → Lambda router with IP allowlist, since 2026-05-21), enriches each alert with pre-gathered context from three MCP bridges (Prometheus / Loki / Jaeger), runs an LLM (Ollama + qwen2.5:14b-instruct primary / 7b fallback) on a dedicated AWS g5.xlarge GPU host in us-west-2 (A10G, see D24) to produce a root-cause analysis, writes the result to a SQLite history store, and emails escalations. A dashboard at /dashboard renders the decision history.

The core thesis after the 2026-04-24 audit: shrink the LLM's job. LLMs are great at narrative synthesis; mediocre at deduplication; bad at numerical reasoning over ambiguous data. Every module in the repo below exists to take one of those "bad" responsibilities off the LLM's plate and hand it to deterministic code. See the Decisions Log for the individual decisions.

3. Alert lifecycle — end-to-end

An alert enters the system as a Grafana webhook POST. This section traces the full lifecycle, naming every file and function hit. Code references are all in monitoring-triage-service/app/.

3.1 Webhook arrival → main.py:154

Grafana POSTs a GrafanaWebhook to /webhook/grafana. FastAPI deserializes into the Pydantic model defined at models.py:42. A GrafanaWebhook contains alerts: list[GrafanaAlert]; each GrafanaAlert has labels, annotations, values (refId → number), fingerprint, startsAt.

The endpoint returns 202 Accepted immediately and enqueues _pipeline.process_grafana_webhook as a FastAPI BackgroundTasks. Grafana never waits — that's deliberate so it can't time-out on our LLM latency. Also means webhooks during a wedged pipeline silently pile up (the wedge symptom from 2026-04-24 morning).

3.2 Dedup + Layer-2 suppression → pipeline.py:80

First check: fingerprint-window dedup via DedupManager.check() (dedup.py:42). Keyed on Grafana's stable fingerprint, window is settings.dedup_window_seconds (default 600). Second+ fire of the same fingerprint within the window → persist a triage_decision=suppressed_duplicate record linking to the prior RCA and short-circuit. No LLM work.

Second check: Layer-2 pre-LLM suppression (pipeline.py:90 calling _check_suppression()). If the same (alert_name, service) was DISMISSED within settings.triage_history_lookback_minutes, dismiss again without paying Ollama cost. Persists a triage_decision=triage_suppressed record with a one-line reason.

3.3 Context gathering → context.py:89

ContextGatherer.gather(alert) runs three fetches in parallel (asyncio.gather) against the MCP bridges:

CallFunctionReturns
prometheus-mcpcontext.py:164 _fetch_prometheus()Time-series for the rule's PromQL; falls back to alert.annotations.expr or instance-scoped query when primary empty.
loki-mcpcontext.py:218 _fetch_loki()Last settings.loki_log_limit lines for the service. Fallback to ambient (any-service) lines ONLY if labels.signal=="log", because ambient fallback for metric alerts leads to the 50-log-line hallucination (see Decisions Log D1).
jaeger-mcpcontext.py:274 _fetch_jaeger()Last settings.jaeger_trace_limit traces. Skipped entirely for non-traced services (TRACED = {"spring-boot", "kong", "otel-collector"}).

All fetches share a per-alert absolute-time window computed from alert.startsAt so all three pillars cover the same epoch. Returns a GatheredContext (models.py:107) with the three fetch results + loki_is_fallback flag + per-pillar timing metrics. The sources_available counter reflects how many of the three returned something non-empty.

Drain3 templating runs on the Loki lines at drain.annotate_lines() (drain_analyzer.py:91) — returns both the annotated lines ([ANOMALY] / [KNOWN] prefix) and a one-line summary string.

3.4 Metric interpreter → metric_interpreter.py:interpret

Called from the pipeline right before the LLM call. Deterministic math, zero LLM. Inputs: alert.annotations.expr, alert.values, alert.labels. Outputs a MetricFacts dataclass with:

  • observed_value — reduce-step value, picked via pick_primary_value() (llm_client.py:173) which skips the threshold-boolean when present
  • threshold + threshold_direction — parsed from the PromQL expr or rule annotations
  • delta + delta_pct — observed minus threshold, signed
  • unit — detected via regex pattern match against PromQL (_UNIT_PATTERNS list); covers ms, percent, boolean, bytes/sec, seconds-to-zero, ratio
  • deployment_type — from settings.service_deployment_type[alert.service]
  • one_liner — human interpretation string the LLM cites verbatim

MetricFacts.as_prompt_block() (metric_interpreter.py:48) renders the struct as a 5-line block the LLM prompt embeds under "## Pre-computed metric facts (ground truth — cite verbatim)".

3.4b Exemplar injection → exemplars/__init__.py:find_for_alert

Before the LLM call, the prompt builder picks the best-matching exemplar — a curated canonical "good RCA" shape — from app/exemplars/library.yaml and injects it into the prompt as a ## Reference exemplar section. The exemplar gives the LLM a structural template tailored to this alert's archetype on attempt 1 — no agent loop, no extra latency. See D17 in the decisions log for the why; docs/happy-path-scenarios.md is the human-facing reference (eleven archetypes).

Match score = 0.10 (alertname regex base) + 0.40 (service ∈ services) + 0.30 (deployment_type match) + 0.20 (signal match) + 0.10 (severity match); highest wins, ties broken by library order (deterministic). When no archetype matches, the loader returns a generic-sre-shape default with the same structural cues. The closed-loop-feedback-override archetype is gated behind a sentinel regex (^__pipeline_explicit__$) so it is fetched explicitly by id (when Epic 5 US-5.3 ships) rather than auto-matched.

The library is the source of truth in code; the LLM-callable retry path (§3.6 bounded-agency) exposes rca_history.list_exemplars and rca_history.get_exemplar for the rare case where the pre-injected archetype doesn't fit. Both are direct in-process calls (same pattern as rca_history.similar) — no HTTP / MCP roundtrip.

3.5 LLM + response validator → pipeline.py:260

LLMClient.investigate() (llm_client.py:256) builds the prompt via _build_prompt() (llm_client.py:396): system message carries SYSTEM_PROMPT (rules A–J + schema description + 3 few-shot examples + the exemplar-library policy paragraph; rules A and J encode the cause-first, plain-language RCA philosophy formalised in D19); user message carries alert details, MetricFacts.as_prompt_block(), correlated-alerts section, the matched ## Reference exemplar (see §3.4b), pre-gathered context, history.

_call_ollama() (llm_client.py:592) POSTs to /api/chat with temperature=0, num_ctx=16384, and format=_RESPONSE_SCHEMA (the inline JSON-schema dict enforcing the response shape at decode time). Ollama token-counts are exported as Prometheus metrics (triage_llm_token_count{type="prompt"|"completion"}).

Response is parsed into LLMDecision (models.py:70). Immediately after parse, validate() from response_validator.py runs three passes:

  1. Banned-phrase scan on rca + reason (_BANNED_PHRASE_PATTERNS) — catches "insufficient data", "cannot determine", etc. Matched phrases go into report.banned_phrase_hits so a retry can quote them back.
  2. Surface-only RCA scan (added D19, 2026-04-28) — first sentence of the RCA is checked against _SURFACE_ONLY_LEDE_PATTERNS (catches openings like "PromQL `<expr>` reported <value>...", "The PromQL expression...", or raw metric{...}=value); the full prose is checked against _SURFACE_ONLY_HEDGE_PATTERNS (catches "indicates that there are X experiencing Y" tails). Triggers a retry with cause-first feedback, since these patterns mean the model restated the alert rather than naming a cause.
  3. Vague-action scan on suggested_actions — entries starting with check|monitor|investigate|... and lacking a concrete payload (backtick, URL, kubectl/ssh/docker/etc.) are pruned in place.
  4. Architecture-mismatch scan — if deployment_type is docker-vm and an action contains kubectl, that specific action is pruned (with reason arch_mismatch:k8s_command_for_docker-vm_service).
  5. Per-alert hallucination blocklist (added 2026-04-28 PM, F-3 in the RCA quality audit — see private monitoring-audit-results repo) — alert-specific patterns at app/hallucination_blocklist.yaml reject RCAs that cite known scrape-internal or wrong-evidence patterns. Initial entries: HighP95Latency + HighKongP95Latency reject RCAs blaming /actuator/* log frequency (those endpoints are scraped by Prometheus, not user traffic, no causal link). Hits trigger a retry with the alert-specific HINT in the feedback prompt.

Step 6c.5 — recurrence gates (US-5.8, added 2026-04-28 PM). Two gates wrap the LLM call: app/recurrence_gate.py:pre_llm_gate runs as Step 1c (after dedup, before LLM) and skips the LLM for opted-in alerts whose fingerprint has fired N times in the window; post_llm_gate runs after the US-5.3 override gate and force-flips DISMISS to ESCALATE if the LLM has dismissed the same fingerprint M times in the window. Critical-severity alerts bypass via _is_critical defense-in-depth (checks both alert.severity and labels.severity). Per-rule opt-in via the recurrence_gate annotation. See D21.

Step 6d — confidence calibration tie-in (F-4, added 2026-04-28 PM). Pipeline clamps decision.confidence to ≤ 0.4 when the validator caught a surface-only / hedge pattern, when rca_quality is data_starved, or when the first action came from the template fallback (suggested_actions_source == "template"). Doesn't change the verdict, only the trust signal — operator sees "low confidence + actionable" and knows to scrutinise. Live evidence from 2026-04-28 morning: model emitted conf=0.95 on textbook surface-only RCAs.

The validator MUTATES decision.suggested_actions — callers see the cleaned list. Violations are logged but don't block the main flow; they inform the retry path.

3.6 Bounded-agency retry → pipeline.py:305

After LLM + validator, the pipeline classifies RCA quality via _classify_rca_quality() (rca_store.py:43). Gates: actionable ⟶ ship. data_starved ⟶ retry. needs_review ⟶ ship but tag for human follow-up.

On data_starved, if settings.triage_bounded_agency_enabled AND we have >10 s of pipeline budget left, engage bounded agency (see D15 in decisions log):

  1. LLMClient.request_tool_or_decide() — sends a second prompt adding bounded_agency.TOOLS_DESCRIPTION and instructing the model to emit EITHER a tool_request JSON OR a final decision.
  2. parse_tool_request() validates the request against one of four Pydantic schemas: PrometheusQueryArgs, LokiQueryRangeArgs, JaegerGetTracesArgs, RCAHistorySimilarArgs. Unknown tools or malformed args → None → fall through to plain retry.
  3. execute_tool() makes a direct httpx call against the relevant MCP URL (settings.prometheus_mcp_url, etc.).
  4. tool_result_to_prompt_block() formats the result for re-prompting.
  5. LLMClient.investigate() runs again with the tool_result_block appended to user_content. This is the THIRD and FINAL LLM call — bounded by design.

If the model emits a decision directly (skipping tool use) on the agency call, that decision is used. If bounded-agency produces nothing usable, falls back to the plain "don't hedge" anti-hedge retry.

3.7 Action-template fallback → pipeline.py:314

After the final LLM decision (with any retries), if decision.suggested_actions is empty (either the LLM returned none, or the validator pruned them all), action_templates.fill_template() (action_templates.py:67) kicks in:

  1. Loads app/suggested_actions.yaml once (lru_cache'd).
  2. First matching match regex wins; pulls the deployment-type-scoped action list.
  3. Substitutes placeholders: {instance}, {instance_host} (via settings.instance_hosts), {service}, {grafana}, {job}.

Pipeline local variable suggested_actions_source tracks whether the list came from the LLM ("llm") or from the template ("template") — future telemetry can plot the fill-source rate.

3.8 Notify + persist → pipeline.py:420

If decision.decision == ESCALATE: EmailNotifier.send_escalation() (notifier.py) composes the HTML email. Sections in order: meta summary, observed-value lede card, RCA, suggested actions, evidence, model reasoning, drain3 summary, correlated alerts table, top traces, deep link to Grafana. Uses the same _to_local_time() helper (mirrored from main.py:17) to render timestamps in Africa/Casablanca.

Either way, RCAStore.save_decision() (rca_store.py:108) writes an rca_history row. Classifier runs on the record if rca_quality isn't already set. After save, DedupManager.record_first_decision() is called with the new decision id so subsequent duplicates within the window get a link back.

Environment resolution happens just before the record is built, via app.v2_mappings.env_resolver(...) (pipeline.py:953). The resolver walks a precedence chain - per-alert labels.env first, then commonLabels.env / groupLabels.env, then annotations, then namespace-prefix inference (prod-payments -> prod), then the logical-namespace map (rental -> stg, observability -> prod), and finally the service token (rental-backend -> stg). Anything outside the KNOWN_ENVS allowlist (prod / stg / preprod / uat / int / dev) falls through to the next tier, so a typo like prdo cannot leak into the dashboard pill. The resolved value lands in RCARecord.env, the persisted rca_history.env column, the dashboard row, the email subject ([env] [ns] [VERDICT] ...), and the URL filter (?env=prod) - all surfaces read the same persisted value so they cannot disagree. See triage-service.html §5.3 for the full precedence table.

4.7 app/action_templates.py

4.7b app/exemplars/

Curated library of canonical "good RCA" shapes, injected into every LLM prompt as a ## Reference exemplar section. See D17 for the why; eleven archetypes are catalogued covering OOM-loop, upstream-latency attribution, synthetic-blip dismiss, cascade incidents, Drain3 novelty post-deploy, bounded-agency retry resolution, adaptive-threshold no-op, closed-loop feedback override, CrashLoopBackOff, network-firewall attribution, and TLS pre-failure expiry.

  • app/exemplars/library.yaml — source of truth. Each entry: id, archetype, match selectors (alertname regex, services, deployment_types, signal, severity), decision, RCA paragraph, evidence shape, actions shape, lesson, doc_anchor.
  • app/exemplars/__init__.py — loader + matcher. find_for_alert(alertname, service, deployment_type, signal, severity) returns the highest-scoring exemplar (or the generic-sre-shape default if none match). format_for_prompt(exemplar) renders as the markdown block consumed by llm_client._build_prompt. list_all() + get_by_id() serve the bounded-agency tool surface.

The prose version of each archetype lives in monitoring-triage-service/docs/happy-path-scenarios.md at the anchor declared in doc_anchor. Adding a new archetype is a single-file YAML edit + one new prose scenario — the matcher picks it up automatically.

4.8 app/bounded_agency.py

Whitelisted tools with per-tool Pydantic arg schemas:

  • PrometheusQueryArgs(expr) — single instant query
  • LokiQueryRangeArgs(query, lookback_seconds=30–3600)
  • JaegerGetTracesArgs(service, operation?, min_duration_ms, limit=1–20)
  • RCAHistorySimilarArgs(alert_name, affected_service?, days=1–30, limit=1–10)
  • RCAHistoryListExemplarsArgs() — no args; lists all curated archetypes from §4.7b
  • RCAHistoryGetExemplarArgs(exemplar_id) — fetch one archetype by id when the pre-injected one is the wrong fit

TOOLS_DESCRIPTION is the user-facing catalog appended to the agency retry prompt. parse_tool_request() is tolerant — returns None on any parse or validation error so the pipeline falls back gracefully.

4.9 app/dedup.py

DedupManager — fingerprint-keyed, 600 s sliding window. check(fingerprint, status) returns (is_dup, first_decision_id). record_first_decision() is called by the pipeline post-save so second fires get a real link. _cleanup() drops expired entries on every check.

4.10 app/drain_analyzer.py — per-service template miners (US-5.1 Phase A, 2026-04-28)

Wraps drain3.TemplateMiner with a per-service router. Each service gets its own TemplateMiner instance + FilePersistence at {drain3_state_dir}/{service}.bin, so spring-boot's templates don't blend with kong's. Key methods:

  • analyze(log_line, service="_unknown") — routes to the per-service miner (lazily creates one if not yet seen). Counters tracked per-service in _lines_per_service + _anomalies_per_service.
  • annotate_lines(lines, service="_unknown") — batch-mode prefix for the LLM prompt. All lines in a batch attribute to one service.
  • get_stats(service=None) — without arg returns aggregate (across all services) plus per-service breakdown; with arg returns just that service's miner stats. Backs /drain3/stats?service=.
  • _get_or_create_miner(service) — lazy per-service instantiation.
  • _service_from_stream_labels(labels) — extracts the service name from a Loki stream's label dict (tries service_name → service → k8s_app → app_kubernetes_io_name → app; falls back to _unknown; sanitizes for filename).
  • seed_from_loki() + _ingest_loop() — both now group lines by service before ingesting, so polled Loki batches respect per-service template trees.
  • maybe_fire_alert(batch_total, anomalous, new_templates) — P1.7 self-bridge. Posts to settings.drain3_self_webhook_url when rate crosses threshold + cooldown elapsed. Carries actual new template strings (F-1 fix 2026-04-28).

Migration: pre-Phase-A drain3_state.bin auto-renames to _unknown.bin on first start so prior cluster history isn't lost (becomes the safe-default bucket for unlabelled traffic).

Thread safety: every read/write of self._miners, _lines_per_service, _anomalies_per_service goes through self._lock (threading.Lock, not async) because the offloaded work runs in the thread pool.

4.11 app/startup_backfill.py

run_startup_backfill(last_seen_iso) — queries Grafana's /api/annotations for firings during the downtime window, dedupes by (alertname, service), filters synthetic names (HourlyDemoTest_*, Verify*, LaptopSmoke_*), POSTs each as a webhook to http://localhost:8090/webhook/grafana.

Disabled when settings.grafana_api_password == "" (safe-by-default). Gates: startup_backfill_threshold_minutes (only run if gap exceeds it), startup_backfill_max_gap_hours (cap replay depth).

4.12 app/rca_store.py

RCAStore — aiosqlite wrapper. Key methods:

  • init_db() — CREATE TABLE + additive column migration (PRAGMA table_info + ALTER TABLE ADD COLUMN per missing column). Idempotent.
  • save_decision(record) — insert + commit. Classifier runs if rca_quality is None.
  • get_decisions(limit, alert_name) — backs the /decisions + dashboard endpoints.
  • get_recent_decision_for_alert() — Layer-2 suppression input.
  • get_alert_frequency(days=7) — N-fire count for a rule.
  • get_recent_data_starved_rcas() — examples to quote back in anti-hedge retry.
  • get_correlated_alerts(fingerprint, at, window_minutes=5) — neighbors for P1.4.

_classify_rca_quality(rca, reason, actions, evidence) returns needs_review when both actions and evidence are empty, else data_starved on banned phrases, else actionable.

4.13 app/notifier.py

EmailNotifier. SMTP via aiosmtplib with STARTTLS. Multiple _-prefixed helpers compose the HTML: _observed_value_block, _top_traces_rows, _correlated_alerts_block, _deep_links. Subject format: "[ALERT] {severity}: {alertname} — {service}".

9. Gotchas (hard-earned)

Ollama defaults are WRONG for triage

temperature=0.8 default means non-deterministic output. Fixed in _call_ollama() by passing explicit "options": {"temperature": 0, "num_ctx": 16384}.

Structured outputs ≠ JSON mode

format="json" guarantees valid JSON but NOT schema compliance. Use format=<schema dict> on Ollama ≥0.5 for decode-time enforcement. The _parse_response retry path becomes dead code once this is on.

Grafana refId order ≠ value order

A 3-step rule emits A=query, B=reduce, C=threshold. C is a boolean (0 or 1), NOT the observed value. Always use pick_primary_value() which skips the threshold step.

Drain3 is sync; offload or the event loop stalls

TemplateMiner is a sync library. Calling it from the event loop with large batches blocks everything (2026-04-22 bug where /drain3/stats hung for 15 s). Offload via asyncio.to_thread(); guard shared state with threading.Lock.

aiosqlite single-connection serialization

If the pipeline is writing + reading concurrently, long-running writes can block /decisions reads on the same connection. Saw this during 2026-04-24 morning when 5 concurrent LLM pipelines all tried to save. Consider WAL mode + per-task connection for Sprint 3.

Deployment-type map is mandatory

If a service isn't in settings.service_deployment_type, it resolves to "unknown" and the template + validator skip architecture-specific logic. Add every new service you introduce.

Env changes require a compose redeploy

Image rolls are operator-triggered via roles/triage_laptop (no Watchtower or auto-pull daemon — audit I-3, 2026-04-28). Changing env in docker-compose.yml or .env requires a full docker compose up -d from ~/cires-ai/ on the laptop, or rerunning ansible-playbook playbooks/laptop.yml from claude-controller.

10. Future perspectives

Near-term (Sprint 3)

  • P2 evaluation dashboard — surfaces rca_quality distribution, confidence histogram, template-fill-rate, banned-phrase-hit rate, arch-mismatch-reject rate, dedup-ratio. The feedback loop that turns quality from vibes into a number.
  • Golden-test set in CI — 20 synthetic webhooks + expected-RCA-contains assertions running in the triage-service build workflow. Makes regressions loud before they ship.
  • Widening dataset — add a second k3s workload, re-run the golden set. Validates that the pipeline generalizes beyond the original 18 rules.
  • Traces in drain3 — extend drain3 from logs to (operation, span.kind, duration_bucket) tuples. A latency anomaly at a specific span boundary is invisible to log templating; this closes that gap.
  • Qwen Coder benchmark — swap the model for qwen2.5-coder:7b on the golden set, compare accuracy + latency. Coder variants are stronger at structured output.

Medium-term

  • Cloud LLM fallback for low-confidence cases — Claude Haiku via Anthropic API, or qwen2.5:32b via a hosted endpoint. Only worth pursuing after the evaluation dashboard shows the 7B ceiling is the bottleneck (i.e. actionable rate doesn't improve with prompt changes).
  • Vector retrieval of past RCAs for dynamic few-shot. Complements the 3 hand-picked examples in SYSTEM_PROMPT — would fetch 2–3 similar past RCAs per alert based on embedding similarity.
  • Webhook auth — shared-secret header check on /webhook/grafana. Harden before any external demo.
  • S3 RCA history backup — nightly aws s3 cp from the laptop so the SQLite isn't the only copy.

Strategic

  • Treat the LLM as replaceable. The deterministic layers (metric_interpreter, response_validator, action_templates, bounded_agency) are the durable value. Swap qwen2.5:7b for Llama 4, Claude, or anything else with one env var change.
  • Measure what the LLM uniquely contributes. If suggested_actions_source="template" rate hits 90%+, the LLM isn't earning its GPU time. Ramp the template fraction up consciously; turn prompts into richer context → narrative.
  • Graduate from single-instance to multi-workload. Everything in this repo is written for the 7-service CIRES demo. Widen to N-service requires rethinking the suggested_actions template match order + the service_deployment_type map → likely a separate config source of truth.
