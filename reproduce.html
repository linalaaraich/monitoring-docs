Reproduce the stack from zero

What to do when the controller's gone, the EC2 instances are terminated, and all you have is the GitHub org + a laptop with docker. End state: the full CIRES observability platform running end-to-end, reachable over tailnet, with an AI RCA pipeline responding to alerts.

Cold-start walkthrough (end-to-end)

0Prereqs on the machine that'll drive the setup
  • AWS CLI authenticated (aws sts get-caller-identity must work) against an account with enough quota: 2 vCPU Standard on-demand minimum (4+ preferred), G family optional.
  • terraform ≥ 1.5, ansible-core ≥ 2.14, docker (for compose).
  • SSH key pair at ~/.ssh/ansible_key + pub variant at ~/.ssh/ansible_key.pub (or matching paths in terraform.tfvars).
  • Tailscale account (free) — create one at login.tailscale.com. Generate an ephemeral+reusable auth key at Settings → Keys; 24 h TTL is sufficient for setup.
1Clone the six repos 
mkdir -p ~/cires && cd ~/cires
for r in provisioning-monitoring-infra monitoring-project monitoring-triage-service \
         monitoring-mcp-servers monitoring-gpu-migration \
         monitoring-load-tests monitoring-chaos-tests; do
  git clone https://github.com/linalaaraich/$r.git
done
2Provision AWS via Terraform, with Tailscale install baked into user_data. 
cd ~/cires/provisioning-monitoring-infra
cp terraform.tfvars.example terraform.tfvars   # fill in db_password, ubuntu_ami_id
export TF_VAR_tailscale_auth_key="tskey-auth-xxxxx"   # enables auto-join on boot
terraform init
terraform apply                                 # ~8 min; creates 2 EC2 + RDS + EIPs + SGs

When apply finishes, every new EC2 instance has Tailscale running and has joined the tailnet as ${project_name}-monitoring / -k3s / -gpu. Verify with tailscale status from the local machine (which also needs to be on the tailnet — run sudo tailscale up --authkey=$TF_VAR_tailscale_auth_key if not already).

3Configure monitoring via ansible, routing over the tailnet. 
cd ~/cires/monitoring-project
export TAILSCALE_AUTH_KEY="$TF_VAR_tailscale_auth_key"
ansible-playbook -i inventory/tailnet.yml playbooks/tailscale.yml       # idempotent check
ansible-playbook -i inventory/tailnet.yml playbooks/site.yml            # full config

After ~12 min you should be able to hit Grafana at http://observability-rca-monitoring:3000 (over tailnet) with admin/admin.

4Stand up the AI stack on the laptop, pulling pre-built images from GHCR. 
# On the laptop (WSL2 / Ubuntu):
sudo tailscale up --authkey=$TAILSCALE_AUTH_KEY --hostname=adolin-wsl --accept-dns
mkdir -p ~/cires-ai && cd ~/cires-ai
curl -O https://raw.githubusercontent.com/linalaaraich/monitoring-gpu-migration/main/compose/docker-compose.yml
curl -O https://raw.githubusercontent.com/linalaaraich/monitoring-gpu-migration/main/compose/drain3.ini  # if present
curl -o .env https://raw.githubusercontent.com/linalaaraich/monitoring-gpu-migration/main/laptop/.env.laptop
# edit .env: set MONITORING_VM_IP=100.74.21.104 (observability-rca-monitoring's tailnet IP)
# and fill in SMTP_* if you want escalation emails.
docker compose pull        # pulls triage + 5 MCPs + Ollama from GHCR + Docker Hub
docker compose up -d       # brings up the whole AI stack
docker compose logs -f triage-service | head -30  # watch for "Triage service started"

From now on, Watchtower (also in the compose) auto-updates labeled containers within ~60 s of a new GHCR push — no more manual docker compose pull.

5Smoke-test the pipeline. 
# From the controller or any tailnet peer:
curl -s http://adolin-wsl:8090/health                   # should return {"status":"healthy",...}
curl -s http://adolin-wsl:8090/drain3/stats | jq        # should show clusters + lines processed

# Fire a load-test scenario from the monitoring VM (low-latency path):
cd ~/cires/monitoring-load-tests
cp .env.example .env    # set KONG_URL=http://10.0.1.194:30080 (k3s private IP)
./scenarios/02-latency-spike.sh                         # ~4 min — should trigger MediumCpuUsage

# Watch /decisions populate:
curl -s http://adolin-wsl:8090/decisions?limit=3 | jq

Caveat

The pinned :main strategy depends on images staying available in GHCR. If a repo is deleted or you rotate organizations, the exact image is gone. For absolute long-term archival, mirror the GHCR images to S3 as OCI archives — not done yet; noted on the Sprint 3 backlog.

What to do when something breaks

  • AWS apply fails on quota — set enable_k3s = false or enable_gpu = false in terraform.tfvars and provision monitoring VM first; request quota increase; re-apply with the flag back on.
  • Tailscale nodes don't see each other — check MagicDNS is enabled at login.tailscale.com/admin/dns. Rejoin a node with sudo tailscale up --accept-dns=true.
  • Grafana links in emails point at localhost — GF_SERVER_ROOT_URL not set. Re-run ansible with the updated inventory/group_vars/monitoring.yml:grafana_external_url.
  • Triage RCAs say "insufficient data" — the rca_quality classifier + retry loop should kill this pattern. If it persists, check the alert rule has a service label set (see Triage service docs §5.x).
  • Watchtower won't update the laptop — the GHCR package may be private. Go to your package settings and flip visibility to public, OR configure Watchtower with a GHCR pull secret (add DOCKER_CONFIG volume mount).
