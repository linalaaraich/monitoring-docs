Why this log exists

When someone asks "why did you build it that way?" six months from now, the commit messages will tell them WHAT changed but not WHY. This page is the durable narrative: every time the team said "that's broken, fix it," we write down the broken thing, what we thought about, what we picked, and how we know it worked. If a decision gets revisited, we update the entry and note the supersession. Nothing here is an opinion piece — every decision references a file, a commit, or a dashboard observation.

Format
Each decision has four fields: Problem (what was broken), Reasoning (what we considered and why), Solution (what shipped), Evaluation (how we know it worked, or why we're still waiting to know). Status tag in the top-right: ✅ fixed + verified, ⚠️ partial, ⏳ pending evaluation.

D1 · LLM hedging with "insufficient data"

✅ Fixed + verified Identified 2026-04-23 evening

The LLM kept writing "insufficient data" as a standalone RCA conclusion.

Problem

Multiple rows on the triage dashboard showed rca_report = "Insufficient metrics data within the alert time window" as the entire root-cause analysis. The alert itself always carried signal — a PromQL expression and a current observed value — but the model was ignoring that and reporting the MCP pillar quality instead of using the available data to reason.

Reasoning

Root cause was a weak prompt combined with a small model (qwen2.5:7b). The prompt had 6 rules but rule B (never write "insufficient data" as a standalone conclusion) was phrased as a rule among many, not as an invariant the model should treat as non-negotiable. qwen2.5:7b doesn't reliably prioritize rule hierarchies inside verbose prompts. Options considered: (1) bigger model (blocked: GPU quota = 0 at the time), (2) stricter prompt (won't stick at 7B), (3) programmatic validator that re-prompts when banned phrases appear.

Solution

Three-layer defense:

  1. Prompt still has rule B (explicit forbidden phrase) — minimum bar.
  2. app/rca_store._classify_rca_quality() tags hedged RCAs as data_starved using regex match on the RCA prose.
  3. app/response_validator.py (see D15) scans for banned phrases and requests a retry when hit. The retry in turn uses bounded-agency (D15) to let the model request one more piece of evidence rather than re-attempt the same hedge.
Evaluation

Verified via synthetic probe P0FixVerification_1035: produced a clean RCA without any banned phrase, confidence=0.70, quality=actionable. Ongoing measurement: the evaluation dashboard (P2) will track banned-phrase-hit rate as a running metric.

D2 · Empty suggested_actions on most RCAs

✅ Fixed + verified Identified 2026-04-24 audit

The LLM emitted suggested_actions = [] on nearly every row.

Problem

On the 2026-04-23 dashboard, only 1 of 15 decisions (TargetDown) had non-empty suggested_actions. Rule E of the prompt told the LLM "empty list is better than vague advice" AND gave BAD/GOOD examples — and qwen2.5:7b was reading "empty is better" as the default and not trying. Each dashboard row that shipped with empty actions was effectively useless to the operator: they still had to think about the alert from scratch.

Reasoning

You cannot prompt a 7B model out of this — rule conflicts at that scale always lean toward the easier path. The real insight: SRE remediation for infrastructure alerts is highly templated. For CPU pressure, you always want kubectl top nodes, top -b -n 1, and a PromQL verification query. The variation between alerts is the instance, not the set of commands. Let the template carry the shape, let the LLM fill placeholders.

Options: (a) force the LLM via validator rejection (one extra call per fire, fragile), (b) static template-only (zero LLM contribution), (c) template as fallback only when LLM returns empty. Chose (c) — the LLM can still contribute context-aware actions, but the operator never gets a dashboard row with empty actions.

Solution

New file app/suggested_actions.yaml holds templates keyed by alertname regex, branched by deployment_type (see D7). Pipeline in app/pipeline.py calls app.action_templates.fill_template() when decision.suggested_actions is empty after the LLM + validator pass. Placeholders like {instance_host} resolve via settings.instance_hosts.

Evaluation

Source tracked via the suggested_actions_source local in the pipeline (llm vs template). Future: evaluation dashboard will plot template-fill-rate as a quality metric — a high rate means the LLM isn't contributing enough and the prompt needs work; low rate means the LLM is reliably producing concrete actions on its own.

D3 · Observed value picked from the wrong refId

✅ Fixed + verified Identified 2026-04-24 audit

TargetDown dashboard row showed OBSERVED VALUE 1 (refId=C) [B=0] and the LLM wrote "target is UP" for an alert firing on up==0.

Problem

Grafana's standard 3-step alert rule pipeline is A=query → B=reduce → C=threshold. C returns a boolean (0 or 1) — did the condition match — not a metric value. Our picker sorted refIds alphabetically and chose the last one (C) as "primary observed value," which always gave the LLM a 0 or 1 instead of the real metric. For TargetDown that meant the RCA was reasoning from "1 = the condition matched" but phrasing it as "the observed up value is 1, so target is UP."

Reasoning

Heuristic: if the highest-ref-id value is exactly 0 or 1 AND there are other entries, it's the threshold step; prefer the one below (the reduce). For single-step rules, the only entry IS the observed value. For already-correct multi-step rules that don't end in a boolean (rare), the last entry is still correct. Covers the three cases we see in practice with no schema introspection needed.

Solution

app.llm_client.pick_primary_value() — one function, used in three places (_format_observed_value in the same file, _observed_value_block in notifier.py, record.observed_value construction in pipeline.py).

Evaluation

Verified via synthetic TargetDown webhook with values={"A":0,"B":0,"C":1}: dashboard shows observed_value="0 (refId=B) [A=0, C=1]" — the metric value is the headline and the boolean is context. LLM correctly reasoned about the target being down.

D4 · llm_confidence never persisted

✅ Fixed + verified Identified 2026-04-24 audit

Every dashboard row showed llm_confidence = —.

Problem

app/pipeline.py:330 was hardcoded llm_confidence=None when building the RCARecord. The LLM was emitting a confidence float in its JSON response (validated by Pydantic), but the pipeline was throwing it away before persisting. A bug that never surfaced until the audit specifically looked for why does every row say "—"?

Solution

One-line fix: 

llm_confidence = f"{decision.confidence:.2f}" if decision.confidence is not None else None
Evaluation

Synthetic probe confirmed: new rows show e.g. conf=0.70 in the dashboard. Old rows (pre-fix) remain — because we deliberately didn't back-fill history.

D5 · rca_quality lied when actions+evidence empty

✅ Fixed + verified Identified 2026-04-24 audit

Rows with empty actions + empty evidence were tagged quality=actionable.

Problem

The classifier ran regex-only on RCA prose. A confidently-phrased but artifact-free RCA ("CPU usage has reached 100%") would pass the regex — no hedge words — and get tagged actionable. But with zero concrete actions and zero evidence, the operator had nothing to do. The tag was misleading.

Solution

_classify_rca_quality() now takes suggested_actions and evidence. If BOTH are empty regardless of RCA prose → tag needs_review. Accepts either raw Python lists (from pipeline) or JSON-serialized strings (from the DB classifier path).

Evaluation

Ongoing. The P0FixVerification_1035 probe landed quality=actionable (both fields populated) — the positive path works. Negative path (empty fields → needs_review) not yet observed organically but codepath is tested.

D6 · Overnight email incident — rogue k3s AI stack

✅ Root-caused + stopped 2026-04-23 → 2026-04-24 overnight

Lina woke up to hourly triage-styled emails through the night — laptop was closed, dashboard was empty of those rows.

Problem

Emails arrived hourly: [ALERT] CRITICAL: HourlyDemoTest_02 — spring-boot and variants. Formatted exactly like real triage emails — observed value, RCA, suggested actions — but ZERO of them appeared on the laptop dashboard. And the laptop was closed overnight.

Reasoning

Three theories in order of probability: (a) laptop didn't actually sleep — Docker + Tailscale still running through lid-close. (b) Grafana's gmail-smtp contact point was bypassing triage and emailing directly. (c) A second triage instance was running somewhere.

Evidence from probing: laptop WSL2 was active (Tailscale showed live tx/rx), but laptop triage uptime was 71 minutes at 09:40 UTC — it had been DOWN for the 8 hours preceding. So NOT (a). Grafana's live config showed gmail-smtp was provisioned but NOT actually referenced in the routing policy — so NOT (b). Which left (c): find the second instance.

SSH to the k3s EC2 node revealed a full ai namespace with ai-stack-triage (34h uptime), ai-stack-ollama (44h), all 5 MCPs, plus 5 ImagePullBackOff ghost pods from a failed redeploy. The k3s triage was supposed to be decommissioned on 2026-04-23 when AI migrated to the laptop — it wasn't. And inside that triage pod, an hourly synthetic-test cron had been firing HourlyDemoTest_HH webhooks to its own localhost:8090/webhook/grafana. Those got processed by the in-cluster triage, emailed out (SMTP creds were still wired), and persisted to the cluster's SQLite. The laptop dashboard read from the laptop's SQLite — it never saw any of this.

Solution

Three actions:

  1. kubectl delete namespace ai on the k3s node — 12 pods + 7 services + 7 deployments gone. Rogue cron dies with them.
  2. Remove gmail-smtp contact point from monitoring-project/roles/grafana/templates/contactpoints.yml.j2 and add deleteContactPoints directive so Grafana tears it down on provisioning reload. Ship via Ansible + container restart. Triage becomes the sole notifier — commit 8860e6c.
  3. Weekly /schedule agent (see below) that diffs kubectl get namespaces against a declared allowlist and opens a GitHub issue on drift. Would have caught this 46 hours earlier.
Evaluation

Post-fix probe of kubectl get pods -A on the k3s node shows only the expected namespaces (kube-system, default, app, frontend, network, observability). Grafana's live API confirms contact-points now has only triage-webhook. The weekly namespace audit is in Sprint 3's backlog as P1.5 / P1.8 — scheduled to catch any future drift within 7 days of occurrence.

D7 · Deployment-type mismatch (kubectl for Grafana)

✅ Framework shipped · ⏳ evaluation pending Identified 2026-04-24 during plan review

The LLM kept suggesting kubectl get pods for services that run in docker-compose on a plain VM.

Problem

Classic example: service=monitoring actually means Grafana, which runs via docker-compose on observability-rca-monitoring — not a k3s workload. The LLM generalized from "service" → "kubectl" and handed operators commands that would return nothing. The RCA body was otherwise fine; the suggested actions were architecturally wrong.

Reasoning

The LLM doesn't know the deployment topology. It can't — the MCPs expose metrics/logs/traces, but not "spring-boot is in k3s, grafana is in docker-compose, node-exporter is a systemd service." We need to tell the model, OR constrain its output so it physically can't emit mismatched commands. We do both.

Solution

Three-layer defense:

  1. settings.service_deployment_type in app/config.py — explicit map from service label to one of {k8s, docker-vm, systemd, external, unknown}.
  2. app.metric_interpreter.interpret() emits the deployment type on every MetricFacts. The LLM prompt includes it inline next to the service label, and prompt rule G explicitly forbids mixing command families.
  3. app.response_validator.validate() runs after the LLM and rejects any suggested action whose command family doesn't match the service's deployment type — e.g. kubectl ... in a docker-vm RCA gets pruned, with a reason string the retry prompt quotes back.

And the D2 templates branch on deployment type — so the template fallback is also architecture-aware.

Evaluation

The validator's arch_mismatch reject counter will be plotted in the Sprint 3 evaluation dashboard. A rising rate means the LLM is still guessing deployment types — prompt/training needs work. A falling rate means the explicit inline hint is working.

D8 · Drain3 anomalies never fired into triage

✅ Bridge shipped · ⏳ evaluation pending Identified 2026-04-24 plan review

Dashboard showed "98 anomalies flagged" but zero decisions had Drain3 as the alert source.

Problem

/webhook/drain3 endpoint existed in app/main.py. app/pipeline.py::process_drain3_webhook() existed and synthesized a Drain3AnomalyDetected GrafanaAlert. The background ingest loop in app/drain_analyzer.py was detecting anomalies and incrementing _total_anomalies. But nothing connected those three facts — the anomaly count just sat on the dashboard as a number, never converted into an alert.

Reasoning

Keep the trigger local to DrainAnalyzer — the thing measuring anomalies is the thing that should decide when to fire. A threshold-based trigger (rate over a sliding window) is simpler than integrating with an external alert engine. Cooldown (drain3_alert_cooldown_seconds) prevents thrashing on persistent anomaly spikes.

Solution

New method DrainAnalyzer.maybe_fire_alert() called from the background ingest loop after every batch. Logic: if len(anomalous)/batch_total >= drain3_alert_rate_threshold AND batch_total >= drain3_alert_min_lines AND past cooldown → httpx.AsyncClient.post to settings.drain3_self_webhook_url (default http://localhost:8090/webhook/drain3). The endpoint synthesizes a GrafanaAlert and runs the full pipeline. Drain3 becomes a visible alert source on the dashboard.

Evaluation

Defaults: drain3_alert_rate_threshold=0.10, drain3_alert_min_lines=100, drain3_alert_cooldown_seconds=600. Tune after first week of production — rate is service-dependent. Watch for "alert storms" if threshold is too low; watch for missed real anomalies if too high.

D9 · Flapping alerts consumed N× LLM calls

✅ Fixed Identified 2026-04-24 audit

The 2026-04-23 dashboard showed MediumCpuUsage firing 5 times in 40 minutes, each generating a fresh LLM pipeline run.

Problem

The existing dedup used (alertname, instance) as its key with a 300s window. But (a) some alerts had instance=None so the key was ambiguous, and (b) 300s was too short for alerts with 5-minute Grafana group_interval — every re-fire fell outside the window. Each fire cost ~50-70s of Ollama inference. Five fires on the same symptom burned 4-6 minutes of GPU time for no new information.

Solution

Re-key dedup on Grafana's stable fingerprint (hash over labels). Window widened to 600s. On second+ fire: persist a short-path triage_decision=suppressed_duplicate record with action_taken=see_previous_rca:{prior_id}, no LLM call. Dashboard shows the flap as a compact row pointing at the prior RCA — operator still sees it happened, but without the gap of a silent drop.

Implementation: app/dedup.py DedupManager.check(fingerprint, status) returns (is_dup, first_decision_id). Pipeline calls dedup.record_first_decision() after the initial RCA persists so subsequent dups link correctly.

Evaluation

Metric: alerts_deduplicated counter was already exported. Add a ratio panel in the evaluation dashboard: deduplicated / (deduplicated + processed). A rising ratio means we're saving more LLM work; watch for it breaking 40-50% on chatty rules.

D10 · Correlated alerts rendered but not prompted

✅ Fixed Identified 2026-04-24 plan review

We pulled neighboring alerts into the email and dashboard but never asked the LLM to reason about them.

Problem

app/rca_store.get_correlated_alerts() returned ±5-min neighbors; we rendered them in _correlated_alerts_block and the dashboard panel. But in the LLM prompt they were buried inside history_context — no specific rule, no explicit question about causation. So the LLM usually just ignored them.

Solution

Move correlation out of history_context into its own prompt section ("## Neighboring alerts (±5 min of this one)") with rule H in SYSTEM_PROMPT: "if correlation is present, your RCA MUST explain whether (a) X caused Y, (b) they share common cause Z, or (c) they are unrelated — explicitly stated, not silently." Pipeline passes correlated list to LLMClient.investigate() as a dedicated kwarg, rendered by _build_prompt.

Evaluation

Qualitative for now. Inspect RCA text on next multi-alert storm — does it name the relationship, or does it still ignore? If rule H compliance is under ~60%, add to response validator as a post-hoc check ("rca references at least one correlated alertname").

D11 · Ollama non-determinism (temperature 0.8 default)

✅ Fixed Identified 2026-04-24 plan review

Same alert, two successive fires, two different verdicts.

Problem

Ollama's default temperature=0.8 is tuned for creative chat. For alert triage it means the same inputs can produce noticeably different verdicts — the RCA text may diverge, severity can shift between warning/critical, confidence drifts. Reproducibility is at stake.

Solution

Add "options": {"temperature": 0, "num_ctx": 16384} to the /api/chat payload in LLMClient._call_ollama(). num_ctx caps the context window explicitly at 16K — qwen2.5:7b advertises 32K but effective quality degrades past ~16K, and 500 Loki lines + traces can push us close.

Evaluation

Post-deploy, fire the same synthetic webhook twice within a minute and diff the two decisions. If they match byte-for-byte (excluding timestamps), determinism holds. This becomes a golden-test assertion in Sprint 3's P2 test suite.

D12 · Structured outputs vs JSON mode

✅ Fixed Identified 2026-04-24 plan review

JSON mode produces valid JSON but not necessarily schema-conformant; we had a parse-retry path to catch the gap.

Problem

Ollama's format: "json" guarantees valid JSON. It does NOT guarantee the JSON matches our expected schema. Missing fields, unexpected fields, wrong types — all possible. _parse_response() handled this with a retry prompt that quoted the Pydantic error back. Adds 25-70s latency when it triggers.

Solution

Ollama ≥0.5 accepts format: <JSON schema dict> and enforces at decode time — invalid JSON is impossible, not just unlikely. LLMClient._RESPONSE_SCHEMA hand-written (kept inline so there are no $defs/$refs Ollama might mis-resolve). Parse-retry path removed from the happy flow.

Evaluation

Parse-failure counter (triage_fallback_total{reason="parse_failure"}) should be zero in steady state post-change. If it's not, Ollama ≤0.4 is running somewhere — check image tags.

D13 · Pre-LLM metric interpreter (shrink the LLM's job)

✅ Shipped · ⏳ evaluation pending Identified 2026-04-24 audit

The LLM was being asked to do four jobs at once: interpret metrics, write narrative, recommend actions, filter noise. It failed the numerical-reasoning job the most.

Problem

Audit bugs #5, #6, #9 all traced to the same root: the LLM was being trusted with numerical interpretation (reading refId, computing deltas, attaching units). That's exactly what 7B models are worst at. It hallucinated units, conflated log-line-counts with metric values, contradicted itself within the same sentence ("observed 0" → "spike to 100%").

Reasoning

Thesis: LLMs are excellent at synthesis and narrative, mediocre at deduplication, and bad at numerical reasoning. The cheapest architectural win is to remove numerical reasoning from the LLM's job. Do the math deterministically; feed the LLM a pre-computed one-liner as authority; the LLM's remaining job is narrative and action suggestion, which it can actually do.

Solution

New module app/metric_interpreter.py. Input: (alert.annotations.expr, alert.values, alert.labels). Output: a MetricFacts dataclass with observed_value, threshold, delta, unit, deployment_type, and a one_liner like "CPU busy = 94.4% — 9.4pp above 80% threshold (MediumCpuUsage, service=k3s-node)".

Unit detection is pattern-based on PromQL (_UNIT_PATTERNS list): histogram_quantile(...) * 1000 → ms, 100 - (...idle...) → percent, up == 0 → boolean, etc. Covers all 18 current rules; falls through to "unit unknown" which the LLM then reasons around.

The LLM prompt gets the one_liner as authoritative ground truth and is instructed to cite verbatim, not re-derive. The few-shot examples in SYSTEM_PROMPT show this shape end-to-end.

Evaluation

Qualitative first: read post-deploy RCAs and check they match the one_liner instead of re-doing math. Quantitative later: parse decision.rca for numeric claims, compare to MetricFacts.observed_value, track drift rate.

D14 · Downtime backfill from Grafana annotations

✅ Shipped · ⏳ evaluation pending Identified 2026-04-24 post-incident

When triage is down, Grafana's webhook retries fail and the alerts are lost — there's no durable replay.

Problem

D6 exposed that we have zero resilience to triage downtime. Grafana fires a webhook, it fails, Grafana gives up, the alert lives only in Grafana's annotation store. The operator has no way to know what was missed without manually querying the annotation API.

Reasoning

Two options: (a) persistent webhook queue inside triage — but triage is WHAT goes down, so its queue is also gone. (b) Treat Grafana's annotation API as the durable source of truth (which it already is). On startup, compute the gap between now and last RCA, query annotations for that window, replay each unique firing through the normal pipeline. Elegant — no new infrastructure.

Solution

New module app/startup_backfill.py. Called from the lifespan hook as a fire-and-forget task (so service readiness isn't gated on Grafana's response time). Config gates: disabled when GRAFANA_API_PASSWORD is unset so it's safe-by-default; only triggers when the gap exceeds startup_backfill_threshold_minutes (default 15); capped at startup_backfill_max_gap_hours (default 24) so a week-old restart doesn't replay a week of alerts.

Filters: skips synthetic test alerts (HourlyDemoTest_*, Verify*, LaptopSmoke_*). Dedupes by (alertname, service) so a rule that fired 20 times during the gap produces one replay, not 20.

Evaluation

Verified on a zero-length gap (no missed alerts, module logged "0 annotations in window" and exited cleanly). A real downtime test — stop triage for 30+ minutes while something fires — is on the deferred list.

D15 · Bounded-agency retry (one MCP call, not a chain)

✅ Shipped · ⏳ evaluation pending Identified 2026-04-24 plan review

The old data-starved retry just said "don't hedge" — the model produced the same hedge again, this time with attitude.

Problem

When the first LLM pass was tagged data_starved, the old flow appended a scolding to the retry prompt. Same context, same model, same temperature — same answer. Retry rate of actionable <- data_starved was low.

Reasoning

Options were (a) full agent framework (tool use, chain-of-thought, multiple loops) — too much surface area, expensive, non-deterministic, overkill for this problem, (b) skip retry, just ship data_starved rows as-is — gives up on the hedge class, and (c) one extra call with one whitelisted tool, Pydantic-validated args, bounded latency. (c) is the minimum agency that pays off: if the model's problem is "not enough evidence," giving it the ability to fetch one more piece of evidence is directly the fix.

Solution

New module app/bounded_agency.py. Four whitelisted tools: prometheus.query, loki.query_range, jaeger.get_traces, rca_history.similar. Each has a Pydantic schema class (PrometheusQueryArgs, LokiQueryRangeArgs, etc.) that validates the LLM's requested args and rejects extras.

Flow when quality=data_starved on first pass:

  1. LLMClient.request_tool_or_decide() — LLM can emit {"tool_request": {"name": ..., "args": {...}}} OR a final decision.
  2. If tool_request: execute_tool() runs the MCP call via direct httpx → re-prompt via investigate() with the tool result appended as additional evidence.
  3. If decision: try to parse as LLMDecision, use directly.
  4. Fall back to the old plain anti-hedge retry if the agency path fails.

Properties: exactly one extra call max (bounded cost/latency), reproducible at temperature=0, uses existing MCPs, no new infrastructure.

Evaluation

Logs emit used_agency=True/False per retry so we can track adoption rate. Target: after ~20 data-starved events, at least 50% should convert to actionable via bounded agency. Under that, the tool whitelist is wrong — add or remove tools based on which requests the model makes most.

What's next (perspectives)

This log is a live artifact — future sprints will add entries. Near-term expected additions:

  • Traces in drain3 — currently drain3 only templates logs. Applying the same template-learning to traces (operation name + span.kind + duration bucket) would expose latency anomalies invisible to log templating. Design work pending.
  • Widening the dataset — add a second k3s workload and re-run the golden-test set. Target: 10 consecutive fires with quality=actionable before declaring the pipeline production-ready.
  • Qwen Coder vs Instruct benchmark — Coder variants are reportedly stronger at structured output. Need a golden set first (P2) before the swap is measurable.
  • Cloud LLM fallback — only worth pursuing if evaluation dashboards prove the 7B ceiling is the bottleneck. Likely Sprint 4+.
