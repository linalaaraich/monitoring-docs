CIRES Technologies · AI Observability & LLM-Triage Platform

Solution Architecture & Design Choices

What the platform is, how it is built, and why each major design decision was made — for review ahead of the production deployment.

Prepared for the supervisor · 2026-06-12 · companion to the Resource & Dependency Specification and Architecture Deep-Dive (file-level detail).

The solution in one paragraph
Alerts never reach a human raw. Every alert from the monitoring stack is intercepted by an AI triage service that investigates first: it pulls metrics, logs, traces, log-anomaly context, alert history and recent deployments through read-only bridges, has a locally hosted LLM write a root-cause analysis, and only then either pages the operator with a named cause ("the ad workload's pod cannot be scheduled") or dismisses the noise — with every dismissal recorded and auditable. No data leaves the network; no external AI API is involved.

1. Architecture — three layers on three hosts

The tiers talk over plain TCP and are deployed by three Ansible commands (monitoring.yml → gpu-host.yml → k8s-manifests.yml); a bring-your-own-cluster bundle exists for deployment on CIRES infrastructure. All images are CI-built and pulled from GHCR.

2. The path of one alert

  1. Grafana evaluates a rule (or the log-anomaly engine detects a novel error pattern) and fires a webhook to the triage service.
  2. Noise gates run first, before any GPU cost: duplicate-fire dedup, repeat-alert suppression, recurrence gating for known flappers (details in §3.4).
  3. If the alert survives, the service gathers a correlated evidence picture — metrics, logs, traces, k8s state, alert history, recent deployments — exclusively through the 6 MCP bridges.
  4. The local LLM writes the RCA: verdict (escalate / dismiss), confidence, a one-sentence human-readable cause, cited evidence.
  5. Validators check the output (see §3.3); ungrounded claims are blocked or demoted.
  6. On escalate: one email per incident, leading with the cause, naming all co-fired alerts. On dismiss: no email, full record kept.
  7. Every decision lands in the dashboard with its evidence trail, incident history, and a feedback form the operator can use to correct the system.

Median time from alert fire to emailed RCA: ~38 s.

3. Design choices and why

3.1 Local LLM, not a cloud API

All telemetry (logs can contain credentials, internal hostnames, customer data) stays on-premises; there is no per-token cost, no rate-limit dependency, and no internet egress requirement. A 14-billion-parameter model (~11 GB VRAM) is sufficient because the prompt engineering does the heavy lifting: the model receives pre-gathered, pre-structured evidence and a tight output contract, not an open-ended question. Validated on an NVIDIA L4 (24 GB).

3.2 MCP-only data access — the hallucination firewall

The LLM can only see data that arrives through six read-only HTTP bridges (Prometheus, Loki, Jaeger, drain3, RCA-history, deploy-events). It has no database handle, no direct Prometheus access, no shell. This makes every claim in an RCA traceable to a bridge response — and a CI lint fails the build if any code path bypasses a bridge. When a bridge is down the system fails open (escalates rather than silently suppressing).

3.3 Evidence-first validation — trust is earned per decision

  • An "actionable" verdict with zero corroborating evidence is automatically demoted to needs-review with capped confidence.
  • "A recent deployment caused this" is forbidden unless the deploy bridge actually returned a rollout in the window — and an empty answer becomes a grounded negative ("no deploys in 2 h — regression ruled out").
  • Log-anomaly RCAs must quote the actual novel log line they blame.
  • Reusable RCA templates ("exemplars") are only injected when they genuinely fit the alert (score gate) — a weak match falls back to a neutral structure rather than dragging the diagnosis toward a wrong shape.
  • Banned-phrase detection catches hedging ("cannot determine the root cause") and triggers a bounded retry that digs deeper before the system is allowed to give up.

3.4 Layered noise control — one notification per incident

Five complementary layers, each cheap-to-expensive in order, each with a documented escape hatch so a real outage always pages:

3.5 Novelty-based log anomaly detection

The drain3 engine learns the log-template vocabulary of every service and fires on novel patterns, not volume — a new stack trace fires; a noisy-but-known access log never does. Three tiers (per-component, per-application, system-wide) catch both "one service went weird" and "the whole app drifted". The platform's own infrastructure logs are excluded at ingest so the system cannot alert on itself.

3.6 Incident-centric data model

Fires are grouped into incidents by fingerprint: the dashboard shows one row per incident with fire count and full history, not one row per fire. Operator feedback attaches to decisions and feeds back into future investigations (prior-verdict coherence), with quarantine for decisions proven wrong so they cannot poison later prompts.

3.7 Everything as code, everything tested against reality

  • 904 automated tests + CI gates: the MCP-only invariant lint, a frontend compile gate, image build blocked until green.
  • Real-induction testing only: verification means breaking something real (kill a pod, flood an API, push a bad deploy) and checking the system's written diagnosis against the known ground truth — never synthetic webhook payloads. Cumulative scored battery: recall 7/7 outages caught, correct cause 51/52 decisions.
  • Audit cadence: every feature is audited against the live system (rendered pages, not HTTP 200s; applied infrastructure, not just correct code) — drift between repo and reality is treated as a bug class of its own.

4. Production path

AWS is the proof-of-concept bed only. Every component is portable open-source (no AWS managed-service lock-in in the data path), so the private-cloud build is a re-run of the same Ansible against CIRES hosts. Hardening before production exposure, in order: webhook authentication, image digest pinning, MCP service tokens, secrets to Ansible Vault (scaffolding already in place), at-rest encryption provisioned natively in the private-cloud build. Long-term integration target: a single OTel host agent per machine plus the existing NOC Zabbix for metrics — no exporter sprawl.

Bottom line
The architecture is three replaceable layers joined by two contracts: all signals flow through OpenTelemetry into the base, and all AI reads flow through MCP bridges out of it. Everything else — model, alert rules, noise thresholds, even the LLM host — can be swapped without touching the other layers. The design bets on grounding over model size: a small local model, given verified evidence and refused permission to guess, outperforms an unconstrained large one for this job.
