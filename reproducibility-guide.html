End-to-end reproducibility for the CIRES Observability Platform

This page is the single top-to-bottom guide for standing up the platform from scratch — AWS account, Terraform, Ansible, k3s cluster, Helm-deployed workloads, AI triage, and end-to-end validation. It is the operational complement to the architecture, Kubernetes learning, and Sprint 2 extension guides.

Who this is for: an operator (future Lina, a teammate, a reviewer) who has the 6 repos and needs to reach a working AWS demo in under a day. Everything below is re-runnable. Every credential is marked. Every side-effect is described.

What you'll end up with

  • 1 monitoring VM (EC2, Ubuntu 22.04): Prometheus + Grafana + Loki + Jaeger + OTel Collector
  • 1 k3s EC2 (Ubuntu 22.04): single-node k3s cluster running Spring Boot, Kong, triage service, 5 MCP servers
  • 1 optional GPU EC2 (g4dn.xlarge): Ollama — can instead be co-located on the k3s node for cost
  • 1 RDS MySQL (managed): application database
  • S3 + CloudFront: React frontend hosting
  • 17 Grafana alert rules firing through a webhook into the AI triage pipeline

AWS account

  • An AWS account with admin or near-admin IAM permissions for the demo (VPC, EC2, RDS, S3, CloudFront, IAM for service roles)
  • CLI credentials configured: aws configure (or AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY env vars)
  • Billing alerts turned on — E1-01 (SCRUM-62) acceptance criterion; configure in Billing → Budgets
  • Default region: us-east-1 (lowest-cost for the chosen instance types; change in terraform.tfvars if needed)

SSH key

Terraform uploads a public key to AWS as a key pair, used for every EC2. Generate if you don't have one:

ssh-keygen -t ed25519 -f ~/.ssh/ansible_key -C "ansible-cires-demo"
# This creates ~/.ssh/ansible_key (private) and ~/.ssh/ansible_key.pub (public)

Optional: Ollama model prep

The AI stack pulls a model on first deploy. llama3.2:3b fits on a t3 class CPU instance in a pinch; llama3.1:8b or llama3.1:70b need the GPU. Model name is set in charts/ai-stack/values.yaml (ollama.model).

Optional: SMTP for email notifications

To send ESCALATE emails, set SMTP credentials (default: Gmail app password). Without these the triage service logs the verdict but skips the email — still useful for demos.

Generating a Gmail app password:

  1. Sign in to the Google account and enable 2-Step Verification if not already on.
  2. Open myaccount.google.com/apppasswords, name it CIRES-triage, copy the 16-char value (spaces can be dropped).
  3. Stash locally — never commit — and source before Ansible/Helm: 
    cat > ~/.cires-demo-env <<'EOF'
export GRAFANA_SMTP_PASSWORD="xxxxxxxxxxxxxxxx"
EOF
chmod 600 ~/.cires-demo-env
source ~/.cires-demo-env
  4. Ansible inventory/group_vars/ai.yml reads it via lookup('env', 'GRAFANA_SMTP_PASSWORD'). For Helm, pass explicitly: helm install ai-stack … --set smtp.password="$GRAFANA_SMTP_PASSWORD".

Step 2 — Terraform: AWS infrastructure

Provisions VPC, 3 EC2s, RDS, S3, CloudFront, 4 security groups, Elastic IPs. Takes ~8 minutes.

2.1

Create terraform.tfvars

cd provisioning-monitoring-infra
cp terraform.tfvars.example terraform.tfvars
$EDITOR terraform.tfvars

Fill in these values:

ubuntu_ami_id
Required (E1-02). Look up the current Ubuntu 22.04 LTS AMI for your region at cloud-images.ubuntu.com/locator/ec2. The example file has a working value for us-east-1.
allowed_ssh_cidrs
Your public IP in CIDR form (YOUR_IP/32). Do not leave the 0.0.0.0/0 default for real deployments.
ssh_public_key_path
Path to your public key (default ~/.ssh/ansible_key.pub).
db_password
Strong RDS master password. Minimum 8 chars, no / @ " per RDS rules.
s3_bucket_name
Must be globally unique — append a random suffix (e.g. cires-observability-demo-a1b2).
enable_k3s / enable_gpu
Staged-deploy flags (default true). Set either to false when your AWS vCPU quota can't fit the full topology on one apply. See the Deploy log tab for why this matters on a fresh AWS account.
2.2

Init, plan, apply

terraform init
terraform validate
terraform plan -out=plan.out
terraform apply plan.out
# ≈ 8 minutes — RDS creation is the long pole
AMI pinning (E1-02 rescope): ubuntu_ami_id is a required input with no default. This prevents silent AMI drift between applies. When Ubuntu publishes a new Jammy image, decide to adopt it intentionally by changing the value; don't let Terraform pick it for you.

# Writes ../monitoring-project/inventory/production.yml

3.3

Deploy the monitoring stack

ansible-playbook playbooks/monitoring.yml
# Or just the common baseline first if you want to stage:
ansible-playbook playbooks/monitoring.yml --tags common,docker
ansible-playbook playbooks/monitoring.yml --tags monitoring

Two plays in monitoring.yml:

  1. Play 1: base host setup (tags common,docker) — roles common, docker, node_exporter, cadvisor. Sets timezone, installs base packages + UFW, Docker CE + compose plugin, and pulls the node_exporter + cAdvisor images.
  2. Play 2: monitoring stack (tag monitoring) — roles prometheus, loki, jaeger, otel-collector, grafana, then renders monitoring-compose.yml.j2 to the path configured by stack_dir (default /opt/stack/docker-compose.yml) and brings the stack up with community.docker.docker_compose_v2. Final tasks wait for Prometheus/Grafana/Loki/Jaeger to respond on their ports.

The Grafana role provisions 4 dashboards (unified-overview, tracing-overview, otel-collector-health, triage-service-health) plus alerting config (contactpoints.yml.j2, policies.yml.j2, alertrules.yml.j2) — the legacy Alertmanager role is already removed on origin/main.

Step 4 — k3s cluster + Helm workloads

This is Epic 3: E3-01 through E3-10. All orchestrated from the single-command playbook chain below.

4.1

Bootstrap k3s (E3-01)

ansible-playbook playbooks/k3s.yml --tags bootstrap

Applies 4 roles in order: common, docker, xanmanning.k3s, k3s_images. k3s is pinned to v1.30.6+k3s1 (from inventory/group_vars/k3s_cluster.yml), Traefik is disabled via k3s_server.disable: [traefik], and write-kubeconfig-mode: "0644" makes the kubeconfig world-readable.

Post-tasks wait for kubectl get nodes to return Ready (up to 30×10s retries), fetch the kubeconfig back to the control machine, and rewrite the server URL from 127.0.0.1:6443 to the EC2 EIP.

# Verify on your laptop (kubeconfig is at ~/.kube/config)
kubectl get nodes
# NAME       STATUS   ROLES                  AGE   VERSION
# ip-10-0-2  Ready    control-plane,master   90s   v1.30.6+k3s1
4.2

Build + import images (E3-02)

ansible-playbook playbooks/k3s.yml --tags images

For each of the 6 first-party services (triage + 5 MCPs), the k3s_images role does:

  1. docker build -t cires/<name>:<image_tag> <source_repo> on the k3s host
  2. docker save cires/<name>:<image_tag> -o /tmp/<name>.tar
  3. sudo k3s ctr images import /tmp/<name>.tar

Image tag is driven by the single image_tag variable in inventory/group_vars/k3s_cluster.yml — bump it to force a rebuild.

# Verify
ssh ubuntu@<k3s_eip> 'sudo k3s crictl images | grep cires'
# Should list all 6 cires/* images
Why no registry: single-node k3s with one or two contributors doesn't justify ECR + CI. The crictl import route is officially supported by k3s and sidesteps the whole network-pull path. The upgrade path to ECR+CI is documented in charts/ai-stack/README.md for the day you add a second node.
4.3

Apply K8s manifests — GPU + OTel (E3-06, E3-07)

# One playbook applies both DaemonSets (plus Prometheus RBAC for E3-08)
ansible-playbook playbooks/k8s-manifests.yml

# Or scope it:
ansible-playbook playbooks/k8s-manifests.yml --tags nvidia        # GPU only
ansible-playbook playbooks/k8s-manifests.yml --tags otel          # Logs/traces only
ansible-playbook playbooks/k8s-manifests.yml --tags prometheus    # RBAC only

Applies:

  • observability namespace + OTel Collector DaemonSet (filelog receiver on /var/log/pods, k8sattributes processor, OTLP exporter to monitoring_vm_ip:4317)
  • NVIDIA device plugin DaemonSet (k8s-device-plugin v0.15.0) in kube-system
  • Prometheus scraper ServiceAccount + ClusterRole + ClusterRoleBinding (for kubernetes_sd_configs access from the external monitoring VM)
E3-06 is a spike: GPU passthrough on k3s is the highest-risk item in the sprint. If the device plugin pod goes CrashLoopBackOff, see the Troubleshooting tab. In the worst case, set ollama.gpu.enabled: false in charts/ai-stack/values.yaml to run CPU-only for a demo.

Step 5 — Wire everything together

5.1

Prometheus kubernetes_sd_configs (E3-08)

The prometheus Ansible role already includes three kubernetes_sd_configs scrape jobs (kubernetes-pods, kubernetes-nodes, kubernetes-cadvisor). Each reads the bearer token from /etc/prometheus/k3s-token, talks to <k3s_eip>:6443, and uses annotation-based relabeling (prometheus.io/scrape=true, prometheus.io/port, prometheus.io/path).

# Run on the control machine — extracts the k3s SA token and deploys it
# as an Ansible vault secret to the monitoring VM, then redeploys Prometheus.
ansible-playbook playbooks/monitoring.yml --tags prometheus

Check http://<monitoring_eip>:9090/targets — all kubernetes-* jobs should be up.

5.2

Migrate the 17 Grafana alert rules to K8s selectors (E3-09)

The rules already live in roles/grafana/templates/alertrules.yml.j2 with selectors rewritten from VM IPs to K8s pod labels:

Old:  instance = "application_vm_ip:8080"
New:  pod =~ "spring-boot.*", namespace = "app"

Old:  instance = "network_vm_ip:8000"
New:  pod =~ "kong.*",        namespace = "network"

Old:  instance = "ai_vm_ip:8090"
New:  pod =~ "triage.*",      namespace = "ai"

Apply via ansible-playbook playbooks/monitoring.yml --tags grafana, then test each rule individually — silent failure is the biggest risk here.

kubectl logs -n ai deploy/triage-service --tail=100 -f
# In another shell, run load-test.sh or manually force a rule to fire

Troubleshooting

Terraform

SymptomLikely cause / fix
Error: validation failed: ubuntu_ami_id must be a valid AMI IDYou didn't set ubuntu_ami_id in terraform.tfvars. That's intentional (E1-02 rescope — no silent AMI drift). Look up an AMI for your region and set it.

Real-world deploy log — 2026-04-21

What actually happened when we tried to deploy the platform on a freshly-minted AWS account. The reproducibility guide assumes a “normal” AWS account; this log captures the new-account-specific obstacles so the next operator can budget time correctly.

TL;DR: brand-new AWS accounts hit two anti-fraud restrictions that are invisible until you try to create specific resources — not quota issues. Budget an extra day before the first deploy if your account is less than a week old.

Phase 1 — mitigation: staged-deploy flags

To work around the vCPU quota (5 < 6 needed) without waiting for AWS, two feature flags were added to provisioning-monitoring-infra:

# variables.tf
variable "enable_k3s" { type = bool, default = true }
variable "enable_gpu" { type = bool, default = true }

# ec2.tf
resource "aws_instance" "k3s" {
  count = var.enable_k3s ? 1 : 0
  # ...
}
resource "aws_instance" "gpu" {
  count = var.enable_gpu ? 1 : 0
  # ...
}

# outputs.tf
output "k3s_public_ip" {
  value = var.enable_k3s ? aws_eip.k3s[0].public_ip : null
}

This lets you apply monitoring VM + networking + RDS + S3 first, then later flip the flags to true and re-apply for k3s and GPU once quota lifts. No Terraform state pollution.

Surprise #1 — run-instances --dry-run is a liar for Free-Tier checks

aws ec2 run-instances --dry-run --instance-type t3.large ...
# "Request would have succeeded, but DryRun flag is set."

So we thought the restriction had lifted. It hadn't. Real terraform apply returned the exact same InvalidParameterCombination: not eligible for Free Tier error as on 04-21. Dry-run validates IAM + parameter shape but does not evaluate the Free-Tier billing restriction. The only reliable test is a real run-instances for the target instance type — and if it succeeds, immediately terminate-instances.

Updated Lesson #2 below.

Surprise #2 — EC2 EIP + private subnet = silent SSH blackhole

We pivoted to a verified AWS account (735115318342). Apply succeeded. Instances came up. Both were unreachable on port 22, even with security group ingress open to 0.0.0.0/0. Symptoms:

  • ssh -v → Connection timed out (not refused; no TCP RST)
  • Instance status checks: 2/2 passed
  • get-console-output: sshd running, keys installed, cloud-init finished
  • cloud-init logs showed apt-get failed with “Network is unreachable” → user_data python3 install got skipped

Root cause: the original Terraform placed aws_instance.monitoring and aws_instance.k3s in aws_subnet.private, whose route table sends 0.0.0.0/0 to the NAT Gateway. EIP-based inbound requires an Internet Gateway route on the subnet — private has none, so inbound SSH packets hit the subnet and get silently dropped. Outbound worked through NAT but asymmetrically (return traffic came in via EIP/IGW, didn't match NAT state table).

Fix applied (committed 1f3b108):

# ec2.tf, both aws_instance resources
-  subnet_id = aws_subnet.private.id
+  subnet_id = aws_subnet.public.id

RDS keeps its two-AZ private subnet group (that's what you do want for a database). Only the EIP-bearing EC2s move to public.

If you inherit this Terraform before the fix merges downstream: change subnet_id = aws_subnet.private.id to aws_subnet.public.id for both aws_instance.monitoring and aws_instance.k3s. RDS keeps aws_db_subnet_group.main unchanged.

Surprise #3 — dynamic ISP rotates allowed_ssh_cidrs out from under you

The operator box's public IP rotated twice in ~2 hours on a dynamic-NAT mobile-ISP uplink (Morocco Maroc Telecom). Each rotation invalidated the allowed_ssh_cidrs = ["X.X.X.X/32"] in terraform.tfvars. Symptom: SSH that worked an hour ago now times out.

Two reasonable fixes:

  1. For solo active-session work on a trusted network: temporarily widen to ["0.0.0.0/0"], then narrow post-session. Safe because sshd is key-only (no password auth) and the private key isn't exportable.
  2. For hands-off deploys: use Terraform's http data source to auto-detect: 
    data "http" "my_ip" {
  url = "https://checkip.amazonaws.com"
}

locals {
  allowed_ssh_cidrs = concat(
    var.allowed_ssh_cidrs,
    ["${chomp(data.http.my_ip.response_body)}/32"]
  )
}

Surprise #4 — Ansible role writes to a directory its play hasn't created yet

Running ansible-playbook playbooks/monitoring.yml failed at roles/otel-collector/tasks/main.yml:17:

fatal: [monitoring-vm]: FAILED! => {
  "msg": "Destination directory /opt/stack does not exist"}

In playbooks/monitoring.yml, the roles (including otel-collector) run before the play-level tasks: block, but /opt/stack is created by a task in that block. Classic Ansible gotcha. Workaround used: ansible monitoring-vm -m file -a "path=/opt/stack state=directory mode=0755" -b then re-run the playbook (idempotent).

Permanent fix (not yet committed): move the “Create stack directory” task into a pre_tasks: block so it runs before the roles, or have the otel-collector role create its own parent with state=directory.

Surprise #5 — xanmanning.k3s role stack of Ansible 2.16+ incompatibilities

The community role xanmanning.k3s v3.4.4 has three independent failure modes against Ansible 2.16+ and a default that doesn't fit our use:

  1. Broken conditional: tasks/ensure_downloads.yml:20 has when: k3s_release_version | regex_search("^[a-z0-9]{40}$") — newer Ansible requires booleans, not None. Mitigation: ANSIBLE_ALLOW_BROKEN_CONDITIONALS=True ansible-playbook ...
  2. Missing become: role default is k3s_become: false — writes to /usr/local/bin/k3s fail with “Destination not writable”. Mitigation: k3s_become: true in inventory/group_vars/k3s_cluster.yml.
  3. Filter plugin error: tasks/ensure_installed.yml:5 fails with “The filter plugin 'ansible.builtin.dirname' failed: expected str…, not _OmitType”. Comes from looping over k3s_ensure_directories_exist when some entries default to omit. No easy runtime override.

Workaround landed: skip the role entirely. The official k3s installer is a single command and works out of the box:

ssh deploy@$K3S_EIP "curl -sfL https://get.k3s.io | \
  sudo INSTALL_K3S_EXEC='--disable=traefik --write-kubeconfig-mode=644' sh -"

# Fetch kubeconfig + rewrite server URL locally
ssh deploy@$K3S_EIP "sudo cat /etc/rancher/k3s/k3s.yaml" \
  | sed "s|https://127.0.0.1:6443|https://$K3S_EIP:6443|" > ~/.kube/config
chmod 600 ~/.kube/config
Keep the images + manifests sub-plays from playbooks/k3s.yml — only the bootstrap play was problematic. Run with --tags images to build/import the first-party Docker images.

Surprise #6 — SG ingress CIDR hardcoded to the wrong subnet

After moving EC2s from private to public subnet (Surprise #2), every cross-VM call still failed because security-groups.tf had 14 rules pinned to var.private_subnet_cidr (10.0.2.0/24) — but the instances now live in 10.0.1.0/24. k3s-node literally could not reach Prometheus, Loki, Jaeger, Grafana, or the OTel collector on the monitoring VM.

Diagnostic signature: MCP pods crash-loop on liveness; their /health routes stall on upstream HTTP calls that TCP-timeout.

# Fix — one sed across security-groups.tf:
sed -i 's|var\.private_subnet_cidr|var.vpc_cidr|g' security-groups.tf
terraform apply

Shipped as commit b0b96b4. Use var.vpc_cidr (10.0.0.0/16) for any intra-VPC rule; it covers both subnets without caring which one holds the client.

Surprise #7 — AI stack Helm chart needed 4 fixes to install cleanly

All discovered by running helm install and watching pods crash. Shipped together in commit 9bc92b7 + f9556b7:

  1. Missing SMTP Secret. triage-deployment.yaml pulled six keys from a Secret ai-stack-smtp-secret that no template created. Added templates/triage-smtp.yaml (filename deliberately avoids the repo's *secret* gitignore pattern).
  2. Ollama probes use curl. The ollama/ollama image ships no curl/wget; exec probe fails with “sh: 1: curl: not found” and kubelet restarts the pod every 15 s. Replaced with httpGet: /api/tags.
  3. rca-history mounts /data read-only. The MCP creates + writes a SQLite DB on startup; read-only mount produced sqlite3.OperationalError: unable to open database file and CrashLoopBackOff. Drop readOnly: true.
  4. Chart-owned namespace collides with --create-namespace. Helm creates the namespace up front for its release metadata; the chart's own namespace.yaml template then re-renders it, conflict. Deleted ai-stack/templates/namespace.yaml and frontend/templates/namespace.yaml; the helm flag is enough.

charts/spring-boot/values.yaml references mukundmadhav/react-springboot-mysql:latest. On the first pull:

Surprise #9 — k3s API :6443 reachable via SSH tunnel, not SG

The k3s SG opens 6443 only from the monitoring SG (so Prometheus can scrape the API). Our operator box is outside the VPC, so direct kubectl from this laptop returns connection refused. Don't widen the SG for this — kubectl is a maintenance-time tool, not a production access path. Use a tunnel:

ssh -N -L 6443:localhost:6443 -i ~/.ssh/ansible_key deploy@$K3S_EIP &
# Now ~/.kube/config server URL can stay as https://127.0.0.1:6443
# (which is what k3s writes by default, no rewrite needed)

Lessons for the next operator (updated)

  1. Check account age. If the IAM user or root account is < 1 week old, assume Free-Tier + CloudFront restrictions. File the unlock case before touching Terraform.
  2. Test with a real launch, not a dry-run. Dry-run doesn't catch the Free-Tier billing restriction. Do aws ec2 run-instances --instance-type t3.medium ... --count 1 (not --dry-run), then terminate-instances immediately. Cost: ~$0.001. Tells you in 10 s whether the account is unrestricted.
  3. EIP-bearing instances go in the public subnet. Full stop. If you see "timeout" (not "refused") on SSH and instance status is 2/2 ok, check the subnet's route table for an IGW route on 0.0.0.0/0.
  4. Run Ansible from a box with a static public IP if you can — or widen allowed_ssh_cidrs to 0.0.0.0/0 for the duration of the session and tighten back afterwards. Dynamic ISPs rotate IPs every 1–3 hours and will lock you out mid-deploy.
  5. Academic framing helps AWS appeals. Mentioning it's a student learning project (with university domain, short lifecycle, and billing alarms) tips quota and unlock appeals toward approval far more than a generic “please approve” message.
  6. Separate support cases for separate restrictions. Quotas, account verification, and Free-Tier lift are three different support queues. Don't bundle — it slows all three.
  7. Keep enable_k3s / enable_gpu / enable_cloudfront flags even after quota lifts. Staged deploys become useful any time you want to cost-optimize off-hours, run a mini demo, or defer a resource whose account-level gate is slow to clear (CloudFront verification).
  8. Pre-flight the monitoring playbook. Until the /opt/stack ordering bug is fixed in monitoring.yml, run ansible monitoring-vm -m file -a "path=/opt/stack state=directory mode=0755" -b before the first ansible-playbook invocation.
