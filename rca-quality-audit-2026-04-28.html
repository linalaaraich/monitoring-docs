The morning of 2026-04-28 shipped a major prose-quality intervention (D19): three reinforcing surfaces rewritten to demand cause-first RCAs. F-1 (critical) — Drain3 webhook didn't carry the lines

The dominant failure for Drain3 alerts. Operator-flagged 2026-04-28 11:20:

The Drain3AnomalyDetected alert for service=drain3 indicates that an anomaly was detected with a novel log template, but no specific metric or log evidence supports a concrete cause. The observed value at fire time is unknown due to missing PromQL expression and metrics data. No correlated alerts in the ±10 min window provide additional context... Drain3 detected 15 anomalous log lines with an anomaly rate of 12.82%. New templates: None (no specific template details available).

Root cause traced through the code

  1. app/drain_analyzer.py:_ingest_batch_sync returned only the anomalous LINES, not the new TEMPLATES. The sibling field new_templates in Drain3Webhook was hardcoded [] on every fire (maybe_fire_alert line 273).
  2. app/pipeline.py:process_drain3_webhook built a synthetic GrafanaAlert with description = "Anomaly rate: 12.82%. New templates: 0" — i.e., the count of templates, not their content. The actual webhook.anomalous_lines were available but never written into the alert.
  3. The LLM prompt builder reads alert.annotations.get("description") verbatim into the user message. So the model saw the count and nothing else of substance.

Three reinforcing surfaces (rules + exemplars + validator) all aimed at output quality, but no amount of prompt engineering can fix "the input doesn't contain the information needed to produce a useful output." This is a different bug from F-2 / F-3 / F-5 — it's at the data layer, not the language layer.

Fix shipped (revision after this audit)

  1. app/drain_analyzer.py: _ingest_batch_sync now returns (anomalous_lines, new_template_strings); tracks brand-new clusters per batch via is_new_pattern=True; deduplicates on cluster_id.
  2. maybe_fire_alert accepts a new_templates arg and forwards it into the webhook payload (capped at 20 templates for wire size; lines remain capped at 50).
  3. process_drain3_webhook builds a rich description with three sections — anomaly rate, the new template strings (verbatim, capped 10), and a sample of anomalous lines (verbatim, capped 8) — totalling a prompt-budget-friendly evidence block. Also adds signal=log to the synthetic alert's labels so the drain3-novelty-post-deploy exemplar scores 1.00.
  4. 4 new tests in tests/test_drain3_evidence_flow.py covering the batch return shape, the webhook payload forwarding, the rich description structure, and the empty-templates-graceful-degrade case.

Suite: 120 / 120 (was 116 + 4 new). Production rolls on the next image pull.

Why F-1 first, even though it wasn't on the original roster

Three reasons:

  1. Highest leverage. Every Drain3 RCA in production was failing for the same reason. Fixing F-2 / F-3 / F-4 / F-5 doesn't help Drain3 alerts at all because the LLM had no input to reason over.
  2. Operator-flagged with a real example. The 11:20 case was concrete and testable. Speculative fixes get deferred; concrete fixes ship.
  3. It's a data-flow bug, not a model-quality bug. Once the lines flow, the philosophy + exemplars + validator have something to work on. Until then, all that machinery was operating on count metadata.

Specific gaps to fix

  1. OTel collector exemplar missing — both OTelCollectorHighSpanDropRate and OTelCollectorDown fall to generic-sre-shape. They're real failure modes (otel-collector OOM, exporter backpressure, batch buffer overflow) and the LLM has no calibration target. Add a new otel-collector-degradation exemplar with the specific evidence shape: span drop rate, exporter queue depth, memory growth.
  2. Cascade-incident regex too narrow — only matches HighDiskUsage + LokiIngestionRateLow. The 4 disk-pressure variants (CriticalDiskUsage, DiskFillingUp, LokiCriticalDiskUsage, LokiDiskFillingUp) all miss. Widen the regex to include all 6 disk-related alertnames AND add monitoring/loki to services to make scores ≥0.90.
  3. Adaptive-threshold-noop regex misses Critical — only matches ^(High|Medium)CpuUsage$, so CriticalCpuUsage falls through. Adaptive-threshold-noop isn't the right exemplar for Critical (those are real, not seasonal noise) — better to add a separate service-resource-saturation exemplar for Critical CPU/Memory cases.
  4. Wildcard services lower scores — exemplars that use services: ["*"] (synthetic-blip-dismiss, drain3-novelty-post-deploy, adaptive-threshold-noop) score 0.70 instead of 1.00 because the matcher gives 0.40 for "service in services" and only 0.10 for service mismatch. The wildcard is intentional design (these archetypes are service-agnostic); just worth documenting that 0.70 is the natural ceiling for them.

These gaps are not shipped yet — documenting here for the next code session. None are urgent: the F-1/F-2/F-3/F-4 fixes already shipped today address the bulk of regression cases.

Live verification 2026-04-28 PM — three more regressions found and fixed

After deploying the morning's F-1/F-3/F-4 work, I induced two real Drain3 alerts to live-verify the philosophy chain end-to-end. Both produced surface-only RCAs that the validators didn't catch. Three additional fixes shipped:

#FailureRoot causeFix shipped
F-1.5 F-1 was leaky — Drain3 RCAs still lacked the rich webhook content despite the F-1 fix. The prompt builder reads drain_summary from ctx.anomaly_summary, which is set by ctx.gather() re-querying Loki for service=drain3 (empty — the lines are emitted from service=spring-boot stdout). The webhook's rich description sat in alert.annotations["description"] but didn't flow into the primary anomaly-evidence path. app/pipeline.py: when alertname=Drain3AnomalyDetected and source=drain3, override ctx.anomaly_summary with the rich description so the LLM sees the actual templates + sample lines.
F-3 widen "Based on the context provided, ..." slipped past the surface-only LEDE regex. Original regex matched observed | repeated | reported | metric | PromQL | query | log entries | logs | trace | values | frequency | rate | elevated | high | increased | recurring. Did not include context | information | data | input | history | provided | prompt | alert | prior | available. app/response_validator.py: widened noun list with the missing words. 4 new tests reproducing the verbatim regression cases.
F-3 Drain3 Model hallucinated a Prometheus / PromQL detection mechanism for what's actually log-template novelty: "Prometheus query: {alertname=\"Drain3Alert\"} == 8 times in the last 7 days". The hallucination blocklist had entries for HighP95Latency and HighKongP95Latency but not for Drain3-class alerts. The LLM grasped at PromQL as a familiar shape because it didn't know how Drain3 actually works. app/hallucination_blocklist.yaml: new Drain3AnomalyDetected section rejecting any \bPromQL\b, \bPrometheus query\b, or hallucinated alertname (Drain3Alert | Drain3Threshold | Drain3Anomaly). 3 new tests.

The confidence clamp from this morning DID fire on the Drain3 RCA at 13:11:49 — conf=0.40 visible in /decisions. Operator sees a low-confidence + actionable row and knows to scrutinise. That's the F-4 design intent.
