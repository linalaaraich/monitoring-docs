Reading the matrix

  • Both alert paths fired on real faults. Grafana raised 3 alerts (1 CPU + 2 critical k8s); drain3 raised a SYSTEM-tier anomaly off genuinely-novel error logs.
  • The drain3 path produced a named cause AND emailed. Its stored evidence quoted my actual injected line — "Error: … Product Catalog Fail Feature Flag Enabled" — and the LLM named the cause (deploy regression / novel template), not a hedge. The email subject was [prod] [observability] [ESCALATE] Novel log-template anomaly. Ground truth = detection.
  • Noise control held. The CPU breach was recurrence-gated + dedup-absorbed — no spam — exactly as designed for low-severity flappers.
  • One real miss: the two critical k8s workload-down alerts fired in Grafana and reached triage, but the LLM had no Kubernetes-state evidence to explain why ad was down, so it hedged, and the anti-noise "shelved-in-disguise" gate suppressed the email. A genuinely-down critical service did not page. Root-caused and fixed below.

Root cause of the one miss

Why critical KubeWorkloadDown didn't page
  • The "why is ad down" answer lives in Kubernetes state (kube-state-metrics replica counts, pod phase / scheduling) — not in app metrics, app logs, or traces.
  • The pipeline's default Prometheus query for an alert is service-scoped ({job=~".*ad.*"}), which matches no series for a kube workload alert → the LLM saw an empty context and hedged "cannot determine".
  • A second, subtler bug: the alert arrives from Grafana labelled severity: critical, but the small model often omits severity in its JSON, so the decision defaulted to warning — silently downgrading a critical and letting the anti-noise gates (recurrence gate, shelved-in-disguise) treat it as suppressible noise.
  • Net effect: hedge + downgrade + anti-noise gate = a critical incident with no email.

The fix (code-complete, committed)

Three changes in monitoring-triage-service (committed to main; 774 tests green incl. new cases):

#ChangeFileEffect
1k8s-state evidence for Kube* alertscontext.py Query kube-state-metrics (desired/available/unavailable replicas, pod phase, last-terminated reason) instead of the empty service-job match → the LLM gets real evidence and can name the cause (0/N available, pod Pending/unschedulable, OOMKilled).
2Severity floor = alert's Grafana severityllm_client.py Clamp the decision severity up to the alert's authoritative Grafana label, so a small-model omission can no longer downgrade a critical to warning.
3Critical/high bypass the shelved-in-disguise gatepipeline.py A critical/high alert pages even when the RCA is thin — silence on a critical is worse than a low-confidence email. Low-severity noise is still shelved (regression-tested).
Honesty / status. The fix is committed and unit-tested, but at the time of writing it has not yet been verified post-deploy on the live GPU host — the deploy + a real re-induction of KubeWorkloadDown (to confirm the critical email actually fires with a named cause) is being handled separately to avoid two agents driving the live triage container at once. This page will be updated with the post-deploy re-induction result. Do not read the fix as proven-live yet.

Overall verdict

Both alert paths work and at least one real email fired during the test. The platform fired Grafana metric + critical-k8s alerts and a drain3 log anomaly on real faults; the drain3 path produced a named, evidence-grounded RCA and sent an email; all 5 MCP bridges served live data into the model; and low-severity CPU noise was correctly suppressed. The one real gap — critical k8s workload-down not paging because the LLM lacked Kubernetes-state evidence — was root-caused and fixed in code (pending live re-induction).
