1.Elevator pitch (memorize this)

"Sprint 2 delivers the CIRES AI Observability Platform: a full-stack monitoring pipeline for the react-springboot-mysql application, plus an AI triage service that reacts to Grafana alerts, pulls context from metrics, logs and traces over MCP, asks an Ollama-hosted LLM for a root-cause verdict, and either sends a structured email to oncall or suppresses the alert — so we stop paging humans for noise.

Underneath, the infrastructure moved from per-VM docker-compose to a single-node k3s cluster deployed via Terraform + Ansible + Helm, while the monitoring plane (Prometheus, Grafana, Loki, Jaeger) stays on a dedicated VM — so a cluster failure doesn't blind us to its own failure."

Three one-liners for the demo

  • Infra one-liner: "terraform apply provisions the VPC, monitoring VM, k3s VM, RDS and S3/CloudFront. ansible-playbook site.yml then brings up the monitoring stack, bootstraps k3s, builds images into containerd, and deploys the K8s manifests. Three Helm installs finish the workloads."
  • AI one-liner: "When Grafana fires, the triage service dedups, fans out to 5 MCP servers in parallel for fresh metrics/logs/traces, Drain3-annotates the logs, and hands the LLM a structured prompt. The LLM returns JSON: ESCALATE, DISMISS, or INCONCLUSIVE. A circuit breaker guarantees we never wedge on a bad Ollama."
  • Why it's a big deal: "It's real Kubernetes, real OpenTelemetry, real LLM tool-use — all reproducible from a fresh AWS account in under a day."

Three planes, three responsibilities

PlaneRuns onWhat lives hereWhy it's separate
Monitoring planemonitoring VM (docker-compose)Prometheus, Grafana, Loki, Jaeger, OTel Collector (central)Must survive cluster failure → not colocated with workloads
Workload planek3s VM (k3s cluster)Spring Boot, Kong, triage + 5 MCP servers, Ollama, in-cluster OTel DaemonSetK8s gives us declarative deploy, health checks, rolling updates, service DNS
Data planeAWS managedRDS MySQL, S3 + CloudFrontAvoid owning stateful infra for a demo; free tier eligible
Keeping the monitoring plane off the cluster it observes avoids a circular dependency. If k3s goes down, Prometheus still reports "k3s is down" — otherwise Prometheus would go down with k3s and you'd learn about the outage from customers.

Entry point: provisioning-monitoring-infra/. This is vanilla HCL with flat .tf files (no modules) because the blast radius is small and modules would hurt readability.

What gets created, in order

  1. VPC 10.0.0.0/16 with DNS support + hostnames.
  2. One public subnet (10.0.1.0/24, us-east-1a) → houses NAT GW + IGW.
  3. Two private subnets (10.0.2.0/24 us-east-1a for EC2; 10.0.3.0/24 us-east-1b to satisfy RDS's 2-AZ subnet-group requirement — no EC2 there).
  4. Route tables: public → IGW, private → NAT GW.
  5. Key pair from ~/.ssh/ansible_key.pub.
  6. 4 security groups (details below).
  7. 3 EC2 instances — each in the private subnet, each with its own Elastic IP so we can SSH without a bastion.
  8. RDS MySQL 8.0, single-AZ, not publicly accessible, SG-restricted to k3s.
  9. S3 bucket (private, all public-access blocked) + CloudFront with Origin Access Control + SPA error-redirect rules.

The flow from Terraform to Ansible

  1. terraform apply writes outputs (private IPs, EIPs, RDS endpoint, CF domain).
  2. ./generate-inventory.sh reads those outputs and rewrites monitoring-project/inventory/group_vars/all.yml and inventory/production.yml.
  3. Ansible now has concrete IPs and endpoints — no manual copy-paste.

Things to know that aren't obvious

  • ubuntu_ami_id is required, no default. We deliberately don't use data "aws_ami" "most_recent" because a silent AMI swap between plan and apply would mean re-testing everything.
  • EIPs on private-subnet instances let us SSH directly (no bastion). Trade-off: each EIP is a tiny recurring cost + surface area. Acceptable for a demo env.
  • Single-AZ: everything is in us-east-1a. Subnet B (10.0.3.0/24) exists only because RDS forces you to declare a subnet group across 2 AZs.
  • SG rules use standalone resources (aws_vpc_security_group_ingress_rule) instead of inline rules — avoids Terraform's well-known drift issue with inline SG rules.
  • terraform.tfstate is currently committed to git (we need to fix this post-sprint — it contains the RDS password). Production workflow: remote backend (S3 + DynamoDB lock).

Helm installs are outside site.yml deliberately: they depend on images being present in containerd, so you run them after k3s.yml is green. Scripting them in Ansible is possible but adds failure modes (Helm release state) for very little benefit on a single-node cluster.

Variable precedence (the gotcha that bites Ansible newcomers)

Highest-priority wins. From lowest to highest:

  1. Role defaults (roles/<r>/defaults/main.yml)
  2. group_vars/all.yml
  3. group_vars/<specific group>.yml
  4. host_vars/<host>.yml (none here)
  5. Play vars:
  6. -e CLI extra vars

So when you set monitoring_vm_ip in all.yml and override in group_vars/k3s_cluster.yml, the k3s-group hosts see the k3s_cluster value and everyone else sees the all value.

Prerequisites to run any playbook (say these if asked)

  1. ansible-galaxy install -r requirements.yml — pulls the Galaxy role + collection.
  2. Private key at ~/.ssh/ansible_key, matching the public key in terraform.tfvars.
  3. deploy user on every host with passwordless sudo (provisioned by EC2 user-data script).
  4. inventory/production.yml populated with real IPs — run generate-inventory.sh after terraform apply.

7.k3s & Helm layer — workload plane

Why k3s (not full K8s, not Swarm, not Nomad)

  • Single 70 MB binary, single systemd service — install in ~30 seconds via xanmanning.k3s.
  • CNCF-conformant: anything that runs on vanilla K8s runs on k3s. No API differences.
  • Ships with a complete control plane and batteries included: containerd, CoreDNS, Flannel CNI, local-path-provisioner, metrics-server.
  • Upgrade path is trivial: multi-node k3s → kubespray/kubeadm → EKS/GKE, all using the same Helm charts.
We disable the built-in Traefik ingress controller in group_vars/k3s_cluster.yml because Kong is our gateway. Two ingress controllers would fight over port 80/443.

Bootstrap (playbooks/k3s.yml)

  1. Common + Docker + xanmanning.k3s apply to k3s_cluster hosts.
  2. Post-task: k3s kubectl get nodes with until-loop until "Ready" (30 × 10s retries).
  3. Fetch /etc/rancher/k3s/k3s.yaml to control machine → rewrite 127.0.0.1:6443 → <ec2-ip>:6443 → install at ~/.kube/config.
  4. Install Helm CLI on control machine if missing.
  5. Second play: k3s_images role builds + imports images (see next subsection).

The registry-less image pipeline (k3s_images role)

This is the part the team will ask about. We do not use Docker Hub, ECR, or GHCR. Instead:

  1. rsync the triage-service + mcp-servers repos from control machine → /opt/image-build/ on the k3s host.
  2. On the k3s host: docker build -t cires/triage-service:latest . (×6 images).
  3. docker save cires/triage-service:latest -o /tmp/triage.tar.
  4. k3s ctr images import /tmp/triage.tar — containerd now has the image.
  5. Helm charts use imagePullPolicy: IfNotPresent → Kubernetes finds the image locally, doesn't try to pull.
No registry means no secrets to manage, no rate limits, no external dep, and offline-deployable. Cost: if we scale to multi-node, each node needs the images imported separately — acceptable trade-off for a single-node cluster.

Helm charts — what each one does

1. charts/spring-boot/ → namespace app

  • Deployment with initContainer that downloads the OpenTelemetry Java agent JAR into a shared emptyDir; main container loads it via JAVA_TOOL_OPTIONS=-javaagent:/otel/agent.jar.
  • Service ClusterIP 80 → targetPort 8080.
  • ConfigMap holds DB URL / OTel exporter endpoint (otel-collector.observability.svc.cluster.local:4317).
  • Prometheus scrape annotations on the pod so k8s-SD picks up /actuator/prometheus.

2. charts/kong/ → namespace network

  • Uses the upstream kong/kong Helm chart (v2.38.0), with a custom values-k3s.yaml override.
  • DB-less mode: kong.yml declarative config is supplied via a ConfigMap (kong-config.yaml).
  • Upstream URL rewritten from VM IPs to service DNS: spring-boot.app.svc.cluster.local:80.
  • Exposed externally via NodePort 30080.
  • Kong OTel plugin → in-cluster collector; Prometheus plugin for Kong-level metrics.

3. charts/ai-stack/ → namespace ai

  • One umbrella chart with multiple Deployments: triage-deployment.yaml, mcp-deployments.yaml (generates 5 deployments from values.yaml), ollama-deployment.yaml.
  • ollama-pvc.yaml — 20Gi PersistentVolumeClaim for model storage (so we don't re-pull llama3.2:3b on every restart).
  • Ollama Deployment has resources.limits.nvidia.com/gpu: 1 when GPU is enabled — CPU-only for now.
  • Triage has its own PVC for the SQLite RCA store + Drain3 state file.
  • Secrets for SMTP creds mounted as env vars.
  • All inter-service refs use in-cluster DNS: prometheus-mcp.ai.svc.cluster.local:8091 etc.

4. charts/frontend/

Mostly unused — the React build is either served by the Spring Boot container (bundled) or by CloudFront + S3 (preferred). Kept as a placeholder.

Raw K8s manifests (manifests/)

OTel Collector DaemonSet (observability ns)

  • Runs on every node (DaemonSet). Exposes 4317 (gRPC), 4318 (HTTP), 8888 (metrics), 13133 (health) as hostPorts.
  • Receivers: filelog reading /var/log/pods/* (mounted read-only) + otlp gRPC/HTTP.
  • Processors: k8sattributes (enriches with pod/namespace/deployment/node via the ServiceAccount — that's what the RBAC is for) + resource (adds k8s.cluster.name) + batch.
  • Exporters: otlp → monitoring-VM-IP:4317 (traces to Jaeger) and loki → monitoring-VM-IP:3100.

NVIDIA device plugin DaemonSet (kube-system ns)

NVIDIA's k8s-device-plugin:v0.15.0 with a toleration for nvidia.com/gpu taint. Exposes nvidia.com/gpu: N as an allocatable resource so pods can request GPUs. Currently inactive because GPU vCPU quota is 0.

Prometheus RBAC (observability ns)

Creates ServiceAccount prometheus-scraper, a ClusterRole granting read on nodes/pods/services + /metrics + /metrics/cadvisor, and a static Secret for the token (K8s 1.24+ no longer auto-creates tokens). The extracted token is manually copied to the monitoring VM at /etc/prometheus/k3s-token; Prometheus then uses it as a bearer token for kubernetes_sd_configs.

Metrics pipeline

  1. Every Spring Boot pod exposes /actuator/prometheus with annotations.
  2. Prometheus on the monitoring VM uses kubernetes_sd_configs with a bearer token → discovers pods by annotation → scrapes over the k3s API server (port 6443) and kubelet (port 10250).
  3. Node-exporter + cAdvisor on both VMs give us host metrics.

Traces pipeline

  1. Kong's OTel plugin and the Spring Boot OTel Java agent both emit OTLP to the in-cluster OTel DaemonSet.
  2. DaemonSet enriches each span with pod/namespace labels (k8sattributes processor).
  3. Batched and forwarded OTLP → Jaeger on the monitoring VM (port 4317 on Jaeger's OTLP receiver, but remapped to host port 4327 because the central OTel Collector on the same VM already owns 4317).

Logs pipeline

  1. The DaemonSet's filelog receiver tails /var/log/pods/ on each k3s node (mounted read-only from the host).
  2. CRI format parser extracts timestamp + stream + container.
  3. A regex parser pulls trace_id out of log body if present (OTel Java agent injects it automatically via MDC).
  4. Batched → Loki push endpoint on monitoring VM.

Correlation — Loki → Jaeger jump

In the Grafana Loki datasource we configure a derived field: when a log line contains trace_id=abc123, Grafana turns it into a clickable link to the Jaeger datasource. One click takes you from "this error log" to "this specific trace" — that's the single biggest usability win of the whole platform.

9.MCP — the concept and how we use it

What MCP actually is

MCP (Model Context Protocol) is Anthropic's open spec for letting an LLM call tools provided by an external server — over stdio or HTTP. Each server exposes a set of typed "tools" (input schema + output), and the LLM host (client) can invoke them during a conversation. Think of it as "function calling, but the functions live in a separate process with a standard protocol."

What we did, pragmatically

We built 5 read-only HTTP bridge servers, one per data source. They are MCP-style services (not full MCP stdio handshake) — each exposes typed tool endpoints like /tools/query_range, /tools/query_logs, /tools/find_traces. The triage service calls them over HTTP with httpx.

We called it "MCP bridges" because the shape is the same (typed tools, clearly documented, one server per data domain), but the transport is plain HTTP rather than stdio. This is simpler to operate in Kubernetes (each server is just a Deployment + Service), works behind Helm, and is trivial to observe with Prometheus. If/when we add a Claude/GPT integration later, we can swap the transport without changing the tool semantics.

The five servers

prometheus_mcp8091Prometheus HTTP APIquery_instant, query_range, get_alerts, list_targets
loki_mcp8092Loki HTTP APIquery_logs, query_range, list_labels, label_values

How the triage service uses them

When an alert fires, context.py fans out three parallel MCP calls (Prometheus, Loki, Jaeger) using asyncio.gather, with per-source error isolation — if Jaeger is down, we still use the Prom + Loki results. Each call is wrapped in a latency histogram (triage_mcp_duration_seconds{server}) and a counter (triage_mcp_requests_total{server,status}) so we can alert on MCP slowness or errors. See monitoring-triage-service/app/context.py.

Important — we're not (yet) doing true LLM tool-calling

The triage service calls MCP servers itself to pre-gather context, then ships the resulting data into the prompt. The LLM does not make its own MCP calls today. Evolution path: once we have a more capable model and/or Claude with tool use, we'd let the LLM call tools iteratively (investigate → hypothesize → query again). That's part of Sprint 3+.

10.Triage service — end-to-end deep dive

Code lives in monitoring-triage-service/app/. Stack: FastAPI + Pydantic v2 + httpx + asyncio + drain3 + aiosmtplib + prometheus_client.

Public endpoints (FastAPI)

  • POST /webhook/grafana — receives Grafana Alerting webhooks. Returns 202 immediately, processes in BackgroundTasks.
  • POST /webhook/drain3 — synthetic alert source when Drain3 detects an anomaly rate crossing a threshold.
  • GET /health — uptime + component readiness.
  • GET /decisions — JSON list of past RCA decisions (query params: limit, alert_name).
  • GET /dashboard — HTML view of decision history (what you demo).
  • GET /drain3/stats — cluster count, anomaly rate, template drift.
  • GET /metrics — Prometheus scrape endpoint.

The pipeline (pipeline.py)

  1. Deduplication (dedup.py) — key = (alertname, instance, status), TTL dict with asyncio.Lock, window = 5 min (configurable). Re-fires reset the TTL so rapid repeats don't all get investigated.
  2. Queue depth gauge++ (triage_queue_depth), all work wrapped in asyncio.wait_for(..., timeout=pipeline_timeout) — default 300s.
  3. Context fan-out (context.py) — parallel asyncio.gather of 3 MCP calls, with return_exceptions=True so one failure doesn't kill the other two. Per-source latency recorded as context.prometheus_ms / loki_ms / jaeger_ms; failures recorded in context.errors.
  4. Drain3 annotation (drain_analyzer.py) — each log line classified [KNOWN] (matches an existing cluster template) or [ANOMALY] (new template). Cluster stats are a Prometheus gauge; an anomaly counter ticks per line.
  5. RCA history lookup (rca_store.py, SQLite) — "has this alert fired before? when?" feeds into the prompt so the LLM can weigh flappiness.
  6. LLM investigate (llm_client.py) — prompt includes alert, pre-gathered context, annotated logs, Drain3 summary, and history context. Ollama is called with "format": "json". Response validated against LLMDecision Pydantic model. Fields: decision (ESCALATE/DISMISS/INCONCLUSIVE), severity, confidence, reason, rca, suggested_actions, evidence.
  7. Parse-failure retry — if the LLM's JSON doesn't validate, we append the Pydantic error to the conversation and retry once. Second failure → NEEDS_HUMAN_REVIEW fallback (automatic ESCALATE).
  8. Action — ESCALATE → HTML email via aiosmtplib (notifier.py) with alert details, LLM reasoning, RCA, suggested actions, history. DISMISS → just log it. INCONCLUSIVE → treated as ESCALATE with a prefix note.
  9. Persist — RCA record saved to SQLite (rca_store.save_decision). Visible in /dashboard.
  10. Safety timeout — if the whole pipeline exceeds pipeline_timeout (5 min default), we send a "raw alert" email so oncall still gets paged, and record it as timeout_passthrough / emailed_raw.

Why two alert sources (Grafana + Drain3)?

Grafana alerts fire on metric thresholds (latency, error rate, resource usage). Drain3 fires when log patterns change — a new template appears or a known template's frequency spikes. Together they catch both "numbers are wrong" and "the app is saying something it never said before."

Drain3 specifics

  • Drain3 is a log template mining algorithm — it clusters log lines by structural similarity and stores the templates.
  • State is persisted to a file (drain3.ini configures the persistence path) so clusters survive restarts.
  • On startup, seed_from_loki() back-fills recent logs into Drain3 so the first few alerts aren't spuriously flagged as anomalies.
  • A background task continues ingesting newly arriving logs so the model stays current.
  • Periodic snapshots are pushed to S3 for durability.

RCA store

SQLite file (rca_store.py), schema: timestamp, alert_name, alert_fingerprint, alert_source, affected_service, severity, triage_decision, llm_verdict, llm_confidence, rca_report, llm_reasoning, action_taken, investigation_duration_ms. Feeds /decisions, /dashboard, and the rca_history_mcp server.

11.Epic 4 — AI triage hardening (all three stories done)

AI-01 Circuit breaker (circuit_breaker.py)

Three-state circuit breaker wrapping every Ollama call:

  • CLOSED — normal operation, failures are counted.
  • OPEN — after N consecutive failures (failure_threshold, default 5), all requests fail fast for cooldown_seconds (default 60). Fallback returns NEEDS_HUMAN_REVIEW immediately.
  • HALF_OPEN — after cooldown, one probe is allowed. Success → CLOSED, failure → OPEN again.

State is exposed as Prometheus gauge ollama_circuit_state (0=closed, 1=open, 2=half_open) so we can alert on it. The retry loop sits inside the circuit breaker: 2 retries with exponential backoff (1s, 2s) on timeouts / connect errors / 5xx. Non-retriable 4xx doesn't count against the breaker (Ollama is healthy; it's us).

AI-02 JSON schema enforcement (llm_client.py)

  • Ollama called with "format": "json" → forces JSON-only output at the server level.
  • Response validated with Pydantic LLMDecision. decision must be ESCALATE | DISMISS | INCONCLUSIVE; confidence is 0.0–1.0.
  • Alias-tolerance: accepts verdict / root_cause / recommended_actions in case the model uses a near-synonym.
  • On parse failure: one retry with the validation error appended to the conversation.
  • Second failure: NEEDS_HUMAN_REVIEW fallback → ESCALATE path.

AI-03 Self-observability (metrics.py)

New metrics added beyond the webhook/pipeline-level counters:

  • triage_queue_depth (gauge) — alerts currently in the pipeline.
  • triage_mcp_requests_total{server, status} (counter).
  • triage_mcp_duration_seconds{server} (histogram).
  • triage_fallback_total{reason} (counter) — reasons: circuit_open, retries_exhausted, parse_failure.
  • triage_llm_token_count{type=prompt|completion} (histogram) — pulled from Ollama's prompt_eval_count / eval_count fields.
  • ollama_circuit_state, ollama_requests_total{status}, ollama_request_duration_seconds.

Dedicated Grafana dashboard panel (triage-service-health.json) shows circuit state, fallback rate, queue depth, MCP latencies.

12.Decisions & trade-offs — defend these

Each decision below has the form what we did, why, what we'd do differently at scale. These are the most likely discussion points.

1. Monitoring on its own VM, workloads on k3s.
Why: avoid circular dependency — monitoring must not go down with the cluster it monitors. At scale: HA monitoring (Thanos/Mimir, Loki microservices mode) in a separate cluster dedicated to observability.
2. Single-node k3s, not multi-node.
Why: sprint timeline + account quota; k3s is CNCF-conformant so there's no rework when we scale. At scale: add worker nodes (pure config), then migrate to multi-AZ EKS when HA is actually required.
3. No container registry; images built-and-imported on the node.
Why: zero credential management, zero external dependencies, offline-capable. At scale: private ECR with OIDC, Helm imagePullSecrets from IRSA.
4. Ansible for glue, not for app deploy.
Why: Ansible excels at host setup (Docker, k3s, kubeconfig, secrets); Helm excels at K8s object lifecycle. Using the right tool for each scope keeps both readable. At scale: ArgoCD/Flux for GitOps-style continuous Helm sync instead of manual helm install.
5. HTTP "MCP-style" bridges instead of stdio MCP.
Why: fits Kubernetes natively (Deployments + Services), each bridge is independently deployable and observable. At scale: add a proper MCP stdio adapter in front of the bridges if/when we adopt Claude tool use.
6. Ollama (local inference) rather than a hosted LLM API.
Why: data sovereignty (alert content may contain sensitive business info), no per-token cost, works offline on CIRES private cloud later. At scale: bigger model + dedicated GPU node; optionally a router that can call Claude for novel/hard cases and fall back to Ollama for known-shape alerts.
7. Pre-gather context in code, don't let the LLM call tools iteratively (yet).
Why: bounded latency (we know exactly how long context gathering takes), bounded prompt size, deterministic behavior. At scale: allow 1–2 iterative rounds with a capable model — "look at the top 3 services by error rate, pick one, drill in."
8. JSON-mode + Pydantic validation for LLM output.
Why: free-text parsing was fragile; structured output is auditable and machine-consumable. At scale: also keep a natural-language "reason" field for humans (we already do).
9. Circuit breaker on LLM calls, fall back to human-review escalation.
Why: an LLM is a dependency, not a guarantee — if it's slow or broken, oncall must still get paged. At scale: add a secondary LLM endpoint and failover between them before falling back to raw escalation.
10. Drain3 alongside Grafana alerts, not as a replacement.
Why: metrics and logs catch different failure modes; Drain3 catches "this app just said something it never said before" which thresholds can't. At scale: add streaming anomaly detection on metrics too (e.g. histogram-based) to cover the third axis.

13.Evolution path (Sprint 3 and beyond)

Near-term — Sprint 3 candidates

  • GitOps: ArgoCD watching the monitoring-project repo so Helm releases sync automatically on merge.
  • GPU unblocked: once AWS grants GPU vCPUs, move Ollama to g4dn.xlarge. Try a larger model (8B or 13B) to see whether verdict quality improves enough to justify the cost.
  • Remote Terraform backend: S3 + DynamoDB lock, remove tfstate from git.
  • HA monitoring: replicate Prometheus with Thanos sidecar → S3 long-term storage.
  • End-to-end CI: GitHub Actions that terraform plan on PR, run Helm chart tests, and molecule-test the Ansible roles.

Medium-term — CIRES private cloud migration

  • Swap AWS EC2 for on-prem VMs; Terraform AWS provider → vsphere/proxmox provider or pure Ansible provisioning.
  • Multi-node k3s cluster (1 control + 2 workers) for real HA.
  • Private container registry (Harbor) + image signing.
  • Real alert routing: PagerDuty / Opsgenie integration in the notifier.

Long-term — the "colocated AI" vision

Eventually the AI triage plane should be colocated with the monitoring plane, not a separate workload. The AI is logically part of monitoring (it reacts to alerts, reads observability data) — treating it as "just another monitored app" is the wrong frame. The circular-dependency concern would be addressed by HA monitoring with a separate failure domain, not by keeping them apart.

LLM capability upgrades

  • Iterative tool-calling — LLM issues MCP calls itself, not pre-packaged context.
  • Multi-model router — Claude for hard cases, Ollama for routine ones.
  • Feedback loop — oncall marks escalations as "correct / noise" and we fine-tune a local model monthly.

14.What I'd do differently next time

  1. Move to Helm earlier. Epic 2 built everything as docker-compose first, then Epic 3 rewrote it for K8s. Going straight to Helm would have saved ~1 week — the abstractions (Service DNS, ConfigMaps, Secrets) are no harder than compose's.
  2. Pick k3s from day 1. We lost time on "is it worth bothering with Kubernetes at this scale?" The answer is yes: the deployment model is portable, the Helm charts are reusable, the learning compounds. k3s makes the overhead trivial.
  3. Enforce JSON output on the LLM from the first call. Free-text ESCALATE/DISMISS parsing in Epic 2 was brittle. Epic 4 fixed it with format: json + Pydantic. Should have been there from day 1.
  4. Keep Jira in sync with code as we go. We ended the sprint with Jira statuses weeks behind reality, which made planning the extension harder than it should have been. 5 minutes a day moving cards would have avoided a multi-hour audit.
  5. Use a remote Terraform backend from the first terraform init. Committing tfstate to git was a convenience that's now a cleanup task with secrets implications.
  6. Spike GPU support before committing to it. We planned around a GPU; got a 0 quota; had to re-plan for CPU-only. A 30-minute AWS dry-run would have caught this on day 1.
  7. Name the compose templates / Helm charts more consistently. Mixing ai-stack, ai-compose, and the ai group_vars bucket invites confusion.
  8. Write the end-to-end validation playbook first (test-driven infra). We wrote integration-k8s.yml at the end — if it had existed from the start, each epic story would have had a green/red signal.

15.Q&A prep — questions you're likely to get

Why k3s over full Kubernetes (kubeadm)?
Same API, much lower operational overhead (single binary, 70 MB, installs in 30 seconds). For a single-node cluster, kubeadm's extra complexity has no benefit. When we scale, k3s itself supports multi-node — we're not stuck here.
Why not Docker Swarm?
Dead-end — Docker Inc. has deprecated Swarm in practice. No Helm. No real ecosystem. k3s gives us the same "simplicity" argument plus a supported upgrade path.
Why does monitoring live on a VM and not in the cluster?
Circular dependency. If Prometheus is inside the thing it's monitoring and the cluster fails, Prometheus fails with it — we learn about the outage from users. In a future HA design we'd run monitoring in a separate cluster or failure domain, but for a single-node demo, a dedicated VM is cleaner.
Why build images on the node instead of pulling from a registry?
No credentials to manage, no external dependency, offline-capable. Trade-off: multi-node scaling needs images imported on each node. Cheap to revisit when we actually have multiple nodes.
What if Ollama is down?
Circuit breaker trips after 5 consecutive failures and opens for 60 seconds. While open, every alert gets a NEEDS_HUMAN_REVIEW fallback → automatic ESCALATE with a raw-alert email. Oncall never misses an alert because the AI broke.
What stops the LLM from hallucinating a verdict?
Three layers: (1) Ollama format: json forces structured output at the server; (2) Pydantic validates the schema; (3) on validation failure, we retry with the error embedded, and second failure falls back to human review. The LLM also must produce a confidence score and evidence list — if confidence is low we show it in the email.
Why HTTP "MCP bridges" instead of real MCP stdio?
HTTP Deployments + Services are native to K8s, each bridge is independently scalable and observable by Prometheus. Tool shapes are identical to what an MCP stdio server would expose. We can plug a stdio adapter in front when we need real MCP clients.
What's the total deploy time from zero to working?
Under an hour from a fresh AWS account: terraform apply (~6 min) → generate-inventory.sh (seconds) → ansible-playbook site.yml (~20 min for monitoring + k3s + images + manifests) → three helm install commands (~5 min) → first Ollama model pull (the slow step, 2–5 min depending on network).
Why not run Prometheus as an Operator in k3s?
Nothing would be wrong with that; Prometheus-Operator is excellent. We didn't because (a) we want Prometheus outside the cluster for the dependency reason; (b) the stack is small enough that operator CRDs are overhead; (c) our existing Ansible role already manages the config cleanly. When monitoring moves into its own cluster, the operator makes sense.
How is the Grafana → triage webhook authenticated?
Honestly — today it isn't; the triage webhook is SG-restricted to sg-monitoring, so only the monitoring VM can reach it. That's defense-in-depth, not strong auth. Next step: signed webhook with a shared secret (Grafana supports HMAC).
What happens if Grafana fires 1000 alerts at once (flap storm)?
Dedup drops same-key re-fires within a 5-min window, so the same alert never re-enters the pipeline. Queue depth is exposed as a Prometheus gauge — if it starts climbing, we can alert on that. The pipeline has a 5-min safety timeout that sends the raw alert if investigation isn't done. Worst case we page oncall with raw alerts; we never wedge.
What does Drain3 actually add over just reading logs?
Drain3 builds a template tree of log lines — structurally similar lines collapse into one cluster. Once a template is known, we can tell (a) whether a log line is a known pattern or a brand-new template (=anomaly), and (b) whether the frequency of a known template is drifting. Grafana alerts can't catch either.
Where does state go when the cluster restarts?
Ollama models: 20Gi PVC backed by local-path-provisioner (re-created if node dies; use a network PV for real HA). RCA SQLite + Drain3 state: triage-service PVC (same caveat). S3 snapshots of Drain3 state give us a coarse backup. RDS is AWS-managed, automated backups on.
What if I need to rollback a bad Helm deploy?
helm rollback <release> <revision> -n <ns>. Revisions are kept automatically. Kubernetes rolling-update semantics mean the old pod stays until the new one is Ready, so a broken image doesn't take the service down.
Why don't you use Prometheus-operator's ServiceMonitor CRDs?
Prometheus is outside the cluster, so the operator can't configure it. We use kubernetes_sd_configs + annotation-based scraping against the k3s API with a bearer token. Same effect, no operator needed.
What's the blast radius if someone terraform destroys?
All AWS resources in the VPC go: EC2s, EIPs, RDS (skip_final_snapshot is true — data is gone), S3 bucket (must be empty first), CloudFront. VPC itself and any external dep is fine. Production action item: set skip_final_snapshot = false on RDS and add prevent_destroy lifecycle on the S3 bucket.
How do we know the platform itself is healthy?
(a) Prometheus scrapes its own /metrics and the OTel Collector's; (b) 17 alert rules cover API latency, error rate, pod readiness, disk, memory; (c) the triage service emits its own metrics (queue depth, circuit state, fallback rate) so we'd see "triage is failing" as a Grafana alert — which triage would investigate, paging oncall via the safety-timeout path if needed.
