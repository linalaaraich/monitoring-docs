1.Elevator pitch

The problem (start here — no tech, just the stakes)

Oncall engineers drown in alerts. Most of them are noise — a transient blip, a known quirk, a flappy threshold. But you can't ignore them, because one in twenty is real. So humans stay up at 2am reading Grafana, correlating Loki logs with Jaeger traces, and deciding "is this real or should I go back to sleep?". That's the work we're automating.

What the platform does (the one-paragraph pitch)

"The CIRES AI Observability Platform is a full-stack monitoring pipeline for the react-springboot-mysql application, plus an AI triage service that reacts to Grafana alerts, pulls context from metrics, logs and traces over MCP, asks an Ollama-hosted LLM for a root-cause verdict, and either sends a structured email to oncall or suppresses the alert — so we stop paging humans for noise.

Underneath, the infrastructure moved from per-VM docker-compose to a single-node k3s cluster deployed via Terraform + Ansible + Helm, while the monitoring plane (Prometheus, Grafana, Loki, Jaeger) stays on a dedicated VM — so a cluster failure doesn't blind us to its own failure."

Why this is interesting (the frame for senior engineers)

  • Real Kubernetes, not a toy. k3s is CNCF-conformant; the Helm charts written here deploy on EKS/GKE unchanged.
  • Real OpenTelemetry. Traces propagate end-to-end through Kong → Spring Boot → RDS; logs carry trace_id; Grafana jumps from log → trace in one click.
  • Real LLM tool-use pattern. The triage service pre-gathers context via 5 MCP bridges, hands the LLM a structured prompt, and validates a structured JSON response with Pydantic. Fail-safe behavior is designed in (circuit breaker, schema-retry, human-review fallback).
  • Reproducible. Fresh AWS account → working platform in under an hour via Terraform + Ansible + three helm installs.

Three one-liners to memorize

Infra

terraform apply provisions VPC + monitoring VM + k3s VM + RDS + S3/CloudFront. ansible-playbook site.yml brings up the stack and bootstraps k3s. Three helm installs finish the workloads.

AI

Grafana fires → dedup → 5 MCP servers fan out for metrics/logs/traces → Drain3 annotates logs → LLM returns JSON: ESCALATE / DISMISS / INCONCLUSIVE. A circuit breaker guarantees we never wedge.

Why it matters

Real Kubernetes, real OpenTelemetry, real LLM tool-use — all reproducible from a fresh AWS account in under a day.

Provisioning order — what gets created, in sequence
  1. VPC 10.0.0.0/16 with DNS support + hostnames.
  2. One public subnet (10.0.1.0/24, us-east-1a) → houses NAT GW + IGW.
  3. Two private subnets (10.0.2.0/24 us-east-1a + 10.0.3.0/24 us-east-1b) exist only to satisfy RDS's 2-AZ subnet-group requirement — EC2s don't live here.
  4. Route tables: public → IGW, private → NAT GW.
  5. Key pair from ~/.ssh/ansible_key.pub.
  6. 4 security groups; intra-VPC rules use var.vpc_cidr (10.0.0.0/16) so they cover both subnets regardless of where the client instance lives.
  7. 2 EC2s in the public subnet (monitoring, k3s), each with its own Elastic IP. SSH works without a bastion; inbound traffic reaches the instance via the IGW route on the public subnet.
  8. RDS MySQL 8.0, single-AZ, not publicly accessible, SG-restricted to k3s.
  9. Private S3 bucket + CloudFront with Origin Access Control + SPA error-redirect rules.
Staged-deploy flags (enable_k3s / enable_gpu / enable_cloudfront)

Brand-new AWS accounts start with quotas that block some resources. The flags let you bring the platform up in stages:

  • enable_k3s = false — skip the k3s EC2 (for quota-blocked standard vCPU).
  • enable_gpu = false — skip the GPU EC2 (for GPU vCPU quota = 0; our current state).
  • enable_cloudfront = false — skip CloudFront distribution (for unverified accounts); S3 bucket still created for Drain3 snapshots.

Our account currently: 8 standard vCPUs (partial grant of requested 16), 0 GPU vCPUs. Plan: set enable_gpu=false, run Ollama CPU-only.

Gotchas that aren't obvious
  • ubuntu_ami_id is required, no default. We deliberately don't use data "aws_ami" "most_recent" — a silent AMI swap between plan and apply would mean re-testing everything.
  • EC2s in public subnet, RDS in private. The public-subnet route table points 0.0.0.0/0 at the IGW so EIPs work for inbound; the NAT Gateway (also in public) handles outbound from private resources. Early version of this Terraform put EC2s in private subnet — silently broke SSH. See reproducibility-guide deploy log surprise #2.
  • Single-AZ: everything runnable is in us-east-1a. Subnet B exists only to satisfy RDS subnet-group 2-AZ rule.
  • SG rules use standalone resources (aws_vpc_security_group_ingress_rule) instead of inline rules — avoids Terraform drift issues with inline rules.
  • terraform.tfstate is currently committed to git — contains the RDS password. Post-sprint fix: S3 + DynamoDB remote backend.
  • skip_final_snapshot = true on RDS — a terraform destroy drops the database with no recovery. Flip for production.

Variable precedence — the gotcha for newcomers

Highest priority wins. From lowest to highest:

  1. Role defaults (roles/<r>/defaults/main.yml)
  2. group_vars/all.yml
  3. group_vars/<specific group>.yml
  4. host_vars/<host>.yml (none here)
  5. Play vars:
  6. -e CLI extra vars

So monitoring_vm_ip set in all.yml is visible everywhere; overridden in group_vars/k3s_cluster.yml only for k3s hosts.

Prerequisites to run any playbook
  1. ansible-galaxy install -r requirements.yml — pulls the Galaxy role + collection.
  2. Private key at ~/.ssh/ansible_key, matching the public key in terraform.tfvars.
  3. deploy user on every host with passwordless sudo (provisioned by EC2 user-data).
  4. inventory/production.yml populated with real IPs — run generate-inventory.sh after terraform apply.
  5. Verify with ansible all -m ping before running any playbook.

Bootstrap (playbooks/k3s.yml) — step by step
  1. common + docker + xanmanning.k3s apply to k3s_cluster hosts.
  2. Post-task: k3s kubectl get nodes with until-loop until "Ready" (30 × 10s retries).
  3. Fetch /etc/rancher/k3s/k3s.yaml to control machine → rewrite 127.0.0.1:6443 → <ec2-ip>:6443 → install at ~/.kube/config.
  4. Install Helm CLI on control machine if missing.
  5. Second play: k3s_images role builds + imports images.
The registry-less image pipeline (k3s_images role)

We do not use Docker Hub, ECR, or GHCR. Instead:

  1. rsync the triage-service + mcp-servers repos from control machine → /opt/image-build/ on the k3s host.
  2. On the k3s host: docker build -t cires/triage-service:latest . (×6 images).
  3. docker save cires/triage-service:latest -o /tmp/triage.tar.
  4. k3s ctr images import /tmp/triage.tar — containerd now has the image.
  5. Helm charts use imagePullPolicy: IfNotPresent → K8s finds the image locally, doesn't try to pull.

Six images built: cires/triage-service, cires/mcp-prometheus, cires/mcp-loki, cires/mcp-jaeger, cires/mcp-drain3, cires/mcp-rca-history.

No registry = no credential management, no rate limits, no external dep, offline-deployable. Cost: if we scale to multi-node, each node needs the images imported separately — acceptable trade-off for a single-node cluster.

Metrics pipeline

  1. Every pod exposes /metrics (Spring Boot: /actuator/prometheus) with annotations.
  2. Prometheus on the monitoring VM uses kubernetes_sd_configs with a bearer token → discovers pods by annotation → scrapes over the k3s API server (port 6443) + kubelet (port 10250).
  3. Node-exporter + cAdvisor on both VMs give us host/container metrics.

Traces pipeline

  1. Kong's OTel plugin and Spring Boot's OTel Java agent emit OTLP to the in-cluster OTel DaemonSet.
  2. DaemonSet enriches each span with pod/namespace labels (k8sattributes processor).
  3. Batched and forwarded OTLP → Jaeger on monitoring VM. Host port remap: Jaeger's OTLP receiver is 4317 internally but exposed on host port 4327 because the central OTel Collector on the same VM owns 4317.

Logs pipeline

  1. The DaemonSet's filelog receiver tails /var/log/pods/ on each k3s node (mounted read-only).
  2. CRI format parser extracts timestamp + stream + container.
  3. Regex parser pulls trace_id out of the log body (OTel Java agent injects it via MDC).
  4. Batched → Loki push endpoint on monitoring VM.
Trace propagation — W3C + B3 headers
  • W3C Trace Context (traceparent/tracestate) is the OASIS standard — Spring OTel agent + Kong OTel plugin both use it.
  • B3 multi-header (Zipkin-compatible) is configured alongside for legacy client compatibility.
  • Jaeger understands both natively — no translation layer.
  • Propagators on Spring: tracecontext,b3multi.
The Loki → Jaeger jump (derived field)

In the Grafana Loki datasource config we declare a derived field that regex-matches trace_id=... in a log body and renders it as a clickable link to the Jaeger datasource:

derivedFields:
  - name: TraceID
    datasourceUid: <jaeger-datasource-uid>
    matcherRegex: "trace_id=([0-9a-f]+)"
    url: http://jaeger:16686/search?traceID=$${__value.raw}

Click a log line → Jaeger trace pops up. This is the single biggest usability win of the whole platform.

In the pre-K8s setup (Sprint 1), Promtail on each VM tailed Docker container logs and pushed them to Loki. The OTel Java agent on Spring and the OTel plugin on Kong used per-VM OTel Collectors. The K8s migration replaced both with the in-cluster OTel DaemonSet's filelog + otlp receivers.

13.MCP — concept & execution

MCP (Model Context Protocol) is Anthropic's open spec for letting an LLM call typed tools on an external server. We built 5 HTTP "MCP-style" bridges — same shape, plain HTTP transport — because HTTP Deployments/Services are native to K8s and trivial to observe. Triage calls them itself (today); a future upgrade lets the LLM call them iteratively.

What MCP is (in plain terms)

Think of MCP as "function calling, but the functions live in a separate process with a standard protocol." Each server exposes a set of tools (typed input schema + output), and an LLM host (client) can invoke them during a conversation. Two common transports: stdio (pipes between the LLM host and the server process) and HTTP+SSE.

What we did, pragmatically

We built 5 read-only HTTP bridge servers, one per data source. They expose typed tool endpoints like /tools/query_range, /tools/query_logs, /tools/find_traces. The triage service calls them over HTTP with httpx.

We called it "MCP bridges" because the shape is the same (typed tools, clearly documented, one server per domain), but the transport is plain HTTP rather than stdio. This fits Kubernetes natively (each bridge is just a Deployment + Service), works with Helm, and is trivial to observe with Prometheus. If/when we add a Claude-compatible integration, a stdio adapter can sit in front.

When an alert fires, context.py fans out three parallel MCP calls (Prometheus, Loki, Jaeger) using asyncio.gather(..., return_exceptions=True) — if Jaeger is down, we still use Prom + Loki results. Each call is wrapped in a latency histogram (triage_mcp_duration_seconds{server}) and a counter (triage_mcp_requests_total{server,status}).

Default limits: prometheus_range_minutes=15, loki_log_limit=50, jaeger_trace_limit=20, per-call timeout context_timeout=8s.

Important — we're not doing true LLM tool-calling yet. The triage service calls MCP servers itself to pre-gather context, then ships the results into the prompt. The LLM does not make its own MCP calls. Evolution: once we're on a more capable model (or Claude with tool use), we let the LLM iterate — see §21.

The pipeline (pipeline.py) — 10 steps

  1. Dedup — key (alertname, instance), TTL dict with asyncio.Lock, default window 300s. Re-fire after resolved resets the window.
  2. Queue depth++, all work wrapped in asyncio.wait_for(..., timeout=pipeline_timeout) — default 300s.
  3. Context fan-out — parallel asyncio.gather of 3 MCP calls, per-source error isolation. Per-source latency recorded.
  4. Drain3 annotate — each log line labelled [KNOWN] or [ANOMALY]. Cluster stats → gauge, anomalies → counter.
  5. RCA history lookup — "has this alert fired before?" added to prompt so the LLM can weigh flappiness.
  6. LLM investigate — Ollama called with format=json. Response → LLMDecision Pydantic model.
  7. Parse-failure retry — if JSON fails validation, we append the Pydantic error to the conversation and retry once. Second failure → NEEDS_HUMAN_REVIEW fallback (auto ESCALATE).
  8. Action — ESCALATE → HTML email via aiosmtplib. DISMISS → log only. INCONCLUSIVE → treated as ESCALATE with a prefix note.
  9. Persist — record saved to SQLite (rca_store.save_decision). Visible in /dashboard.
  10. Safety timeout — if the pipeline exceeds 5 min, a "raw alert" email is sent and recorded as timeout_passthrough / emailed_raw. Oncall always gets paged.
LLM decision schema (LLMDecision) 
{
  "decision": "ESCALATE" | "DISMISS" | "INCONCLUSIVE",
  "severity": "critical" | "warning" | "info",
  "confidence": 0.0–1.0,
  "reason": "one-line summary",
  "rca": "2–5 sentence root cause",
  "anomaly_summary": "Drain3 findings summary",
  "suggested_actions": ["action1", "action2"],
  "evidence": ["metric/log/trace line"]
}

Alias tolerance: the parser accepts verdict/root_cause/recommended_actions as fallbacks in case the model uses near-synonyms. INCONCLUSIVE is treated as ESCALATE (better to page than miss).

Why two alert sources (Grafana + Drain3)?

Grafana fires on metric thresholds (latency, error rate, resource usage). Drain3 fires when log patterns change — a new template appears, or a known template's frequency spikes. Together they catch both "numbers are wrong" and "the app is saying something it never said before."

Drain3 specifics
  • Drain3 is a log template mining algorithm — it clusters log lines by structural similarity and stores the templates.
  • State persists to a file (path configured via drain3.ini + drain3_state_dir) so clusters survive restarts.
  • On startup, seed_from_loki() back-fills recent logs so the first few alerts aren't spuriously flagged as anomalies.
  • A background task keeps ingesting newly arriving logs so the model stays current (polling interval drain3_poll_interval=30s).
  • Anomaly threshold: drain3_anomaly_threshold=5 new templates in a window.
  • Periodic snapshots pushed to S3 for durability.

15.Epic 4 — AI triage hardening

Three small stories that make the AI pipeline reliable and observable. All three are code-complete.

AI-01 · Circuit breaker for Ollama calls

Three-state breaker wrapping every Ollama call (circuit_breaker.py):

  • CLOSED — normal; failures counted.
  • OPEN — after failure_threshold=5 consecutive failures; fails fast for cooldown=60s. Fallback returns NEEDS_HUMAN_REVIEW immediately.
  • HALF_OPEN — after cooldown, one probe allowed. Success → CLOSED. Failure → OPEN.

State exposed as Prometheus gauge ollama_circuit_state (0=closed, 1=open, 2=half_open). Retries sit inside the breaker: 2 retries with exponential backoff (1s, 2s) on timeouts / connect errors / 5xx. Non-retriable 4xx doesn't count against the breaker (Ollama is healthy; it's us).

AI-02 · JSON schema enforcement

  • Ollama called with "format": "json" — server-level JSON enforcement.
  • Pydantic v2 validation against LLMDecision.
  • Alias tolerance (verdict/root_cause/etc.).
  • One retry with the validation error appended; second failure → NEEDS_HUMAN_REVIEW fallback.

AI-03 · Self-observability (metrics)

Metrics added beyond the base webhook/pipeline counters:

  • triage_queue_depth (gauge)
  • triage_mcp_requests_total{server, status} (counter)
  • triage_mcp_duration_seconds{server} (histogram)
  • triage_fallback_total{reason} (counter) — circuit_open, retries_exhausted, parse_failure
  • triage_llm_token_count{type=prompt|completion} (histogram) — from Ollama's prompt_eval_count/eval_count
  • ollama_circuit_state, ollama_requests_total{status}, ollama_request_duration_seconds

Dedicated Grafana panel (triage-service-health.json) renders these.

20.Decisions & trade-offs — defend these

Each decision has what we did, why, and at scale. Every bullet is a candidate question.

1. Monitoring on its own VM, workloads on k3s.
Why: avoid circular dependency — monitoring must not go down with the cluster it monitors. At scale: HA monitoring (Thanos/Mimir, Loki microservices mode) in a separate cluster dedicated to observability.
2. Single-node k3s, not multi-node.
Why: sprint timeline + account quota; k3s is CNCF-conformant so there's no rework at scale. At scale: add worker nodes (pure config), then migrate to multi-AZ EKS when HA is required.
3. No container registry; images built-and-imported on the node.
Why: zero credential management, no external dep, offline-capable. At scale: private ECR with OIDC, Helm imagePullSecrets from IRSA.
4. Ansible for glue, not for app deploy.
Why: Ansible excels at host setup (Docker, k3s, kubeconfig, secrets); Helm excels at K8s object lifecycle. Right tool per scope. At scale: ArgoCD/Flux for GitOps-style continuous Helm sync.
5. HTTP "MCP-style" bridges instead of stdio MCP.
Why: K8s-native (Deployments + Services), independently scalable, Prometheus-observable. At scale: add a stdio adapter in front when we adopt Claude tool use.
6. Ollama (local inference) rather than a hosted LLM API.
Why: data sovereignty (alert content may contain sensitive info), zero per-token cost, works offline on CIRES private cloud later. At scale: bigger model + dedicated GPU; optionally a router that sends hard cases to Claude, routine ones to Ollama.
6a. CPU Ollama with llama3.2:3b while GPU quota = 0.
Why: account's G+VT on-demand vCPU quota is 0 (pending AWS Support appeal). A 3B model is the largest that reliably produces structured JSON on CPU within the pipeline timeout. Trade-off: cold first-call takes >30 s even at 180 s per-attempt timeout — tonight's smoke test saw all three Ollama attempts time out and the circuit breaker open, with the pipeline correctly fail-safing to ESCALATE. At scale: drop ollamaRequestTimeout back to 30 s and switch to llama3.1:8b on GPU — same code path, 2–3 s responses.
6b. ESCALATE on LLM failure, never silent.
Why: if the LLM is slow, broken, or returns un-parseable output, the triage circuit breaker opens and the pipeline defaults the verdict to ESCALATE. A paged human is always better than a dropped alert. The email subject carries a [FALLBACK] prefix so oncall can tell LLM-verdicts from deterministic ones at a glance.
7. Pre-gather context in code; don't let the LLM call tools iteratively (yet).
Why: bounded latency, bounded prompt size, deterministic behavior. At scale: 1–2 iterative rounds with a capable model.
8. JSON-mode + Pydantic validation for LLM output.
Why: free-text parsing was fragile; structured output is auditable and machine-consumable. At scale: keep a natural-language "reason" field for humans (we already do).
9. Circuit breaker + human-review escalation on LLM failure.
Why: an LLM is a dependency, not a guarantee. Oncall must always get paged if we can't decide. At scale: secondary LLM endpoint + failover before raw-escalation fallback.
10. Drain3 alongside Grafana alerts, not as a replacement.
Why: metrics and logs catch different failure modes; Drain3 catches "this app just said something new" which thresholds can't. At scale: add streaming anomaly detection on metrics too.

23.Q&A prep — likely questions

If a question lands outside this list, say "let me pull up the code" or "good Sprint 3 question" — both are better than guessing.

Why k3s over full Kubernetes (kubeadm)?
Same API, much lower operational overhead (single binary, 70 MB, installs in 30 seconds). For a single-node cluster, kubeadm's extra complexity has no benefit. When we scale, k3s itself supports multi-node — we're not stuck.
Why not Docker Swarm?
Dead-end — Docker Inc. has deprecated Swarm in practice. No Helm ecosystem. k3s gives us "simplicity" plus a supported upgrade path.
Why does monitoring live on a VM and not in the cluster?
Circular dependency. If Prometheus is inside the thing it's monitoring and the cluster fails, Prometheus fails with it — we learn from users. In a future HA design we'd run monitoring in a separate cluster/failure domain; for a single-node demo, a dedicated VM is cleaner.
Why build images on the node instead of pulling from a registry?
No credentials to manage, no external dependency, offline-capable. Trade-off: multi-node scaling needs images imported on each node. Cheap to revisit when we have multiple nodes.
What if Ollama is down?
Circuit breaker trips after 5 consecutive failures and opens for 60s. While open, every alert gets a NEEDS_HUMAN_REVIEW fallback → auto ESCALATE with a raw-alert email. Oncall never misses an alert because the AI broke.
What stops the LLM from hallucinating a verdict?
Three layers: (1) Ollama format: json forces structured output; (2) Pydantic validates the schema; (3) on validation failure we retry with the error embedded, and a second failure falls back to human review. The LLM must also produce a confidence and evidence list — if confidence is low we surface it in the email.
Why HTTP "MCP bridges" instead of real MCP stdio?
HTTP Deployments + Services are native to K8s; each bridge is independently scalable and observable. Tool shapes are identical to what an MCP stdio server would expose. We can plug a stdio adapter in front when we adopt real MCP clients.
What's the total deploy time from zero to working?
Under an hour from a fresh AWS account: terraform apply (~8 min, RDS is the long pole) → generate-inventory.sh (seconds) → ansible-playbook site.yml (~20 min) → three helm install (~5 min) → Ollama model pull (~2–5 min).
Why not run Prometheus as an Operator in k3s?
Prometheus-Operator is excellent; we just chose not to because (a) we want Prometheus outside the cluster for the dependency reason; (b) the stack is small enough that operator CRDs are overhead; (c) our Ansible role already manages config cleanly. When monitoring moves into its own cluster, operator makes sense.
How is the Grafana → triage webhook authenticated?
Today: SG-restricted to sg-monitoring — only the monitoring VM can reach it. That's defense-in-depth, not strong auth. Next step: HMAC-signed webhook with a shared secret (Grafana supports it).
What happens in a flap storm (1000 alerts at once)?
Dedup drops same-key re-fires within a 5-min window. Queue depth is a Prometheus gauge — we can alert on it. The pipeline has a 5-min safety timeout that sends a raw alert if investigation isn't done. Worst case we page with raw alerts; we never wedge.
What does Drain3 add over just reading logs?
Drain3 builds a template tree of log lines — structurally similar lines collapse into one cluster. Once a template is known, we can tell (a) if a line is a known pattern or brand-new (=anomaly), and (b) if the frequency of a known template is drifting. Thresholds in Grafana can't catch either.
Where does state go when the cluster restarts?
Ollama models: 20Gi PVC backed by local-path-provisioner (lost if node dies; use network PV for real HA). RCA SQLite + Drain3 state: triage PVC (same caveat). S3 snapshots of Drain3 state give a coarse backup. RDS is AWS-managed with automated backups.
How do I rollback a bad Helm deploy?
helm rollback <release> <revision> -n <ns>. Revisions are kept automatically. K8s rolling-update semantics mean the old pod stays until the new one is Ready — a broken image doesn't take the service down.
Why don't you use Prometheus-Operator ServiceMonitor CRDs?
Prometheus is outside the cluster, so the operator can't configure it. We use kubernetes_sd_configs + annotation-based scraping against the k3s API with a bearer token. Same effect, no operator needed.
What's the blast radius of terraform destroy?
All AWS resources in the VPC go: EC2s, EIPs, RDS (skip_final_snapshot=true — data is gone), S3 bucket (must be empty first), CloudFront. Production action item: flip skip_final_snapshot=false on RDS and add prevent_destroy on the S3 bucket.
How do we know the platform itself is healthy?
(a) Prometheus scrapes its own /metrics and the OTel Collector's; (b) 17 alert rules cover API latency, error rate, pod readiness, disk, memory; (c) the triage service emits self-metrics (queue depth, circuit state, fallback rate) so "triage is failing" shows as a Grafana alert — which triage investigates, paging oncall via the safety-timeout path if needed.
