Section One

The Parable

In plain language: this is a system that watches our software stack 24/7 and, when something goes wrong, writes a short incident report before a human has even opened their laptop.

Imagine an ER nurse + detective sitting next to your on-call engineer.

The nurse watches the patient's vitals constantly — heart rate, oxygen, temperature. In our world, those are metrics (Prometheus), logs (Loki), and traces (Jaeger). When a vital crosses a threshold, an alert fires.

Instead of waking the engineer at 3am to interpret the vitals themselves, the detective — our triage service — picks up the phone, pulls the last 15 minutes of vitals from all three sources, cross-references it with the patient's history, asks a small local AI model (Ollama) for a verdict, and then either (a) wakes the engineer with a written diagnosis, or (b) dismisses the alert as noise so they keep sleeping.

The engineer wakes up to a short, human-readable email: "This is what happened, this is why, this is what to try first."

That's it. Everything else — Kubernetes, Terraform, MCP, Drain3 — is just the machinery that makes this nurse-plus-detective reliable, reproducible, and cheap to run.

Section Two

The Big Picture

Follow the story of one alert, from load test to inbox. No ports, no specs — just the plot.

The platform lives in AWS us-east-1, inside a single VPC with two active EC2 instances: a Monitoring VM and a k3s node. (A third GPU EC2 is defined in Terraform but unused — AWS GPU quota is still at 0.) An RDS MySQL database sits alongside for the sample app. That's all the AWS shape you need to remember.

The flow of one incident

  1. Load hits the app. load-gen.sh fires a stream of REST calls at Kong (the API gateway) on the k3s node. Kong forwards to the Spring Boot pod, which reads/writes to RDS. Normal traffic — metrics, logs, and traces start flowing.
  2. Observability picks it up. Prometheus scrapes the k3s pods for metrics. Spring Boot and Kong emit OpenTelemetry traces; the in-cluster OTel Collector forwards them plus container logs to Loki and Jaeger on the Monitoring VM.
  3. A failure is injected. inject-failure.sh backend-down scales the Spring Boot deployment to 0 replicas. Kong immediately starts returning 5xx to every request.
  4. Grafana notices. A pre-provisioned alert rule — "backend 5xx rate > 5% for 1 minute" — evaluates every 30 seconds. Within a minute or two, it fires.
  5. The alert is delivered as a webhook, not an email. Grafana POSTs a JSON payload to the triage service (FastAPI) running inside the k3s cluster at /webhook/grafana.
  6. Triage deduplicates. If this same alert has fired in the last 5 minutes, it's dropped. Otherwise the pipeline continues.
  7. Triage gathers context in parallel. It asks three MCP servers — one each for Prometheus, Loki, Jaeger — for the last 15 minutes of data around the failing service. All three calls run concurrently with an 8-second budget.
  8. Drain3 annotates the logs. Each returned log line is tagged [KNOWN] (matches a known template from the healthy baseline) or [ANOMALY] (new shape). This lets the LLM see at a glance what's unusual.
  9. The RCA history is checked. "Has this alert fired before? How often? When last?" That context is prepended to the prompt.
  10. The LLM is called. The full context is sent to Ollama running locally in the same cluster (llama3.2:3b, CPU-only). It returns a JSON verdict: ESCALATE, DISMISS, or INCONCLUSIVE, with a root-cause narrative and suggested actions.
  11. An email is composed and sent via Gmail SMTP to the on-call engineer, containing the alert, the AI's verdict, the root cause, the evidence, and a link back to the Grafana dashboard.
  12. The decision is stored. Every verdict — escalation, dismissal, or timeout fallback — lands in a SQLite RCA history database, available for audit or future LLM context.
The headline: one shell command triggers a failure that autonomously produces a written, human-readable root-cause email — end-to-end — in roughly 5–15 minutes on CPU inference (drops to ~30 seconds on GPU once the quota lands).

Section Four

The Critical Conversations

Three hand-offs where the interesting logic happens. Read these slowly — they're the questions you're most likely to be asked.

(a) Grafana / Drain3 → FastAPI Triage

How the alert enters the AI system
IFGrafana evaluates a rule (e.g. 5xx rate > 5% for 1 min) and the rule goes from Normal to Firing… THENGrafana's webhook contact point POSTs a JSON payload to http://triage:8090/webhook/grafana. The triage service accepts it with HTTP 202 and immediately hands it to a BackgroundTasks worker so the webhook never blocks.
The Drain3 side-channel
IFDrain3 detects an elevated anomaly rate in the log stream (new templates appearing faster than normal)… THENIt POSTs to /webhook/drain3 with the anomalous lines. The triage service wraps them in a synthetic Grafana-shaped alert and runs the same pipeline — so log anomalies and metric alerts get treated identically from step 2 onward.

(b) Triage → Ollama LLM

The LLM is not called for every webhook. Two cheaper checks happen first, and the LLM only runs when both let the alert through. The ordering is important — and worth stating out loud.

Layer 1 — Deduplication. If the same (alert_name, instance) fired within the last 5 minutes, the webhook is dropped silently. This is the cheapest guard; it stops flappy alerts from re-triggering the pipeline.

Layer 2 — Pre-LLM suppression (new in Sprint 2). If the same (alert_name, service) produced a DISMISS verdict — or was itself Layer-2-suppressed — within the last 15 minutes, the triage service replays that decision and returns triage_suppressed without calling Ollama. On a CPU-only Ollama where each call costs 3–15 minutes, this is the difference between a responsive pipeline and one that spends its entire budget on noise. Gated on triageService.suppressionEnabled in the Helm chart.

Layer 3 — LLM verdict. Only if Layers 1 and 2 pass does the triage service gather context from the MCP servers, annotate logs with Drain3, and call Ollama.

When the LLM gets called
IFAn alert has survived deduplication (hasn't been seen in the last 5 min)…
ANDContext from Prometheus + Loki + Jaeger has been gathered in parallel (with an 8 s budget)…
ANDDrain3 has annotated the returned log lines as [KNOWN] or [ANOMALY]…
ANDThe RCA history has been queried for prior occurrences… THENAnd only then — the full bundle is sent to Ollama as a single chat completion with format: "json". The LLM must respond with a Pydantic-validated JSON object containing decision, severity, confidence, reason, rca, suggested_actions, evidence.
The safety net around the call
IFThe Ollama call times out, fails to connect, or returns invalid JSON twice in a row… THENA circuit breaker records the failure. After 5 consecutive failures the breaker opens for 60 seconds — all subsequent calls short-circuit to a safe fallback: a pre-written NEEDS_HUMAN_REVIEW escalation email. The raw alert still reaches the engineer; the AI just abstains.

(c) Triage → MCP → Prometheus / Loki / Jaeger (and what "MCP" actually means here)

This is where most people expect magic. It's actually simpler than it looks — and the naming is a little misleading, so worth stating the shape plainly.

The LLM never queries anything. It doesn't speak HTTP, it doesn't call the triage service, it doesn't reach out to the MCPs. The triage service is the orchestrator — it calls the MCPs, assembles a single evidence bundle, then hands that bundle to Ollama as one chat-completion request. The LLM reads the bundle and writes a verdict. One request in, one JSON out. No loop.

What actually happens on each webhook
IFThe triage pipeline needs context for alert BackendHigh5xxRate on service spring-boot that fired at 10:00:00Z… THEN
  1. Triage service issues three concurrent HTTP GETs to the MCPs:
    • GET prometheus-mcp:8091/tools/query_range?promql=...&start=1759312280&end=1759312800
    • GET loki-mcp:8092/tools/query_logs?logql=...&start=1759312280000000000
    • GET jaeger-mcp:8093/tools/find_traces?service=spring-boot&start=1759312280000000
  2. Each MCP forwards to its backing system, returns JSON. Triage builds a GatheredContext object (metrics, logs, traces).
  3. Drain3 annotates each log line as [KNOWN] or [ANOMALY] in-process.
  4. Triage assembles a single prompt: system message + user message containing the alert, the GatheredContext, the Drain3 anomaly summary, and RCA history.
  5. Triage POSTs once to http://ollama:11434/api/chat with {model: "llama3.2:3b", messages: [...], format: "json"}.
  6. Ollama runs inference (~5–15 min on CPU), returns a single JSON object. Pydantic validates it. Done.

So the answer to "where does the LLM get its data" is: it's handed a bundle. The MCPs and the LLM never communicate. The triage service is the only thing that talks to both.

Why "MCP" at all — three reasons stacked

1. Security boundary. The MCPs expose only GET endpoints over a narrow verb list (query_instant, query_range, query_logs, find_traces, services). The triage service — and by extension the LLM — can see the system but can never change it. No DROP TABLE, no kubectl delete, no git push. This is the answer to "isn't giving an AI production access scary?"

2. Abstraction layer. The triage code calls prometheus-mcp, not Prometheus directly. If we migrate to Mimir, VictoriaMetrics, or a hosted Chronosphere tomorrow, only the MCP implementation changes — the triage pipeline doesn't know or care.

3. The honest caveat — we use MCP naming, not strict MCP semantics. Anthropic's MCP protocol is designed for LLM-driven tool calls: the model itself decides what to query, emits a tool call, reads the result, decides the next step — a true agent loop. Our implementation pre-fetches a fixed bundle and hands it to the model. The LLM doesn't drive. Two deliberate reasons:

  • Local llama3.2:3b has weak tool-calling. 3B-parameter models routinely hallucinate tool names, invent arguments, and forget to close agent loops. Claude and GPT-4 do this reliably; local 3B models don't. For a demo-critical pipeline, pre-fetching is the safer shape.
  • On CPU, every tool round-trip is another 5–15 minute inference. A 4-step agent loop would run 20–60 minutes per alert. One-shot keeps us to a single inference.

Moving to true LLM-driven MCP tool calling is on the Sprint 3 backlog (item 2c in monitoring-docs/sprint3-backlog.md). It unlocks sharper, targeted investigation — but requires either the pending GPU quota or a cloud-LLM path (Claude / GPT via API). It's a real architecture, not a today-choice.

Easy line to remember during Q&A: "MCP in our stack is the security boundary and the swap point. The LLM reads the bundle the triage service assembles; it doesn't drive tool calls — yet. That's a Sprint 3 upgrade once the GPU lands."

Section Six

Emergency Cheat Codes

Honest, confident replies for the questions most likely to ambush you. Borrow the exact wording.

"I don't know the answer to that technical detail."

"That's a great question — let me be honest, I'd rather check the exact number than guess. What I can tell you is the shape of the answer: [give the direction]. I'll confirm the specifics in the repo right after the demo and follow up."

"Why did you choose Ollama over Qwen / DeepSeek / a hosted API?"

"Three reasons. First, data locality: alerts contain log lines and metric labels that can be sensitive, and Ollama lets the entire pipeline stay inside our VPC — no data leaves the account. Second, cost and reproducibility: Ollama runs the same model binary on my laptop, on CPU EC2, or on GPU EC2 without rewriting anything. Third, model-swap freedom: Ollama is the runtime, not the model. I'm using llama3.2:3b today because it fits on CPU while GPU quota is pending, but I can swap to Qwen, DeepSeek, or Llama 3.1 8B with a single values.yaml change when the GPU comes online. The investment is in the pipeline, not the model."

"How does the MCP bridge actually work?"

"Each MCP is a small FastAPI service — around 150 lines — that exposes the underlying system (Prometheus, Loki, Jaeger, Drain3, RCA history) as a handful of HTTP GET endpoints named like tools: query_instant, query_range, traces, services. The triage service calls those endpoints before it calls the LLM, gathers the results, and embeds them in the prompt. The LLM itself doesn't reach out — the MCP is just a read-only, HTTP-native contract between the triage orchestrator and the observability stack. The security benefit is that these bridges are all GETs: the LLM can see the system but can never change it."

"This seems over-engineered for an intern project."

"It's scoped as a real platform because observability is a platform problem — you can't prove out alert triage on a single service. I needed the three pillars, a sample app under real load, an alerting path, and a safe sandbox for the AI. Each piece earns its keep: Kubernetes is there because Sprint 2 explicitly scoped out of per-VM compose to a single-node k3s; Drain3 is there because raw logs are too noisy for an LLM to digest; MCP is there because the LLM must be read-only; the circuit breaker is there because an AI that fails silently is worse than no AI. The complexity matches the problem — and every piece is covered by a Jira story."

"Why not just page a human directly when Grafana fires?"

"That's exactly what we do when triage is down — the circuit-breaker fallback sends the raw alert email. The AI layer is an opt-in enrichment, not a dependency. Its value is reducing false escalations: today we page on every rule that fires. With triage, we page only when the AI confirms it's real, and we dismiss or down-grade the rest — with a stored reason so the operator can audit the decision. That's the long-term business case: cutting alert fatigue without losing coverage."

"Where does the AI make mistakes, and how do you know?"

"Two known failure modes. First, the model can return malformed JSON — handled by Pydantic validation, a one-retry with the validation error fed back in, then a fallback to NEEDS_HUMAN_REVIEW. Second, the model can hallucinate — handled by keeping the prompt grounded in pre-fetched, real context and by storing every decision in the RCA history so we can later audit accuracy. We don't yet have a labeled ground truth for large-scale precision/recall; that's on the Sprint 3 backlog as a feedback-loop story."

"Why k3s instead of full Kubernetes / EKS?"

"k3s is a single-binary Kubernetes distribution maintained by Rancher — fully conformant, runs in under 512 MB. For a single-node demo environment on a t3.xlarge it's perfect: one install command, no control-plane cost, and the manifests port 1:1 to EKS when the time comes. Nothing we've written is k3s-specific."

"What happens if Ollama takes too long?"

"Four guards. The Ollama HTTP client has a per-request timeout — 1800 s (30 min) on CPU, scaled to give the three-pillar prompt enough time to complete. The triage pipeline itself has an outer budget of 2400 s (40 min); if that trips, a safety-gate email is sent with the raw alert context so the engineer isn't left in the dark. The circuit breaker trips open after 5 consecutive failures, skipping Ollama entirely for the next 60 s. And before any of that, a Layer 2 pre-LLM suppression replays recent DISMISS verdicts from RCA history so we don't burn 10 minutes of CPU on an alert we just dismissed."

"What's left for Sprint 2, with the deadline tomorrow?"

"Epics 1 and 2 — AWS infra and the AI RCA MVP — are code-complete and proven end-to-end. Epic 3, the k3s migration, is done and running in production. Epic 4 (AI hardening: circuit breaker, JSON mode, self-observability) is also code-complete. Remaining work is Jira housekeeping — a handful of status updates and two ticket closures for superseded stories — and exposing the triage service through Kong, which is deferred to Sprint 3 and documented."

If a question lands and your mind goes blank: repeat the question back slowly, then say "Good question — let me think." Count two seconds. The panel will not begrudge you two seconds. They will begrudge a guess that's wrong.
Section Seven

Technical Deep Dive

Don't read this before the demo. It's here for two hours later when a curious engineer pulls you aside and you want to pull up receipts.

K3s Helm Chart Structure

The Helm charts live in monitoring-project/charts/. Four charts, each with a Chart.yaml, values.yaml, and a templates/ directory.

  • spring-boot/ — Deployment (1 replica, OTel Java agent injected via JAVA_TOOL_OPTIONS), ClusterIP Service :80 → :8080, ConfigMap with RDS connection string, liveness/readiness on /actuator/health. Namespace: app.
  • kong/ — Upstream Helm chart pinned to a specific version, DB-less mode, kong.yml mounted as ConfigMap. Routes: /api/* and /actuator/* → spring-boot.app.svc.cluster.local. NodePort :30080. OTel plugin + Prometheus plugin enabled. Namespace: network.
  • ai-stack/ — The big one. Templates: triage-deployment.yaml, mcp-deployments.yaml (templated loop across 5 MCPs), ollama-deployment.yaml, plus Services, PVCs, ConfigMap, SMTP Secret. Triage has a /data PVC shared with the RCA-history MCP for the SQLite file. Ollama has a 10 Gi PVC for model weights. Namespace: ai.
  • frontend/ — placeholder; React currently served by Spring Boot.

Values worth knowing: imageTag: "2026-04-22b" (matching what's imported into containerd — bumped each rebuild for clean rollouts), ollama.model: llama3.2:3b, ollama.gpu.enabled: false, triageService.ollamaRequestTimeout: 1800, triageService.pipelineTimeout: 2400, triageService.suppressionEnabled: true, triageService.historyLookbackMinutes: 15.

How images get into k3s: docker build on the k3s host → docker save | gzip → k3s ctr images import. No registry. The k3s_images Ansible role does this for all 6 cires/* images.

Terraform Resource Breakdown

Repo: provisioning-monitoring-infra/. Providers v5. One state file per environment. Files:

  • vpc.tf — /16 VPC, 2 public subnets, IGW, route tables. Nothing fancy.
  • ec2.tf — 3 EC2 instances: monitoring (t3.large, Ubuntu 22.04), k3s (t3.xlarge), gpu (defined but AMI-pinned; unused while quota=0). Each gets an Elastic IP via aws_eip + aws_eip_association. AMI ID is pinned via var.ubuntu_ami_id.
  • security-groups.tf — 5 SGs: monitoring, k3s, gpu, rds, ssh-bastion. Grafana (:3000), Prometheus (:9090), Loki (:3100), Jaeger (:16686), Kong NodePort (:30080) opened to the operator IP. RDS port :3306 opened only to the k3s SG.
  • rds.tf — db.t3.micro MySQL 8.0, single AZ, encrypted, 20 Gi gp3, private subnet, parameter group tuned for the demo.
  • s3-cloudfront.tf — versioned private bucket, CloudFront distribution with OAC, TLS via ACM cert (requires verification — see the AWS account memory).
  • outputs.tf — 14 outputs including monitoring_public_ip, k3s_public_ip, rds_endpoint. Consumed by generate-inventory.sh to emit the Ansible inventory.

Triage Service — Components & Flow

Repo: monitoring-triage-service/. Python 3.11, FastAPI, asyncio. Entry point: app/main.py.

Files & responsibilities

  • main.py — FastAPI app. Endpoints: POST /webhook/grafana, POST /webhook/drain3, GET /health, GET /decisions, GET /dashboard, GET /metrics, GET /drain3/stats. Lifespan manager wires up all dependencies.
  • config.py — Pydantic Settings. Env-var driven: Ollama URL / model / timeouts, MCP URLs, Loki API URL, SMTP credentials, DB paths, dedup window, pipeline timeout.
  • models.py — Pydantic models. GrafanaWebhook, GrafanaAlert, Drain3Webhook, GatheredContext, LLMDecision (with decision: ESCALATE|DISMISS|INCONCLUSIVE, confidence, rca, suggested_actions, evidence), RCARecord.
  • dedup.py — In-memory TTL dict + asyncio.Lock. Keys alerts by (alertname, instance, status). 5-minute window. Returns True for duplicates so the pipeline short-circuits.
  • context.py — ContextGatherer.gather() runs three asyncio.gather'd HTTP calls to the Prometheus, Loki, Jaeger MCPs with an 8 s timeout. Any one failure downgrades sources_available but does not fail the pipeline.
  • drain_analyzer.py — Wraps the drain3 library. seed_from_loki() pulls healthy logs at startup, builds the template tree, persists to /data/drain3_state. annotate_lines() tags each log line as [KNOWN] or [ANOMALY].
  • rca_store.py — SQLite repository. save_decision(), get_decisions(), get_alert_frequency(). Schema: one row per triage decision with full context.
  • llm_client.py — The heart. investigate() builds the prompt, calls Ollama with format: "json", parses the response through Pydantic, retries once on parse failure with the validation error fed back, falls back to NEEDS_HUMAN_REVIEW on second failure.
  • circuit_breaker.py — 3-state (closed, open, half-open). Trips open after 5 consecutive failures, cooldown 60 s. llm_client gates every Ollama call on _circuit.is_open.
  • notifier.py — EmailNotifier. send_escalation() builds a card-based HTML email with alert details, RCA verdict badge, Drain3-annotated log samples, slowest Jaeger span, and Grafana quick-links pulled from the alert's Grafana annotations (Source, DashboardURL, PanelURL, Silence); sends via aiosmtplib. send_timeout_alert() for the pipeline-timeout safety path uses the same card layout.
  • pipeline.py — TriagePipeline._process_alert() is the canonical sequence: dedup → Layer 2 pre-LLM suppression (via rca_store.get_recent_decision_for_alert) → context → drain3 → history → LLM → act (escalate or dismiss) → persist. Wrapped in asyncio.wait_for(pipeline_timeout); on timeout, sends a raw-alert safety email and records triage_decision="timeout_passthrough".
  • metrics.py — 70+ Prometheus metrics. Webhook counts, pipeline duration, Ollama duration & status, MCP per-server latency, Drain3 cluster count, fallback reasons, LLM token counts, circuit state, queue depth.

Ordering (what matters)

  1. Dedup first — cheap, cuts 80%+ of work on alert storms.
  2. Context fan-out before LLM — the LLM gets grounded evidence, not unbounded tool-use.
  3. Drain3 annotation is just label-prepending on log lines — it doesn't replace the logs, it augments them.
  4. RCA history is the last piece of pre-LLM context — cheap SQLite lookup.
  5. LLM call is the only step that can take minutes — everything else is sub-second.
  6. Email + persist happen after the verdict; failures here are logged but don't poison the pipeline.

Why this shape

The LLM is treated as a judge, not a researcher. The researcher work (pulling logs, metrics, traces, history) is deterministic Python — fast, testable, bounded. The LLM receives a complete dossier and returns a verdict. This keeps the slow, expensive, hallucination-prone step small and contained.
