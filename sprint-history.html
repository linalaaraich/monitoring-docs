Sprint 0 — Discovery & problem framing (February → early March 2026)

Sprint goal. Before writing any infrastructure code, figure out what was actually worth building. Two parallel tracks: benchmark the existing monitoring landscape (what's out there, what works, what doesn't) and interview the people who would use this (what problems are they actually living with day-to-day). Output: a problem statement strong enough to justify a multi-sprint build, and a solution hypothesis worth testing.

What the work looked like.

  • Monitoring-solution benchmarking. Read through and prototyped against the major open-source observability stacks. Prometheus + Loki + Jaeger emerged as the de-facto OSS combination — well-supported, broad community, deployable without vendor lock-in, and integrates with the existing JVM / Spring ecosystem without modification. SaaS alternatives (Datadog, New Relic, Honeycomb) were costed and ruled out for this engagement on a mix of budget and data-sovereignty grounds.
  • SRE practice study. Worked through the Google SRE Book + Workbook, distinguishing the four golden signals (latency, traffic, errors, saturation), the difference between symptoms and causes in alerting, the SLO / SLI / error-budget framing, and the operational habits that make on-call sustainable. Translated SRE vocabulary into Tanger-Med's specific context (small team, mixed services, no dedicated on-call rotation).
  • Field research with employees. Talked to the people closest to the production systems — what wakes them up, how they find out something is broken, what their first move is when an alert lands. The recurring answer was the inflection point of the whole project: "we find out things are broken because a client tells us, or because someone notices after the fact in a log review." Detection was lagging the actual breakage by hours or days. The team was reactive by structure, not by choice.
  • Problem statement crystallised. The team needs a way to detect production problems early — before they reach a client, and without requiring a human to be reading logs at the right moment. Stated this way, the problem framed both halves of the eventual solution: (a) a real observability stack that produces signals worth acting on, and (b) something on top of that stack that does the human-attention work automatically.
  • Solution-space exploration. Brainstormed and pressure-tested several architectures: a traditional rules-only alerting setup (rejected — already exists conceptually, doesn't address the "needs a human reading it" half); an AI-summarisation layer over raw alerts (closer); a full AI triage layer that turns alerts into RCAs with verdicts and remediation suggestions (the eventual choice). Recorded which parts of the AI-triage hypothesis were risky and what would have to be true for the project to succeed.
Sprint 0 outcome

A defensible problem statement (client-reported / after-the-fact detection is the actual pain) and a solution hypothesis (build a real observability stack, then layer AI triage on top so alerts arrive pre-investigated). Sprint 1 onwards is execution against that hypothesis. Without Sprint 0, Sprint 1 would have been a generic "set up Prometheus" project; with Sprint 0, every Sprint 1 decision was made in service of the proactive-detection goal.

Why Sprint 0 belongs in the timeline

It's tempting to skip the discovery phase in a retrospective and start the timeline at "first code commit." Sprint 0 is the reason the rest of the work is coherent — every architectural choice in Sprint 1–3 (external instrumentation, MCP-bridged data access, exemplar-driven RCA prose, operator-feedback closure) traces back to the framing that came out of February's field research. The report needs this section so the "why this and not something else" question has an answer.

Sprint 1 — Observability foundation (2026-03-10 → 2026-03-30)

Sprint goal. Execute on the first half of the Sprint-0 hypothesis: stand up a full-stack observability platform for a representative web stack (mukundmadhav/react-springboot-mysql) using open-source tools and deployable by anyone with the playbook. No AI yet — this is the pillar on which everything else is built.

Topology shipped. Three on-prem VMs in the 192.168.127.0/24 subnet:

VMRoleServices
monitoring-vm · .10Observability stackPrometheus, Alertmanager, Loki, OTel Collector, Jaeger, Grafana, node-exporter, cAdvisor
application-vm · .11Application + gatewaySpring Boot (with OTel Java agent injected externally), Kong (with OTel plugin at the gateway layer), MySQL
network-vm · .12Network / supporting toolingBastion / DNS / supporting services

What shipped.

  • Ansible roles for every component. One role per service (roles/prometheus, roles/loki, roles/jaeger, roles/grafana, roles/otel_collector, roles/kong, roles/spring_boot, roles/cadvisor, roles/node_exporter, roles/mysql). Each role idempotent, with a docker-compose template, env file generation, and a health-check task.
  • Single playbook that builds the whole stack. ansible-playbook playbooks/site.yml -i inventory/onprem.yml brought a fresh set of VMs to fully-observable in ~15 min.
  • Three-pillar telemetry. Metrics via Prometheus (scrape spring-boot's /actuator/prometheus, Kong's stats endpoint, node-exporter, cAdvisor). Logs via Loki + Promtail. Traces via OTel Collector → Jaeger. Trace IDs propagated through Kong's OTel plugin so a single user request shows up as one trace from gateway to upstream.
  • Grafana dashboards. The four canonical views — service overview, alert overview, log explorer, trace explorer — provisioned via Ansible templates.
  • Initial alerting via Alertmanager. Metric-threshold rules on CPU / memory / disk / target-down, routed through Alertmanager to a Gmail SMTP contact point.
  • End-to-end reproducibility. monitoring-docs/reproducibility-guide.html + build-guide.html documented every step from "VMs exist" to "alerts firing into email".
Sprint 1 decisions worth carrying forward

External instrumentation only. Spring Boot is not modified to instrument itself — the OTel Java agent is mounted at start time. This is a durable principle: the platform produces telemetry from the outside, the application does not need to know it's being observed. Carried through Sprint 2's k3s migration unchanged.

What carried forward (rather than shipped at sprint end).

  • The three-VM topology — replaced in Sprint 2 by AWS EC2 + k3s. The Ansible roles survived; the inventory changed.
  • Alertmanager — removed in Sprint 2 (decision D6, 2026-04-24). Grafana unified alerting with a single triage-webhook contact point replaced it.
  • The Gmail SMTP contact point — replaced by the triage service's own SMTP send so escalation emails carry the AI verdict + RCA + suggested actions, not just a Grafana alert dump.
  • The 192.168.127.x address space — pre-AWS legacy; live system is on a Tailscale tailnet now.

Sprint 2 — AWS migration + AI RCA MVP (2026-03-31 → 2026-04-23)

Sprint goal. Move the platform off on-prem VMs onto AWS (Terraform-provisioned EC2), migrate the application workload to k3s, and add an AI layer that produces structured root-cause analyses from incoming alerts. The on-prem foundation from Sprint 1 stays useful as a reproducibility target; the production-shaped deployment lives on AWS.

The sprint deadline moved twice (April 9 → April 23) — captured in the ~~April 9, 2026~~ ~~April 23, 2026~~ strikethrough in the original tracker. Final landing: 2026-04-23. A follow-on Epic 5 (UEBA-flavoured stories) ran past sprint close until 2026-04-29 as an in-flight workstream.

Epic 1 — AWS Infrastructure

Terraform-managed AWS account, VPC, subnets, security groups, EC2 instances, IAM, S3 buckets for state + Loki. Pinned Ubuntu AMI to remove silent drift. Free-Tier-aware quotas (CloudFront verification, EC2 limits). EIPs on the durable instances. Repo: provisioning-monitoring-infra.

Epic 2 — AI RCA System MVP

The biggest new surface in the project. Composed of:

  • 5 MCP servers (monitoring-mcp-servers/) — prometheus-mcp:8091, loki-mcp:8092, jaeger-mcp:8093, rca-history-mcp:8094, deploy-events-mcp:8095. Each speaks JSON-RPC and exposes 3–4 tools over a Prometheus-style /metrics endpoint.
  • FastAPI triage service (monitoring-triage-service/) — webhook receivers (Grafana + Drain3), async pipeline, structured-output LLM call via Ollama, dedup + suppression, dashboard at /dashboard, SMTP escalation.
  • Cross-pillar correlation — context.py fans out to three MCPs in parallel before the LLM call, building one pre-gathered evidence pack the LLM consumes.
  • Drain3 log-template clustering — runs server-side over Loki, surfaces novel templates as a fourth signal alongside metrics / logs / traces.
  • Local LLM — qwen2.5:7b-instruct via Ollama. Initially on a g4dn.xlarge EC2 (decommissioned), then moved to the laptop's GTX 1060 (still the production runner today).

Epic 3 — Kubernetes migration

Application workload moved from the application-VM docker-compose into a k3s cluster on a dedicated EC2 (observability-rca-k3s). Helm charts for spring-boot, kong, frontend. xanmanning.k3s Galaxy role provisions k3s as a systemd unit. The monitoring VM stays in docker-compose — it's stable, deployable, and not gaining anything by going onto k3s. Decision D11.

Epic 4 — AI Triage Hardening

From "MVP that responds to webhooks" to "service operators can trust." Dedup + suppression layers, structured-output schema enforcement, error envelope on every MCP response, pipeline timeouts, the dashboard, the email notifier, and a first pass at action-template fallback. Two-tier dedup design (in-memory fingerprint + pre-LLM history-based suppression) captured in D4.

Sprint 3 — RCA quality + feedback + hallucination firewall (2026-04-23 → 2026-05-08)

Sprint goal. Take the Sprint-2 pipeline from "produces RCAs" to "produces RCAs the operator can act on without supervision." Four epics: backfill the Epic-5 close-out into Sprint 3's record, ship the operator feedback loop, wire the Drain3 baseline lifecycle, and close the hallucination-firewall gap exposed by the 2026-04-29 0b215ef3 incident.

The 20-day investigation window (2026-04-30 → 2026-05-19). After Epic 4 was added on 2026-04-29 and the Tier-0/2 stories shipped same day, the team deliberately slowed down before the larger MCP refactors (S3-HF-04 through S3-HF-09). Roughly three weeks went into prototyping output-quality improvements in scratch branches and refreshing documentation, with no commits to main by design — the goal was to know which ideas were worth the refactor cost before paying it. Nothing structural shipped during the window; the production triage container stayed on d6d10ef from 2026-04-29, and the 17 daily static audits run over the window all reported 226/226 tests green and the same 7 stable doc-drift items (no new drift accumulated).

Ideas prototyped against the audit corpus

Each candidate was scored on the same 4-axis RCA rubric the chaos harness uses (cause-named / evidence-cited / actionable / prose-shape) over a 28-decision sample drawn from the live-audit log and the chaos-run-3 + chaos-run-4 outputs. Ranked by what landed on the Sprint 3 picklist on resume:

  • Exemplar / context section ordering. Re-ran the prompt with the ## Reference exemplar section placed after ## Pre-Gathered Context instead of before, and with the matched exemplar inlined under the alert summary. The post-context ordering scored marginally worse on cause-named (0.62 vs 0.71) on the validator-flagged subset — the LLM dropped the exemplar's structural cue once the evidence was already in scope. Kept the existing pre-context order. Captured as a footnote to D17 for the report.
  • Evidence-pillar weighting (metrics / logs / traces / drain3). Tested a weighted re-ranker on the pre-gathered evidence block — promote the pillar whose alert is firing, demote the others. On the chaos sample it had no measurable effect (RCAs already lead with the firing pillar in 24/28). Shelved as not-worth-the-complexity. Recorded in a tested-and-rejected.md scratch file in the local branch.
  • BM25 retrieval dry-run. Stood up a BM25 prototype against the existing exemplar library plus the 28-decision audit sample to test how curated-RAG retrieval (the deferred Sprint-4 US-3.3/US-3.4) would behave once Epic 2 feedback volume materialised. Two findings: (a) BM25 over 14 archetypes is degenerate — top-1 hit was always the exemplar already matched by exemplars.find_for_alert; (b) the prototype confirmed Epic 2's feedback table extension is the actual gating dependency, not the retriever choice. Sprint-4 candidate #3 stays as scoped.
  • Hypothesis-menu validator threshold sweep. Swept the 7 regex patterns shipped in S3-HF-03 against a synthetic-prose harness — neutral idiom sentences ("either way", "possibly because of") to measure false-positive rate. Result: 0/120 false positives at default strict mode; relaxing to "warn-only" mode produced no additional catches on the 28-decision sample. Default triage_hypothesis_menu_strict=True stays as is. Documented at Solution Brief §5.3.
  • Confidence-clamp threshold exploration. Tried 0.30 / 0.40 / 0.50 as the clamp ceiling. Below 0.40 ran into the prose-already-suppressed problem (the LLM started hedging its own confidence pre-clamp, so the clamp had less work to do but the operator saw weaker prose); above 0.40 the "withheld actions" notice started appearing alongside RCAs that did have the evidence to support actions. 0.40 retained as the trust line. No code change.
  • Trace-depth feasibility scan (pre-S3-HF-07). Sampled 12 live Spring Boot traces from Jaeger via the controller for JDBC parameterization. Result: db.statement spans use bind parameters (?, ?, ?), not literal values — so PII redaction is not a blocker for get_trace(trace_id). Sprint-3 plan annotated; S3-HF-07 picklist note updated to "no redaction blocker." This is the load-bearing pre-step for Sprint 3's biggest remaining story.
  • RCA prose A/B (cause-first vs observation-first). Two prompt variants tested over a fresh chaos replay set: cause-first (current; "X is the cause of Y because Z") and observation-first ("Z is observed; consistent with X causing Y"). Cause-first kept its prose-shape edge (D19 framing); observation-first regressed on cause-named when evidence was thin. No change. Reinforces D19.
  • Pipeline-duration per-stage instrumentation. Drafted the histogram-per-stage instrumentation that's been on the carry list since 2026-04-29 (recent fires were 5–13× documented typical — 323/399/533/755/1081 s). Implementation drafted in a scratch branch, did not merge — depends on Epic 4's bounded-agency MCP refactor (S3-HF-05) so the retry path is properly attributable. Resurfaced as Sprint-4 candidate #15.

Sprint 4 — Planned scope

Sprint goal. Make the RCA output something a dev would actually read and act on. Sprint 3 closed the structural-quality work (Epic 4 hallucination firewall). Dates. TBD at the Sprint 3 retro. Estimated total effort: 10–14 d for one engineer if scoped to items 1–12 below.

P0 reframed 2026-05-19 — no GPU migration

The original P0 was the GPU migration to us-west-2 + qwen2.5:14b. Dropped on cost grounds 2026-05-19. The latency problem (6-23 min per RCA) is now attacked as a bundle of smaller fixes rather than a single hardware swap: hard pipeline timeout (P9), per-stage instrumentation, Ollama concurrency cap, and the MCP native tool-calling rewrite (smaller prompt → faster inference). Combined target: median ≤ 90s, worst ≤ 240s.
