Executive summary

The platform is in a healthy steady state. All 18 Grafana alert rules evaluate cleanly with health=ok and the noDataState=OK + execErrState=Error protection added on 2026-04-27 is live across the board. The three adaptive-threshold rules from US-5.4 are firing baselines correctly. The triage container on the laptop is running the post-exemplar build (revision=2fb5a5d09eb4...), and the full Python test suite is green at 89/89.

Three drift items surfaced — none urgent, but worth recording:

  1. The handoff said Watchtower auto-pulls images on the laptop. Watchtower does not exist. The laptop has no Watchtower container, no cron job, and no systemd timer that pulls. Image rolls happen via the roles/triage_laptop ansible playbook, which is invoked manually. The mental model needs updating; pull is operator-triggered, not automated.
  2. service_deployment_type map has two stale entries. node-exporter is mapped to systemd but actually runs as a docker container on observability-rca-monitoring (prom/node-exporter:latest). mysql is mapped to k8s but no mysql pod exists on the k3s cluster. Both produce stale arch-mismatch behavior in the validator.
  3. Three of the eleven exemplars are gated on alertnames that don't exist in the live ruleset. Explicit operator request ("real failure modes plus more specific things") — these are forward-looking placeholders, not a bug. Documenting which match real rules vs which await new rules.

Forward-looking gap: no node-exporter on the k3s host (10.0.1.194). Host-level CPU / memory / disk metrics for the k3s node are not scraped by Prometheus; only container-level via k3s-kubelet-cadvisor. HighCpuUsage / CriticalDiskUsage can therefore only fire for the monitoring VM. The node_exporter ansible role exists but was never applied to k3s. Improvement plan #2 below.

Deployment-type map vs reality

The map at app/config.py:service_deployment_type is the authoritative source the validator's arch-mismatch scan and the suggested-actions templates both consult. Cross-check:

ServiceMap saysActually runs asStatus

mysqlk8snot deployed anywherestale entry
prometheus / loki / jaeger / grafanadocker-vmdocker on monitoring-vmmatch
node-exportersystemddocker on monitoring-vm (prom/node-exporter:latest)drift
k3s-nodesystemdk3s service on the EC2 hostmatch
cadvisor(missing)docker on monitoring-vmnot in map

Why this matters: the validator's arch-mismatch scan rejects suggested actions that don't match the deployment_type. If the map says node-exporter is systemd but the action is docker restart node-exporter, the arch-mismatch fires legitimately — but in reality, docker restart would be the right action, so the validator is flagging valid actions as invalid. Same in reverse if the map drifts to docker-vm and a node-exporter alert fires for a host running it as systemd elsewhere.

The otel-collector ambiguity is real: it runs in BOTH places. The map can only carry one deployment_type per name. Practical consequence: an otel-collector alert on monitoring-vm gets the k8s arch hint, which is wrong. Two-disambiguator approaches exist (instance-host lookup; namespace label) but neither is wired in yet.

Image roll mechanism — Watchtower is not a thing

The session handoff repeatedly described "Watchtower polls GHCR" as the auto-pull mechanism. That's incorrect. Verified on the laptop:

  • docker ps -a | grep watch → no result
  • crontab -l | grep -iE "docker|pull" → no result
  • systemctl list-units --type=timer | grep -iE "docker|pull|update" → no result

What actually rolls images: the roles/triage_laptop ansible role at monitoring-project/roles/triage_laptop/tasks/main.yml, invoked by hand from the operator's controller. The role's default laptop_compose_pull=false (commit 48eb3fd) means even running the playbook doesn't pull unless that variable is overridden.

This is fine — operator-triggered rolls are appropriate for an early-stage stack. The point of recording it is so the mental model matches reality. Searches for "why didn't my image roll" should look at "did the operator run the playbook" and not at "is Watchtower stuck."

Improvement plan

Five items, ranked by reviewer legibility × effort. None block ongoing Epic 5 work.

I-1 — Fix the deployment_type map drift (15 min)

Edit app/config.py:service_deployment_type:

  • Change "node-exporter": "systemd" → "node-exporter": "docker-vm".
  • Remove "mysql": "k8s" (not deployed).
  • Add "cadvisor": "docker-vm" for completeness.
  • (Optional) Document the otel-collector ambiguity in a code comment — it runs in both k3s and docker-vm, and the map only encodes one type.

Land it as a small commit (triage: deployment_type map drift fixes). Re-run the test suite to confirm 89/89 still green.

I-2 — Deploy node-exporter on the k3s host ✅ Shipped 2026-04-28

Original estimate of "1 hour, role exists, just apply it" was wrong — the existing roles/node_exporter is a placeholder that emits a debug message; the actual node-exporter on monitoring-vm is launched by the unified docker-compose stack, which doesn't apply to the k3s host. Real options were considered: DaemonSet on k3s (~½ day, architecturally correct), systemd via ansible buildout (~2h), or standalone docker container (~1h).

Chosen path: DaemonSet on k3s. Manifests at monitoring-project/manifests/node-exporter/daemonset.yaml; corresponding ansible task block in playbooks/k8s-manifests.yml (tag node-exporter). hostNetwork + hostPID + /proc, /sys, /rootfs hostPath mounts; tolerations for the control-plane taint so the DaemonSet schedules on the single-node cluster. Discovered by the existing kubernetes-pods Prometheus scrape job via prometheus.io/scrape annotations through the k3s API-server proxy — no prometheus.yml.j2 changes required.

Verified live: pod node-exporter-cnjl8 Running, :9100 listening on host, Prometheus has 14 active targets (was 13) with the new one as job kubernetes-pods, instance 10.0.1.194:6443, health up. node_load1 samples from both monitoring-vm and the k3s host now flow into Prometheus. Existing HighCpuUsage / CriticalDiskUsage rules group by instance with no port filter, so they now cover both hosts independently. Committed as monitoring-project@c936202.

I-3 — Update the session handoff to reflect the actual auto-pull shape (5 min)

The handoff already got patched this morning to record the Tailscale SSH access shape. Add a corresponding note that there's no Watchtower; image rolls are operator-triggered via roles/triage_laptop. Already partly captured in the laptop-access section; explicit auto-pull mention would help.

I-4 — Decide on the cascade-disk-loki and crashloop-bad-config exemplar regexes (30 min)

Two archetypes name alertnames that don't exist:

  • cascade-incident-disk-loki regex includes LokiIngestLag — we have LokiIngestionRateLow. Either rename in the regex or rename the rule.
  • crashloop-bad-config regex includes KubePodCrashLooping — there's no rule by that name; the Kong/Spring failures came in as TargetDown. Either add a Prometheus rule using kube_pod_status_phase{phase="Failed"} / kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"}, or drop the alternative from the regex.

Recommend: drop LokiIngestLag (rule isn't going to be renamed) and add a Prometheus KubePodCrashLooping rule, since CrashLoopBackOff is a real failure mode the platform has empirically faced. ~30 min including a re-provision pass.

I-5 — Document the forward-looking exemplars (10 min)

Two archetypes (bounded-agency-resolves-inconclusive, tls-cert-expiry-pre-failure) match alertnames that don't exist anywhere. Tag them clearly in app/exemplars/library.yaml with a comment like # forward-looking — requires new alert rules so the next reader knows it's intentional, not abandonment. Mirror the note in docs/happy-path-scenarios.md if needed.
