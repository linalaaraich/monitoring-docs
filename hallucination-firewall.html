Epic 4 · the structural defence against bad RCA output

The hallucination firewall

Six reinforcing mechanisms that together keep the LLM's output operationally trustworthy. Each mechanism addresses a specific failure mode observed during construction; together they make the difference between an AI RCA you can leave a junior operator to read at 03:00 and one you can't. This page is the canonical entry point — for the prose-shape detail, deep-link into the relevant Solution Brief §5 subsections.

Three failure modes the firewall exists to catch

Failure mode 1

Hallucination

The model invents a service, a metric value, or a remediation that does not exist in the evidence pack (the 0b215ef3 incident's invented products service is the canonical case).

Failure mode 2

Surface-only LEDE

The RCA restates the alert rather than naming a cause — leading with PromQL, with the observed value, or with "based on context" / "the alert indicates" openers.

Failure mode 3

Hypothesis menu

Under uncertainty, the model emits a list of possibilities ("this could be a slow query, a connection pool issue, or a GC pause") rather than committing to one with evidence.

Six reinforcing mechanisms

Each mechanism is independent — any one of them can fire without the others — but they are deliberately layered so a single failure mode is caught by more than one. The pipeline stage numbering matches the ten-stage diagram in triage-service.html.

Mechanism 1 · Stage 5

Exemplar library

Fourteen hand-authored RCA archetypes injected as a ## Reference exemplar section before the evidence pack. The model gets a structural target tailored to this alert before it sees the data.

Mechanism 2 · Stage 6b

Alert-keyed hallucination blocklist

Per-alert YAML rejects phrases that are wrong-by-construction for that alert (e.g. HighKongP95Latency rejects /actuator/*; Drain3AnomalyDetected rejects PromQL). Hits trigger a retry with a HINT.

Mechanism 3 · Stage 6b

Surface-only LEDE validator

_SURFACE_ONLY_LEDE_PATTERNS regex set: catches PromQL ledes, "based on observed/repeated/context" openers, "The <X> alert for" leads, alertname-first form, and "Looking at the metrics".

Decision D19 · 4 rounds of widening
Mechanism 4 · Stage 6b

Hypothesis-menu validator

Seven regex patterns targeting "possibly X or Y" / "may be due to (slow query | pool | GC)" / "either A or B" prose, with negative lookahead for idiomatic "either way" / "either case". Companion cause-evidence rule requires non-stop-word overlap between RCA prose and cited evidence.

Story S3-HF-03 · 22 dedicated tests · 0/120 false positives on the synthetic harness
Mechanism 5 · Stage 6d

Confidence clamp + diagnostic-steps fallback

Forces confidence ≤ 0.40 if surface-only fired, RCA quality is data_starved, or actions look templated. Strips suggested_actions and emits read-only diagnostic_steps instead. Email + dashboard render a "Withheld — confidence clamped to 0.40" notice.

Story S3-HF-01 (Tier 0) · F-4
Mechanism 6 · Stage 6c

Bounded-agency retry

Exactly one additional MCP call from a 6-tool whitelist (Prom instant, Loki range, Jaeger get-traces, RCA history, deploy events, get_trace). Pydantic schema + retry feedback string constrain the second call; re-prompt; revalidate; keep first-pass if retry still bad.

Decision D15 · "one MCP call, not a chain"

The MCP-only invariant — the rule that makes the firewall durable

Project-wide rule

Every datum the LLM sees in its prompt must arrive through an MCP server. Direct httpx or requests calls to Prometheus, direct aiosqlite reads of the RCA history database, and direct in-process from app.exemplars import … imports are all forbidden in the LLM-adjacent code paths.

The invariant is the rule under which the six mechanisms above are worth running. If a piece of evidence reaches the LLM without provenance — a direct Prometheus query that bypasses prometheus-mcp, an in-process import that bypasses rca-history-mcp — then the validator suite cannot tell whether a hallucination came from the model or from upstream stale data. The 0b215ef3 incident on 2026-04-29 exposed three such bypasses in the production code; closing them is the Sprint-3 Epic-4 scope.

The bridge set behind the invariant is six (as of 2026-06-11): prometheus-mcp :8091, loki-mcp :8092, jaeger-mcp :8093, drain3-mcp :8094, rca-history-mcp :8095, and deploy-mcp :8096. The sixth was added the day a fabricated "most recent deploy introduced a regression" RCA demonstrated the invariant's corollary: a claim with no data source behind it is unfalsifiable, which is its own hallucination vector. deploy-mcp derives rollout events from kube-state-metrics series already in Prometheus, so deploy claims are now groundable in both directions — cite a real rollout, or rule deploys out ("no deploys in window"). See the engineering log, 2026-06-11.

The CI lint — the rule made mechanical

Social enforcement (code review + audit reports) is the first layer; the second is mechanical. Story S3-HF-08 shipped the continuous-integration lint that forbids the bypass patterns: httpx/requests/direct-DB calls outside the _mcp_call helpers and the MCP servers themselves. The lint sequencing was deliberate — it only ran on green after S3-HF-04 and S3-HF-05 had closed the existing offenders, so it never had to fail on legacy code (a lint that fails on existing code is one the team works around rather than fixes).

How we know it's working

The four-axis RCA quality rubric — cause-named, evidence-cited, actionable, prose-shape — is the standing measurement. The chaos harness at monitoring-project/scripts/chaos/ runs the rubric automatically; the daily live audit runs it manually against three synthetic injected webhooks.
